# Project Steward

Project Steward 是一个会从项目对话和真实结果中改进自己的项目治理 Skill，也会读取两者之间的完整实施过程。一次工作结束后，它会先按时间覆盖请求、决定、命令、等待、警告、超时、重试、中断、半成品、纠正和最终证据，再把多个用户结果分别拆开：哪些做法已经成功，哪些能力没有做到，问题为什么发生，下一次最早可以在哪里预防，以及目标 Skill 当前承担的职能是否过窄、过宽或适当。真正能够跨项目复用的机制会进入 Project Steward 自己的路由、方法、验证或专项资料。

Project Steward 保存跨项目可复用的治理方法；每个项目自己的产品决定、架构事实和长期约束仍由该项目已有的规则、设计文档、代码、配置和测试负责。

## 它怎样从对话中进化

一段对话可能包含多个成功结果和多个问题。Project Steward 不会先用“是否直接关系最终结果”过滤细节，而会先建立一次临时过程台账：

历史范围先由当前请求冻结。“这个会话”只指当前任务；其中出现的其它任务链接、参考会话和附件会作为当时的过程证据登记，但不会被递归打开。只有用户在本次学习请求中明确点名，或随后确认扩展范围，才会把另一项历史加入复盘。早先为另一个结果提供过参考，不会让它永久进入以后所有对话学习。

```text
请求与结果变化
→ 判断、授权、实际动作和命令
→ 等待、警告、超时、重试、中断与半成品
→ 用户纠正、确认与最终证据
→ 归入一个结果、跨结果问题、未知项或确认无影响的偶然信息
```

来源只有读到明确末尾才算完整。读取前会先确认可用的行数、字节数、分页能力或输出预算；只有能够一次完整容纳的来源才整份读取，否则固定内容身份并按页、游标或稳定区间读到末尾。Git 只在准确项目根直接存在 `.git` 且当前问题确实需要历史、工作树或发布状态时使用，不会先在任意目录运行再靠报错找仓库。多个互不依赖的探测和验证会分别保留输出与退出状态；一个可选检查失败不会吞掉其它成功证据，已经有效的结果也不会为了补一个缺口被无理由重跑。长而嘈杂或需要跨轮观察的命令会在启动前把输入身份、完整报告或受控日志、进程身份和退出状态放到可回读位置；临时执行句柄丢失后先恢复这些事实，不会只因为旧输出看不见就重跑昂贵任务。

完成影响判断后，再按结果逐个恢复：

```text
用户最终要得到的结果
→ 实际采用的决定和动作
→ 用户接受、纠正或拒绝的内容
→ 最终证据
→ 已证明有效的机制
→ 缺失或错误的能力
→ 下一次最早预防点
```

成功经验也属于经验。用户明确认可、可复现成功和真实用户链成立，都可以证明一种做法值得继续使用；纠正、返工、半迁移和最终结果失效，则说明 Project Steward 的现有方法缺了什么。

Project Steward 不会只在纠偏时学习，也不会把沉默误当成认可。用户明确接受、重复选择、不同任务中反复出现的相邻结果、可复现的真实用户链和独立正式合同，能够支持保留或扩大一种能力；用户没有继续纠正、没有回复、没有修改，或者一次结构检查通过，都不能单独证明长期接受。缩小职能则需要用户明确排除、持续误触发或职责已经正式迁出的证据，不能因为历史里没有出现某项能力就自动删除它。

它还会把相邻能力还原成用户真正要完成的上层结果。共享输入职责、最早判断、核心对象或来源、用户结果和实际使用位置的能力，会被组织成一个完整角色，由 Project Steward 提出一份整体合同供用户一次确认，不要求用户逐项补全本可由历史强证据推导出的能力；只共享主题或实现技术的需求继续保持独立。后续纠正证明旧定义过窄时，会重建整体行为合同并迁移全部活动入口，而不是在旧定义后不断加能力清单。

职能范围和操作权限始终分开。一个 Skill 能研究、判断、设计或治理更多用户结果，不代表它自动获得联网、安装、运行、写入、删除、提交或发布权限；这些动作仍按当前请求和宿主规则分别决定。扩大后的共同判断可以成为默认入口，昂贵研究、外部检索、生成和实施继续按明确条件加载。

只有会改变未来路由、动作、输出、验证或停止位置，并且有明确后续用途的机制才会更新 Project Steward。每项经验都会分别提炼共同路径和特殊维度，两者不是二选一：同一个问题可以先进入跨项目共用的方法，再按平台、版本、规模、顺序或生命周期等条件叠加会改变动作的专项处理。范围虽窄但高频或经常发生、后果严重、具有稳定检测信号，或受正式平台条件决定的问题，仍会保留足以重新发现和处理它的专项维度。共同路径不会被某个专项症状缩窄，特殊条件也不会为了“通用”被抹成一句空话；一个问题同时符合多个特殊维度时，只组合本次真正会改变识别、观测、动作、验证或停止位置的部分。

用户只要求分析或复盘时，Project Steward 保持只读。用户首次要求吸收、自我进化、优化或迭代时，Project Steward 会先展示未来行为、职能边界、默认与按需能力、代表性输出、影响文件和成功标准，然后停下来；这次请求不直接触发写入。用户看过这份整体方案后明确确认，或一开始就明确要求跳过方案确认并立即实施，才会修改 Skill 自身。

自我进化方案确认后，默认完成本轮获准改动的验证、精确提交、推送和远端 HEAD 核对；用户明确要求只改本地时才停在本地验证。现有工作树中的其它修改不会被顺手纳入，创建远端、改变可见性、删除、改写历史和强制推送仍需要对应授权。

每个初始轮次、自动续跑、目标恢复和上下文压缩后的续接，在第一次改变状态前都会重新核对写入权限和停止位置；每次都只从最近一次用户明确动作及其尚未完成的结果恢复合同。审计发现、助手建议、内部计划、目标名称、待办清单和自动提示都不会变成新的实施授权；只读结果已经交付且没有新的明确写入请求时，即使目标仍标记为进行中或还有待办，也不会进入项目写入。

确认只覆盖用户看到的那份方案和当时的活动文件。真正写入前，Project Steward 会重新读取受影响文件并与方案快照比较；非冲突变化会保留并合并，若变化已经改变约定行为、影响文件、实际使用位置、验证方法或用户最终得到的结果，则先更新方案并重新确认。

如果正确规则其实已经存在、但一次行动没有执行它，Project Steward 不会再堆一条同义原则。它会把合同前移到最早路由或动作门槛，用当前任务中的代表性请求核对实际读取、动作和停止位置，并用确定性测试保护稳定结构。

历史里同时出现报错、保护规则、临时绕行和残留时，Project Steward 会先把它们放回同一条因果链：现象、直接原因、合法保护、最早可控的架构或根所有权原因、绕行、残留。主要学习主题取证据支持的最早可控原因；无法证明更深原因时就停在直接原因，不补造解释。绕行和残留可以成为独立清理结果，但不会反过来盖住根因；同一会话里的产品身份等其它独立结果仍会分别保留。后续纠正若改变主要原因，旧方案和旧确认随即失效，必须重新规划和确认。

Project Steward 也会在自我进化时治理自己的体积。活动 `SKILL.md` 只保留路由、触发、读取顺序、权限、输出和停止位置，完整方法由对应 reference 唯一维护。每次写入前后都会核对主文件行数、字符数、全部直接 reference 和规则所有者；主文件上限为 220 行、14,000 个字符。新路由导致超限时，必须在同一次改动中迁移或合并旧细节，不能靠删除能力入口或把整理留给以后。

自我进化只使用活动的 `SKILL.md`、`references/`、`scripts/`、`assets/`、元数据与测试。`archive/` 只保留历史和来源价值，不能重新成为执行入口；除非用户明确要求并说明今后谁会使用，否则不会再建立 `.project-steward/experience` 或另一套共享经验来源。

## 三条核心路径

### 1. 从历史对话吸收能力

```text
使用 $project-steward 阅读这段项目对话。
按用户最终结果分别找出成功机制、暴露的问题、踩过的坑和最早预防点。
把能够跨项目复用的部分更新到 Project Steward 自身。
```

结果不是一篇聊天总结，而是 Project Steward 的活动能力发生变化：未来什么请求会触发、它会采取什么不同动作、怎样验证已经真正生效。

### 2. 动手前主动预防

```text
使用 $project-steward 为这次重构做事前预防。
结合项目现有规则和 Project Steward 当前方法，找全影响范围，
确定唯一真源、最终接口、旧路径退出条件和真实用户链验收。
```

Project Steward 会把用户结果写成可观察行为，建立生产者、边界、消费者和最终结果的影响图，再决定迁移和验收。公共接口变化时，文档、示例、schema、公共导出、验证与发布脚本、真实用户链工具和生成物来源也属于正式消费者；事件回调派生的异步工作必须由生命周期所有者追踪到空闲、取消、关闭和重启边界。没有项目配置也能正常工作，不会为了留痕创建经验目录。

综合审计还会检查这些公开验证器本身是否真的执行了代表性输入。语法检查、成功导入、帮助输出和脚本存在只能证明入口可解析；验证器仍调用旧接口，或 CI 从未进入它声称保证的主流程时，相应能力会标为保证链缺陷或当前未覆盖，不会借产品测试通过获得背书。

公开验证器的包装器也必须被实际执行。它的时间预算会覆盖必需子检查的代表性时长，以及启动、报告落盘、关闭和清理；子检查已经显示通过但包装器超时、清理失败或非零退出，仍不能算公开保证链通过。预算来自可观察阶段和稳定运行证据，不靠任意延长掩盖挂起。

桌面界面的事件处理器不会同步承担随输入增长的文件遍历与复制、网络或 provider 调用、媒体解码、索引重建和进程等待。Project Steward 会让界面先登记操作身份、generation、输入与目标，再由后台所有者处理排队、冲突、取消和唯一终态；无关交互继续响应，迟到结果只清理旧任务。验收从自然入口使用真实代表性输入，在任务完成前证明事件循环已经处理另一项无冲突操作，再覆盖完成、替代、取消和关闭排空。`callLater`、排队信号、单次定时器、动画完成和 Future 回调也属于生命周期工作；销毁后访问、过期回调和延迟写入即使没有让进程返回非零，也不能算通过。

桌面 smoke 会先列出主窗口、其它主要窗口、延迟创建页面、菜单、对话框和覆盖层，再从自然入口完成首次进入与再次进入。`ReferenceError`、未定义属性、主题或翻译、绑定循环和销毁后访问等运行时框架诊断，即使退出码为零也属于失败。应用单例、单实例锁、事件循环和主题或语言注册表等进程级事实，则通过同一个生产 `main` 入口在新进程中验证，不让测试套件残留的全局状态替启动链背书。

网页或概念稿中的玻璃、模糊和半透明不会被直接当成 Windows/QML 应用的默认风格。Project Steward 会先分离结构、互动和视觉表面，再按真实任务密度、背景变化、合成与 QML 渲染能力、对比度、焦点状态和目标硬件性能决定是否采用；高密度编辑工作区默认保持稳定不透明，只在职责明确的有限区域使用玻璃，并提供布局与对比度都成立的不透明回退。

桌面验证会分开离屏或 headless 与真实 Windows 会话。前者证明组件、应用状态、布局几何和应用内交互，后者证明最大化与最小化、系统标题栏、原生命中、DPI 与多显示器迁移、系统背景材质和合成器行为；离屏驱动缺少原生能力时会隔离实机检查，不会修改产品来迁就测试驱动。

每项用户可见承诺还会单独对应正常入口、实际分支和最终证据。测试开关或环境变量绕过自动打开网页、保存、恢复等分支时，Project Steward 只报告未被绕过的部分已经验证，并把其余承诺明确标为仅诊断、未验证或受阻，不会用一条成功链代替整个交付。

手工复制生产物、跳过正式构建任务或直接调用下游消费者同样只能证明没有被绕过的部分。阻塞正常入口的权限、宿主设置或其它外部条件改变后，Project Steward 会从新鲜状态重新运行同一个正常入口，确认它实际选择目标分支、正式消费者读取本轮结果并形成最终产物；不会把较早替代路径的成功拼成标准入口已经恢复。

一项检查只有在规则的精确触发条件确实被本次变化命中，并且验证器实际覆盖相应输入、分支或用户承诺时，才会成为完成门槛。检查会被区分为适用且必需、辅助、范围外或用户取消；用户取消会更新本次完成合同，但不会抹去已经发生的失败证据，仍只依赖该检查的承诺继续标为未验证。

历史提交、旧截图、当前运行结果和用户最新纠正发生冲突时，Project Steward 会先区分“用户现在要什么”“当前实现是什么”和“过去发生过什么”。当前明确纠正决定目标行为；运行结果与源码证明准确状态下的现状；旧 Git 只证明对应提交的历史。目标仍不可靠时，会先给出可人工核对的行为合同，不从过期实现猜产品意图。

启动、加载、滚动进入、媒体预热、播放完成和自动切换等时序结果会按连续过程治理。Project Steward 会为资源与切换建立稳定对象身份、操作所有者和完成策略，让旧回调只能清理旧对象，新内容就绪后再原子切换；稳定画面只有一个主视觉对象。验收从最早可见表面记录到后一稳定状态，检查闪屏、到达时空白、意外重叠、回跳和重放，不用最终截图或“过一会儿能播放”代替过程证据。

多页面滚动、章节演出、局部轮播和媒体播放互相影响时，Project Steward 会先选择每个区域的唯一主架构，再排动画。它会说明原生连续手感、完整落页、相邻内容可见性和局部输入接管之间的现实取舍，定义进入构图、完整就位、内部演出、终态释放和再次进入，并按方向决定滚轮、触摸、按钮与键盘何时推进局部状态、何时交还页面。返回可以自然反向、保持终态或明确重播；有意义的例外不会被全站默认抹掉。局部延迟或最终落点通过但用户仍觉得迟钝时，会重新检查整段架构和输入所有权，不继续只调阈值。

涉及跨进程或网络、持久化、临时状态、恢复、凭据和多种构建产物时，它还会在动手前从权限归属、状态生命周期、数据表示、边界转向和实际运行入口派生本次不变量，提前找出同源变体。跨进程业务结果使用独立结构化通道，普通日志、退出码和 EOF 不负责猜测结论；流式处理会验证跨分片与最终 flush。源码正确、普通构建通过和用户入口实际选中当前产物会被当成不同证据层，父子进程的依赖与资源清单还要和运行目录实际文件集合完全一致。

跨平台或多目标项目还会把变化映射到真实平台、编译目标、构建 profile、feature 和条件编译分支。宿主测试、生产构建、静态检查、目标平台编译和真实用户链分别保留自己的退出状态；宿主侧通过不会替未被编译的目标专属代码背书，最后一次相关修改后只重跑受影响目标并取得新鲜证据。

协议、schema 或持久格式迁移会同时覆盖当前版本新建、由旧版本真实生产或保存的历史状态、失败后仍可恢复的原状态，以及当前消费者关闭并重新打开。验收读取正式序列化器实际落下的文件、记录或消息，并用当前 schema、存储或线协议检查字段省略、显式 `null`、默认值、类型与版本；内存模型通过或测试手写一份 JSON 不能替代这条边界。

这类迁移会在第一次昂贵全量回归前先预检改变的真源身份和直接消费者，检查硬编码旧版本、生成快照、模型或列表角色、国际化输出、公共能力消费者、测试收集身份以及适用的架构或静态预算。合同、迁移器、生成链和直接消费者先通过定向检查，代码与测试驱动冻结后再跑全量套件；全量失败先归类并以定向回归定位，只有影响全局或项目规则要求时才重新运行整套。

外部、持久化、模型和进程 JSON 会进入一个唯一结构化边界。它统一拥有字符编码与字节预算、嵌套深度与节点数、重复键、非有限数值、超长整数与指数、目标类型范围、schema、版本和错误映射；生产代码、迁移器、验证器和维护脚本不会各自保留宽松解析。验收让正式生产者的实际序列化字节经过真实存储或传输，再由同一边界和正式消费者读取；消费端手写对象、schema 对内存模型通过和解析器单测都不能替代。

设置页、首次运行向导、托盘菜单或 CLI 里的每个可编辑值都会建立从真实能力到最终消费者的效用账本。Project Steward 会核对 provider 或设备目录给出的稳定身份、允许值和适用条件，配置提交后当前运行时是否真正应用，重启后是否恢复，以及用户是否能观察到声音、设备、角色、背景、模型或其它行为变化。一次动作只修改它准确选择的目标，未选中的同级路由、provider 或设备设置保持不变；全部目标通过一次配置提交发布，失败时旧的持久状态与活动状态保持可用。没有消费者的字段不会继续伪装成可用设置；首次向导和日常设置会复用同一能力目录、校验、测试和提交入口。

用户询问一个设置是否有效、修改后仍没有效果，或者一个宽泛名称实际控制多阶段链路中的局部参数时，Project Steward 会把“已经接通”“活动运行时已经应用”和“对用户所说的结果有效”分开。它会列出正式输入到最终结果之间全部分类、门控、聚合、解码或过滤阶段，以及每层实际读取的配置、默认值和硬编码值，说明现有控件准确影响哪一段。稳定且需要用户校准的隐藏参数会以一个身份迁移能力描述、配置、提交、持久化、活动实例、状态回读、界面和测试；不具备稳定用户取舍的内部参数不会被随意暴露，界面也不会暗示其它控件能够替它调节。验收让同一份受控正式输入在设置前后经过真实阶段和最终消费者，并继续验证重启恢复；后置关键词过滤不能替上游设置修复背书。

实时连接会把传输打开、权威身份握手和领域就绪分开。session 与 generation 由唯一运行时所有者签发，客户端收到当前身份后才释放排队请求；首次连接、重新连接、显式 reset 和旧 generation 消息分别验收。能力快照也会分开已经配置、进程在线、准确端点可达和当前可调用，只有准确路由及其依赖确实就绪时才公开调用 URL，不会把静态配置或存活进程伪装成可用能力。

模型参与任务判断、运行时事件或结构化回复时，Project Steward 还会核对真正发送到 provider 的线请求，而不只看提示词中间对象。执行 route 被当前产品模式禁用时，确定性 gate 会直接选择一次普通对话调用，不让模型判断一个不可能采用的任务 route；执行可用时，路由、首次回复和 `task brief` 由一次类型化响应共同返回，任务正式登记后才能向用户表达接收、排队或开始。用户消息、对话历史、系统规则、运行时事件、任务原始约束和重试指令分别保留来源身份与角色；强制 route、schema、输出示例和 `response_format` 必须表达同一合同。任务完成事实继续由生命周期所有者提交，模型不能用一句完成式文案推进状态；宿主已经单独展示路径或附件时，正文也不会再制造第二份元数据或为了修补重复而擅自分裂显示与朗读真源。验收经过实际 provider 序列化、正式响应、解析与 gate、运行时状态以及界面、TTS 或其它最终消费者，并在接收阶段证明产物尚未完成、结果阶段证明产物已经可用。

长期记录可以完整保存，而每次模型调用只消费一次有界上下文投影。Project Steward 会分开完整记录真源、界面查看位置、上下文组装策略和 provider 最终线请求；近期原始回合、连续性摘要和相关召回都保留来源、角色、顺序或覆盖范围。滚动、定点跳转、搜索和筛选默认只改变用户正在查看的位置，不会暗中裁剪下一次模型输入；上下文超出预算或组装失败也不会删除、覆盖或重新解释完整记录。验收让正式生产者先写入超过单次窗口的真实记录，再由界面和恢复消费者读取完整内容，同时证明 provider 实际只收到符合预算的可追溯投影。

控制台、日志文件、查看器和诊断导出分别是正式日志消费者。用户要求打印完整模型请求与回复时，Project Steward 会从正常用户动作经过最终 provider 序列化、实际响应、日志配置和指定落点，核对同一关联链中的完整正文、错误和结束结果；受控本地协议端点可以替代不稳定远端服务，但 mock 网络、formatter 单测或一条示例日志只能证明局部。开发命令能看到 stdout 不代表 GUI 或后台产物也有控制台，为了补证据而改变窗口类型、打包方式或启动体验仍需要对应授权。

同一个用户回合中的场景、意图、回复策略、事实引用、任务判断和最终台词如果共享同一模型与输入，并且中间没有新运行时事实、外部执行或人工授权，会由一次类型化响应返回，而不是仅因步骤名称不同重复调用模型。生产提示词保持简短、正向和职责明确，历史失败反例留在离线评测中；需要执行任务时，CLI 只收到目标、相关上下文、约束、授权工作区、预期结果和验收条件组成的 `task brief`，不会继承角色性格、关系培养和面向用户的表达要求。聊天专属控制协议不会进入共享身份提示或执行 `task brief`。

动作、表情、显示和语音会从同一份已定稿语义结果产生明确投影，但先按消息来源、语义阶段和受众资格决定是否消费。模型控制意图优先使用类型化字段并由唯一响应入口解析；必须使用内联标记时，也会明确跨分片、结束处理和多个标记的顺序，而不会让动作、界面和 TTS 各自猜测模型原文。系统消息、运行时事件、CLI 原文、路径和按钮不会因为表现为字符串就自动取得角色或朗读资格；只有合格语音投影才进入 Markdown、动作标记、emoji、链接和路径清理。屏幕可以保留合同要求的视觉内容，TTS provider 只收到应当发声的自然语言，流式增量、最终帧和重试也不会各自造成一次完整朗读。

长期记忆会按用户事实、角色特质、关系变化和任务事实分别判断证据资格。用户事实只由用户明确陈述或确认的记录支持；角色特质来自角色在不同情境中的重复选择和表达，用户评价只形成关系证据；任务状态和结果来自运行时已提交事件与真实产物。用户画像、角色画像和关系画像都是可由有效原子记忆重建的派生视图，纠正和失效先改变原子证据，再重建画像与检索，避免旧回复或一次讨好被写成永久事实。

需要模型跨多轮整理记忆时，对话会先独立提交，整理器再按项目定义的稳定工作单元批量处理。字符数和 token 上限只控制输入预算，不会暗中变成调用频率；正常运行只处理达到门槛的完整批次，重启则从持久游标补齐全部积压，包括最后一个不足门槛的尾批。模型只能提出带真实回合证据的记忆操作，宿主校验后先提交记忆与索引再推进游标；失败保留原游标，重试使用同一批次身份去重。验收会经过正式对话入口、真实 provider 序列化、解析、存储、重启、检索和记忆界面，不用替换 provider 或手写结果冒充完整链路。具体批量门槛仍由项目配置和成本评测决定，不会固化成 Project Steward 的通用数字。

长期记忆召回不以短期对话历史非空为前提；应用首次连接、显式 reset 后和重新连接后的第一轮都必须能从正式检索器进入上下文。记忆查看器、检查器和维护工具需要修改事实时，会经过与正常整理器相同的类型化领域命令、记忆服务、持久化、索引和审计链；领域层没有相应命令时保持只读，不会直接写 driver、数据表或索引形成第二个事实入口。

新增持久化、缓存、日志、恢复、窗口状态或自动创建目录时，Project Steward 会把所有正式入口、CLI、窗口、smoke、测试 fixture 和共享 helper 重新视为潜在写入生产者，解析它们真实使用的输出根。helper 不会静默替测试创建工作区或满足核心前置条件；验证前后会比较项目状态与已登记输出根，把新增残留追到生产者和清理责任，删除未获授权时按已同意的归档合同处理或准确报告。

工作区由同步软件、生成器、编辑器监视器、其它 Agent 或进程同时改动时，Project Steward 会保存受影响路径的基线并在覆盖、恢复、暂存和提交前重新读取。来源不明的变化不会被恢复、覆盖或顺手纳入；它只会冻结冲突动作，安全的只读调查仍可继续。若新文件确实属于当前结果，会先确认来源与产品职责，再迁移清单、正式消费者和真实验收，不能因为文件已经出现或布局刚好容得下就视为完成。

把写任务交给共享工作区中的 Agent 或其它执行单元时，会先限定文件所有权、禁止重叠并要求返回实际变更、证据、未验证承诺、进程和残留。写入者结束却没有交接的改动属于未验证的部分交付；主任务会重新清点当前差异，把它们映射回生产者和消费者并取得新鲜验证。并发期间的半迁移状态不会被当作产品缺陷，也不会被当作已经完成。

多次命令的结果不同时，Project Steward 不会直接推断同一个文件、分支、进程或任务发生了变化。它会从权威发现结果取得准确标识并直接复用，核对每次工具实际收到的字面输入、工作目录或命名空间以及解析后的对象身份；不同身份只表示查了不同对象，“未找到”也只说明本次实际查询的对象不存在。只有同一对象在可比条件下确实变化后，才会考虑同步、并发写入、缓存或外部进程并决定是否等待或重试；普通单次检查不会增加这套对照。

本地文件工作区使用一套按真实文件系统语义规范化的路径身份，再分别决定内容是否可见、可搜索、可修改、可版本化和必须被观察。目录树、搜索、监听、版本变化和文件命令不再维护各自的名称特判；控制文件即使损坏或无法解析也不会从监听与修复链中消失，测试则必须使用真实目录枚举、监听器或原生命令产生的路径形态。

会继续生成工程状态、缓存、恢复文件或导出层级的系统，要拥有自己的短工程根。Project Steward 会在创建前解析 `SUBST`、PowerShell 驱动器、符号链接和目录联接，按规范化真实路径、共同消费者的最窄限制、最长合法后缀和保留余量计算预算；公开创建入口只接受业务名称和必要选项，并返回实际工程路径。源素材可以留在原位置，消费系统的工程状态不会再嵌套进生产者的深层输出目录。路径保护在下游工具确实不能保证更长路径时仍然保留；路径别名只用于有完整生命周期的诊断，不算最终修复。Windows 上出现重复盘符时，会先证明它是别名还是分区，解除别名后同时验证映射消失、真实目标仍在，不会用分区工具处理 `SUBST`。

产品升级或更名则分开治理当前公开产品名称、稳定技术标识和旧公开名称。界面、面向用户的 CLI 能力描述、Skill、活动文档、示例和当前配置会迁移到同一公开名称；包名、命令名、协议、模块命名空间和安装目录只有兼容合同确实要求时才改变。旧名称可以留在明确的历史材料中，但不能继续出现在活动入口，最终还要由真实界面、CLI 或公开能力入口证明用户看到的是当前产品。

如果一项风险只有昂贵完整链、长时间累计、特定顺序或外部系统才能暴露，Project Steward 会在写代码前先设计可区分的边界信号和短实验。时间、并发、背压、环境、数据沿袭和验证器干扰可以按实际条件同时叠加，但不会把这些专项检查强加给普通确定性改动。同一稳定键的确定性缓存、代理、索引或分析结果可能被多个线程或进程同时请求时，会用覆盖整个生产过程的同键租约，在租约内重新检查后只生产一次；不同键仍可并行，损坏或旧版本结果也只触发一次重建。

用户可见的任务进度不会再把“当前阶段”和“完成比例”混成一个数字。只有正式工作生产者同时给出已完成量、总量和单位时才显示百分比；总量未知、单次外部请求或无法连续测量的阶段显示不定进度。多阶段任务不会用人为权重拼接，不同单位或未知成员也不会通过平均百分比伪造聚合进度。长任务由独立生命周期所有者分配任务身份和 generation，正式登记后释放发起它的聊天或界面回合；状态查询读取当前快照，取消、追加和授权携带准确任务与请求身份，迟到事件和旧窗口不能影响当前尝试。修改进度能力时，Project Steward 会把结构化合同一次迁移到生产者、任务队列、控制入口、事件、持久化、聚合、界面和公共调用者，退出旧标量字段、固定阶段数字与第二份活动任务状态，并用真实长任务生产者、正式结果和当前可见消费者验证。

诊断指标也必须证明自己真的测量了所声称的事实。零值不会被用来表示“没有测量”，默认常量、代理信号和缺失回调也不能冒充健康状态；指标会在代表性持续时间、负载或数据规模上与独立用户结果校准。两者冲突时，用户结果保留为失败证据，没有正式生产者的指标会退出成功条件，或在合同确实需要时明确显示为未知。

大量条目的界面会在实现前同时检查对象规模、实际实例化的控件、一次通知引发的重算、隐藏面板和嵌入运行时。尚未访问的昂贵消费者不会默认随应用启动；延迟创建或缓存会分别验证首次访问、再次访问、状态保持和关闭。编辑草稿绑定正式对象与版本，语义不明的全局变化不会覆盖草稿；后台任务与表单并发更新时，表单只提交脏字段。

同一对象会被编辑命令、其它控制器或后台任务共同修改，或者界面会动态增删集合项时，Project Steward 会把权威提交、带身份和版本的语义事件、活动缓存协调以及框架可观察绑定连成一条正式状态链。普通查询方法能够读到新值，不代表界面会自动重新求值；存储写入成功，也不代表打开中的编辑器已经更新。异步基线快照与实时事件并发时，较晚返回的旧快照只能更新自己的基线分区，再合并基线之后的增量，不能整表替换掉已经显示的新状态。验收会保持当前表面打开，走完空集合到首项、继续增加、移除到空、快照与实时事件交错，以及另一正式入口修改后的即时显示与后续编辑，不用关闭重开、手工刷新或固定延时冒充活动投影成立。

当架构复杂度取决于多个输入或对象是否重叠、并发、互相影响或需要合并时，Project Steward 会先冻结普通业务不变量、代表性工作负载、明确例外和例外启用证据。未经用户目标、产品合同或真实数据证明的最坏情况不会进入核心路径，也不会提前增加合并、同步、缓存或恢复边界。默认角色依赖内容资格时，它只在第一份合格内容真实进入时分配；空容器不会抢占默认值，用户手动覆盖后自动规则不会再次抢回。

直接操作会把选择集合、持久关联、本次操作集合和操作入口分开。关联对象从任一等价成员发起都要得到同一操作集合和目标映射，解除关联后选择状态不能让旧关系继续生效；操作身份、成员基线和目标计划一次原子发布。验收从每个等价入口使用真实指针、键盘或触摸经过父级滚动与命中竞争，并实际执行释放、取消、空白清除和模式退出；直接调用内部拖动函数不能代替这条链。对象角色标记还要在选中和未选中状态下都能独立辨认，不能只靠选中高亮表达。

另一个项目或引擎被用作实现参考时，Project Steward 会先保留当前项目的唯一状态与消费边界，再把参考实现拆成整体依赖、可迁移机制、运行假设和不适用部分。用户明确要求完整研究并判断哪些能力值得目标项目吸收时，它会盘点规范真源、手工来源、生成视图、名称与独立行为、运行假设和授权边界；普通项目介绍仍只读取回答问题所需的材料。只要采用建议时停在只读结论，明确要求计划或实施后才进入目标项目改动。

参考产品里的功能不会因为有独立页面、显眼按钮或大量同类条目，就自动在目标产品获得同级入口。Project Steward 会先判断它是核心对象、对现有对象的操作、获取渠道、视图或筛选、状态反馈还是可选集成；结果进入产品后若与现有对象共享保存、查找、编辑、删除、恢复和交付流程，就接入现有统一入口或对象上下文。只有目标项目自身已经证明用户有独立且反复发生的结果、不同的关键决定或持续生命周期，而且现有路径无法自然承载时，才会建议主导航、主要按钮或独立工作区。界面没有裁切、自动化能找到控件和功能链能够运行，都不能单独证明这个入口层级正确。

正式吸收会为目标项目建立一份规范记录，并由它确定性生成目录、搜索索引、预览和其它投影。能力必须经过公开采用或物化入口进入真实产物，再由正式消费者形成可见结果；演示或画廊只能证明预览。Project Steward 还会区分制作期能力与共享契约：现有协议已经能完整消费物化结果时不扩大合同，消费者必须识别或编辑新语义时才升级共享契约并迁移全部调用点。来源身份、内容哈希和授权说明随产物传递，工具只整体重写自己拥有的生成文件，不为稳定格式重排用户清单。

如果目标是学习开源代码项目，Project Steward 会先追溯原始上游，区分运行时依赖、源码分叉、兼容适配器、直接资源复用和只借鉴机制，再冻结目标自己的产品身份、命名空间、数据与任务真源、版本和更新政策。直接复用或改编后再分发的代码与资源，必须在目标 README 的“第三方资源与致谢”中说明原始仓库、许可证、复用范围和修改；只学习视觉锚点、核心动作、工作流或反复刻方法并独立实现，没有复制来源 IP、示例、资源或代码时，不会把来源写成目标依赖。用户提供的是 fork 时，只有确实采用 fork 的独有改动才另列 fork。每项吸收仍记录固定来源、许可证、采用范围、修改、迁移测试和拒绝部分；核心只依赖目标原生合同，兼容包保持在边界外侧。后续上游变化作为新的候选人工审计，不通过自动同步重新取得核心所有权。

跨项目工具接入会把能力实现、各根正式验证、隔离互操作、当前实例正式采用、稳定运行入口、持久配置和各根发布状态分别结项。独立合规实例中的互操作成功，不会替用户当前实例满足参与方的不变量背书；当前实例仍违反存储根、内容真源、版本或生命周期要求时，Project Steward 会保留已经成立的实现与互操作证据，把正式采用标为受阻，并在未获迁移或例外授权时停止持久激活。

复合交付包不会只检查顶层清单或一份 schema。Project Steward 会从真实生产者入口展开伴随合同、资源账本、运行时接口和实际资源，再区分“已经声明可用”与“已经被场景或配置正式采用”；只有采用关系进入消费者执行计划，并对最终可见、可听或可使用结果产生实际贡献，才会把对应能力判为接通。消费者自行迁移或手写的样例只能证明内部链路，不能替真实生产者互操作背书。

外部 CLI、执行工具和协议兼容性使用逐适配器证据矩阵，不再用“可执行文件能启动”“能力握手成功”或一个假 CLI 通过概括完整兼容。每个明确支持的适配器会分别核对实际执行产物、能力合同、正式启动与隔离、临时输入传递、安装版工具真正发出的上游线协议、结构化业务结果和最终用户链；没有可强制工作区隔离的适配器不会暴露 Shell，能力在公共 helper 中也默认关闭。外部 Agent 是产品声明的任务执行者时，它负责解释任务和选择工具，宿主负责能力、授权和执行边界，不会因为任务看起来只是确定性文件操作就绕过它；宿主原生路线需要产品事先明确声明，不能作为不可见的优化或静默回退。外部工具的成功与检查项只算声明，宿主会从执行前基线独立核验本轮内容和实际变化，未改变的既有文件不能冒充新产物；流式执行保留每次工具调用、错误和恢复关系，顶层成功也不会抹掉仍未解决的工具错误。未实现或未验证的其它工具明确留在范围外；真实隔离环境与本地协议记录端点无法同时运行时，两条证据只分别支持自己经过的层，不会被拼成一次实际上没有运行过的端到端链。

网络服务适配器还会先冻结产品必须保持的凭据要求、默认或零配置职责、成本、隐私和正式能力。上游推荐的新端点或新版本一旦改变这些不变量，就会被当成新的产品决定而不是普通升级；连接测试也必须复用正式运行的适配器、认证、端点、序列化、流式模式和响应解析。测试只走非流式、绕过认证或访问另一个端点时，通过只证明那个探针，不能把聊天或其它正常能力标成可用。

每个 CLI 的权限选项、即时解释和实际启动参数来自同一适配器能力目录。调用者只能选择适配器、核验后的可执行文件和类型化业务选项，不能通过完整命令字符串、原始参数数组或“高级参数”在适配器参数之后覆盖工作目录、隔离、权限、设置、输出和工具能力。验收会核对操作系统实际收到的参数顺序与最终有效值，并用重复或后置参数证明覆盖会在启动前被拒绝。运行中的授权请求使用执行、任务、请求和工具调用身份投影到界面，再把允许或拒绝返回准确等待者；自动模式复用同一策略和事件账本，不会靠识别终端文字或盲写 `yes` 冒充协议。工作目录和提示词属于协作边界，只有真实强制隔离才能被描述为无法越出工作区。

比较同一模型的直连 API、不同 Harness 或 CLI 路径时，Project Steward 会冻结模型、参数、输入、历史、权限和评分口径，每次只改变调用路径，并把 `scenario_id`、标题和期望标签留在评测编排器中。候选先通过各自真实线协议、解析和消费者链，再保存原始响应、最终正文、延迟、token 或可比成本并做盲化质量评审；适配器错误会与模型能力分开，不会用单一指标或测试特制请求宣布胜者。

运行中修改配置会重建 provider、存储根或共享服务图时，Project Steward 会根据旧图与候选图的实际身份差异决定影响范围，不按 patch 字段名猜测。每个前台或后台操作持有一代不可变服务上下文；切换事务准备并验证候选、持久化配置、排空旧租约，再在一个提交点发布配置、服务图和代次。持久化失败不会先中断旧服务，回滚磁盘再次失败时活动运行时仍恢复明确旧代并单独报告分歧。物理数据根只有全部存储、任务历史、缓存和恢复消费者能共同迁移时才允许热切换，否则明确要求重启。桌面界面只把补丁交给后台串行队列，并在新代真正可消费后报告成功。

整体依赖和性能方案仍用当前项目的代表性负载决定采用方式。若新增并行 worker、GPU 或浏览器快速后端、缓存捷径等替代生产者，每个实际执行单元都要分别证明与标准路径等价；中途失效会废弃整次高速结果并从新鲜状态完整回退，不能发布快慢路径混合产物。大型内容只有在正式进入不可变状态并留下绑定内容身份的有效回执后，后续消费者才能复用那次完整校验。

### 3. 问题发生后沿根因治理

```text
使用 $project-steward 找出这个重复问题最早从哪里产生。
如果需要修复，一次迁移所有调用点并退出旧架构，
最后证明真实用户链已经恢复。
```

诊断会停在证据、影响范围和最终修法；用户明确要求修复时，才修改项目。进度说明和最终报告会把判断标成观察到的事实、待验证假设或已确认根因，只有直接证据定位第一处偏离并排除关键竞争解释后才确认根因。发现一个边界缺陷后，会在同一受影响链内检查权限、生命周期、表示方式、边界转向和实际运行产物的同源变体。协议迁移会从真实旧状态进入正式迁移器，检查实际序列化结果、失败时的原状态保全，以及当前消费者关闭并重开。完成不能只证明函数返回正确，还要证明正式生产者生成结果、结果穿过真实边界、消费者读取，并在用户可见结果中成立。扫描、测试和审计命令自身失败时结论只能是未知；有状态服务的恢复需要锁定确切实例，并由同一个消费者比较重启前后的结果。

错误事件还会保留发生阶段、作用范围、操作身份、稳定类别和可恢复性。启动、连接、会话、回合、任务、一次操作与关闭由各自生产者提交类型化事实，界面和通知只消费合同允许的范围；局部超时不会被显示成启动失败，也不会覆盖已经成立的全局健康状态。验收会先建立成功的上层状态，再让真实局部生产者失败并确认后续允许动作仍可继续，随后单独验证真实全局失败进入自己的投影；手写正确事件只证明消费者。

遇到难复现、低可观测、多个解释都说得通或验证器可能干扰的缺陷时，它不会靠反复跑昂贵长测碰运气。共同路径先保留一次真实失败，为竞争解释设计不同信号，在最早边界补足观测，再用确定性模型、短小重现或故障注入排除原因；同一个问题可以同时叠加时间累计、并发顺序、吞吐背压、环境进程、数据缓存和验证器等特殊维度。输入自带发生时间或序列时会保留正式时钟，固定睡眠只作为等待上限，关键断言必须与正式结果存在稳定映射；独立部署目标和浏览器场景使用新鲜环境或经过证明的完整重置。交互前台和后台维护共享排他资源时，会先停止后台重新取锁，等待当前后台释放且不推进未完成游标，再启动前台，前台完成后才恢复调度。连续播放、实时采集、动画或流式处理会同时对齐墙钟、正式生产进度、消费或展示确认和最终可见结果，序列连续和“丢失为零”不能证明没有整体变慢；验收会分开启动短窗、目标平台真实消费、持续累计、过载与恢复，正常负载能力和过载时如实报告及降级分别得出结论。只有产品、环境和验证器已经冻结后，昂贵完整链才用于最终确认。

“最新”和时间先后属于产品语义时，有限精度时间戳不会被当成全序。正式提交边界会分配序列、revision 或事务内单调排序值，持久化、查询和界面共同消费它；UUID、对象 ID 和列表位置不会被拿来猜时间。验收会冻结时钟，让真实生产者写入多个相同时间戳的对象，再从重开后的正式消费者证明最新对象仍然正确。

并发操作由正式生产者分配稳定身份和 generation，并把它原样带过开始、更新、完成、失败、取消与清理。消费者不会按最后一项、当前选中项或列表位置猜目标；验收会让两个真实操作交错经过正式事件边界，证明其中一个失败或取消时不会修改、移除或终止另一个操作。

真实生产者返回集合或多个合法对象时，关键断言会按生产者给出的稳定语义身份寻找目标，不用对象总数、列表位置或当前选中项猜测。可编辑或持久事实从权威状态和重开验证，派生或瞬态投影从正式计算或展示消费者验证；生产者新增合法对象本身不会被误报成模型丢失或重复。

用户明确要求自行迭代、做到底或根据证据自行停止时，内部轮次不是新的授权边界。连续修正仍受原用户结果、同一受影响链、写入与删除权限和停止位置约束；每轮都会检查正式产物、日志语义、落盘状态、恢复残留、后台进程和旧入口。真实验收失败时先区分测试驱动、夹具和产品链，不能修改产品来迁就坏的验证边界。新鲜证据指向范围外问题时会准确报告，不借连续工作扩大任务。

写入工具返回成功只表示调用已经结束。Project Steward 会在下一项依赖动作前直接回读权威目标；文件、存储、远程状态或正式消费者没有出现预期变化时，先修复写入边界，不把回执当成完成。测试、扫描和审计会先核对预期对象与工具实际输入，再分别保留结果并按各自的退出语义区分通过、零发现与执行失败。命令成功但输入为空、过期或漏掉候选内容时，结论仍是未覆盖或未知。

测试套件报告绿色前，Project Steward 还会把用户承诺和关键回归对应到测试框架实际收集的唯一身份，检查同名覆盖、发现命名、过滤、排除和生成身份碰撞。测试源码存在、命令成功或总数看似合理都不能替代收集证据；缺失、重复或未执行的关键测试继续按未覆盖处理。

新的独立请求替换一项已经写入但尚未完成验证的结果时，Project Steward 会先冻结最小交接状态：已经改变的对象、已经成立的证据、尚未验证的承诺、启动的进程与残留，以及原权限和停止位置。新请求不会被解释成继续或回退旧结果的授权；完成必要说明后，新结果使用新的权限边界和验收。

## 持久操作与恢复

导出、复制、保存、下载、同步和最终化等动作一旦被接受，后续输入失效、取消、生产失败或重启恢复都必须属于同一次操作。Project Steward 会直接建立以下顺序：

```text
身份、授权、结构与操作准入
→ 持久化 pending
→ 重新读取并校验当前输入
→ 正式生产者执行
→ 物理结果完成或证据保全
→ 唯一终态
→ 正式消费者读取
→ 用户实际看见并确认
```

恢复身份同时包含物理存储根、业务对象和事务，避免同一对象被复制或迁移到另一位置后互相吞掉恢复结果。`pending` 先于父目录、临时文件、备份、元数据和变更清单等全部物理副作用；操作完成由唯一所有者接收显式结果，只产生一个账本、结构化事件和日志共同消费的终态。队列、调度器或多个观察者可能看到同一次自动触发时，还会建立稳定发生身份，在一个原子边界内写入发生记录、任务和调度进度；执行批次与发生身份分离，结果不确定的崩溃不会被静默重放，显式重试产生新批次。测试会先记录动作前的事务身份，再读取生产者真正新增的事务和实际路径；不会预测文件名、另建计数器或时钟，也不会手写一份事务结果冒充生产链。后台任务、读取器和分发器都必须由唯一所有者等待到完成，权威状态走无损通道，高频遥测才允许有界或合并。

有状态 daemon、后台服务或调度器启动时，Project Steward 会把唯一运行权放在恢复和调度之前：进程外壳先保持无持久副作用，取得权威端点或服务租约的胜者才初始化状态服务、恢复任务并接受客户端；竞争失败者只关闭自己创建的资源，不得改变任务状态、重试次数或调度游标。验收会让两个独立进程同时竞争带有非终态任务的同一端点，证明只有胜者恢复一次，正式消费者也只从胜者读取结果。

一次操作同时产生主文件、旁路文件、质量报告、证明材料和历史记录时，它们作为一个结果集合发布或撤回，不会让失败的主结果留下孤儿报告或成功记录。测试、性能、审计和真实用户链产生的运行证据也有正式生命周期：保留全部失败与中断，并可按明确类别只保留最近一次完整成功；新成功完整落盘后，较早成功才成为清理候选。运行中的、状态未知的和没有工具所有权标记的目录不会被清理；打开文件或同步占用导致的清理失败会被单独记录，不会篡改测试本身的终态。实际删除或归档仍遵守当前用户与项目权限。

真实验收还会先列出音频、视觉、窗口、输入、文件、网络、设备和后台进程副作用，并使用仍能证明同一边界的最低扰动输入。音频链优先用静音或不可听输入验证传输、编码和解码，振幅离线分析，不播放持续刺耳的测试音。用户对副作用提出异议时，会立即停止准确生产者并退出对应测试模式。长错误和恢复路径在低高度窗口中使用有界状态区，重试、保存、打开目录和确认等行动仍保持可达。

同一恢复动作被重复点击、多个窗口触发或消息重放时，会按稳定动作身份和当前 generation 加入同一尝试或确定性拒绝，不启动第二个恢复生产者。取消也必须匹配仍在运行的 generation；旧界面或超时回调留下的取消不能影响新尝试，更不能取消或回滚已经完成的替代结果。

## 架构内聚、重复与上帝模块

Project Steward 现在有一条直接专项路径：

```text
检查这个项目是否高内聚低耦合，
是否有重复或相近功能可以合并，
是否存在上帝类、上帝模块或职责过度集中的文件。
```

文件行数、函数数和依赖数只用于筛选候选，不直接当作结论。专项检查会建立职责、变化原因、状态生命周期、公共表面、调用方向、真源和变更波及图，回答：

- 一个大文件究竟是完整领域，还是同时拥有多个互不相关职责；
- 两段代码只是长得像，还是在重复同一个业务决定或维护同一真源；
- 中心对象是否迫使消费者依赖大量无关成员；
- 前端、领域层、原生层或不同平台是否并行维护同一合同；
- 应该由哪些最终领域所有者接管，旧 facade、旧 helper、旧类型和兼容路径何时退出。

检查是硬只读边界：找到明确修法也不会自动改项目。筛选同时按物理文件和逻辑所有者聚合，`partial class`、头文件与实现文件或其它分片不能靠拆文件规避上帝模块判断；文本重复扫描还会区分声明、定义、生成物和真正的语义真源。要求治理时，完成标准是新领域边界已被所有调用者消费、旧架构不再活动、依赖方向和真实用户链都通过验证，而不是把函数平均搬到多个文件。

开始度量时会固定审计来源、内容身份和逻辑所有者的聚合定义。脏工作树以审计当时的实际文件为基线，不会用 Git HEAD 替代；候选或聚合口径在审计后被其它工作改变时，旧基线失效。最终报告会区分审计快照到当前状态、本任务实际改动和相对 Git 的差异，只在能够追溯到同一审计基线且聚合定义相同的情况下报告前后变化。

拆分宽 facade 或把多个构造参数收进组合根时，还会逐成员记录旧方法、属性、信号和跨语言绑定的最终所有者，并记录必须共享同一实例的配置、事件、存储、provider、锁与生命周期对象。批量改写不会根据其它调用点常见的局部变量名补造依赖；完成时既检查旧成员残留，也实际运行不同调用形态并核对协作者身份，不能用 lint 或全量测试单独代替接口迁移证据。

事件、DTO 和公共字段会逐项建立存活账本，把唯一语义所有者、正式生产者、传输或存储边界、生产消费者、生命周期阶段和用户结果连起来。只有测试或说明文档引用不能证明运行时表面值得保留；权威事实、必要投影和有明确消费者及保留期的诊断信息会分开，死事件和死字段会退出。同一语义在整个生命周期只保留一个名称和合同，重复别名不会被当成兼容成果。

旧架构退出时，仓内零引用只足以判断消费者范围已经封闭的内部符号；HTTP、WebSocket、IPC、CLI、插件入口、框架注册和公共导出还要核对机器可读发现、活动文档、扩展合同与已知外部消费者，证据不足就保留为未知或受阻。同类残留复扫会先定义禁止的所有权或依赖方向、允许边界和命中分类，关键词与目录只能生成候选。迁移测试也会逐项映射到原始发现和目标行为；同一测试文件不等于同一迁移边界，无关断言不会为了让套件变绿而顺手改写。

异步工作流如果把一个业务阶段的输入校验、类型化命令生成、任务持久化、结果应用和展示更新分散在多个中央分派器中，Project Steward 会按阶段恢复职责闭环。阶段所有者负责从业务输入到结果应用，执行器只负责平台或计算操作，展示投影只读取已经提交的状态；组合根负责装配，通用分派器只按稳定类型路由。验收会从真实用户动作取得命令身份，让它经过正式序列化与存储、执行器、类型化结果、阶段结果应用和当前界面，并用架构守卫阻止中央业务分支、宽控制器和旧 facade 回归。

全面审计会先建立维度覆盖账本，再建立问题账本。它会按项目形态逐项检查产品定位、全部正式功能、代码质量、架构与重复、数据与恢复、界面视觉、交互状态、完整用户旅程、无障碍与国际化、性能与资源、兼容性、构建测试与 CI、安装升级发布、日志、文档许可证和外部边界，并把每一项标为已审查、部分审查、未审查或不适用。没有发现问题、跑过一条测试或看过一张截图都不等于该维度已经审查；GUI 项目也不会再把界面和体验降级成轻量抽查。只有全部适用维度均已审查，才会称为完成的全面审查，否则明确交付受限综合审查以及补齐入口。

全面审计本身会输出可由后续普通修复任务直接消费的交接账本。每项发现保留稳定编号、审计内容身份、根因和责任边界、受影响的生产者与消费者、逐项完成条件，以及本地工作树、本地提交、实时远端、发布制品等适用证据平面的独立状态。用户随后要求治理前一轮审计的“全部”或“上述”问题时，每项原始发现都会沿用该身份，并逐项进入已解决、经新证据重新分类、经用户明确同意退出范围或受阻。完整测试和真实用户链通过只证明相应行为，不会让未结项的结构发现自动消失，也不会让未更新的远端平面自动消失；仍有开放或未知项时，Project Steward 不会宣称全部问题已经解决、可合并或可发布。

## 用户环境档案与执行环境

Project Steward 可以为当前用户建立独立于 Skill 和项目的环境档案，默认位置是当前工具用户目录下的 `project-steward/environment-profile.json`。它保存经过允许的终端偏好、解释器和工具绝对路径、包与缓存根、SDK、非敏感运行要求和核验来源，不保存令牌、Cookie、完整环境变量、进程快照或项目依赖清单。

```powershell
python scripts/user_environment_profile.py inspect
python scripts/user_environment_profile.py plan
python scripts/user_environment_profile.py apply --write
python scripts/user_environment_profile.py verify
python scripts/user_environment_profile.py resolve --capability python
```

`inspect` 和 `plan` 保持只读；`apply --write` 需要明确的档案写入授权，且不自动授权安装、下载或修改系统设置。`verify` 会核对记录的路径，`resolve` 则把本次真正要使用的绝对可执行文件和必要环境变量交给正式命令消费。其它项目任务只在环境事实会改变动作或验收时读取相关条目，不为展示完整性扫描整台机器。

可执行文件当前存在并能输出版本，只证明当前可用。Project Steward 在把路径交给持久消费者前还会区分稳定安装、用户确认的持久工具根、项目构建输出、缓存、下载解压目录和临时产物，并核对所有者、保留期限与升级方式。构建或临时入口只用于会话级验证；消费者无法表达临时绑定且用户没有授权安装或写配置时，不会把它伪装成长期工具路径，而会把稳定入口和正式采用准确报告为未完成或受阻。

正式构建跨越多个启动器、构建器、Shell 或子进程时，Project Steward 不会只在当前终端分别运行工具并据此判断环境正常。它会沿正常入口核对父子进程实际选择的可执行文件、工作目录、路径和参数语法、继承后的环境、生成命令以及最终消费者，在第一个发生身份或语义偏离的交接边界定位问题。昂贵预构建若要被包装器或子进程复用，还会先统一包含目标、profile、feature、工具链、编译与链接工具、平台 API、目标配置和有效环境的构建身份；目标名称相同或缓存存在不是复用证据，后续子进程选择同一身份并让最终消费者读取对应产物才是。项目专属的交接规则和取值仍留在项目执行合同，不写进用户环境档案。

对于 Android 构建、下载或其它长任务，外层等待超时不等于构建失败。Project Steward 会区分超时来自命令执行器、构建工具还是应用，检查实际阶段、原进程、日志、产物和消费者结果；任务仍有进展时继续观察原任务，不启动可能争用缓存、锁、端口或输出目录的重复构建。预计输出很长或需要跨轮观察时，会先建立稳定报告或日志、输入身份、执行尝试与进程身份、争用资源和独立退出状态；等待或轮询自身失败只让相应证据保持未知。在确认原进程和子进程已经终止、资源已经释放、残留已经分类前，不会启动新的执行尝试。短小且能一次完整返回的命令不增加这套流程。

PowerShell 中一组语句最后成功，不会替前面的探测背书。证据型查询会使用停止式错误处理或逐项 `try/catch` 保存各自状态；只有权威查询成功后才计算数量、空集合和清理摘要。命令不存在、查询失败或结果不完整时结论是未知，不会因为后续打印出“0”而改写成零发现。

## 其它项目能力

### 项目目录治理

当用户认为项目根目录过多、想知道哪些目录真实使用，或者要求移动、归档、忽略和清理时，Project Steward 会先建立目录证据账本。账本把物理类型与大小、Git 跟踪和忽略状态、正式生产者、消费者、路径真源、生命周期、目标职责和证据强度放在一起；`tracked`、`untracked`、`ignored`、目录名称和最后修改时间都只算现状信号，不会单独推出“正在使用”或“可以删除”。

目录会按活动项目输入、活动本地状态、依赖与工具链、可再生产物、制作工程与原始材料、历史材料和未知项分类。`.gitignore` 只治理版本边界，优先使用意图明确的根定规则，并在 Windows 上检查大小写折叠和邻近路径；宽泛规则意外暴露或隐藏的内容会重新进入分类，而不是再用更宽规则盖住。构建目录或日志被清理后重新出现时，会追到再次创建它的生产者，决定调整正式输出根还是保留一个稳定的忽略目录。

移动前会先确定活动项目根、本地状态根、依赖缓存根、制作工作根和归档根各自由谁拥有，再建立源到目标、生产者、消费者、Git 影响和验证入口的清单。活动路径迁移后退出旧路径、双读、回退和同步副本；归档完成后核对文件数量、字节数和内容身份，并确保活动入口不再读取归档。把已跟踪目录移出仓库会明确报告为 Git 删除。删除仍需要准确目标和单独授权，不能由“开始整理”或“已经归档”推导。

只读盘点器可以直接输出顶层目录的物理和 Git 证据：

```powershell
python scripts/inspect_project_tree.py <项目根>
python scripts/inspect_project_tree.py <项目根> --no-sizes
```

它不会写入项目，也不会判断目录是否安全可删。完成整理后会重新检查目录职责、工作树差异、忽略来源、归档完整性、旧路径退出，以及会自动重建的目录实际出现在哪里；只有活动路径发生变化时才运行对应生产者到最终消费者的真实链，不为纯目录说明或 `.gitignore` 修改启动无关构建和端到端测试。

| “为项目选择并应用许可证。” | 盘点内容与第三方边界，给出方案；确认后写入并核对最终状态 |
| “初始化并发布这个仓库。” | 若目标包含异机运行或服务器部署，先用干净克隆合同区分必须跟踪的构建、运行和仓库能力输入，再审计实际暂存索引，并按用户指定的停止位置分别完成提交、远端创建、推送、required checks、部署或 GitHub 首页核对；来源不明的并发变化不会被恢复或混入，项目规则要求单独同意删除时，提交或推送授权不能替代它 |
| “全面检查项目健康状况。” | 执行只读综合审计，先按项目形态建立维度覆盖账本，逐项检查功能与 Bug、代码质量、架构、数据、UI、完整用户体验、无障碍、性能、兼容性、构建发布、日志、文档和外部边界；每项标明已审查、部分审查、未审查或不适用，并分开工作树、本地提交、缓存远端引用、实时远端检查和发布制品。外部服务承担默认或零配置能力时核对当前官方合同，并在获准时经过项目正式入口验证现实可用性；随后再给问题账本和风险顺序。只有全部适用维度都已审查才称为完成的全面审查，并继续把功能可用、可合并与可发布分别判断，不用局部通过拼成更高层结论 |

仓库事务不会把“产品修改完成”“已提交到本地分支”“已推送到远端分支”和“远端结果已经验证”混成一句完成。每次提交或推送前后都会分层报告工作区与索引、本地分支、本轮新增提交及用途、相对上游的 ahead / behind、远端 HEAD，以及尚未执行或尚未验证的推送、打包、部署和远端检查；如果新提交会增加未推送提交数量，或一次推送会连同此前提交一起进入远端，会在动作前说明准确提交集合和远端将得到的结果。

处理 README 时，Project Steward 会先确认项目身份和公开材料资格，再设计读者路径。通用 Skill 的核心工作流、实际依赖和真实使用方式决定项目身份；`agents/openai.yaml` 一类宿主元数据只说明对应工具中的展示、安装或兼容入口，除非宿主专属能力确实改变了项目能够接受的输入、动作或结果，否则不会把项目写成该宿主专用。

现有 README、内部图片、截图、流程图和生成物只提供候选线索。它们必须能够对应产生时的项目状态、当前活动真源和准备承担的公开职责，才可以进入正文或视觉。用户已经指出过时、版本不明、与当前实现冲突或无法完成对应的材料会退出证据池；文件仍在、图片能打开或结构审计通过，都不会替内容准确性背书。整页重写还会明确选择复用已有、制作新的、排版表达或跳过，并在实际页面中检查读者能否看懂，而不是把“仓库里有图”当作已经完成视觉设计。

个人仓库的 hero 下方可以由一份活动配置生成首屏辅助区。当前配置位于 [`assets/readme-profile/profile.json`](./assets/readme-profile/profile.json)：中文 `README.md` 是默认页，英语与日语分别使用 `README.en.md` 和 `README.ja.md`；第二行连接 X、Telegram、博客和个人主页；第三行从目标 GitHub 仓库实时显示 Stars、Forks 与许可证。官网和文档不会作为默认首屏入口。配置只在目标 owner 匹配时使用，缺少翻译文件或许可证时不会留下失效链接；个人偏好、目标仓库身份和动态状态由不同来源负责。

`scripts/readme_header.py` 负责校验配置并从真实仓库身份生成带管理标记的 HTML。完整 README 新写或重写默认同时交付配置中的三种语言；只改现有首屏时不会制造占位翻译。其它徽章只有在真实发布、CI、Discussions 或下载入口会帮助读者判断项目，并且用户确认后才增加；访问计数和代码行数等装饰数字默认不加。

已有界面进入连续修改时，Project Steward 会先区分新建、局部演进、视觉重做、体验重做和结构重做。用户要求返回此前接受的版本时，该版本重新成为唯一视觉基线，被否定方案不会与它混成另一套界面；新增链接、关闭入口或其它功能时，显示标签、用途说明、真实动作、位置、命中和关闭结果分别确认，功能接入本身不授权重做容器。

技术或框架迁移触及可见产品时，Project Steward 会把实现责任迁移和界面呈现变化分开。框架、组件库和动画工具按状态、生命周期、平台与性能责任选择，不会被当成“更有设计感”的理由；加载过程、首屏、响应式、媒体和互动先按同一入口与时序状态证明等价，只有明确获准的区域随后进入改版。

涉及保留、新增、移动、换序、改名或退出时，它会按稳定对象身份记录原所有者、目标锚点、正式顺序、真实行为和必须保持的兄弟对象，避免把“新增”做成替换、把截图坐标变成布局真源。用户已经看见并明确接受的现有差异会从阻塞项中分开；后续验收仍防止它被放大或传播，但不会借通用最佳实践重新扩大范围。

时间线、事件记录和工作日志等长期有序内容会先拆成连续追溯、定点跳转、查询筛选和人为分组四类访问意图。它们可以读取同一内容真源，却不自动互相替代；新增日期、搜索或目录入口时，不会静默删掉原有的连续浏览结果。每项意图分别记录平台自然输入、可发现的备用入口、位置与选择恢复以及退出依据，再用真实内容和真实滚轮、触摸、键盘或按钮验证。后台共用查询、入口位于同一区域或新控件功能更多，都不能单独证明旧入口可以退出。

视觉参考会拆成结构、互动机制、运动关系、构图、内容密度和视觉皮肤，只迁入用户实际点名的关系。批量角色或媒体素材逐项读取自己的身份、服装、姿态、道具和用途证据，不从同批其它图片或偶然生成结果补造设定；作为动画首帧时，还会为肢体、翅膀、尾巴、衣摆和特效保留运动包络与安全区。

可见验收不会停在“截图文件已经生成”。截图或录屏必须被实际打开或解码，在目标显示比例下逐项查看信息层级、内容密度、裁切、对比度、焦点和状态表达；文件路径、数量、尺寸或捕获成功只证明媒体存在。没有看到目标画面时，视觉结论保持未知。

一组图片、视频、状态和转场共同依赖同一主体时，Project Steward 会先冻结身份事实、共享视觉变量、单项状态变量和获准的共享锚点，再登记派生物与页面消费者的依赖。共同锚点尚未确认时可以比较探索稿，但不会把高成本派生生产当成已经获准；锚点改变后，受影响的旧派生物会失效并重新生产或验收，不会与新批次静默混用。视觉方向则明确第一与第二焦点、不得抢焦点的元素、色彩面积和明度关系，以及由透视、遮挡、尺度、材质和光照建立的空间体积，不用“炫酷、梦幻、3D”替代可检查的画面关系。

外部图片、视频或三维工具参与素材生产时，Project Steward 会先冻结当前真实支持的参考输入、比例、时长、首尾帧、透明背景和已证明不稳定项，再决定正式来源。自然动作可以由合格视频提供并派生静态帧，不能直接输出透明背景时可以建立可抠像源到透明母版的链，多元素批次则先保证每项可独立拆分。每个活动素材都记录来源、处理中间物、派生版本、最终消费者和可直接使用、局部使用、重做或退出状态，不会因为文件已经生成就替它补造用途。

最终要交付可编辑页面、模型、动画或其它视觉产物时，Project Steward 会先冻结产物形态、正式消费者和既有可编辑基线，草图、设定图、截图与生成图只是中间参考，不能替代最终可编辑交付物。层级对象还会明确父级或挂载点、局部坐标轴、枢轴、基础位置 / 旋转 / 缩放及动画增量的唯一所有者，退出并行世界坐标和动画硬编码；验收从自然入口覆盖关键视角、姿态与动画状态，同时核对运行时变换链和最终画面。

任务原本像一个短动作，却因为必要审计、真实运行、外部等待、并发变化或验证链扩展时，Project Steward 会说明为什么扩展、已经完成什么、当前是在执行、等待、验证还是需要决定、下一项可观察结果是什么，以及是否真的需要用户输入。它不会用“还在处理”反复占位，也不会把内部步骤当成交付结果。

透明媒体出现矩形薄雾、暗边或 poster 与播放画面分叉时，Project Steward 会从透明母版、Alpha 处理、交付编码、poster、正式清单一直核对到活动消费者，区分整幅低 Alpha 噪点、边缘污染和编码伪影。验收同时检查 Alpha 的空间分布、明暗背景合成、实际 `currentSrc`、播放和静态回退，不用“带 Alpha”或“浏览器能播放”代替最终画面。

## 第一次使用

如果你希望它从一次已经发生的工作里进化：

```text
使用 $project-steward 阅读这个会话的全部历史和完整过程证据。
先按时间覆盖请求、决定、命令、等待、警告、超时、重试、中断、
半成品、用户纠正和最终证据，再按多个用户最终结果归类。
分别提炼成功经验、暴露的问题和最早预防点，
判断目标 Skill 当前职能是过窄、过宽还是适当，
把属于同一上层角色的相邻能力组织成一份整体合同，
把可跨项目复用的能力更新到 Project Steward 自身；
项目专属事实继续留在项目原有真源。
```

如果你只希望分析而不修改 Skill，把最后一句改为：

```text
本轮只交付可更新能力候选，不修改文件。
```

只提供 GitHub 仓库、本地目录或源码包时，默认入口仍是先把项目讲懂：

```text
使用 $project-steward 看懂这个项目：
https://github.com/owner/repository

先告诉我它解决什么问题、用户最终能得到什么，以及它什么时候有用。
```

提供源码包时，Project Steward 会先把内容解压到独立项目目录，再从脚本返回的项目根开始研究。没有另行指定目标根时使用 `E:\Work\BaiduSyncdisk\Code\Example`；明确指定目录时使用指定位置。已有同名目录不会被覆盖。

## 项目模板

模板保存某类项目每次都应执行的稳定默认、检测信号和验收合同。仍需根据项目结构判断的方法留在 Project Steward 自身。

```text
base → surface → archetype → stack → capability → project overrides
```

仓库自带五个模板：

| 模板 | 负责的范围 |
| --- | --- |
| `base` | 单一事实来源、完整迁移、真实用户链、诊断证据和精确 Git 根 |
| `product-ui` | 用户任务、界面使用质感、完整状态、设计系统和真实视口验收 |
| `desktop-app` | 窗口外壳、原生能力、持久化与关闭链 |
| `tauri-vue` | Tauri v2、Vue 窗口边界、权限和 Windows 实机链路 |
| `local-file-workspace` | 普通文件夹、统一内容路径策略、目录树、文件操作、源文件保真与可选版本管理 |

常用只读命令：

```powershell
python scripts/project_templates.py list
python scripts/project_templates.py inspect <项目根>
python scripts/project_templates.py plan <项目根> --template base
python scripts/project_templates.py verify <项目根>
```

`adopt` 和 `upgrade` 会写入项目配置，只在相应请求明确授权后执行。

桌面应用的方法还会处理同一窗口在紧凑栏、工作区和悬浮控制条之间切换时的标题栏、内容区尺寸、系统按钮保留区、拖动命中、用户位置和多显示器缩放。屏幕捕获产品会把每个自有顶层窗口的捕获可见性作为正式产品合同，并从最终录制产物验证；面向人的设备或窗口选择器则把稳定机器身份与用户标题、默认顺序和诊断信息分开。存在辅助进程和事件流时，还会在连接前建立进程所有权，分开结构化业务结果、完整日志、终止原因、进程结果和传输收尾，等待结果与事件消费、日志写入和订阅者排空，并把有界零退出码、标准流编码和无孤儿进程纳入真实验收。页面或窗口派生延迟界面工作时，会按对象职责绑定生命周期，并在替换、重载和关闭后排空事件循环。自动化或验证脚本需要关闭后重开时，会等待公开的释放完成或失败状态，不用私有任务、对象消失或固定睡眠猜测资源已经释放。

## 自托管 Star History

第三方 Star History 图片因为 GitHub 星标时间戳访问边界变化或公共服务令牌限流而失效时，不需要为每个项目维护一份生成脚本。Project Steward 提供中央可复用工作流；每个项目只增加一个很薄的调用器，使用该仓库运行时自动签发的短期 `github.token`，把亮色和暗色 SVG 原子发布到自己的 `star-history` 分支。没有新星标时不会产生新提交，也不需要个人访问令牌或第三方服务。

在调用仓库建立 `.github/workflows/star-history.yml`：

```yaml
name: Update Star History

on:
  schedule:
    - cron: "17 3 * * 1"
  workflow_dispatch:

permissions:
  contents: write

jobs:
  update:
    permissions:
      contents: write
    uses: CheshireMew/project-steward/.github/workflows/star-history.yml@main
```

README 随后引用自己仓库输出分支中的文件：

```html
<picture>
  <source media="(prefers-color-scheme: dark)" srcset="https://raw.githubusercontent.com/OWNER/REPOSITORY/star-history/star-history-dark.svg">
  <source media="(prefers-color-scheme: light)" srcset="https://raw.githubusercontent.com/OWNER/REPOSITORY/star-history/star-history.svg">
  <img alt="GitHub Star History" src="https://raw.githubusercontent.com/OWNER/REPOSITORY/star-history/star-history.svg">
</picture>
```

公开仓库连续 60 天没有活动时，GitHub 可能停用定时工作流；已有图片仍在，但不再更新。接入、修复或替换默认会继续完成精确提交与推送，手动运行并等待工作流，再检查 `star-history` 分支、两个 raw SVG 和 GitHub README；输出分支尚未生成时不会把本地文件写完报告成图表可用。完整诊断、接入和恢复方法见 [`references/github-star-history.md`](./references/github-star-history.md)。

## 安装与验证

将完整的 `project-steward` 文件夹放入支持 Agent Skills 的工具所使用的 Skills 目录。运行时需要保留 `SKILL.md`、`agents/`、`references/`、`scripts/` 和 `assets/`。用户环境档案位于 Skill 与项目之外，不随 Skill 安装包复制。

运行全部活动测试：

```powershell
python -m unittest discover -s tests -v
```

修改 README 后运行：

```powershell
python scripts/audit_readme.py README.md
```

校验个人配置，或为已经交付三种语言的目标仓库生成与核对首屏辅助区：

```powershell
python scripts/readme_header.py validate --profile assets/readme-profile/profile.json
python scripts/readme_header.py render --profile assets/readme-profile/profile.json --repository OWNER/REPOSITORY --language zh-CN --branch main --readme-root <项目根>
python scripts/readme_header.py verify --profile assets/readme-profile/profile.json --repository OWNER/REPOSITORY --language zh-CN --branch main --readme <项目根>/README.md
python scripts/audit_readme.py <项目根>/README.md --header-profile assets/readme-profile/profile.json --repository OWNER/REPOSITORY --language zh-CN --branch main
```

修改模板时同步版本、注册表哈希和消费者测试，并从一个全新的 Skill 外部临时项目完成识别、采用、读取、检查和升级。
