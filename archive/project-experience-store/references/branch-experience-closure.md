# 已归档：分支与探索结束前的经验收口

用于合并、放弃、回滚或结束一条探索路线之前。目标是把代码和认识分开处置：一段实现可以退出，但其中已经验证的结论不能因此丢失；同时也不把每次尝试都变成长篇项目日志。

## 1. 进入条件

只有出现以下情况时执行：

- 准备合并或关闭一个实际分支；
- 一条实现路线将被放弃或回滚；
- 一次探索已经得出会改变当前项目或其它项目判断的结论；
- 用户明确要求在阶段结束前整理经验。

普通提交、日常进度和没有形成新结论的尝试直接结束，不创建收口记录。

## 2. 逐项选择去向

按当前证据把分支中的认识分成五类：

| 去向 | 什么时候选择 | 完成前必须存在 |
| --- | --- | --- |
| `discarded` | 尝试没有形成仍成立的认识 | 放弃理由 |
| `project-current` | 结论只对当前项目长期有效 | 已创建或更新的项目主题 ID |
| `shared-candidate` | 核心判断可能跨项目成立，但仍需验证 | 已建立的共享候选 ID |
| `shared-registered` | 已通过跨项目准入并确认可复用 | 已注册的共享经验 ID |
| `history-pointer` | 原材料仍有追溯价值，但不应成为当前结论 | 原材料位置或稳定指针 |

一个条目只选一个主要去向。项目当前结论先原位更新；跨项目价值再从该项目主题提炼，不能跳过项目证据直接把分支想法登记为通用经验。

## 3. 执行顺序

1. 读取分支或探索实际改变的文件、测试、运行结果和用户反馈。
2. 对每项认识说明它现在是否仍成立、证据是什么、适用范围是什么。
3. 先完成需要的项目主题写入和共享经验创建或更新。
4. 形成一个收口计划 JSON：

```json
{
  "summary": "这条探索最终留下了什么",
  "items": [
    {
      "label": "结论或尝试",
      "disposition": "project-current",
      "reason": "为什么这样处置",
      "target_id": "existing-project-topic"
    }
  ]
}
```

`history-pointer` 使用 `pointer` 字段保存原材料位置；`discarded` 只需 `label`、`disposition` 和 `reason`。

5. 用户确认处置后运行：

```powershell
python scripts/project_experience.py close-branch <项目根> `
  --work-id <分支或探索的稳定标识> `
  --plan-file <收口计划 JSON> `
  --confirmed-by <确认者>
```

脚本会确认所有项目主题和共享经验目标真实存在且状态一致，再写入一条收口事件。相同计划不会重复登记。

## 4. 输出与停止

第一段说明这条分支结束后真正留下了什么。随后只列：

- 退出的尝试及理由；
- 已更新的项目当前结论；
- 已形成或再次更新的跨项目经验；
- 只保留指针的历史材料；
- 尚未达到共享准入门槛的候选。

收口记录完成并验证目标存在后停止。它不维护路线图，不逐次记录推进过程，也不替代 Git 历史、项目文档或应用运行日志。
