# 模型调用协议治理

用于模型参与业务判断、任务路由、运行时事件说明、状态表达或结构化回复的项目。它治理的是宿主怎样把真实信息送入模型、怎样消费正式响应，以及模型生成内容与运行时事实怎样分工；普通提示词创作、语气润色和一次性内容生成不进入本方法。

模型输出 JSON 时，同时读取 `structured-data-boundary.md`，由它唯一负责解析、schema、资源预算和稳定错误；任务状态或进度进入用户结果时，同时读取 `task-progress-governance.md`，由任务生命周期所有者唯一负责排队、运行、失败和完成事实。本方法不复制这两类真源，只负责模型调用怎样准确消费它们。

## 1. 先冻结模型调用的用户结果

开始前写清：

```text
模型在本轮承担的职责：对话生成 / 任务判断 / 运行时事件说明 / 结构化决策 / 其它
模型不得决定的业务事实：
用户最终会看到或使用什么：
请求从哪个正式入口产生：
响应由哪些解析、运行时、界面、语音或文件消费者使用：
当前故障发生在请求形成、线传输、正式响应、解析、状态提交还是呈现：
本轮权限和停止位置：
```

模型是语言或候选决策生产者，不自动成为任务状态、文件存在性、持久化结果、授权或宿主元数据的真源。最终界面出现了错误文字，也不能先假定只需修改提示词；先找到错误事实第一次进入请求、响应或状态链的位置。

### 先冻结模型调用图，再决定是否拆分

按一个用户可见结果画出实际模型调用图，记录每次调用的输入增量、模型或 provider、正式输出、后续消费者、延迟和 token 成本。若同一模型面对同一份新输入，几个步骤只是依次产出路由、场景、回复策略、事实引用和最终台词，而且中间没有外部执行、人工授权、已提交运行时状态或另一种模型能力介入，这些语义应由一次类型化响应共同返回，再由本地结构化边界校验。调用次数不能靠给同一轮换上 `chat`、`recall`、`repair`、`planner` 或 `renderer` 名称来证明必要。

只有后一调用必须消费第一调用之后才会成立的新事实，或者两次调用承担不同模型能力、不同权限、外部工具执行、人工决定或独立可恢复生命周期时，才保留拆分。每次拆分都要说明单次响应为什么无法承载、增加的成本、失败和重试语义，以及它怎样改善最终用户结果。结构化响应里的场景、意图、策略、引用和任务说明是供程序消费的简短决策字段，不要求模型输出隐藏思维过程，也不把详细“证明”当作回复质量的必要条件。

### 确定性执行资格先于模型路由

模型判断“聊天、追问还是执行”之前，宿主先从当前产品模式、已启用能力和正式执行边界确定本轮允许出现的 route 集合。某种模式按产品合同根本不允许执行时，不调用模型判断一个不可能采用的任务 route，也不先生成结构化任务再丢弃；本轮直接进行一次普通对话调用。这个 gate 只决定哪些能力当前可用，不根据自然语言关键词替模型判断用户语义，也不暗中改选另一个执行者。

执行 route 可用时，任务判断、面向用户的首次回复和结构化 `task brief` 应由同一次类型化响应共同返回。宿主只消费当前 route 允许的字段；任务生命周期所有者正式接受并登记任务后，才能把“已经接收、排队或开始”的事实发布给用户。公开命令或宿主原生快速路径只有在产品已经把它定义为独立入口并拥有自己的验收合同时才绕过模型路由，不能把关键词捷径留作第二套隐形判断。

## 2. 每类输入保留来源身份和消息角色

为实际进入一次调用的全部信息建立来源表：

| 输入类别 | 必须保留的事实 | 允许的消息角色与用途 |
| --- | --- | --- |
| 当前用户请求 | 本轮新动作、原文与稳定 turn 身份 | `user`；只有真实的新用户输入才能新增当前用户消息 |
| 对话历史 | 原始角色、顺序、turn 身份和是否已提交 | 保持原角色；不能把旧命令重新包装成本轮新请求 |
| 系统规则 | 产品职责、权限、输出合同和稳定约束 | `system` 或 provider 的等价控制通道 |
| 运行时事件 | 已提交的任务状态、结果、错误、产物身份和事件版本 | 系统或明确的事件通道；不能冒充一条新的 `user` 消息 |
| 任务原始约束 | 已接受任务的目标、限制和授权范围 | 作为带身份的任务事实随事件传递，不从对话文本重新猜测 |
| 重试指令 | 上一次失败类别和本次只允许纠正的合同 | 系统纠错；不能改变用户意图、任务状态或重新接受任务 |

同一段原始用户命令可以作为已接受任务的 `task brief` 被运行时结果引用，但不能因此再次成为当前 `user` 消息。运行时事件必须直接说明“发生了什么”和“这不是新的用户请求”；模型不能仅靠相邻文本猜测调用目的。

开始实现或诊断前冻结实际请求合同：

```text
request purpose、route 与强制 dialogue act：
最终 messages 的角色、顺序、来源身份和去重规则：
任务事实与运行时事件的身份、版本和允许声明：
response_format 或等价输出模式：
schema、必需字段、路由专属输出示例和错误合同：
输入窗口与最大输出预算：
正式回答字段、推理字段、工具调用字段和结束语义：
```

上下文包、prompt builder 或内存中的 messages 只是中间表示。provider 适配器完成默认值、角色折叠、历史裁剪和请求序列化后产生的最终线请求，才是“实际发送给模型的信息”的权威证据。

### 完整记录与模型上下文是两个边界

完整持久记录、界面查看投影、模型上下文组装结果和 provider 最终线请求服务不同消费者。完整记录保存正式生产者已经提交的原文、角色、顺序、稳定身份和必要版本，是回看、审计、恢复和重新组装的真源；界面可以按滚动、跳转、搜索或筛选投影它；模型上下文则只是在当前调用目的和输入预算内，从完整记录与其它合格来源派生的一次有界输入。不能因为模型窗口有限就先截断持久记录，也不能让当前界面只显示某段内容时把其余记录从模型资格中静默删除。

开始实现或迁移前建立上下文投影合同：

```text
完整记录真源、正式写入边界与保留语义：
界面查看投影、当前位置与恢复身份：
上下文组装策略与输入预算：
近期原始回合、可追溯的连续性摘要和相关召回怎样取得资格：
每项上下文片段的来源身份、原始角色、顺序、覆盖范围与版本：
界面导航是否允许改变下一次模型输入，以及唯一明确入口：
裁剪、摘要、召回或组装失败时的降级与完整记录保全：
provider 序列化后怎样证明实际预算、来源和顺序：
```

具体项目可以按实际质量和成本选择近期原始回合、可追溯的连续性摘要和相关召回，但选择器只产生投影，不取得记录所有权。摘要必须保留来源或覆盖范围，使后续调用能够解释它代表哪些已提交记录；召回结果保留稳定身份和原始事实角色，不能被包装成本轮新请求。界面滚动、跳转、搜索或筛选默认只改变查看位置；只有用户明确动作或产品合同中的唯一上下文控制入口，才允许改变下一次组装策略。裁剪、摘要、召回或组装失败只能形成有界降级或明确失败，不能删除、覆盖或重新解释完整记录。

### 生产对话上下文与执行任务上下文分开

面向用户的对话调用只携带完成本轮表达所需的角色身份、关系、有效记忆、当前请求和输出合同。生产提示词使用简短、正向、可执行的职责和表达约束；失败回复、反例清单、历史纠正原文和离线评分规则留在评测材料中，不持续注入每轮上下文。确定性可判定的 schema、事实引用、权限、任务状态和宿主元数据由结构化边界或运行时 gate 负责，提示词不重复承担一套脆弱的文本禁令。

对话模型决定需要执行任务时，给执行者的是结构化 `task brief`：目标、与任务有关的上下文、约束、授权工作区、预期结果和验收条件。角色性格、关系培养、表达风格、陪伴记忆以及面向用户的台词不会进入 CLI 或其它任务执行器，除非它们本身就是用户任务的明确输入。任务接收、执行中和完成后的用户回复仍由对话调用消费运行时已经提交的事实生成；执行者不会反向取得角色表达所有权。

只服务对话呈现的动作、表情、音色或其它响应协议，只进入对话 route 的最终线请求。角色身份可以由多个调用共享，但聊天专属控制协议不能追加到执行者也会消费的共享身份提示或公共 prompt builder；开始修改前要枚举该提示的全部正式消费者，并从 provider 序列化后的实际请求证明执行 `task brief` 没有继承对话控制要求。

## 3. 路由、schema 与示例必须表达同一合同

普通对话、任务接收、任务结果、取消、失败和其它运行时事件分别建立输出合同。强制路由存在时，schema、必需字段、输出示例、校验器和 fallback 都必须与该路由一致；不能给强制任务结果同时提供普通对话示例，再期待模型忽略冲突。

示例按 route 或等价稳定身份选择，只展示该路径允许的字段和值域。没有进入当前调用的其它路由不附带同级示例。任务结果仍需携带原任务目标和限制，使模型能够区分“报告已经发生的结果”和“重新执行用户命令”。

`response_format`、JSON mode、tool schema 或其它 provider 输出约束必须出现在最终序列化请求中。提示词里写了“返回 JSON”不能替代线协议字段；线协议字段正确也不能替代 schema、示例与当前 route 的语义一致。

## 4. 运行时事实和生成正文各有一个所有者

任务接收、排队、运行、失败和完成只消费任务生命周期所有者已经提交的状态。任务尚未执行时，模型最多表达已经成立的接收或等待事实；只有正式生产者完成工作、结果登记成功并由运行时提交完成事件后，结果说明才能表达完成。模型生成一句完成式文案不能反向推进状态。

路径、文件名、附件、按钮、状态标签或其它由宿主确定性展示的元数据，继续由宿主拥有。调用合同明确告诉模型哪些事实会在正文外显示，以及正文应承担什么；模型不得重复制造一份元数据真源，也不能凭提示词推测尚未产生的产物。

模型回复同时驱动动作、表情、音色或其它非正文行为时，用户语义正文与控制意图属于同一正式响应合同。控制意图优先使用有类型字段或等价协议通道，由唯一响应入口解析并绑定同一响应身份与版本；动作、表情或其它控制消费者、界面投影和语音投影不能各自解析模型原文。provider 只能流式输出文本而必须使用内联控制标记时，标记仍是线协议，不是自然语言；合同必须定义准确语法、跨分片缓冲、最终 flush、多个控制意图的顺序与冲突语义，以及未知或残缺标记的错误处理。普通括号或标点不自动取得控制语义，只有产品合同明确指定的内容才从显示或语音投影中移除。

界面正文、TTS、通知和其它呈现是否共用一份内容，由当前产品合同决定。不能为了修补某个消费者的重复内容，擅自新增第二套正文、朗读 helper 或恢复分支；确实需要不同表达时，先证明消费者目标不同，再定义从同一语义结果产生的明确投影。

每条进入呈现层的消息保留来源、语义阶段、稳定身份和允许的受众。界面、TTS 与通知先按这些事实判断消费资格，再对已经合格的同一语义结果生成各自投影；系统规则、运行时事件、CLI 原文或宿主元数据不能因为最终表现为字符串就自动取得角色正文或朗读资格。文本清理只能改变合格投影的表现，不能把原本不合格的消息洗成可朗读内容。

## 5. 正式响应通道和恢复语义

provider 返回的 `content`、`reasoning`、tool call、finish reason 和原始响应各自只证明自己的通道。推理内容合理不能证明正式回答存在；正式 `content` 为空、只有空白或不满足输出合同时，本轮仍是无可消费结果。

解析和 gate 使用稳定错误类别区分空内容、非 JSON、schema 不符、route 不符、引用不存在的运行时事实、提前声明状态和重复宿主元数据。消费者不从异常文字或模型解释猜测类别。

只有 provider 合同、操作幂等性和当前状态允许时才做有界重试。重试携带准确失败类别，只纠正原调用的输出合同；它不新增用户消息、不重新接受任务、不重复执行已经发生的副作用，也不改变已提交状态。最终 fallback 必须与当前 route 和已知事实相容，不能用固定完成句或无关道歉掩盖失败。

## 6. 迁移到一条活动调用链

最终链由一个请求合同所有者、一个 provider 序列化边界和一个正式响应入口组成。迁移时枚举普通对话、任务判断、后台结果、取消、重试、恢复、调试日志、测试 provider 和维护工具中的全部调用点，再一次迁移：

```text
正式用户动作或运行时事件
→ 请求合同与来源身份
→ provider 最终序列化请求
→ 正式模型响应
→ 唯一结构化入口与 gate
→ 任务或对话运行时
→ 控制意图事件、宿主元数据与正文投影
→ 动作、表情、界面、TTS、通知或其它最终消费者
```

新链接通后退出把运行时事件包装成用户消息的 helper、全路由共用但语义冲突的示例、调用点局部拼 prompt、重复解析、消费端补字段、并行正文和仅为旧合同存在的 fallback。外部 provider 需要兼容时只在适配器边界表达明确版本差异，项目内部不保留两套请求语义。

## 7. 从实际线请求验证到用户结果

关键测试从正式用户动作或运行时生产者开始，经过实际请求构造和 provider 序列化，再让响应经过正式解析、运行时和最终消费者。可以用记录线协议的本地测试端点代替不可控的远端模型，但不能跳过正在验证的 provider serializer，也不能由测试直接手写消费端 context pack 或已经校正的结果对象。

至少核对：

1. 普通对话的最终请求只有真实当前用户输入成为新增 `user` 消息，历史角色和顺序保持。
2. 运行时事件不新增伪造用户消息；原任务命令只以带身份的任务事实出现，route、schema 和输出示例一致。
3. 最终线请求确实包含目标 `response_format` 或等价约束、输出预算及本轮必需事实。
4. 推理存在但正式内容为空、结构错误和重复宿主元数据分别到达预期错误与有界恢复路径。
5. 接收阶段正式产物尚不存在，界面不能声称完成；完成事件出现时，正式产物已经由生产者生成并能被消费者读取。
6. 宿主单独显示的元数据不会在正文中重复，正文进入当前产品合同规定的界面、TTS 或通知消费者。
7. 旧消息包装、通用冲突示例、并行正文和宽松 fallback 已经退出活动源码、测试、文档与调试入口。
8. 同一轮可合并的路由、场景、策略、引用和台词只产生一次模型调用；保留的额外调用都有新的事实、能力或权限边界证据。
9. 执行者收到的 `task brief` 只含任务所需事实，生产提示词没有携带失败反例库，角色上下文也没有泄漏到 CLI 执行链。
10. 执行被产品模式禁止时，一个看起来像任务的输入仍只产生普通对话调用，不生成任务 route、不接触执行器；执行可用时，路由、首次回复和 `task brief` 只产生一次模型调用，首次回复不会早于任务正式登记。
11. 正式消息生产者分别产生可朗读角色消息和不可朗读的系统或运行时事件，界面、TTS 与通知按来源和语义阶段取得正确投影；消费端不能先丢失身份再靠清理后的文字猜测资格。
12. 对话控制协议只出现在聊天线请求中，不进入执行 `task brief`；正式响应把控制标记拆到不同流式分片后，仍由唯一解析入口按合同顺序产生控制事件、显示投影和语音投影，并让真实动作消费者、当前界面与 TTS provider 边界读取同一响应身份。直接调用标签解析、文本清理或动作函数不能代替这条链。
13. 正式记录生产者提交超过单次输入预算的有序记录后，完整记录仍能由界面或恢复消费者读取；上下文组装器从这些记录生成带来源和覆盖范围的有界投影，provider 最终序列化请求实际遵守预算与角色顺序。测试不能手写已经裁剪好的 context pack，也不能通过改变界面当前位置暗中改变模型输入。

中间 builder 单测、prompt 快照、模型原始响应看起来合理、解析器单测或消费端手写结果，各自只证明一层。最终报告分别说明请求合同、线请求、响应解析、运行时状态、呈现消费者和用户结果达到的证据等级。

## 8. 输出与停止位置

第一段直接说明错误事实第一次进入模型调用链的位置，以及最终由哪个请求、状态或呈现所有者收口。随后给出来源与角色表、实际线请求合同、route/schema/示例一致性、状态与宿主元数据所有权、恢复语义、迁移与旧路径退出、真实 provider 边界和用户链证据。只要求诊断时停在这些证据和最终修法；明确要求实施时才迁移项目调用点。
