# 仓库发布执行与验证

## 4. 初始化 GitHub 仓库

“初始化 GitHub 仓库”是一个连续用户结果，但本地 Git 初始化、首次提交、创建 GitHub 远端和首次推送仍是可分别停止的状态改变。开始时在第 1 节账本中明确完整目标和本轮停止位置；用户只要求本地初始化时，完成本地阶段后说明 GitHub 尚未创建并停止。

按以下顺序执行，不跳过中间候选和索引复核：

1. 读取目录内的项目规则、已有文件和用户原有改动；用 `git rev-parse --show-toplevel` 判断真实 Git 边界。目录已经位于父级工作树内时，不创建嵌套 `.git`，先说明真实边界。
2. 使用当前已经可用且经过认证的 GitHub 正式接口只读核对账号或组织、目标仓库是否已经存在及当前权限。检查不授权安装客户端、登录账号、创建远端或改变设置；无法证明准确所有者时停止。
3. 按第 2 节建立干净克隆交付合同，并按第 3 节审计本地物理文件和拟上传候选。候选尚有隐私、非必要或未知项时先解决边界，不进入远端创建。
4. 只有用户明确授权本地初始化时才运行 `git init`。初始化不自动添加全部文件、不自动创建提交，也不擅自改变用户已有分支名；依据已经确认的项目事实建立或更新 `.gitignore` 与 `.gitattributes`，不凭猜测删除文件。
5. 只把获准清单中的准确路径或内容片段加入索引，禁止用 `git add -A`、`git add .` 或等价整树暂存绕过候选账本。暂存后重新读取索引的完整路径、差异和内容身份，并让第 3 节的必要性与隐私检查消费这份真实索引。
6. 只有索引与获准清单一致、目标验证对同一内容身份成立且用户授权提交时，才创建首次提交。提交后核对提交树与已审核索引完全一致，并重新检查作者姓名和邮箱的公开结果。
7. 只有用户明确授权创建 GitHub 仓库，并确认所有者、准确仓库名和 public、private 或其它实际支持的可见性后，才创建空远端；不根据账号惯例猜可见性。目标已经存在时不重复创建，转入现有远端身份与分叉核对。
8. 新远端创建后回读所有者、仓库名、可见性和空仓库状态，再在没有远端名冲突时写入准确远端地址。首次推送必须另有授权，使用非强制更新，并遵守第 6 节的发布事务和并发检查。
9. 推送命令成功后记录提交身份并停止，不等待实时远端页面、Actions 或部署。用户另行明确要求远端验收时，再按第 7 节从准确提交核对 HEAD、默认分支、提交树、README 与适用的已完成检查；仓库承诺可构建或运行时，由该独立结果决定是否需要远端干净克隆。

初始化状态按“内容边界已通过 / 本地 Git 已初始化 / 首次提交已创建 / GitHub 空远端已创建 / 首次推送已完成 / 实时远端已验证”分层报告。后层成立不能反推前层，停在任一层时都准确说明尚未发生的 GitHub 变化。

## 5. 本地主页预览

README 与素材按主 Skill 的 README 路径制作。设计 Logo、设计图片或写 README 时继续遵守图片盲边界，不打开、查看、截图或渲染任何图片。本地阶段至少证明：

- README 的图片和链接能从仓库相对路径解析；
- 首屏身份节点、普通文本、图片宽度合同和正文顺序完整；对 GitHub 常见宽度和窄屏只做结构与字号预算计算，不作画面判断；
- 文案只陈述仓库能够证明的功能；
- 许可证链接指向唯一范围说明；
- 预览使用的正是准备提交的文件，而不是另做一份样稿。

达到“本地预览”停止位置后，给出文件差异、结构验收入口和未进行人工画面判断的边界，等待用户决定是否继续发布。

## 6. 创建提交、远程仓库与推送

停止位置包含远端结果时，先消费 `repository-publication.md` 的“远端结果先通过目标前置门”，把准确远端、上游、目标引用与本地提交是否为独立结果绑定到本次事务；这一步早于任何 `git add`、commit 和 push。门槛未通过时，可以完成用户明确要求的只读检查，但不创建索引或提交，也不运行已经证明没有目标的 push；只在用户另行明确授权本地提交结果时转入本地提交合同，不能从推送请求自动降级。

开始发布事务时，保存本次获准路径、各路径当前身份、候选提交树、对应验证和远端 HEAD。验证后以及覆盖、恢复、暂存、提交前都重新读取受影响路径；同步客户端、生成器、编辑器监视器、其它 Agent 或进程产生的变化，只有在来源、职责和当前结果已经确认后才能纳入。不能解释的变化不得用 `git restore` 消掉。普通项目不得顺手暂存，只停止与这些路径冲突的发布动作；Project Steward 自我进化整仓发布则停止整个发布事务，不能靠遗漏变化继续。

候选内容改变时，只使验证账本中受影响的证据失效。完成最终验证后，暂存索引必须对应同一候选内容，并重新核对索引中的变化事实、正式消费者和新鲜证据仍然匹配；提交后再核对提交树、剩余已跟踪变化和新出现的未跟踪文件。提交之后出现的工作树变化不会自动改变已创建提交：普通项目必须判断它是否证明提交遗漏了正式交付物，无关变化可以保留并报告，相关或未知变化在推送前停止；Project Steward 自我进化整仓发布把任何新变化视为提交遗漏，在推送前重新收口整个工作区。

### 推送执行必须消费自动远端后果账本

最终候选冻结后、执行任何 push 之前，消费 `repository-publication.md` 的“推送前先冻结自动远端后果”。账本必须对应当前候选、准确事件、目标引用和实时可取得的远端生产者，并证明每项自动结果与本次授权、禁止项和停止位置相容；账本缺失、相关状态未知或存在冲突时不推送。工作流、复用 action、目标引用或远端自动生产者在候选确认后变化时，回到该方法重新取得授权兼容性，不能用较早检查或非强制推送可能拒绝来替代。

### 远端前进后先重建发布基线

目标远端已有提交时，在暂存或创建提交前取得当前跟踪目标的实时远端 HEAD，并同时固定先前观测的旧远端、此次取得的新远端和本地候选基线。远端已经前进时，分别读取旧远端到新远端的变化、本地候选相对旧远端的变化及两者的重叠路径；取得远端成功、Git 能自动合并或文本没有冲突，都不能代替这份语义比较。远端身份或变化范围无法可靠取得时，发布候选保持未知并停止。

逐项判断重叠变化回答的是同一个实现细节，还是许可证、schema、公开身份、生成合同或其它会支配多个消费者的权威合同。远端目标分支已经明确建立新合同，而本地候选只因基线较旧仍保留旧声明时，把新远端作为当前基线，回到该合同的唯一方法所有者确定最终语义和全部正式消费者；只有仍属于本次获准结果的消费者才进入迁移，其它缺口保持阻塞并取得相应写入权限。若本地候选本来就包含用户明确批准的新合同，或者两边分别表达不兼容决定、权利与目标仍未知，停止并交付准确冲突，不能按提交时间、`ours`、`theirs`、文件多数或自动合并结果猜权威。发布路径只负责基线、整合和候选闭包，不复制许可证、schema 或公开身份方法，也不因需要整合远端而扩大普通工作树的发布范围或获得修复验证失败的权限。

完成获准的 rebase、merge 或冲突处理后，重新冻结最终候选的基线、树、提交身份、工作区、索引和未跟踪文件；从此次取得的目标远端到 `HEAD` 读取完整最终差异，把整合改变的合同和消费者映射回验证账本，并只让受影响证据失效。whitespace、许可证、生成合同及项目规定的每项检查分别保留退出状态，不能把整合前的暂存检查或后续成功命令当作最终候选通过。推送前再次取得目标远端并与本轮整合基线比较；目标已经变化就重新建立上述账本，不能把非强制推送将会拒绝当作并发检查。推送成功后的停止位置继续由既有发布合同决定。

创建提交、创建远程、选择或改变可见性和推送是相互独立的动作：

1. 用户授权提交后，核对作者配置、分支、工作区、当前基线和准确删除清单，再只暂存获准且来源明确的内容。任何受项目规则约束但尚未单独获准的删除都必须在暂存前停止。审计对象是 Git 实际索引，不是工作区印象：检查暂存文件清单、状态、统计和完整差异，运行 whitespace、密钥、许可证、超大文件、依赖或项目规定的检查，并在提交后核对提交树与已批准暂存集一致。
2. 用户授权创建 GitHub 仓库后，确认所有者、准确仓库名和可见性。未明确可见性时停止，不默认为 public 或 private。
3. 远程已存在时读取其默认分支和 HEAD，不用本地猜测覆盖。
4. 新远程没有提交时，使用用户当前约定或本机初始化得到的分支；只有用户明确指定时才改名为 `main`、`master` 或其它名称。
5. 远程已有提交时，不用强制推送建立表面一致；先处理真实分叉。

每条检查命令必须单独确认执行成功并立即保留退出状态，不能让后续命令覆盖失败。密钥扫描器成功运行后零匹配才是零发现；测试数据使用与真实凭据明显不同的假值，除非当前任务本来就在验证检测器。依赖审计若因镜像或接口不支持而失败，结论是未知；可以在不持久修改用户配置的前提下使用项目官方审计端点复核，不能把审计未运行说成零漏洞。

Git 仓库中的已跟踪工作树差异、暂存索引、未跟踪文件和被忽略路径是不同的工具输入集。先以候选账本确定哪些对象必须受检，再核对所选命令实际读取哪一组。`git diff --check` 只能检查它实际选中的 Git 差异；仓库没有首个提交、候选全是未跟踪文件，或者命令的差异集为空时，即使退出成功也不能证明候选内容通过。未获暂存授权时，直接对已批准候选路径执行等价只读检查；获得授权并暂存后，再让索引检查消费同一候选。被忽略路径是否应进入候选仍由干净克隆交付合同决定，不由工具默认排除代替。

远端不存在时，推送请求不会自动授权创建仓库，也不会给出可见性。先用只读身份和所有者权限检查确认缺口；创建远端、选择 public 或 private、设置默认分支、推送以及之后改变可见性仍分别需要明确授权。不能根据同一账号的其它仓库可见性替用户推断新仓库。

### 本地主题分支退役先证明当前提交图包含关系

用户问“另一个分支是否已经合并”或要求“如果被默认分支完全包含就删除”时，当前分支名、工作区是否干净、推送是否成功和两个分支是否同一 SHA 都不能替代提交图证明。先冻结准确仓库、来源本地分支和目标本地分支，运行 `scripts/repository_branch_containment.py <仓库根> --source <来源> --destination <目标>`；检查器只读取本地引用与 worktree，不获取远端、不删除分支，也不替用户授予删除权限。

“当前提交图完全包含”定义为来源分支可达的每个提交都能从目标分支到达，使用祖先关系和双方独有提交数共同证明。来源独有提交为零即可成立，两个分支同一 SHA 只是充分但非必要条件。这个结果不能证明历史上一定执行过 merge 命令：rebase、squash、cherry-pick、引用移动和服务端合并会产生不同历史形状；只有任务另需历史机制时才读取提交父关系、reflog、PR 或服务端证据，并把“当前结果已包含”和“曾经怎样合并”分开回答。

本地分支、远端分支和其它 worktree 分别成立。用户同时问远端时，另行从实时远端读取准确引用，不能用本地 tracking ref 代替。只有来源分支被目标完全包含、不是目标分支、不是当前分支、没有被任何 worktree 检出，而且用户已经明确授权删除该准确本地分支时，才使用非强制删除；任一条件未知或失败都保留分支。不得用强制删除把未包含提交解释成“已经清理”。删除后只核对来源本地引用已经退出、目标引用仍是动作前 SHA、工作区与索引未改变；远端分支删除是另一项授权。

### 分支目标状态与保护策略必须相容

发布前消费第 1 节已经冻结的本次交付路径、交付后允许存在的本地与远端分支、长期贡献路径和分支保护或 ruleset 目标状态。分别读取当前本地分支、其它 worktree、实时远端分支、默认分支、有效保护规则或 ruleset，以及会写入自动展示分支、发布分支等引用的正式生产者；本地 tracking ref 不能代替实时远端。“本次不创建其它分支”不能推导出“交付后只保留 main”，自动生成的分支也不能因名称不像源码分支就被忽略。

先建立兼容性账本：本次直接推送、候选分支与 PR 或其它交付路径，是否会被 required checks、必须经 PR、管理员强制执行和 bypass 范围阻断；必需检查能否在候选身份上真实产生；最终分支集合是否仍包含正式生产者需要的输出分支；每项删除是否同时满足提交图包含关系、worktree 占用条件和准确删除授权。交付路径、最终分支集合、长期贡献路径或保护目标互相矛盾时，交付冲突并等待用户决定，不替用户选择一项，也不静默放松保护。仅要求把当前提交直接推到 main、不为本次改动创建分支，不授权删除现有分支或修改远端设置。

长期分支保护只能在最终候选已经冻结，并且同一候选上的代码、文档、README、许可证与致谢、版本化素材及适用验证全部收口后启用；否则后续内容修正可能被刚建立的规则反向阻断。变更前保存准确现状、目标值和恢复值，用远端接口要求的完整 schema 提交，并为读取与写入命令分别保留退出状态。接口返回验证错误不能证明远端完全没有变化；写入后必须重新读取准确分支的有效规则或 ruleset，逐字段确认目标状态。

保护生效后候选内容又变化，原来的内容冻结、检查和发布闭包随受影响范围失效。为补交修正而临时放松保护是新的远端设置变更，必须另有明确授权，并在动作前记录准确现状、临时目标、恢复值和失败停止位置；修正完成后按已授权恢复并回读有效状态。临时放松不能作为正常收尾步骤，也不能让“最后恢复了保护”替代对中间未保护窗口、实际提交和最终规则的核对。本节只验证已获授权动作是否相容，不授予分支删除、保护修改、bypass 或其它远端写入权限。

### 冻结公开发布候选、标签与资产

用户要求“发布”、“推到 GitHub”或“给新用户下载”时，在改变任何远程状态前把停止位置说成用户结果：只推候选分支、创建 PR、合并进默认分支，还是同时创建可下载 Release。候选分支、PR 和默认分支是三个可分别成立的远程表面；不能在用户期待仓库首页已经变化时，只交付一个未合并分支后再用安全流程解释差异。

停止位置明确是“准确候选进入默认分支”时，先冻结候选 SHA、基准分支、实际保护规则或 ruleset、required checks、允许的合并方式和目标历史形状。此时等待的只是该候选达到合并所必需的检查；可选 CI、部署和其它消费者仍是异步结果。仓库级 `allow_*` 设置只是线索，分支规则与实际合并响应才是权威。merge commit 被拒绝时，从有效规则允许的方法中选择与用户结果一致的方式；用户没有要求 squash 且线性历史允许 rebase 时，优先保留提交粒度。方法切换不能绕过检查、改写其它已发布历史，也不授权修改代码、测试、工作流或远端设置来修复失败。

服务端 rebase 或 squash 会生成新的提交身份。合并后重新取得 PR 状态、远端默认分支 HEAD 与候选结果的包含关系，不能假设旧本地默认分支可以快进。“远端默认分支已包含结果”和“本地默认分支已同步”分别交付；本次结果包含本地同步时，移动本地默认分支引用前必须证明原本地独有提交仍可由来源分支、备份引用或 reflog 找回，并且工作区与索引不会被覆盖。无法证明时保留分叉并报告，不为表面整齐强行对齐。

项目将标签、Release 和可下载资产作为正式用户交付时，发布候选按以下顺序冻结，后一层不得为尚未成立的前一层背书：

```text
冻结准确提交 SHA、目标分支、版本和发布合同
→ 同一 SHA 上全部必需本地检查成功，并已有满足合同的远程 CI 结果
→ 从该 SHA 的新鲜检出或等价隔离输入构建最终资产
→ 核对资产边界、文件允许集合、版本、公开身份和启动入口
→ 在一次性副本执行 smoke，再证明原候选清单和内容身份没有变化
→ 计算最终资产摘要
→ 创建指向该 SHA 的标签和 Release，上传同一内容身份的资产
→ 回读远程标签、资产摘要、默认分支与公开安装入口
```

如果应用第一次启动会在自身目录写入配置、缓存、日志、解压组件或其它状态，不在正式资产根上直接 smoke 后再凭预期文件名“清理”。先记录原候选清单与内容身份，把完整交付单元复制到已登记的一次性验证根，从副本的正式入口启动，将新状态映射到真实生产者和保留或归档责任，最后重新核对原候选未变。用户没有授权删除时，不为了得到干净报告删除 smoke 副作用。

必需 CI 尚未在最终 SHA 上成立时，不创建面向用户的正式标签、Release 或上传资产；推送或派发对应运行后立即停止，把发布候选标为等待异步证据。只有用户在运行已经结束后明确继续发布，才读取该结果并从冻结 SHA 恢复。已公开标签和同名资产默认保持不变；公开后发现候选错误时，把新版本、撤下或其它用户可见修复作为另一项发布决定；不因下载数量为零就默认强制移动已发布标签或替换资产是普通收尾。

### 有意重建为单一根提交

只有用户明确要求把准确仓库和分支的历史替换为一个新的首次提交时，才进入单根提交事务。普通的“提交”“推送”或含糊的“继续”不授权改写历史；创建或改变远端、选择可见性、归档旧仓库、删除文件与强制更新远端也各自需要原任务已经明确覆盖或另行授权。

事务开始前建立不可省略的账本：

- 准确的本地仓库、远端所有者、仓库名、目标分支和仓库可见性；
- 已批准候选树的内容身份，以及针对该树完成的验证；
- 当前 HEAD、旧本地分支引用、已观测远端分支 SHA、默认分支和远端 HEAD；
- 旧历史备份的位置、内容身份和可恢复性；
- 预期根提交的主题、作者、树对象、父提交为空和提交数为 1；
- 精确租约条件、远端变化时的中止条件和推送后的远端检查。

在改写本地引用前，按已获授权的方式保留旧 `.git`、引用或等价历史备份，并实际验证备份能够识别原 HEAD；没有删除授权时不得为了得到“干净的新仓库”删除旧历史。新根提交只能从已经批准和验证的候选索引或树创建，创建后核对其树对象与候选完全一致、父提交为空、目标分支提交数为 1。更新本地分支引用时使用预期旧值作为条件，当前引用变化就中止，不能覆盖来源不明的并发修改。

远端更新前重新读取目标分支。历史替换使用精确的 `--force-with-lease=<branch>:<observed-sha>` 或语义等价的条件更新，不使用裸 `--force`；若远端不存在时的预期值与远端已有提交不一致，或已观测远端分支 SHA 之后远端发生变化，立即中止并重新确认，不能扩大租约。

推送后必须重新获取远端，并核对仓库可见性、默认分支、远端 HEAD、根提交树、父提交为空、提交数为 1，以及禁止路径或应归档内容未进入新树；这是历史替换自身的同步结果，不包含等待 GitHub Actions。当前用户结果依赖远端检查时，把它标为异步且未验证并停止；用户在检查结束后明确继续，才消费已完成结果。若后续修复使最终候选发生变化，应以新候选重新验证并再创建一个无父提交的根，而不是在它后面追加修复提交；再次更新远端时也必须使用新读取的精确租约。

## 7. 发布验证

推送完成不等于发布已经可用。沿最终用户链路验证：

1. GitHub 仓库的所有者、名称与可见性正确。
2. 默认分支是预期分支，远程 HEAD 指向刚发布的提交。
3. README、许可证和关键素材在该提交中存在，Git blob 与本地提交一致。
4. GitHub 仓库首页能够读取 README，图片、锚点和链接可用。
5. GitHub 的许可证识别结果与范围设计一致；混合许可证显示 `Other` 不自动视为失败。
6. 停止位置只是普通提交、候选分支推送或运行派发时，在推送或派发 required checks、GitHub Actions、部署任务后立即停止并报告异步状态，不等待结束。停止位置明确是默认分支包含候选时，required checks 是该结果的前置门，按冻结候选等待并完成允许的合并；与当前结果无关的可选检查单独报告。
7. 用户要求可部署或可运行时，从远端准确提交取得的干净克隆仍能完成交付合同，并由真实入口形成最终用户结果；本地工作树、远端提交存在和部署成功是不同证据。
8. 当标签、Release 或可下载资产属于本次用户结果时，它们指向同一已验证 SHA，远端资产摘要与未被 smoke 改写的本地正式候选一致。

跨项目结果在上述检查后仍逐根保留结论。只有账本中的每个目标根都取得相应提交、推送和远端证据时，才能说所有目标根已经发布；互操作通过但其中一个根未入库、未提交或未推送时，应分别报告“跨项目链已通过”和该根尚未发布，不能把两项拼成更高层结论。

验证失败时说明失败位于本地提交、干净克隆、安装或构建、传输、远程分支、远端检查、部署、GitHub 渲染还是识别层。读取状态、日志和失败产物属于只读发布验证；修改源码、配置、工作流或远端设置来修复失败，只有原请求已经明确要求持续修到发布可用，或用户另行授权时才执行。未经授权不通过强制推送、删除远程或改可见性来“修好”。
