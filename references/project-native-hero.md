# 项目原生 Hero

用于设计 README 的表达性视觉怎样承接已经成立的身份和正文职责。整页模式传入内容阶段已经确定的主页主身份与素材落点；仅素材模式传入当前 hero 的素材沟通任务。它只消费上层已经冻结的非图片项目事实、语义概念、几何合同、视觉作用和素材动作，不重新选择项目主特色、事实等级、视觉方向、正文入口或图片位置。

## 先写 Hero 输入

```text
上游沟通重点：主页主身份 / 素材沟通任务
主要用户：
第一次可观察结果：
区别性能力或机制：
最佳合格证据：
已核定活动项目事实及其适用状态：
图片排除边界：
Logo 正式身份源结论与同步验证：
事实等级：
已选视觉合同：
已冻结语义概念与几何合同：
视觉作用、素材动作与证据边界：
正文落点：正向项目定义之后 / 所解释章节的引入文字之后
```

项目对象、动作和关系只能从活动定义、代码、文档、测试、接口、数据合同、配置、命令和真实行为中取得。设计过程不得打开、查看、截图、渲染、OCR、取色、临摹、比较或分析任何现有、旧版、参考、生成、远程或用户附带图片，包括当前 Logo 和 hero。图片路径只可用于决定引用是否迁移，不得参与概念与表面选择。

Logo 与 hero 是两个职责不同的素材。完整 README 优化还必须交付一个可在首屏独立使用的 Logo，并把它作为紧凑身份图先于表达性视觉生成；本页不重新寻找或裁决身份源，只消费 `visual-direction.md` 已冻结的结论。上游发现正式代码或配置生产者时，Logo 优先复用或确定性派生并保留同步验证；只有上游确认身份源缺失时，才从项目身份事实独立建立新概念。hero、机制图、结果图和旧 Logo 都不能向它捐赠母题、配色或构图。项目事实不足时使用项目名称或首字母形成中性排版标志，不补造项目对象或品牌性格。全宽 hero、机制图、结果图或展示图不能充当 Logo，也不能进入首屏管理区的 `identity_image` 位置。hero 只负责让主要读者继续理解主价值、结果合同或关键机制，并在完整首屏管理区和正向项目定义之后出现；解释具体章节时紧跟该章节的引入文字。其它独立主要意图继续由 Markdown 中的快速开始、命令、提示词或链接承载，不把所有能力塞进 hero，也不因为 hero 聚焦一项价值而移除它们。

## 确定信息职责

hero 可以包含：

1. 类别或技术语境。
2. 仓库名称。
3. 一句具体描述。
4. 由活动项目事实确定的对象、关系或结果合同。
5. 少量稳定的仓库元数据。

这些是信息职责，不是固定位置。根据项目移动、缩放或省略。

语言切换、文档、贡献、反馈、个人入口、Stars、Forks、许可证和其它需要点击或实时更新的状态不属于 hero 元数据。它们使用上层已经核定的首屏辅助区，作为 Logo、项目名称和本地化一句话介绍之后的 Markdown / HTML 保持可访问和可更新；不能画进 SVG、PNG 或 WebP，也不能为了容纳链接或徽章重新选择 hero 构图。即使 Logo 或 hero 内含项目文字，项目名称和一句具体价值也要作为独立 HTML 文本存在，不能让图片成为唯一真源。首屏辅助区不能把第一屏挤成只有链接和数字；它先完成并闭合，正文用正向项目定义建立理解，hero 再在内容阶段指定的位置承接证据或机制，不能用 hero 抢占 Logo 的第一个图片位置。

标题、说明和元数据直接采用视觉合同中的字体角色。系统字体是 GitHub 可靠渲染的实现条件，不等于无衬线标题和等宽元数据必须同时出现。只有项目证据或明确家族合同支持某种字体角色时才使用它。

## 让项目事实决定构图

先把项目事实中的对象、动作和结果按真实关系写成最简单的阅读顺序，再映射到已经冻结的几何合同：

- 单一产物成为画面重心，标题围绕它建立进入顺序。
- 转换、阶段或因果关系沿实际方向展开，标题占用关系自然留下的位置。
- 多个输出合同只有在必须比较时并列，并保留接口或数据合同证明的边界。
- 层级、网络或组合关系使用空间、连接和尺度表达，不把每个节点自动包装成卡片。
- 项目事实不足分支只使用排版、比例和留白，不增加伪造的“证明区”。

构图由项目事实和视觉合同共同产生。左右分栏、居中标题、满版样本、纵向序列或其它形式都只是可能结果，不是开始制作时的预设。任何现有图片都不能用于选择、排除或调整这些形式。

## 决定标题与证据如何相遇

### 一张综合 Hero

视觉的主要作用是结果证据，且当前适用的结果合同可以由少量项目对象与关系准确表达时，把语境、项目名、具体价值、项目主题元素和结果关系组合成一个 PNG/WebP 或 SVG。设计仍只消费非图片项目事实。

### 标题后紧跟结果说明

结果细节无法在短 hero 中准确表达时，在正向项目定义之后先用简洁 SVG 引出结果，再用相邻 Markdown、命令或数据说明保留细节，不读取或制作截图来反向决定 hero。

### 标题结合机制解释

项目最值得理解的是一个真实流程、转换或关系，且视觉阶段已经选择机制解释时，用静态 SVG 把该机制、项目名和具体价值放进同一阅读路径。图中只呈现仓库能够支持的对象和关系，并在相邻文字中说明它解释的是工作方式，不是运行结果证明。机制图放在正向项目定义或对应章节的引入文字之后，不能因为画面包含项目名就上移为 Logo。

视觉阶段选择跳过时，不为了完成 hero 形式而制造素材；使用清楚的 Markdown 标题和首段建立第一屏，然后返回整页模式。

采用结果证据时完成：

```text
语境 → 项目名 → 具体价值 → 过程提示 → 已由项目真源证明的结果关系
```

采用机制解释时完成：

```text
语境 → 项目名 → 具体价值 → 真实关系或过程 → 证据边界
```

选择前回答：

1. 哪些对象与关系是第一采用读者必须理解的？
2. 一项结果合同就能说明项目，还是必须比较多个输出？
3. 标题是否经常变化，需要独立可编辑 SVG？
4. 合并标题和结果关系是否减少重复，并保持职责清楚？

## 标题与结果组合

项目真源已经能用一项结果合同解释项目时，组合为：

```text
类别 + 仓库名称 + 具体描述 + 已确认的对象与结果关系
```

关系、文字和代码原生几何使用 SVG；确实需要栅格输出时，也只从冻结的语义与几何合同生成 PNG/WebP，不读取参考图或旧图。多个结果需要更多空间时，标题 SVG 与 Markdown 结果说明作为相邻模块。发布的 SVG 不依赖远程或无法解析的本地栅格链接。

## 去文字语义检查

完成源码后，不打开图片；在语义和几何合同中暂时移除仓库名、说明、标签和元数据，再核对剩余对象、边界、连接与项目事实的映射：

1. 如果剩下的是一个没有项目事实也成立的技术面板、三步卡片、仪表盘或左右分栏占位结构，返回概念步骤。
2. 如果几何关系仍逐项对应当前项目的真实对象、结果合同或机制，恢复文字继续进行结构检查。
3. 排版型 hero 移除文字后可以不剩身份图形；它的通过条件是没有用装饰冒充项目事实。

同一任务处理多个没有家族合同的项目时，分别完成项目事实、语义概念和几何合同，并只比较这些文字合同。相似表面只能由各自项目事实独立支持；不得打开成品互相比较。

## 验收

1. hero 是否准确消费上层主页主身份或素材沟通任务，而没有重新选择或稀释它？
2. 每项表面选择是否来自已选视觉合同，而不是仓库类型、旧示范或任何图片？
3. 去文字语义检查后是否仍保留当前项目特有的对象关系，或者诚实地不保留身份图形？
4. 视觉材料是否承担已选的结果证据、机制解释或身份支持？
5. 项目名称、普通文本定义和 README 顺序是否让第一次访问者知道项目做什么？
6. 机制解释是否没有冒充实际效果，结果证据是否能追溯到上层核定且当前适用的非图片项目事实？
7. 标题与证据或机制是否形成同一阅读路径？
8. hero 是否给正文中的快速开始和其它独立入口留下清楚位置？
9. 首屏辅助区是否保留在可点击、可更新的 Markdown / HTML 中，而没有被烘焙进视觉素材？
10. 第一个图片节点是否仍是紧凑 Logo，表达性视觉是否位于正向项目定义或所解释章节的引入文字之后？

语义合同去掉文字后只剩通用技术面板，或几何对象只是装饰时重新设计。完成后返回当前 README 子类型，并明确记录没有打开、查看或渲染任何图片，也没有进行人工画面判断。
