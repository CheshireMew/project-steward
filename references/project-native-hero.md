# 项目原生 Hero

用于设计 README 的表达性视觉怎样承接已经成立的身份和正文职责。整页模式传入内容阶段已经确定的主页主身份与素材落点；仅素材模式传入当前 hero 的素材沟通任务。它消费上层已经选定的合格材料、证据等级、视觉合同、视觉作用和素材动作，不重新选择项目主特色、证据等级、视觉方向、材料资格、正文入口或图片位置。

## 先写 Hero 输入

```text
上游沟通重点：主页主身份 / 素材沟通任务
主要用户：
第一次可观察结果：
区别性能力或机制：
最佳合格证据：
已核定原生视觉材料及其适用状态：
证据等级：
已选视觉合同：
视觉作用、素材动作与证据边界：
正文落点：正向项目定义之后 / 所解释章节的引入文字之后
```

原生视觉材料是项目真正处理的对象，例如集群关系、张量、表格、代码、图层、时间线、地图、图标、终端输出或生成产物。本方法只使用上层已经核定的材料；内部图片、旧截图或历史流程图不因文件存在而重新获得资格。

Logo 与 hero 是两个职责不同的素材。完整 README 优化还必须交付一个可在首屏独立使用的 Logo，并把它作为紧凑身份图先于表达性视觉生成；已有合格标志就复用，没有就根据当前视觉证据合同制作，证据不足时使用项目名称或首字母形成中性排版标志，不补造项目对象或品牌性格。全宽 hero、机制图、结果图或展示图不能充当 Logo，也不能进入首屏管理区的 `identity_image` 位置。hero 只负责让主要读者继续理解主价值、真实结果或关键机制，并在完整首屏管理区和正向项目定义之后出现；解释具体章节时紧跟该章节的引入文字。其它独立主要意图继续由 Markdown 中的快速开始、命令、提示词或链接承载，不把所有能力塞进 hero，也不因为 hero 聚焦一项价值而移除它们。

## 确定信息职责

hero 可以包含：

1. 类别或技术语境。
2. 仓库名称。
3. 一句具体描述。
4. 真实项目材料。
5. 少量稳定的仓库元数据。

这些是信息职责，不是固定位置。根据项目移动、缩放或省略。

语言切换、文档、贡献、反馈、个人入口、Stars、Forks、许可证和其它需要点击或实时更新的状态不属于 hero 元数据。它们使用上层已经核定的首屏辅助区，作为 Logo、项目名称和本地化一句话介绍之后的 Markdown / HTML 保持可访问和可更新；不能画进 SVG、PNG 或 WebP，也不能为了容纳链接或徽章重新选择 hero 构图。即使 Logo 或 hero 内含项目文字，项目名称和一句具体价值也要作为独立 HTML 文本存在，不能让图片成为唯一真源。首屏辅助区不能把第一屏挤成只有链接和数字；它先完成并闭合，正文用正向项目定义建立理解，hero 再在内容阶段指定的位置承接证据或机制，不能用 hero 抢占 Logo 的第一个图片位置。

标题、说明和元数据直接采用视觉合同中的字体角色。系统字体是 GitHub 可靠渲染的实现条件，不等于无衬线标题和等宽元数据必须同时出现。只有项目证据或明确家族合同支持某种字体角色时才使用它。

## 让项目材料决定构图

先把项目材料按真实关系排成最简单的阅读顺序：

- 单一产物成为画面重心，标题围绕它建立进入顺序。
- 转换、阶段或因果关系沿实际方向展开，标题占用关系自然留下的位置。
- 多个真实输出只有在必须比较时并列，并保留它们原有的边界或比例。
- 层级、网络或组合关系使用空间、连接和尺度表达，不把每个节点自动包装成卡片。
- 证据不足分支只使用排版、比例和留白，不增加伪造的“证明区”。

构图由项目材料和视觉合同共同产生。左右分栏、居中标题、满版样本、纵向序列或其它形式都只是可能结果，不是开始制作时的预设。

## 决定标题与证据如何相遇

### 一张综合 Hero

视觉的主要作用是结果证据，且少量当前适用的真实输出缩放到 README 宽度后仍然可识别时，把语境、项目名、具体价值、项目主题元素和证据组合成一个 PNG/WebP 或 SVG。

### 标题后紧跟证据

截图很多、页面密集或细节会在短 hero 中变小时，在正向项目定义之后先用简洁 SVG 引出证据，再用相邻大图展示需要保留的细节。

### 标题结合机制解释

项目最值得理解的是一个真实流程、转换或关系，且视觉阶段已经选择机制解释时，用静态 SVG 把该机制、项目名和具体价值放进同一阅读路径。图中只呈现仓库能够支持的对象和关系，并在相邻文字中说明它解释的是工作方式，不是运行结果证明。机制图放在正向项目定义或对应章节的引入文字之后，不能因为画面包含项目名就上移为 Logo。

视觉阶段选择跳过时，不为了完成 hero 形式而制造素材；使用清楚的 Markdown 标题和首段建立第一屏，然后返回整页模式。

采用结果证据时完成：

```text
语境 → 项目名 → 具体价值 → 过程提示 → 真实证据
```

采用机制解释时完成：

```text
语境 → 项目名 → 具体价值 → 真实关系或过程 → 证据边界
```

选择前回答：

1. 缩放到 GitHub 内容宽度后证据还能理解吗？
2. 一个产物就能说明产品，还是必须比较多个输出？
3. 标题是否经常变化，需要独立可编辑 SVG？
4. 合并标题和证据是增加清晰度，还是只减少页面高度？

## 标题与演示组合

第一张截图、输出或图已经能解释项目时，组合为：

```text
类别 + 仓库名称 + 具体描述 + 真实证据
```

矢量材料保留 SVG；截图、照片或生成图使用合成后的 PNG/WebP。多个产物需要更多空间时，标题 SVG 与证据图作为相邻模块。发布的 SVG 不依赖远程或无法解析的本地栅格链接。

## 去文字轮廓检查

完成初稿后暂时隐藏仓库名、说明、标签和元数据，只看背景、构图、边界、连接、项目材料和主题元素：

1. 如果剩下的是一个没有项目材料也成立的技术面板、三步卡片、仪表盘或左右分栏占位结构，返回构图步骤。
2. 如果画面关系仍能对应当前项目的真实对象、产物或机制，恢复文字继续检查。
3. 排版型 hero 隐藏文字后可以只剩留白；它的通过条件是没有用装饰冒充项目证据，且恢复文字后层级与项目语气成立。

同一任务处理多个没有家族合同的项目时，分别完成视觉证据合同，并比较成品的背景材料、信息空间关系、字体角色、容器语言、主题元素和密度。相似表面只能由各自项目证据独立支持；否则返回对应项目的视觉方向。

## 验收

1. hero 是否准确消费上层主页主身份或素材沟通任务，而没有重新选择或稀释它？
2. 每项表面选择是否来自已选视觉合同，而不是仓库类型或旧示范？
3. 去文字后是否仍保留当前项目特有的对象关系，或者诚实地只剩排版留白？
4. 视觉材料是否承担已选的结果证据、机制解释或身份支持？
5. 第一次访问者能否不读正文就知道项目做什么？
6. 机制解释是否没有冒充实际效果，结果证据是否能追溯到上层核定且当前适用的真实产物？
7. 标题与证据或机制是否形成同一阅读路径？
8. hero 是否给正文中的快速开始和其它独立入口留下清楚位置？
9. 首屏辅助区是否保留在可点击、可更新的 Markdown / HTML 中，而没有被烘焙进视觉素材？
10. 第一个图片节点是否仍是紧凑 Logo，表达性视觉是否位于正向项目定义或所解释章节的引入文字之后？

去文字后只剩通用技术面板，或视觉材料只是装饰时重新设计。完成后返回当前 README 子类型。
