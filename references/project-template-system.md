# 项目模板系统

用于新项目建立基线、已有项目采用模板、模板升级和漂移验证。模板保存已经稳定成某类项目默认约束的治理决策、检测信号和验收合同；仍需结合情境判断的方法由 Project Steward 的主流程和专项资料负责，项目源码、业务内容和一次性诊断证据仍由项目自身负责。

## 1. 三个真源

- `assets/project-templates/catalog.json` 是可用模板、版本和内容哈希的唯一注册表。
- 每个注册模板 JSON 是该层治理规则、默认决策、检查和人工验收的唯一真源。
- 项目内 `.project-steward/project.json` 是该项目已经采用的模板版本、项目决策、覆盖和偏离理由的唯一真源。

注册表只表示模板可被列出、确定性检测或显式选择，不表示它对所有项目自动生效。项目配置只保存治理元数据，不复制源码、README、测试、构建配置或业务数据。

项目自己的长期结论继续位于项目已有的规则、设计文档、代码、配置和测试中。模板配置不复制这些正文，模板消费者也不能把某个项目的做法自动解释为所有项目的默认。

## 2. 模板层

模板按固定顺序组合：

```text
base → surface → archetype → stack → capability → project overrides
```

- `base`：任何软件项目都需要的真源、变更、验证和维护边界。
- `surface`：只在项目具有真实用户界面或其它明确产品表面时成立的体验与界面合同。
- `archetype`：桌面应用、服务、库、CLI 等项目形态。
- `stack`：Tauri + Vue、Electron、Rust 服务等具体技术栈。
- `capability`：Android、同步、插件系统、LLM、支付等可选能力。
- `project overrides`：当前项目明确采用的不同决策和偏离理由。

每个注册模板必须包含：

```text
schema_version
id
version
layer
name
description
requires
detection
defaults
invariants
checks
manual_verification
```

`requires` 只声明模板依赖，不在模板内部重新选择上层路径。依赖解析必须无环、无重复，并按层级排序。同一模板栈中的检查 ID 和不变量 ID 必须唯一；项目覆盖改变决策值，不复制或篡改模板正文。

`detection` 使用 `always`、`all`、`any` 或 `explicit_only` 四种互斥形式。`explicit_only: true` 表示该模板没有足够可靠的通用文件信号，只能由用户显式选择、现有项目配置固定或其它模板依赖带入；它必须出现在注册表和 `list` 中，但不能出现在 `inspect` 的自动建议里。

## 3. 识别与选择

只读识别命令：

```text
python scripts/project_templates.py list
python scripts/project_templates.py inspect <项目根>
```

`inspect` 读取项目根直接存在的文件、包元数据、精确根 Git 能力和现有项目配置，输出技术栈信号与建议模板。它不得向父目录发现 Git 仓库，不运行构建，不安装依赖，不写项目。

模板选择按以下优先级：

1. 用户明确指定的模板。
2. 现有项目配置已经固定的模板。
3. 检测条件全部满足的模板。
4. `explicit_only` 模板保持未选择，并在检测详情中说明只能点名采用。
5. 无法确定的层保持未选择，并把缺少的事实交给上层；不能用相似文件名猜出技术栈或领域能力。

`base` 总是加入。`product-ui` 只由稳定设计上下文路径、上层依赖或用户显式选择进入；一般的 `src`、Vue/React 依赖或几个组件文件不足以证明项目需要完整界面治理。显式选择模板时自动解析它的依赖。检测结果是建议，不覆盖用户明确的项目类型；项目实际同时使用多个技术栈时分别选择对应层，不把一个模板当成所有平台的替代品。

## 4. 项目配置

采用后的配置采用 schema v1：

```json
{
  "schema_version": 1,
  "managed_by": "project-steward",
  "catalog_version": "2026-07-31.1",
  "project_name": "Example",
  "templates": [
    {
      "id": "base",
      "version": "1.0.0",
      "sha256": "模板内容哈希"
    }
  ],
  "decisions": {
    "source_of_truth": "project-files"
  },
  "overrides": {},
  "deviations": [],
  "adopted_at_utc": "ISO-8601",
  "updated_at_utc": "ISO-8601"
}
```

`decisions` 是模板默认决策按层合并后的项目值。`overrides` 只放用户明确采用的不同值。`deviations` 每项必须说明模板不变量、当前做法、理由、影响和复查条件；不能用空白豁免让失败检查消失。

配置不得保存绝对项目路径，以便项目移动、克隆和跨设备读取。模板内容由 `templates` 中的 ID、版本和哈希回到注册表解析；没有匹配版本时报告漂移，不静默使用最新版解释旧配置。

## 5. 四个动作

### 计划

```text
python scripts/project_templates.py plan <项目根> [--template <id> ...]
```

计划输出当前模板、目标模板、依赖顺序、默认决策、保留覆盖、版本变化和将写入的唯一项目文件。计划只读。

### 采用

```text
python scripts/project_templates.py adopt <项目根> [--template <id> ...]
```

采用只在项目配置不存在时创建它。目标已存在时拒绝覆盖，并提示改用 `plan` 或 `upgrade`。采用不是代码重构；已有项目不符合模板时，先把真实差异交给根因治理或记录经过批准的偏离。

### 升级

```text
python scripts/project_templates.py upgrade <项目根>
```

升级读取现有项目配置，把已固定模板迁移到注册表当前版本，保留项目覆盖和偏离记录，并更新合并后的决策。次版本新增的默认决策可以由升级补入；已有决策值与当前模板不同时必须通过 `--decision` 明确接受默认或保留为覆盖，不能静默覆盖。升级前必须先查看 `plan`；不能因为目录里出现一个新模板就自动加入项目。

### 验证

```text
python scripts/project_templates.py verify <项目根>
```

验证由三层组成：

1. 注册与配置：模板 ID、版本、哈希、依赖和项目配置可解析。
2. 确定性检查：必要文件、包依赖、配置值和已实现的技术栈检查。
3. 人工与运行验收：代码链、平台行为和真实用户结果。

脚本完成前两层并返回尚需人工验收的项目。Agent 必须继续消费这些项目；存在人工项时只能说“确定性检查通过，仍需真实验收”，不能说模板已经全部通过。

## 6. 新项目、已有项目与官方脚手架

新项目的顺序是：

```text
用户结果与平台 → 选择真实框架脚手架 → 建立源码 → 采用模板 → 按模板预防合同实现 → 真实验收
```

模板不复制会快速过时的框架脚手架。需要创建 Tauri、Vue、Rust 或其它项目时，先确认当前框架版本和官方命令；模板负责项目长期决策与验收。

已有项目的顺序是：

```text
检查现状 → 计划采用 → 处理不符合项或批准偏离 → 写入配置 → 验证 → 后续漂移检查
```

不得先写一份“已采用”配置，再把所有失败都解释成未来工作。

## 7. 冷启动验收

模板系统发生变化后，用一个全新的 Skill 外部临时项目验证：

1. 只凭模板 ID调用注册表，不能使用当前任务绝对路径或内部 helper。
2. `inspect` 从真实项目文件识别模板。
3. `plan` 解析依赖和默认决策。
4. `adopt` 生成项目配置。
5. `verify` 重新读取该配置和项目事实。
6. 制造一个真实不符合项，证明消费者会失败。
7. 制造版本漂移，证明 `plan` 能说明变化，`upgrade` 后重新通过。

交付时分别说明结构解析、真实实例化、确定性检查和平台运行实际达到哪一层。
