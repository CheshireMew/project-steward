# 根因修复的验证与连续收口

## 7. 完成证据

### 首次生产写入前固定失败证据

进入实施并准备首次修改生产源码、配置、schema 或运行时资源前，为每个已进入范围的稳定发现 ID 固定当前候选内容身份、正式复现或关键测试身份、实际失败结果、最早错误边界和正式消费者。测试身份先通过框架的正式发现或收集入口核对为唯一；复现必须经过故障所属的正式生产者与边界，不能只手工构造私有状态。尚未取得可证伪的失败结果时停在诊断，不开始生产写入，也不能把准备新增测试写成已经取得失败证据。

破坏性复现、不可取得的外部状态或当前环境无法安全重现使修复前失败不能直接运行时，记录准确限制、已有最高保真非写入证据和修复后可证伪的验收入口；这项例外不把失败证据改名为已经通过。写入后使用同一发现 ID 和复现身份取得新结果；身份、夹具或前提发生变化时说明差异，不能用另一条更容易通过的路径关闭原故障。

按层验证：

1. **失败证据**：修复前能够稳定失败。
2. **生产者**：正式输入产生正确结果。
3. **边界**：结果真实写入、传输或调用原生能力。
4. **消费者**：正式消费者读取同一结果。
5. **用户链**：用户能够看见或使用。
6. **实际运行产物**：从用户入口及其子进程证明最终选择的绝对路径、产物身份、新旧关系和依赖或资源闭包；内容清单的允许文件集合与运行目录实际集合必须完全一致，源码、普通构建和生成或原生产物分别报告。
7. **生命周期**：失败、等待、断开、重试、取消、终态、重启恢复和关闭没有遗留第二所有者、临时依赖或静默降级。
8. **退出检查**：旧入口、旧状态和旧名称不再活动。
9. **回归**：必须保持的旧行为仍成立。
10. **承诺覆盖**：每项用户可见承诺都经过自己的正常入口和实际分支；被环境变量、测试开关、手工状态或诊断动作绕过的承诺只能标为仅诊断、未验证或受阻，不能借用其它分支的成功证据。
11. **迁移合同**：真实历史状态经过正式迁移，实际序列化结果通过当前合同校验，失败时原状态可恢复，当前消费者关闭并重新打开后仍得到目标结果。
12. **活动投影**：保持当前编辑器或表面打开，由每个合同内正式变更入口提交状态；活动缓存、可观察依赖和当前画面读取同一身份与版本，后续编辑立即消费新状态，不依赖关闭重开、手工刷新或固定延时。
13. **测试收集身份**：每项关键测试的预期唯一身份都出现在测试框架的实际收集结果中；同名覆盖、未收集、意外排除或重复身份都不能进入完成证据。

函数测试、构建成功、产物存在和界面截图各自只证明一层。涉及生成文件、包装脚本或原生产物时，必须让真实入口解析并消费当前产物；用户没有授权生成或打包时，让过期产物明确失效，并把尚未生成的层级报告为证据缺口，不能静默选用。完成报告要说清实际达到的层级和仍未验证的条件。

当用户反馈的是“没有反应”这类最终体验时，完成证据必须覆盖最后一个用户可观察消费者。日志中间层已经生成业务事实，却在后续模型调用、语音合成、播放、界面状态或持久化记录失败，仍然是完整链路失败；报告时要把已成立的中间证据和仍失败的后续边界分开，不能用前者替代后者。

事务型操作的验收先记录动作前的真实事务身份，再从生产者新增的事务读取实际路径、终态和确认状态。测试不得根据成功次数预测名称，不得建立第二个时钟、文件编号器、状态机或恢复解释器；这些做法只能证明测试自己的假设与自己一致。

正式生产者会生成集合、关系或多种合法对象时，关键断言必须从生产者输出取得目标对象的稳定语义身份，再验证这个对象穿过存储或传输边界后的事实。除非对象总数、列表位置或当前选中项本身就是产品合同，否则不能用它们代替目标身份；生产者增加合法对象也不能被报告成模型丢失或重复。断言还要区分可编辑或持久事实与派生或瞬态投影：前者从权威状态和重开结果验证，后者从正式计算或展示消费者验证，不能拿一种状态的偶然值替另一种状态作结论。

验证过程本身也要可证。每条测试、静态扫描、依赖审计和残留检查先核对预期覆盖对象及内容身份，与工具实际选择的输入、版本、过滤和排除项是否一致；实际输入为空、过期或不完整时，即使命令成功也只能标为未覆盖或未知。每项检查还要单独保留退出状态，失败后立即停止或明确标为未知，不能被同一脚本后续命令的成功覆盖。扫描器成功运行且覆盖预期对象后，零匹配才是零发现；宽泛正则的相似文字命中必须人工核对，不能直接当成旧架构，也不能为了得到“零”而无依据排除。

### 结项状态先重建原账本

上下文压缩、恢复、目标状态丢失或重建后，或用户询问剩余量、要求低成本收口时，先从最强稳定真源重新取得原交接账本，逐项核对稳定发现 ID、语义标题、原完成条件和最后一次有效证据。摘要、计划和近期修改文件只是投影；同一 ID 对应不同语义标题、原账本不可取得，或目标或任务的权威状态缺失时，受影响项及平台状态保持未知或开放，不得输出数字比例、`还剩 N 项`或全称完成。

Goal、计划、任务计时器和用量记录只证明它们从实际创建或绑定到当前结果之后持续覆盖的区间。不存在与当前用户结果、范围和代次匹配的活动记录时，直接依据原账本与正式证据结项；不得在实现或验证结束后补建、重置或重新绑定记录来制造完成状态、总耗时或总用量。宿主要求关闭或报告现有记录时，只处理确实覆盖当前结果的记录，并把时间与用量标明为该记录的实际覆盖区间；只有它从用户结果被接受到最终交付连续覆盖全程时，才可称为本结果总量。

### 候选冻结前完成结项预检

从原发现账本取得每个稳定 ID、原完成条件和证据平面，消费 `root-cause-remediation.md` 的“同源变体收口”，在冻结候选或启动最终完整套件前展开结项预检：

```text
稳定发现 ID 与当前内容身份：
原完成条件和已取得证据：
正式生产者 → 传输或存储边界 → 全部正式消费者：
替代入口、构建或测试目标及实际运行产物：
等待、取消、关闭、生命周期终结、重启和逐项超时或取消控制：
直接诊断、落盘或持久化消费者：
旧入口、旧目标、旧路径和旧控制残留：
唯一测试或检查身份及实际收集结果：
状态：已解决 / 未验证 / 开放 / 受阻
```

这里只派生有同一事实或边界证据的维度，不扩张为新审计。不能用总测试数、生产产物未含测试标识、间接日志断言或套件级外层超时替代源码与目标职责、直接消费者和最窄测试控制。任一应由当前候选和本轮最终套件关闭的范围内完成条件仍开放或未知，不得冻结候选、启动最终完整套件或准备全称结论；先补齐目标检查或保留准确未验证状态。其它平台、远端、实机或外部条件继续单列证据平面，只限制对应结论，不冒充本地失败。

结项预检通过后，把同一账本、最终差异和候选内容身份交给下一节的唯一验证计划。其后生产源码、测试、构建目标、验证控制面或计划发生相关变化时，候选与既有完整套件证据失效，重新生成预检；不能用变化前的绿色结果补位。

### 结项前消费最终验证计划

准备报告“全部问题已解决”“所有检查通过”或其它全称结论前，必须依据最后一次实际差异、候选内容身份、原发现账本和当前用户承诺，重新生成并消费 `ci-execution-governance.md` 拥有的唯一验证计划。这里不复制 CI 的适用性、预算或运行资格规则，只核对最终计划已把公开架构、源码质量、合同、测试收集、正式用户链及项目明确列出的其它义务映射为必需、辅助或范围外，并逐项取得合法终态。真实用户链通过只能关闭它实际覆盖的承诺，不能替代计划遗漏的公开控制项；计划未重放、输入仍是修改前差异或必需义务没有结果时，全称结论保持未验证。

完成摘要必须从逐项最终状态和最后一次有效证据生成。已解决、经新证据重新分类、经用户同意退出范围、受阻、未验证，以及不同证据平面继续保持各自状态；“闭环”只能表示每项都有合法终态，不能把它们改写成“全部已修复”。全局零发现必须同时写明扫描器实际覆盖的输入和未覆盖边界；无法证明完整覆盖时使用“在已声明范围内未发现”，不能说整个项目中为零。

“全部通过”“所有检查通过”等全称结论，只能覆盖摘要中明确列出且最后一次有效状态均为通过的检查集合。每项实际执行过的非通过结果都要保留检查身份、状态、覆盖范围和与当前用户结果的相关性；即使它来自任务前既有脏状态、无关格式差异、环境失败或验证器错误，也只能单独标为不阻塞、未覆盖、未知或失败，不能从完成摘要中消失。一个证据平面通过不能替另一个平面改名或补位。

### 全称结论经过确定性发现账本

承接既有诊断或审计账本，并准备回答“全部问题已经解决”“上述问题都做完了”或同义全称结论时，先把本节已经建立的逐项终态、最后有效证据、未验证边界和全部实际验证事件交给 `scripts/validate_findings_closure.py`。验证器只消费已经取得的结构化证据，不替代原账本、根因判断、测试收集或用户链，也不能为缺失证据补造通过；未承接既有发现账本的单点修复不调用它，继续按实际受影响链结项。

输入使用 `project-steward-findings-closure/v2`，分开原始合同和当前结果。`original_findings` 从 `project-audit-release-and-evidence.md` 的修复交接账本取得；每项含唯一 `id`、`title`、`source`（`reference` 原文定位与 `content_identity` 来源内容身份），以及非空 `conditions`。每个条件含父发现内唯一 `id`、原条件 `text`、`evidence_scope` 和非空 `required_evidence_kinds`。证据种类表示该条件实际必需的检查集合，不是任取其一，也不是所有问题统一跑一遍的清单；范围和种类在实施前由正式消费者与原合同决定。

`findings` 每项只含 `id` 与 `conditions`；当前条件只提交 `id`、`state`、`last_evidence`、`unverified_boundaries`、`claims_automated_regression` 及适用的 `disposition`。发现集合和各自条件集合必须与原清单完全相等，不得遗漏、重复、新增或换名；原文、标题、来源、证据要求只从原清单投影，不能由当前结果覆盖。父发现状态由全部条件派生：全部已解决才为 `resolved`；有开放、未验证或受阻条件时分别保留 `open / unverified / blocked`，不同合法终态并存为 `mixed`，不把重新分类或退出范围算作修复。输出沿用原发现与条件顺序，生成 `稳定发现 ID → 最终状态 → 最后一次有效证据 → 未验证边界`，同时展开条件、原文和来源身份。

每条实际验证事件必须保留唯一身份、状态、覆盖范围、产品 / 验证器 / 环境等分类、是否阻塞和与当前结果的相关性；输出单列全部非通过验证事件。`last_evidence` 除用户授权外必须以同一 ID 引用 `validation_events` 中状态和范围一致的记录，不能一边记录失败一边引用为通过。同一证据被多条件或发现共享时记录必须一致。已解决条件的验证证据范围须与原 `evidence_scope` 相同，并覆盖全部必需种类；静态检查不能替代要求的真实运行或用户链。自动回归声明只能由状态为通过、预期身份与测试框架实际收集身份完全相同的自动测试证据成立；真实用户链、测试源码存在、测试总数或计划新增测试都不能代替。只有全部条件都声明并证明自动回归时，父发现才能作同一声明。

脚本只校验传入账本的一致性，不独立检查来源是否真实、事件有无遗漏、证据是否新鲜，也不能判断自然语言条件是否被忠实提取、文字边界是否确实在范围外，或标为真实运行的测试是否绕过核心边界；这些仍由原账本、最终验证计划与正式证据负责。来源身份不是自动真实性证明，不能一边改写原清单一边让校验器背书。范围内仍缺的条件保持未验证，不能放进备注后声明已解决。输入必须在传入前脱敏，不包含日志原文、凭据或私人数据。

从标准输入传入 JSON，或用 `--input <既有账本路径>` 读取项目原有记录；不为运行它新建持久经验库。`--format markdown` 直接输出交付表，默认 JSON 同时包含判定和 `markdown` 字段。以下是一次真实用户链已经通过、但没有声称自动回归保护时的最小完整输入结构；示例内容不是实际证据：

```json
{
  "schema": "project-steward-findings-closure/v2",
  "claim": "all-findings-resolved",
  "original_findings": [{
    "id": "F-1", "title": "保存后能重新读取",
    "source": {"reference": "review#F-1", "content_identity": "example-review-revision-1"},
    "conditions": [{
      "id": "reopen", "text": "正式入口保存后由新消费者重新读取同一对象",
      "evidence_scope": "当前平台的保存与重开",
      "required_evidence_kinds": ["user-chain"]
    }]
  }],
  "findings": [{
    "id": "F-1", "conditions": [{
      "id": "reopen", "state": "resolved",
      "last_evidence": [{
        "id": "save-reopen", "kind": "user-chain", "status": "pass",
        "scope": "当前平台的保存与重开"
      }],
      "unverified_boundaries": ["其它平台不在本次范围"],
      "claims_automated_regression": false
    }]
  }],
  "validation_events": [{
    "id": "save-reopen", "status": "pass", "scope": "当前平台的保存与重开",
    "classification": "product", "blocking": false,
    "relevance": "正式入口保存后重开读取同一对象"
  }]
}
```

自动测试证据的 `kind` 使用 `automated-test`，同时提供从正式运行取得的 `expected_test_identity` 和 `collected_test_identity`；不能把示例身份填成实际收集结果。条件状态支持 `resolved / reclassified / withdrawn / blocked / unverified / open`；重新分类、退出范围和受阻必须带 `disposition`，退出范围还必须有 `authorization` 证据。证据状态支持 `pass / fail / blocked / unknown / not-run`；证据种类除上述三种外还支持 `static-check / runtime / manual-review / diagnosis`。必需验证种类不接受 `authorization`，授权只能证明范围处置而非修复。验证事件分类支持 `product / verifier / environment / scope / other`。`unverified_boundaries` 即使为空也显式给出，范围内仍缺的证据必须使发现保持未验证、开放或受阻，不能靠这份数组把已承诺结果改成范围外。

旧 `project-steward-findings-closure/v1` 仍可从同一 CLI 读取，其字段与一致性检查保留，但有效旧账本一律返回 `1`、`condition_coverage_verified: false` 和迁移提示，不再授予全称结论资格。旧 `original_finding_ids` 和已报告状态不能自动生成完整条件；调用者必须回到原报告恢复来源与条件后提交 v2。两种输入统一返回 `project-steward-findings-closure-result/v2`；`condition_coverage_verified` 只表示相对传入原清单的结构覆盖，`closure_complete` 只表示已表示条目的合法终态，均不独立证明原报告完整或全部修复。

验证器退出状态也是结项门槛：`0` 表示当前声明范围内的每项发现都实际为已解决；`1` 表示输入有效但仍有开放、未验证、受阻发现、阻塞性非通过事件，或存在只能表述为重新分类或退出范围的合法终态；`2` 表示账本结构、唯一身份、证据或自动回归声明自相矛盾。只有状态 `0` 允许生成“全部发现已解决”，但只要存在任何非通过验证事件，就仍不得改写成“所有检查通过”；状态 `1` 或 `2` 时保留验证器输出和原证据，报告准确阻塞，不手工绕过投影。

### 验证命令先固定正式身份

静态类型检查、格式检查、lint 和扫描器运行前，先从项目配置、正式包装脚本或默认命令确定准确工作目录、runner、默认输入范围、模块或包解释方式、过滤和排除项。临时增加路径参数、从其它目录调用或绕过包装器属于另一命令身份，可能把归档、生成物或同名包纳入并改变模块解析；这类失败先归为验证器或前置条件失败，不能直接归为产品失败，也不能为迁就错误验证入口修改产品。

测试套件作为完成证据前，先从本轮用户承诺、回归合同和受影响边界建立预期关键测试身份清单，再通过测试框架的正式发现或收集入口取得实际唯一身份和选择结果并逐项对应。检查同一作用域内后定义覆盖前定义、命名不符合发现规则、路径或标记配置排除、参数化或生成身份碰撞，以及预期测试完全缺失；测试源码存在、命令成功或总数看似合理都不能替代这份对应关系。任一关键身份缺失、重复或没有被执行时，对应承诺保持未覆盖，先修复测试收集边界并重新收集、运行，再继续产品链验收；不能修改产品来迁就失效的测试边界。

### 多轮证据不重复累计

多轮验证同时保留每次运行身份、实际选择的唯一测试节点和结果。可以报告每轮总数，但总覆盖只能按唯一测试节点去重；重跑、交集和先前已包含的节点不能相加成新增覆盖。分类也必须来自实际节点和检查职责，架构测试、功能测试、静态检查和用户链不能因汇报方便互相改名。无法取得唯一身份或交集时，只分别报告各轮数字和未知重叠，不给出虚假的累计总数。

## 8. 证据驱动的连续收口

用户明确要求自行迭代、做到底或在证据充分时自行停止，或者一次真实验收在同一受影响链内暴露新的同源缺陷时，内部轮次不是新的授权边界。先冻结同一用户结果、同一受影响链和已冻结权限；每轮只处理能够由当前生产者、边界、消费者或生命周期证据解释的高价值问题，不把连续工作扩张成项目综合审计。

每轮遵循同一个闭环：

1. 保存本轮失败证据并在最早错误边界修复。
2. 重新运行受影响的生产者、真实边界、消费者和用户链。
3. 检查这次新鲜运行证据，而不复用修改前的干净结论：正式产物、结构化状态、日志语义、恢复或临时目录、子进程和后台任务、退出与取消结果、旧标识符和旧入口。
4. 新证据仍属于同一根因与链路时，更新迁移范围并继续；它属于独立用户结果、低收益润色、产品取舍或新权限时，记录准确边界并停止。

真实验收失败时，先确定失败发生在环境、测试驱动或夹具、产品生产链还是最终断言。只有存在瞬态证据时才做一次有界的原样重跑，用于区分偶发状态和稳定缺陷；同一点再次失败或已有确定性证据时，应修复测试驱动自己的边界并重新进入同一真实链，不能修改产品来迁就测试驱动或夹具，也不能用手写结果绕过刚刚失败的核心边界。

停止需要同时满足：目标行为和必须保持的回归通过；新鲜运行的正式产物可消费；日志、持久化、恢复、进程和旧路径检查没有与成功结论冲突的高价值异常；剩余事项只是不影响当前结果的润色、独立产品决定、外部状态或新授权。满足后主动交付，不再为了消耗时间或额度继续寻找改动。

## 9. 完成项目结果并按已选路径停止

修复或诊断完成后，把本次最早错误位置连接到下一次改动前可以采用的做法：

```text
稳定问题类别：
最早预防点：
适用项目范围：
可确定检测信号：
真实验收方法：
不应沉淀的一次性细节：
```

承接此前诊断或审计的“全部问题”或“上述问题”时，最终交付必须给出紧凑的逐项对账：`稳定发现 ID → 最终状态 → 最后一次有效证据 → 未验证边界`。每项沿用原交接账本身份；分类汇总、测试总数或“均已解决”结论不能替代逐项映射。缺少有效证据的发现必须显式标为未验证、受阻或开放。

根因治理完成后，交付本次项目的根因、最终边界、迁移与退出证据、真实验收和仍缺的证据，随后停止。用户在请求开始时同时明确要求 Project Steward 自我进化时，才把上面的稳定问题类别、最早预防点、适用范围、检测信号和真实验收交给对话学习路径；用户要求保存当前项目长期事实时，把结论写回该项目已有的规则、设计文档、代码、配置或测试。只有用户另行明确要求更新模板时，稳定默认才进入模板演进。
