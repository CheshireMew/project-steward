# 设计系统对齐与漂移根因

用于统一设计语言、审查系统漂移和准备跨消费者迁移。目标不是把局部改得相似，而是确定一个规范来源并让所有生产消费者读取它。

## 1. 先给候选来源分配角色

同一表面中的设计系统、组件库和视觉参考不能共同充当规范。先标明每个来源能决定什么：

| 来源类型 | 能决定什么 | 不能自动决定什么 |
| --- | --- | --- |
| 当前项目设计系统 | 已有 token、组件、状态和生产表现 | 不能用历史实现覆盖用户最新决定 |
| 项目明确采用的官方系统或平台规范 | 对应平台、组织或产品范围内的规范关系 | 不能扩张到未采用的系统，也不能把另一套规范混入同一表面 |
| 组件库或实现工具 | 可复用能力、实现约束和可用 API | 不能因为被安装就成为产品的设计真源 |
| 审美参考或风格家族 | 构图、节奏、材质或视觉关系的启发 | 不能冒充官方规范，也不能决定完整组件行为 |
| 平台效果近似 | 在目标平台能力内复现某种可见关系 | 不能声称与原平台效果、材料或行为等价 |

用户说“像某产品”或提供参考图时，默认把它当作关系参考；只有用户或项目事实明确采用某套系统时，才把它升级为规范来源。需要判断当前官方身份、版本、组件或安装方式时，必须使用与本轮授权一致的当前来源；未核实时只说明设计关系，不编造包名和版本。

## 2. 再确定规范真源

按顺序寻找用户确认的设计系统文档、设计 token、共享组件库、主题文件和生产界面惯例。记录颜色、排版、间距、形状、组件 API、用户可见的对象与行动名称、状态投影、动效和同类流程从哪里产生。主题颜色按最终可见状态追溯：表面、文字或图标、边界、焦点和选择反馈由同一个状态合同协调，局部样式只读取或实现这份合同。

文档、token 和实现冲突时，不选择最容易修改的一份当真源。根据用户最新决定、生产消费者和明确的规范归属确定唯一来源，再把其它层迁移到它。

## 3. 创建或交接可移植设计系统

只有用户要求创建、提取、迁移或长期复用设计系统时，才建立可移植包；普通页面设计和局部修复不自动增加这项交付。先按职责定义包，而不是先照搬某个项目的目录：

| 职责 | 内容 | 真源要求 |
| --- | --- | --- |
| 身份与来源 | 稳定名称、适用范围、版本或修订、来源与许可、活动文件索引 | 一个清单负责身份和路径，不在多个说明文件重复维护 |
| 设计决定 | 设计原则、颜色角色、排版、空间、形状、状态、动效和使用边界 | 一份规范说明负责设计含义，不让示例页面反向定义规范 |
| 机器规则 | 语义 token、主题映射和平台需要的结构化值 | 每个语义值只有一个活动来源，生成格式由它派生 |
| 组件与模式 | 共享组件、状态、组合关系、内容约束和平台差异 | 组件实现读取机器规则，不复制一套局部常量 |
| 使用与预览 | Agent 或开发者的读取顺序、代表性组件和目标视口中的预览 | 预览必须读取正式包，不能手写一份看起来一致的演示数据 |

文件名和具体格式由当前项目、目标平台或用户选择决定；已有项目不为了符合外部范例而改成固定目录。新建或完整迁移时，一次确定每类事实的所有者并迁移全部消费者，不能长期保留并列的旧格式、兼容 helper 或第二套 token。

编译后的 CSS、Tailwind 映射、组件索引、平台主题和文档表格属于派生产物，不是竞争真源。记录它们由哪个活动来源生成，使用确定性检查验证同步关系，并从用户或 Agent 的正式读取入口确认这些产物确实被使用。来源、许可或适用范围无法确认时，把它标为待确认事实，不用品牌名称或参考图补写出处。

## 4. 把漂移分成三类

| 根因 | 判断 | 正确修法 |
| --- | --- | --- |
| 系统缺少能力 | 当前需求合理，但某个语义角色、主题分支、组件状态或模式不存在 | 在规范来源补齐完整的状态合同，再迁移全部消费者 |
| 消费映射不完整 | 语义来源已经存在，但平台调色板、框架控件或共享组件只读取了其中一部分 | 在最接近渲染的共享边界完成一次映射；该边界无法可靠表达全部状态时，统一迁移到能够表达合同的共享组件 |
| 绕过已有复用 | 已有 token 或共享组件能满足，但局部自己实现 | 替换为共享来源并让第二套实现退出活动调用 |
| 概念不一致 | 页面流程、信息架构、命名或层级与相邻功能不一致 | 先重做职责与流程，再落到组件和 token |

不能用新增局部变量修复绕过复用，也不能用统一颜色掩盖概念不一致。相似外观但意图不同的组件不强行合并；意图相同的多个实现不长期并存。

## 5. 建立迁移合同

```text
规范来源：
受影响的主题分支、语义角色、组件家族、状态或流程：
每个状态的最终表面、文字或图标、边界、焦点与选择组合：
全部生产消费者：
平台调色板、框架组件、共享组件与局部覆盖的读取关系：
保留的职责和视觉关系：
需要新增的系统能力：
旧来源如何退出活动路径：
用户可观察结果：
```

涉及可移植设计系统时，同时写清身份清单、设计决定、机器规则、组件与模式、使用与预览分别由什么文件承担，哪些文件是派生结果，以及怎样验证派生结果和正式消费者一致。

一次性盘点并迁移所有调用点。主题或组件状态出现问题时，按语义角色、调色板映射、共享组件类型、直接框架控件和局部覆盖查找消费者，再用实际渲染路径确认范围；可见问题负责定位审计入口，正式来源负责确定消费者清单。修改页面名称、品牌资产或共享组件时，同时检查导航、深链、页眉、favicon、应用图标、启动界面、元数据、图片和视频中烘焙的旧版本。

favicon、清单图标和其它强缓存消费者还要从正式入口核对最终解析地址、响应或嵌入内容身份、版本指纹与实际显示。仓库中的源文件已经替换、组件引用名称正确或同一地址手动刷新，都不能单独证明活动消费者已经迁移到当前资产。

删除实体文件仍需单独授权。用户已经授权实施迁移但没有授权删除时，可以把被替代文件移入明确归档；活动路径中不能保留旧入口、兼容 helper 或第二个真源。

## 6. 防止新漂移

新增值只有在承担可复用语义且现有系统无法表达时才成为 token。组件复用以职责和行为一致为依据，不以“看起来相似”判断。不同平台可以有不同表现，但共享身份、任务结果和状态语义。

如果存在确定性检查，只检查可证明的不变量，例如 token 使用、组件消费者、资源身份和结构字段。审美判断和真实用户结果仍由目标界面的可见验收完成。

## 7. 输出

第一段说明漂移的根因和应该修系统、迁移复用还是重做概念关系。随后列规范真源、受影响消费者、一次性迁移范围和可观察通过结果，不用散乱的页面级修改清单代替根因。用户要求创建或交接可移植设计系统时，再说明包内各类事实的所有者、派生产物、正式读取入口和一致性验证；普通设计系统审查不自动生成文件结构。
