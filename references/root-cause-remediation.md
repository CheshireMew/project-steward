# 根因治理

用于已经出现缺陷、重复回归、半迁移、架构漂移或跨层链路失效的项目。目标是找到错误第一次产生的边界并完成最终迁移，不在每个症状旁增加特判。

## 1. 区分现象、根因和放大点

建立证据表：

| 项目 | 要回答的问题 |
| --- | --- |
| 现象 | 用户真实看到什么，怎样稳定复现 |
| 行为基线 | 用户现在要什么、当前实现是什么、历史来源只证明哪个时点；冲突与未知项在哪里 |
| 首次错误 | 哪个生产者或边界第一次产生错误事实 |
| 放大点 | 哪些缓存、恢复、状态同步或消费者让影响扩大 |
| 旧架构 | 哪些类型、helper、入口、数据源或兼容路径仍在活动 |
| 影响 | 哪些用户结果、平台、数据或恢复能力失效 |
| 目标边界 | 修复后由哪个唯一真源和接口负责 |
| 证据缺口 | 哪些结论仍只是推断 |

错误最后显示在界面，不表示根因在 CSS；原生命令报权限错误，不表示只需加一项权限；保存失败发生在关闭时，不表示关闭按钮本身是唯一问题。

旧提交、旧截图和旧测试只能按它们的适用状态参与诊断。它们可以解释回归从何处引入，但不能自动决定修复后的目标行为；目标由用户当前明确要求、接受结果和项目活动真源共同确定。当前运行结果与目标冲突时，前者是失败证据，不是把目标改回现状的理由。目标仍不可靠时先交付待确认的行为合同，不进入修复。

普通对象反复进入版本管理、登录、同步或其它高级能力的错误路径时，先检查产品模型是否把可选能力错当成了核心对象的拥有者或前提。若是，应迁移核心类型、命令、状态、持久化和界面层级；给“能力不存在”增加特判只会保留错误定位。

界面症状跨区域、主题、状态或视口重复时，把它作为共享边界问题检查：布局与外壳所有权、控件拓扑、完整状态族、设计系统真源和真实可见验证。只有证据匹配时才使用高频模式，不逐项套用整库。

媒体预览看起来少了一部分、被裁切或出现大块比例留白时，不能从最终截图直接断言正式内容已经缺失，也不能先用一种缩放模式覆盖症状。先分别取得源媒体或正式素材、输出尺寸与比例契约、渲染表面的逻辑尺寸与物理像素、布局容器与外壳空间预算；从第一处偏离契约的边界判断是生产内容缺失、渲染表面错误还是布局构图错误。外壳或固定区域改变后，下游渲染容器和最终媒体构图必须重新验收。

## 2. 诊断路径

用户只要诊断时：

1. 复现真实现象，或说明当前无法复现的准确条件。
2. 从用户动作反向追到消费者、边界和生产者，再从生产者正向验证。
3. 用代码、配置、运行输出或真实文件证明最早错误位置。
4. 缺陷与启动、加载、过场、滚动、资源到达或媒体切换有关时，沿时间顺序找到第一个错误里程碑，并区分最终状态正确但中间过程失败的情形。
5. 列出完整影响范围、最终架构和迁移顺序。
6. 说明修复后怎样证明旧路径退出。

交付诊断后停止，不借“验证根因”实施修复。

命令找不到、版本错位、包安装位置、缓存、SDK、终端差异或长任务超时参与现象时，先把根因归入项目源码或配置、用户与机器环境、命令执行器、外部服务四个边界之一，不能用“环境问题”混写。已有用户环境档案只提供当前事实候选，仍要由绝对可执行文件、版本、目录或真实进程核验；档案缺失不等于项目有缺陷。只有检测确认、未来任务会复用且用户允许写入的机器事实才更新档案，项目依赖和一次报错仍留在项目或本轮。

外层等待超时不能直接归类为构建失败。先确认实际阶段、原进程与子进程、日志和产物是否继续变化、命令是否已退出，以及正式消费者能否读取结果。原任务仍有进展时继续观察，不启动可能争用锁、缓存、端口或输出目录的重复任务；只有成功退出且产物可消费、明确失败退出、进程消失且没有产物、连续观察没有进展并形成诊断证据，或达到用户明确时间与成本边界时才停止。

## 3. 修复路径

用户要求修复时：

1. 先保留一个能证明缺陷的失败测试、复现实验或可观察证据。
2. 定义最终真源、类型、命令或接口，以及生产者和消费者各自职责。
3. 一次性迁移所有调用点、状态、持久化字段、事件、导出、平台适配，以及会教用户或扩展作者使用该契约的文档、示例、schema、SDK 片段、验证与发布脚本、真实用户链工具和生成物来源。
4. 在新链已经接通且原功能完整迁移后，退出旧类型、旧 helper、旧命令、旧恢复路径和仅为半迁移存在的兼容层。
5. 用户未允许删除时，把必须保留的历史材料移到已同意的归档位置；不能继续从归档运行。迁移前建立准确的“源文件 → 归档文件”清单，归档后逐项核对字节数与哈希或直接逐字节比较。先重命名再继续修改同一文件不等于保存了原内容；只有归档副本与动作前来源一致，且活动入口不再读取归档，才算完成保留。
6. 运行标识符边界明确的残留搜索并检查每项命中，证明活动源码、测试、配置、文档、示例、生成物来源和公共导出只剩最终身份；归档、生成结果和自然语言误报要明确排除，不能靠忽略全部命中宣称完成。

外部协议需要过渡时，把兼容适配器放在唯一边界外侧，记录版本、拥有者、最后期限和删除测试。项目内部不能继续读写两套真源。

## 4. 同源变体收口

找到第一个最早错误边界后，在同一事实和同一受影响链内派生变体，再冻结迁移范围：

- **权限归属**：创建、读取、改变、取消和恢复是否由同一正式身份约束，连接、会话、客户端、进程和持久化所有者是否会错位；
- **状态生命周期**：持久化失败、等待、断开、重新调度、取消、终态、重启恢复和关闭是否遗漏转移或清理；
- **数据表示**：原文、序列化或转义文本、结构化字段、流式分片、参数、环境、请求头、日志、事件和持久化记录是否仍会产生同一错误；正式序列化器的实际输出是否通过 schema、存储或线协议校验，字段省略与显式 `null` 是否符合合同；改变 chunk 边界和最终 flush 后是否等价；
- **边界转向**：重定向、代理、重试、回调、并发、中止和关闭是否把目标、顺序、所有者或失败收口带离最终合同；
- **实际运行入口**：源码、生成文件、包装脚本、解释器和原生产物中，用户入口实际选择的是否仍是旧实现或过期产物，以及其子进程是否解析到同一执行计划中的工作目录、包导出、相邻依赖和资源，允许集合与实际集合是否完全相等。

这不是扩大成项目综合审计。只对已经证明受同一事实或边界影响的维度建立失败证据、迁移调用点和验收。主要测试通过后才连续发现同源问题，说明迁移范围的生成方法仍缺维度；更新范围并一起收口，不能修一个、重跑一次、再等下一个偶然暴露。

## 5. 持久化和临时状态迁移

涉及持久化状态时同时处理：

- 新 schema 和单向迁移；
- 当前版本新建状态、由旧版本正式生产或保存的真实历史状态，以及各自的准确版本与内容身份；
- 旧字段何时读取、何时立即重写；
- 不可用路径、未完成操作和恢复副本怎样保留；
- 失败或中断后能否安全重试；
- 新运行时是否已经停止读取旧字段。

迁移验收使用同一份状态矩阵：当前版本从零新建；真实旧状态进入正式迁移器；迁移后的实际文件、记录或消息通过当前 schema、存储或线协议校验器；当前消费者读取、关闭并重新打开；失败注入后原版本、原内容和原身份保持可恢复，失败产物不会取代正式状态。真实旧状态应来自旧版本生产者、旧版保存路径或可核对的历史制品，不能由测试直接手写迁移后对象或凭当前模型猜一份旧对象。一次迁移完成后立即重写并由当前消费者只读新合同，运行时不保留长期双读。

临时状态不能只验证“没有落库”。按创建、持久化失败、等待、断开、重试或重新调度、取消、终态、重启恢复和关闭逐项确认所有者、保留条件与清理条件。恢复链需要知道临时依赖已经丢失时，持久化记录只保存不含该数据的需求或所有权标记，并进入明确等待或失败；不能静默换用另一个依赖，也不能把临时值转存到参数、环境、日志或事件。

用户动作已经被接受、随后仍可能失败或留下外部结果时，`pending` 必须在易失败的输入重校验前持久化。发布成功、失败保全和无产物失败只能描述已经完成的物理事实：先完成正式目标或恢复副本的写入、移动、刷盘与必要校验，再记录唯一终态。释放生产者、文件句柄、设备或远程会话失败时，事务保持未决，不能因为等待超时就提前宣告完成。

## 6. 平台与生命周期

桌面窗口、Android、后台任务、远程同步和关闭刷盘属于生命周期链。修复时核对：

```text
启动 → 恢复 → 正常操作 → 外部变化 → 保存 → 关闭请求 → 刷盘 → 退出 → 再次启动
```

每个平台使用自己的真实边界。共享业务语义可以统一，原生权限、文件系统和生命周期实现不能用一个平台的假接口代替。

回调、事件处理器或 `void` 风格命令如果能启动异步操作，生命周期所有者必须登记派生工作，并让空闲、取消、关闭、重启和测试完成边界等待或收口。每个线程、任务、读取器和订阅分发器都要有唯一创建者、可等待完成信号、取消后的排空路径和唯一释放者；超时只表示等待未完成，不表示工作已经结束。只等待事件处理器返回、却让它启动的 Promise 继续运行，仍然是生命周期链失效。

权威状态转换、终止原因和致命错误使用无损通道；高频进度、帧率或其它遥测才可以有界、合并或丢弃旧值。不能为了避免慢消费者阻塞而丢掉操作终态，也不能让逃逸任务在事务已经宣告完成后继续写状态。

跨进程生产者同时输出业务结果和诊断内容时，先确定唯一结构化结果通道并让正式消费者只从该通道改变业务终态；结果帧至多一次，缺失、重复或版本不兼容都形成明确失败。stdout、stderr、日志尾部、退出码和 EOF 分别保留文本、进程与传输语义，不能从自然语言或最后一行猜测结果。完整日志写入和结果帧消费都必须在关闭宣告前完成；有界摘要只能是可追溯到完整记录的投影。

验证有状态服务重启或恢复时，通过权威端点、端点到进程的映射、锁文件或服务管理器确定确切实例，先处理正在运行的工作并保存重启前的正式消费投影；只停止该实例并重启后，再由同一个消费者读取。按进程名称批量终止，或只证明数据库文件仍在，都不能证明服务恢复和消费结果成立。

## 7. 完成证据

按层验证：

1. **失败证据**：修复前能够稳定失败。
2. **生产者**：正式输入产生正确结果。
3. **边界**：结果真实写入、传输或调用原生能力。
4. **消费者**：正式消费者读取同一结果。
5. **用户链**：用户能够看见或使用。
6. **实际运行产物**：从用户入口及其子进程证明最终选择的绝对路径、产物身份、新旧关系和依赖或资源闭包；内容清单的允许文件集合与运行目录实际集合必须完全一致，源码、普通构建和生成或原生产物分别报告。
7. **生命周期**：失败、等待、断开、重试、取消、终态、重启恢复和关闭没有遗留第二所有者、临时依赖或静默降级。
8. **退出检查**：旧入口、旧状态和旧名称不再活动。
9. **回归**：必须保持的旧行为仍成立。
10. **承诺覆盖**：每项用户可见承诺都经过自己的正常入口和实际分支；被环境变量、测试开关、手工状态或诊断动作绕过的承诺只能标为仅诊断、未验证或受阻，不能借用其它分支的成功证据。
11. **迁移合同**：真实历史状态经过正式迁移，实际序列化结果通过当前合同校验，失败时原状态可恢复，当前消费者关闭并重新打开后仍得到目标结果。

函数测试、构建成功、产物存在和界面截图各自只证明一层。涉及生成文件、包装脚本或原生产物时，必须让真实入口解析并消费当前产物；用户没有授权生成或打包时，让过期产物明确失效，并把尚未生成的层级报告为证据缺口，不能静默选用。完成报告要说清实际达到的层级和仍未验证的条件。

事务型操作的验收先记录动作前的真实事务身份，再从生产者新增的事务读取实际路径、终态和确认状态。测试不得根据成功次数预测名称，不得建立第二个时钟、文件编号器、状态机或恢复解释器；这些做法只能证明测试自己的假设与自己一致。

验证过程本身也要可证。每条测试、静态扫描、依赖审计和残留检查先核对预期覆盖对象及内容身份，与工具实际选择的输入、版本、过滤和排除项是否一致；实际输入为空、过期或不完整时，即使命令成功也只能标为未覆盖或未知。每项检查还要单独保留退出状态，失败后立即停止或明确标为未知，不能被同一脚本后续命令的成功覆盖。扫描器成功运行且覆盖预期对象后，零匹配才是零发现；宽泛正则的相似文字命中必须人工核对，不能直接当成旧架构，也不能为了得到“零”而无依据排除。

## 8. 证据驱动的连续收口

用户明确要求自行迭代、做到底或在证据充分时自行停止，或者一次真实验收在同一受影响链内暴露新的同源缺陷时，内部轮次不是新的授权边界。先冻结同一用户结果、同一受影响链和已冻结权限；每轮只处理能够由当前生产者、边界、消费者或生命周期证据解释的高价值问题，不把连续工作扩张成项目综合审计。

每轮遵循同一个闭环：

1. 保存本轮失败证据并在最早错误边界修复。
2. 重新运行受影响的生产者、真实边界、消费者和用户链。
3. 检查这次新鲜运行证据，而不复用修改前的干净结论：正式产物、结构化状态、日志语义、恢复或临时目录、子进程和后台任务、退出与取消结果、旧标识符和旧入口。
4. 新证据仍属于同一根因与链路时，更新迁移范围并继续；它属于独立用户结果、低收益润色、产品取舍或新权限时，记录准确边界并停止。

真实验收失败时，先确定失败发生在环境、测试驱动或夹具、产品生产链还是最终断言。只有存在瞬态证据时才做一次有界的原样重跑，用于区分偶发状态和稳定缺陷；同一点再次失败或已有确定性证据时，应修复测试驱动自己的边界并重新进入同一真实链，不能修改产品来迁就测试驱动或夹具，也不能用手写结果绕过刚刚失败的核心边界。

停止需要同时满足：目标行为和必须保持的回归通过；新鲜运行的正式产物可消费；日志、持久化、恢复、进程和旧路径检查没有与成功结论冲突的高价值异常；剩余事项只是不影响当前结果的润色、独立产品决定、外部状态或新授权。满足后主动交付，不再为了消耗时间或额度继续寻找改动。

## 9. 完成项目结果并按已选路径停止

修复或诊断完成后，把本次最早错误位置连接到下一次改动前可以采用的做法：

```text
稳定问题类别：
最早预防点：
适用项目范围：
可确定检测信号：
真实验收方法：
不应沉淀的一次性细节：
```

根因治理完成后，交付本次项目的根因、最终边界、迁移与退出证据、真实验收和仍缺的证据，随后停止。用户在请求开始时同时明确要求 Project Steward 自我进化时，才把上面的稳定问题类别、最早预防点、适用范围、检测信号和真实验收交给对话学习路径；用户要求保存当前项目长期事实时，把结论写回该项目已有的规则、设计文档、代码、配置或测试。只有用户另行明确要求更新模板时，稳定默认才进入模板演进。
