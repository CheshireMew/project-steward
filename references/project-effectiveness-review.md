# 项目实际效果与目标适配评估

用户问“实际效果怎么样”“好不好用”“值不值得”“能否解决 X”时使用。目标是判断现有证据能说明什么，以及项目对用户真正用途是否有帮助。

## 先确定要验证的结果

“实际效果”可能指不同问题：

- 用户问项目有没有真实产物、结果质量如何：检查仓库已有示例、评测和原始输出。
- 用户问自己环境里能否工作，或明确要求运行、复现：按上层动作权限进入真实运行。
- 用户问是否适合某个目标：把该目标拆成产生、保存或传输、维护、取回、最终使用五个环节，沿真实实现逐段检查。
- 用户问外部替代方案或当前产品：在这个明确问题范围内读取官方一手资料。

问题含糊但只读材料足以形成有用判断时，先完成能够确认的部分，并说明还缺哪一层证据。

## 证据顺序

按下面顺序使用能够拿到的最高层证据，并保持证据身份：

1. 本次从真实入口复现并观察到的最终结果。
2. 仓库提交的原始产物、日志、结构化数据和可打开的界面，并由本次检查确认内容。
3. 项目自带 review、benchmark 或 case study；它们代表作者提供的评测。
4. README、功能说明和预期结果。
5. 由源码和多项材料推导出的判断。

文字评测附带原始 JSON、报告、图片或日志时，核对会改变用户判断的数量、内容和结论是否一致。README、review 和产物来自不同版本时，直接说明差异。实现机制的结论归到真正负责该环节的组件；token 减少、节点数量、测试通过等单一指标只说明对应维度。

## 按用户结果评价

先写用户最终想得到的结果，再沿链路检查：

```text
真实输入
→ 项目处理
→ 保存或传输
→ 更新、删除、纠错和过期处理
→ 最终入口找到并使用结果
```

优先回答三个问题：现在确实可用的部分是什么，噪音或错误从哪里进入，用户怎样使用或限定范围才能得到可靠结果。功能数量和任意总分不代替这三个判断。

如果用户真正关心 Agent 记忆，检查记忆写入条件、保存粒度、来源记录、跨会话持久化、更新与失效、纠错与取代、压缩或归档、召回与重排、上下文预算，以及旧回答是否会被重新当作事实。项目事实、任务经历、提炼结论和当前工作记忆需要分别判断。

## 输出方式

第一段直接给出效果判断和当前证据层级，例如说明仓库已有产物能够证明什么、本次是否亲自复现、哪些结论仍来自作者评测或源码推断。随后用连贯段落说明有效部分、主要限制和对用户目标的影响。只有多个案例或方案需要按相同字段比较时使用表格。

已经足以支持用户当前判断时返回上层主流程。
