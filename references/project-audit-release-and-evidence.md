# 项目审计的测试、发布与证据

## 10. 审计构建、测试和发布

本节审查构建、测试与发布体系的入口、责任、选择规则、正式消费者、既有结果和风险，不把这些入口组成一份必须在综合审计中全部执行的命令清单。全面审查可以在盘点全部适用入口并分析其保证关系后完成本维度覆盖；实际运行深度另行记录。只有某项具体结论缺少运行证据时，才按 `ci-execution-governance.md` 选择当前机器上的最小目标检查；完整套件、全部公开验证器、发布链和远端检查仍属于用户明确要求、代码冻结或发布候选结果。

检查：

- 当前开发、生产和平台构建入口是否真实可用；
- 开发服务器、编译器、链接器、运行时和应用各自产生的输出是否按阶段、退出状态与用户结果分级；
- 核心测试使用真实生产者还是消费端假数据；
- Windows、Android、Web 或其它正式目标是否有与发布风险匹配的检查，并把相关源码、配置和依赖映射到实际目标、构建 profile、feature 与条件编译分支；宿主测试或默认目标通过不能证明未参与该次编译的目标专属代码；
- 生成物是否来自当前源码，而不是旧缓存；
- 用户入口与它启动的子进程是否解析到同一构建计划中的产物、包导出、依赖和资源；内容清单的允许文件集合是否与运行目录实际集合完全相等，缺失、改变和额外陈旧文件是否都会被拒绝；
- 本地提交、远程分支、制品和用户下载之间是否有可核对边界。

### GitHub 仓库必须审计实际上传边界

准确项目根已经连接 GitHub、存在 GitHub 上的公开或私有交付，或者当前项目明确计划初始化 GitHub 仓库时，读取 `repository-publication.md` 的“审计 GitHub 上传边界”。综合审计只消费这份共享方法并报告发现，不在这里建立第二套敏感文件或目录黑名单。

活跃开发中的普通综合审计先核对当前物理文件、候选、索引、当前树和实时默认分支的职责与明显风险；不会仅为取得“全面”称谓扫描全部历史、其它分支、标签、Release 资产和 Actions 制品。完整上传边界、隐私或历史暴露审计只有在用户明确要求发布、公开、上传边界审计或历史清理，发现凭据或私人内容信号，或者进入发布候选时才展开全部适用证据平面。未展开的历史平面记录为待验证，不会冒充零发现，也不会让已经完成的项目维度分析变成全面测试或发布验收。

检查对象至少分开本地物理文件与拟上传候选、Git 索引、当前已跟踪树、本地提交和可达历史、实时 GitHub 默认分支、其它活动分支与标签；项目实际使用 Git LFS、Release 资产或 Actions 制品交付文件时，再加入对应公开表面。被忽略和未跟踪内容用于判断未来候选与本地隐私边界，不得被误报成已经上传；本地 `origin/*` 也不能代替实时 GitHub 内容。

每个实际或候选路径都要从干净克隆交付合同核对正式生产者、消费者、生命周期和上传必要性。缓存、构建输出、日志、数据库、备份、下载依赖、编辑器状态、原始制作材料、重复产物和大文件只是重点候选；没有消费者证据才说明它不应进入仓库，不能按名称、扩展名、大小或是否为二进制直接定性。已经跟踪或在历史中存在也不证明必要。

隐私检查覆盖凭据与环境配置、私钥和证书、本机路径与账号或主机身份、用户内容、数据库、日志、转储、会话、备份、真实测试数据，以及文档、截图、媒体元数据、压缩包和二进制容器中的私人或内部内容；同时核对 Git 提交作者姓名与邮箱的公开暴露。扫描器必须实际消费待判断的索引、提交对象、适用历史或实时远端内容，并记录版本、输入、排除与退出状态。工具缺失、输入为空、历史未取得、远端不可访问或二进制未覆盖时，本维度只能标为部分审查或待确认，不能报告“没有隐私文件”。

数据库、日志、备份、运行状态和生成结果要同时记录上传必要性与内容敏感性，不能把两者合并成一个严重程度判断。扩展名、文件大小、二进制格式或存在真实运行记录只能把它们列为检查候选；没有正式消费者证明“不应上传”，只有安全投影、权威来源或等价直接证据才能证明其中包含真实凭据、私人用户内容、内部数据，或者已经证明不敏感。无法安全核对内容时标为未知，不把未知自动升级成敏感，也不因为仓库应保持整洁就补造隐私结论。

默认分支当前树没有发现不能清除其它分支、标签或 Git 历史中的既有暴露；工作区删除、`.gitignore` 命中或新提交移除也不能证明 GitHub 已经清除。审计发现真实凭据时，把撤销或轮换列为第一处置；取消跟踪、移动、归档、删除、历史重写、强制推送和远端制品清理分别进入仓库发布或目录治理的获准修复路径。只读综合审计不修改 `.gitignore`、不初始化 Git、不改变索引、不创建远端，也不清理历史。

发现需要历史清理时，由 `repository-publication.md` 唯一拥有当前树、本地引用、实时远端活动历史、旧 SHA 缓存、PR、fork 和其它克隆的分层合同。修复交接账本必须写明用户已经接受的准确清理层；只有确认敏感且对应层属于接受结果时，服务器缓存或托管方工单才进入完成条件。不能在修复后因为发现一个未获准、非必要或尚未证明相关的外部残留，反向扩大原发现并把已经成立的项目结果改成受阻。

交付时为每项发现写明证据平面、路径与内容身份、隐私类别、必要性、正式消费者、当前本地与 GitHub 暴露状态、证据缺口及所需处置权限。只有预期上传清单、真实索引或提交树、实时远端树和适用历史均由有效检查覆盖，才可以把 GitHub 上传边界标为已审查。

### 公开验证器必须实际进入保证链

README、项目规则、CI、发布流程或维护文档中公开宣称的验证脚本、性能检查和真实用户链工具本身也是审计对象。先盘点每个入口的实际命令、当前接口、代表性输入、正式消费者和它声称保证的用户结果，再核对 CI 或人工流程究竟执行了主流程，还是只做语法检查、导入、文件存在或帮助输出。

在当前运行权限和成本边界允许，并且某项具体审计判断确实依赖运行结果时，让选中的最小目标验证器使用代表性输入真正执行，并核对它实际选择的内容身份和退出语义。lint 或成功导入只能证明脚本能够被解析；验证器仍调用已经退出的接口、私有状态或旧产物时，这是保证链自身的缺陷，即使产品测试全部通过也不能把该能力标为已覆盖。CI 应实际执行它公开承诺负责的验证器，或者明确把它标为人工且当前未覆盖；综合审计负责检查这项保证关系，不为证明检查过它而代替 CI 运行全部入口。未来计划、注释和文档声明不能冒充当前执行证据。未获运行授权或缺少外部前置条件时保留为待确认，不在只读审计中修改脚本。

公开包装器本身也是正式消费者；一旦它被选为本轮目标检查，就必须实际执行，不能只绕过它运行内部子检查。它的超时预算要覆盖代表性输入下必需子检查的实际稳定时长，以及启动、报告落盘、关闭和清理余量；外层执行器的等待预算还要覆盖包装器自身收尾。子检查已经打印通过，但包装器随后超时、清理失败或非零退出时，整条公开验证链仍是失败或待确认，不能摘取内部成功当作公开入口通过。预算来自可观察阶段和代表性运行证据，不靠任意放大掩盖挂起；持续无进展时仍按长任务合同诊断并收口。

运行构建、测试、预览或真实浏览器必须已经获得当前规则和用户请求允许。单独的“允许运行 build”只授权执行构建及生成它正常产生的产物，不把只读审计改成项目修复；构建失败形成审计证据，修改源码、配置、测试或工作流仍需已有修复授权或另行确认。构建成功也只证明该构建入口和产物边界，不能代替未运行的失败恢复、交互或最终用户链。用户没有授权生成或打包时，审计应确认过期产物不会被静默选用，并把原生产物闭包与冷目录消费标为未验证；未来 CI 计划不能冒充当前已经生成和消费的证据。

构建命令存在不表示当前能构建；历史 CI 徽章不表示当前分支通过。终端出现 `warning` 不自动等于构建失败，也不自动等于可以忽略：先确认消息的生产者、完整上下文、命令最终状态、正式产物和用户链是否受影响，再决定解释、观察或治理。

工具调用或外层等待超时也不自动等于构建失败。审计证据必须区分执行器停止等待、原进程仍在运行、构建工具明确失败和应用已经退出，并说明当时阶段、进程、日志或产物是否继续变化、最终退出状态和消费者结果。没有这些证据时标为待确认，不用重复启动同一构建来制造新的状态。

### 分开功能、合并和发布就绪度

审计涉及交付状态时分别给出三项结论，不能用其中一项替代另一项：

- **功能可用**：当前工作状态下，正式生产者、真实边界、消费者和用户结果已经成立；它不自动证明待合并内容完整或仓库可复现。
- **可合并**：候选变更范围准确，生产代码、测试、验证与发布脚本、文档等正式消费者已经迁移，针对同一份当前内容的必需检查通过，并且没有已知旧入口或未归属变化；它不自动证明制品和远端发布链成立。
- **可发布**：只在发布候选或用户明确要求发布就绪审计时判断；干净检出能够重建并消费当前制品，发布配置、许可证、README、版本、已经完成的远端检查和用户取得结果的路径均符合本次发布合同。活跃开发审计不等待远端检查来取得这项结论，而是把可发布状态标为当前阶段未评估或待异步证据。

某一层不适用时说明原因；证据不足时标为待确认。历史测试通过、局部补跑或功能演示不能拼接成更高一层就绪结论。

## 11. 审计 README、许可证和日志

README 检查第一屏、证据、首次成功路径、主要入口、限制和维护信息。许可证检查代码、内容、数据、素材和第三方条款是否覆盖准确。日志只判断是否适用、是否有稳定入口、关键操作能否关联，以及是否有真实消费者。

需要逐段重写、许可证选择或逐字段日志审计时，建议进入对应专项路径；综合审计不实施。

## 12. 证据等级

- **已证实**：项目文件、配置解析、真实命令、运行结果或用户可见结果直接支持。
- **较强推断**：多个事实一致，但缺少最终运行、平台或权利证明。
- **待确认**：缺少用户目标、项目环境、历史状态或真实消费者。

每个问题同时说明证据位置、影响用户结果和建议路径。没有证据的通用最佳实践不进入优先级。

## 13. 输出

### 综合审计必须交付修复交接账本

综合审计本身必须交付一份可由后续普通修复任务直接消费的账本，不能只给按严重程度排列的文字摘要，再依赖后续任务重新解释范围。每项确认发现和仍待确认的高影响事实使用稳定发现编号；编号绑定审计根、版本或工作树内容身份和问题语义，不绑定临时行号、排序位置或措辞。审计后文件移动、风险顺序改变或取得新证据时沿用同一编号；证据证明原判断错误时更新状态和理由，不删除原发现来制造全部闭环。

每项账本至少写清：

```text
稳定发现编号与简短标题：
审计根、版本或工作树内容身份：
证据位置、来源身份、取得时刻与证据等级：
根因及当前唯一责任边界：
受影响的生产者、传输或存储边界、正式消费者与用户结果：
应迁移到的目标所有者或真实边界：
逐项完成条件及必须取得的生产、边界、消费和可观察证据：
本地工作树、本地提交、实时远端、发布制品或其它适用证据平面的独立状态：
当前状态：开放 / 待确认 / 经新证据重新分类 / 经用户明确同意退出范围 / 受阻 / 已解决
建议顺序与对应专项路径：
```

状态按发现和证据平面分别成立。源码在本地修好，只能关闭本地实现条件；实时远端、发布制品、外部服务或最终消费者仍是旧状态时，相应平面继续开放或待确认，不能把某一平面的完成折叠成整个发现已经解决。测试总数、一次完整回归或其它发现的真实用户链通过，也不能替代该发现列出的逐项完成证据。只有全部适用完成条件都由当前内容身份的新鲜证据满足，或者按上列状态得到明确重新分类、退出范围或受阻结论，后续任务才能关闭该发现；仍有开放或待确认项时不得宣称“全部问题已经解决”、可合并或可发布。

按以下顺序交付：

1. 总体健康结论、根因级风险和第一优先事项。
2. 维度覆盖账本，逐项列出适用性、检查对象、方法、证据、已审查 / 部分审查 / 未审查 / 不适用状态和补齐入口。
3. 项目事实、证据强度，以及本地、实时远端和外部能力证据平面。
4. 项目基线与模板漂移。
5. 产品、真源、功能清单和架构链。
6. 数据、生命周期、界面视觉、完整用户旅程、无障碍和平台外壳。
7. 性能、资源、规模、兼容性、安装升级和外部边界。
8. 构建、测试与发布，并分别给出功能可用、可合并和可发布结论。
9. README、许可证和日志适用性。
10. 建议执行顺序及对应专项路径。
11. 仍需确认的事实。
12. 修复交接账本，保留每项发现及各证据平面的当前状态和完成条件。

每项建议说明它修复哪个用户结果以及为何现在优先。到此停止。
