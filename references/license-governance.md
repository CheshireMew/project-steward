# 仓库许可证治理

用于为一个或多个仓库审计、选择和应用许可证。许可证选择先回答“谁有权授权什么”，再回答“希望别人怎样使用”；项目语言和框架只用于识别内容边界，不直接决定许可证。

本方法提供仓库整理依据，不替代针对具体司法辖区的法律意见。

## 1. 先确认授权权利

逐类检查：

| 内容 | 需要确认 |
| --- | --- |
| 原创代码 | 作者、雇佣或委托关系、外部贡献者和既有授权 |
| Fork 或复制代码 | 上游许可证、版权声明、修改义务和兼容性 |
| 文档与文章 | 作者、翻译权、转载许可和引用范围 |
| 数据与抓取内容 | 数据库权利、平台条款、个人信息和单条内容版权 |
| 模型、字体、音乐、图片、视频 | 原始条款、署名、商用和再分发条件 |
| 角色、标志和品牌 | 版权授权与商标使用是不同问题 |
| 依赖和 vendored 包 | 每个第三方包继续遵守自己的许可证 |

作者只能许可自己拥有或已经获准再许可的权利。无法确认时：

1. 标出准确文件或目录。
2. 保留已有第三方声明。
3. 将其排除在作者许可证之外，或等待权利证明。
4. 停在建议模式，不生成暗示全仓库归作者所有的许可证。

公开 GitHub 仓库没有许可证时，默认版权仍然适用；GitHub 用户可依据平台条款查看和 Fork，不因此获得一般性的复制、修改、发布或商用许可：

https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository

## 2. 确定采用目标

先按仓库的主产品分配稳定默认，不因语言、框架、是否桌面应用或是否联网改变：

- 主产品是原创软件代码、桌面应用、CLI、服务、网站、库或其它可执行软件时，默认 `AGPL-3.0-or-later`。
- 主产品是一个 Agent Skill 或正式的 Agent Skill 集合时，默认 `MPL-2.0`。根目录 `SKILL.md`、正式 Skill 清单、安装入口和仓库说明共同证明它是主产品；宿主软件里的嵌套适配器、测试夹具、示例、vendored 或第三方 Skill 文件不会把宿主仓库改判为 Skill 仓库。
- 内容、数据、角色、品牌和媒体不是软件默认的附属牺牲品；混合仓库继续按第 3 节分区授权，AGPL 或 MPL 只覆盖作者有权授权的对应软件或 Skill 文件。

分类证据充分时，稳定默认本身就是已经选定的许可证，不再停下来询问用户选择。新仓库和当前没有许可证的仓库可直接进入范围与权利核对；已有许可证、Fork、外部贡献者或第三方冲突仍先保留现状并审计权利，不能把稳定默认当成静默重新授权的依据。用户明确批准重新授权且权利成立时，再按第 4 节保留历史并迁移；权利冲突可以阻塞实施，但不改问一次许可证偏好。

用户明确覆盖稳定默认时，用采用目标选择最接近的备选：

| 明确采用目标 | 候选 | 主要后果 |
| --- | --- | --- |
| 小工具、浏览器扩展、示例代码，希望最大化采用 | `MIT` | 允许闭源再利用，保留版权和许可声明 |
| 库、框架、协议实现，希望宽松采用并明确专利授权 | `Apache-2.0` | 允许闭源再利用，包含明确专利条款和 NOTICE 义务 |
| Agent Skill、插件或可嵌入组件，希望修改过的原文件继续开放 | `MPL-2.0` | 文件级互惠；新文件和更大的闭源作品可保持其它许可证 |
| 发布给用户的桌面应用、CLI 或完整程序，希望衍生发布继续开放 | `GPL-3.0-or-later` | 分发相应衍生程序时承担源码和同许可证义务 |
| 网络服务或自托管应用，希望在线修改版也向用户提供源码 | `AGPL-3.0-or-later` | 网络交互用户可获得对应源码 |
| 原创研究、说明文档，希望允许商业传播并保留署名 | `CC-BY-4.0` | 允许分享和改编，要求署名 |
| 原创文章或知识库，希望改编内容继续采用同类条款 | `CC-BY-SA-4.0` | 允许商业使用，改编内容需相同方式共享 |
| 原创内容希望允许非商业分享和改编 | `CC-BY-NC-SA-4.0` | 禁止商业使用，因此不称为开源 |
| 作者拥有数据库权利并希望数据库衍生物共享 | `ODbL-1.0` | 约束数据库，不自动解决单条内容的版权 |
| 角色、未公开商用素材或品牌需要保留控制 | 保留所有权声明 | 不授予通用复制、改编或商用许可 |

`-only` 与 `-or-later` 是不同的 SPDX 表达。用户没有特别要求锁定版本时，GNU 许可证默认建议 `-or-later`，但必须在项目许可通知中明确写出选择；仅放一份 GNU 许可证全文不能代替项目自己的版本声明。

MPL 的文件级范围依据：

https://www.mozilla.org/en-US/MPL/2.0/FAQ/

GPL 与 AGPL 的分发、网络交互和版本说明依据：

https://www.gnu.org/licenses/gpl-faq.en.html

Creative Commons 不建议把 CC 许可证用于软件；CC 用于文字、图片、音乐和其它创作内容：

https://creativecommons.org/faq/

OSI 定义的开源必须允许任何领域的使用，包括商业用途。带 `NC` 的内容许可证不能描述为开源软件：

https://opensource.org/osd

## 3. 判断是否需要分区授权

当仓库同时包含两类以上权利对象时，给出范围表：

| 范围 | 建议文件 | 说明位置 |
| --- | --- | --- |
| 全部原创软件代码 | `LICENSE` 或 `LICENSE-CODE` | `LICENSING.md` |
| 原创文章和文档 | `LICENSE-CONTENT` | `LICENSING.md` |
| 角色、图片、音乐、视频和品牌素材 | `ASSET-LICENSE` | `LICENSING.md` |
| 数据库 | `LICENSE-DATA` | `LICENSING.md` |
| 第三方文件 | `THIRD_PARTY_NOTICES.md` | `LICENSING.md`，对应目录仍保留原始声明 |

`LICENSING.md` 是混合仓库范围说明的唯一真实来源。没有直接复用第三方代码或资源时，README 只保留一句许可证摘要并链接到它，不维护第二份路径表；直接复用或改编第三方代码、脚本、模板、示例、数据、图片、音频、视频或其它资源并随目标分发时，README 必须包含“第三方资源与致谢”，逐项写明准确原始上游、实际采用的 fork 独有改动、版权与许可证、复用范围和目标路径、修改性质，并链接 `THIRD_PARTY_NOTICES.md`、目录内原始声明或其它完整许可文件。README 不复制完整许可证正文和仓库路径表，详细范围仍由 `LICENSING.md` 与第三方通知负责。

只学习高层方法、架构判断、视觉锚点、核心动作、工作流或反复刻方法，并在没有复制来源 IP、代码、资源、示例或实质相同表达的前提下独立实现，不会仅因研究行为触发 README 致谢，也不能把来源写成目标正在使用的第三方依赖。拿到 fork 或镜像时先追溯真正产生被复用内容的原始上游；只有实际采用 fork 的独有改动，才把 fork 作为另一项来源。

范围说明必须能回答：

```text
哪份许可证适用于哪些路径：
哪些内容明确排除：
第三方内容继续遵守什么：
版权所有者和年份：
GNU 项目选择 only 还是 or-later：
```

一个依赖通过包管理器使用，不代表需要复制它的完整许可证到根目录；vendored、修改或随发行物一起分发时，根据其条款保留声明和源代码义务。

### 下载、安装与再分发分别成立

运行时、模型、工具或资源能够从上游下载，只证明取得入口存在；上游允许用户安装、项目允许缓存、项目可以把副本装入安装器或发布包，是四个不同结论。许可证账本必须分别记录取得来源与身份、安装条件、缓存边界、再分发授权及其通知、源码、署名或其它义务，不能用“官方下载”“本机已安装”或包管理器可用替代再分发依据。

包含多个可执行文件、库、模型、权重、字体、媒体或其它资源的运行时归档是一个复合交付闭包。发布前逐项记录成员身份与版本、准确上游、适用许可证或条款证据、项目是否实际打包，以及该成员的再分发结论；同时绑定最终归档的内容身份。某个源码仓库的许可证只覆盖它实际授权的内容，不能替同一归档里的预编译二进制、第三方库、模型、权重或资源授权。

成员集合消费 `project-audit-release-and-evidence.md` 的实际制品组件溯源账本，不从声明依赖、应用 import、运行时锁或人工通知文件反推。每个实际文件、模块、原生库、runtime hook、bootloader 和数据文件都必须唯一映射到所属发行包、运行时、构建工具或项目组件，再记录准确版本、来源、许可证、再分发结论和必须随包提供的通知或源码义务。构建工具注入的 bootloader、启动器和运行时载荷属于实际交付成员；所有者未知或映射含糊时，权利闭包失败关闭。

任一实际成员的权利或义务仍未知时，复合包的再分发资格失败关闭，不生成或发布该包。可以改成由用户从已验证上游自行取得，但说明只能承诺已经证明的取得、安装与校验层，不能把这种流程表述为项目已经拥有再分发权。运行时锁、完整构建依赖锁、下载目录或组件清单必须把取得与再分发状态分开保存，打包器和发布验证器消费同一份逐项账本；`NOTICE` 与致谢只履行已经成立的义务，不会创造许可证没有授予的权利。

## 4. 重新授权

已有许可证时先检查：

1. 当前许可证及其版本。
2. 仓库历史中已经发布的版本。
3. 贡献者及其贡献是否由 CLA、雇佣协议或其它许可覆盖。
4. 新旧许可证是否兼容。
5. 变更只适用于未来版本，还是作者确实有权对全部历史代码重新授权。

已经依据旧许可证获得的副本通常继续享有当时授予的权利。更改根许可证不能追回旧版本，也不能替没有同意的贡献者重新许可其代码。

批准重新授权时，不直接抹去旧文本。逐字节保存旧许可证，记录最后一个采用旧许可证的提交 SHA，并在 `LICENSING.md` 说明新许可证从哪个提交开始。历史副本用于解释版本边界，不代表新版本同时采用两份许可证。

Fork 保留上游许可证、版权和 NOTICE。只有上游条款允许、且用户拥有自己修改部分的权利时，才能增加兼容的额外声明；不要把 Fork 当成全新原创仓库。

## 5. 建议模式输出

先给结论，再给依据：

```text
首选许可证与 SPDX 标识：
适用范围：
为什么适合当前采用目标：
使用者能做什么：
作者保留了什么：
主要义务和代价：
真正可行的备选：
第三方或未确认内容：
准备新增或修改的文件：
还需用户确认的事实：
```

账号级请求默认盘点公开仓库，包含原创仓库和 Fork；除非用户明确要求，不读取或修改私有仓库。用当前已认证的 `gh` 获取仓库清单、真实默认分支和公开证据；`gh` 不可用或未登录时停止远程实施，不自动安装或登录。

批量分配使用一行一个仓库的完整矩阵，不要先写一部分仓库再等待其它判断。每行至少包含：

| 字段 | 含义 |
| --- | --- |
| 仓库与可见性 | 准确 `owner/name`，public、private 或 internal |
| 默认分支与 HEAD | 不假设 `main`，实施前用于防止方案过期 |
| Fork 与上游 | Fork 默认保留上游许可证 |
| 当前许可事实 | GitHub 检测结果、根级与嵌套许可文件 |
| 内容边界 | 代码、文档、数据、模型、媒体、字体和第三方内容 |
| 贡献者信号 | 只用于提示权利核对，不当作权属证明 |
| 权利结论 | 可以授权、应保留、待确认或只能分区授权 |
| 建议处置 | 新增、替换并保留历史、维持现状或暂不处理 |
| 目标与范围 | SPDX 标识、适用路径、排除路径和说明文件 |
| 依据与风险 | 采用目标、主要代价、阻塞项和置信度 |

矩阵之外再汇总：纳入仓库数、每种处置数量、需要用户确认的共同事实，以及实际会创建提交的仓库清单。用户紧接着说“按这个方案添加/应用”时，视为批准这份准确矩阵的远程写入，不重复询问同一个确认；目标或内容发生变化时重新预检。

## 6. 应用模式

进入写入前必须已经确定：

- SPDX 标识或保留所有权方案；
- 版权所有者与年份；
- 适用路径和排除路径；
- 是否需要 `only` / `or-later` 项目通知；
- 每个目标的真实默认分支和当前 HEAD；
- 目标文件名，以及动作是新增、替换并保存历史，还是保留现状；
- 现有许可证的最后适用提交、贡献者许可与重新授权依据。

使用许可证目录中的正式文本和哈希。MIT 模板替换年份与版权所有者；其它正式许可证正文保持原样。项目自己的范围声明、GNU 版本选择、第三方列表和素材使用条款写入单独的通知文件，不修改正式许可证正文。

方案文件属于当前任务产物，不写入 Skill 源码。它采用本 Skill 实施资源定义的 schema v2。应用脚本先预演整个矩阵，打印每个目标、动作、来源、渲染哈希、现状哈希和预期分支 HEAD。任一项目预检失败时不开始写入任何项目。

本地实施使用 `--write`，GitHub 实施使用 `--publish`。远程实施为每个仓库创建一个包含全部批准许可文件的原子提交，并以非强制方式更新准确分支；仓库之间不承诺全局原子性。部分仓库成功后发生失败时，报告真实状态，不删除或回滚已经公开的提交。

写入后核对：

1. 正式正文与目录哈希一致。
2. 版权所有者和年份准确。
3. `LICENSING.md` 的范围说明与实际文件一致，README 如有摘要只链接它。
4. 历史许可证副本、第三方声明和上游版权仍在。
5. 本地 Git 差异或远程提交只包含批准的文件。
6. 远程 HEAD 和每个 Git blob 与渲染结果一致。
7. GitHub 许可证识别已记录；混合授权显示 `Other` 时按范围设计判断，不伪装成单许可证。
8. 本地结果、远程预演和实际发布状态没有混淆。

## 7. 正式标识与文本来源

本 Skill 的目录使用 SPDX License List 的稳定标识、正式名称、文本和规范链接：

https://spdx.org/licenses/

许可证目录是写入时的文本真源；本方法只负责选择与范围，不复制第二份许可证正文。
