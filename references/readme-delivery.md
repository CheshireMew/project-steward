# README 完整交付

用于用户要求“优化 README”“重写仓库主页”或交付完整 GitHub 首页时，把仓库准备、正文、视觉、多语言、许可证、Star History、验证和已有远端发布组织成一个结果。它只拥有编排顺序、结果账本、适用条件和停止位置；正文取舍、视觉方法、许可证选择、Star History 生成与仓库发布继续由各自 reference 唯一维护。

只问 README 现状、原因或建议时建立同一账本但保持只读。用户明确要求优化、重写、创建或完整处理 README 时，才执行账本中已经成立的写入动作。

## 1. 先冻结完整交付账本

在评价正文或生成素材前记录：

```text
准确项目根与上层 Git 边界：
当前是否已经初始化 Git：
工作区、索引、分支与并发变化：
远端所有者、仓库名、默认分支与可见性：
README 是否存在、当前动作与活动语言：
项目身份、第一采用读者与第一次成功入口：
现有视觉、图片和其它公开材料的资格：
个人 profile 是否适用：
许可证文件、GitHub 识别与权利边界：
Star History 生产者、输出分支、raw 文件与消费端：
GitHub About、topics、Issues、Discussions 与 Release 事实：
本次允许的本地写入、提交、推送和远端元数据动作：
需要单独确认的创建远端、可见性、删除、强推或法律选择：
最终停止位置：
```

检查目录是否位于父级 Git 工作树中；不能因为当前目录没有 `.git` 就创建嵌套仓库。用户要求完整优化且准确项目根尚未初始化时，只有当前请求明确包含初始化结果才进入 `repository-publication.md` 的初始化路径；否则报告缺口，不把“检查是否初始化”改写成未经授权的 `git init`。

README 不存在时选择新写；存在但读者路径、项目身份或公开事实错误时选择重写；事实正确但顺序和职责错误时选择重组；主要问题是重复与密度时选择压缩。一次交付只保留一个最终动作，不在新页面后面继续维护旧结构或兼容段落。

## 2. 完整优化的默认结果

用户明确要求 Project Steward 优化一个 README 时，默认结果不是只改几段文字，而是：

1. 仓库边界、README、公开身份和发布条件已经核对。
2. 第一采用读者能在首屏知道项目是什么、何时需要、交给它什么、会得到什么以及下一步做什么。
3. 正文按采用、第一次成功和维护深入分层，没有把内部方法库复制成首页长文。
4. 视觉、图片、链接和徽章都来自当前合格事实，并在 GitHub 常见桌面宽度、窄屏和深浅主题中可用。
5. profile 适用时，配置的完整语言页和贡献指南已经交付，项目导航、个人入口和仓库状态通过正式生成器进入每份 README；文档、贡献和反馈分别抵达真实且职责不同的目标，单个项目专属入口不成立时不影响其它组。
6. 许可证存在且范围准确；缺失时完成权利与采用目标判断，再按许可证方法要求取得具体方案确认并应用。
7. 公开 GitHub 仓库需要 Star History 时，正式生产链已经生成输出并被 README 消费，而不是只写了一份 YAML 或示例链接。
8. 本地审计、真实渲染和远端消费者分别取得证据；已有远端且本次确认包含发布时，精确提交、推送并核对远端结果。

用户只指出正文不说人话、术语太多、顺序难懂或看不出用途时，只改变正文的写作与验收。已经纳入完整优化的语言页、贡献指南、个人入口、仓库状态、许可证和 Star History 继续作为同一个结果完成，除非用户明确退出其中某项；不能把对正文的纠正解释为把其它交付改成按需。

仓库不是 GitHub 项目、为私有仓库、没有远端、缺少权限或外部服务不成立时，不生成伪造徽章、空链接或假远端结果。把该项标为不适用或受阻，其余仍能独立成立的 README 结果继续完成。

## 3. 正文不再充当活动方法镜像

README 是公开采用页面，不是 `SKILL.md`、reference、测试或变更日志的合并副本。内部治理能力新增、修正或细化，本身不构成修改 README 的理由。只有它改变了项目公开身份、第一采用读者、可执行入口、第一次成功、适用边界、维护入口或读者需要看到的证据时，才更新对应页面位置。

写作读取 `content-architecture.md`，并执行以下退出条件：

- 每项内部机制只有正式方法所有者和测试消费者，README 不成为第二个逐条消费者。
- 首页用少量稳定类别和真实请求入口概括能力；完整内部条件链接到 `SKILL.md` 或专项 reference，不改写成连续说明段落。
- 每个段落必须改变理解、信任、选择、操作或下一步；删除后无影响的文字退出。
- 同一节连续出现多段普通正文时，优先改成关系清楚的列表、请求示例、步骤、短表格或链接，而不是继续追加转折句。
- 自我进化的确定性测试验证活动所有者与路由，不要求新规则原文同时出现在 README。
- README 的测试只保护项目身份、读者路径、主要入口、许可证与致谢、公开素材、语言、状态区和维护导航等公开合同。

项目希望保留完整能力目录时，使用已有活动文档或新增有明确维护者入口的专项文档；README 只提供必要上下文和链接。不能用折叠块或 HTML 注释藏起一份仍被测试强制维护的第二套方法库。

## 4. 内容、视觉与多语言顺序

完整交付按固定顺序消费：

1. `content-architecture.md` 建立公开读者合同、入口台账、材料预算和最终章节职责。
2. 需要表达性视觉时读取 `visual-direction.md`，再依次读取 `project-native-hero.md` 和 `github-readme-canvas.md`；素材制作再加载对应 SVG、混合或动效方法。
3. 目标 owner 命中 `assets/readme-profile/profile.json` 时，由 `scripts/readme_header.py` 从真实语言文件、明确解析的项目导航目标、仓库身份和许可证文件生成首屏辅助区；不能临时改写内存中的 profile 绕过项目差异。
4. `scripts/audit_readme.py` 检查本地图片、SVG、header 和正文密度；它不替代事实核对、远程端点或实际渲染检查。

整页新写、重写或完整优化个人仓库时，同一 profile 中配置的语言属于同一个交付结果。缺少 `README.en.md`、`README.ja.md` 或其它配置语言时，它们是本次要创建的完整交付物，不是省略入口或判定 profile 不适用的依据。每份语言页来自同一公开事实、入口台账和章节职责，不能把默认语言完整交付、其它语言只放标题或自动跳转。语言中性的共用 hero 可以复用；包含正文语言的 hero 必须分别交付并验证。

首屏顺序默认是：项目身份或 hero、语言与项目导航、个人入口、仓库状态、一句公开定义和第一个采用章节。语言组后可以用竖线追加文档、贡献和反馈，并逐项确定目标：文档读取当前项目的活动说明，由调用方通过正式项目导航参数交给生成器；贡献固定读取独立贡献指南；反馈读取已启用的正式渠道。完整优化发现贡献指南缺失时，新增一份与当前项目规则一致的简洁 `CONTRIBUTING.md`，不把内部方法复制进去。文档或反馈目标不成立时只省略并报告该入口，不生成占位页，也不能因此移除已经交付的语言、贡献、个人入口或仓库状态。

profile 的适用性只由目标 owner、目标项目的正式配置和用户明确要求决定，不由某个配置文件当前是否存在决定。项目已有首屏合同时只覆盖职责相同的组；例如项目自有语言合同不能顺带禁用 profile 的个人入口。新增根目录语言页或贡献指南前，检查目标仓库的文档分类、链接检查和 CI 路由；这些正式消费者若只认识原有文件，应在同一 README 任务中迁移到新文件集合，不能把消费者尚未更新作为放弃交付的理由。

## 5. 许可证、Star History 与仓库元数据

许可证存在时读取 `license-governance.md` 核对 SPDX、范围、第三方声明、README 摘要和 GitHub 识别；准确时保持现有许可证，不为了完成清单重复生成。许可证缺失、范围不明或需要重新授权时，先完成权利和目标方案，按许可证路径的确认边界实施。

公开 GitHub 仓库要求 Star History 时读取 `github-star-history.md` 和 `repository-publication.md`。本地调用器、远端工作流、API 星标数、输出分支、亮暗 SVG、raw 地址和 README `picture` 是一个连续链；任一层尚未成立时只报告准确阶段。零星标仓库可以生成真实的零基线，不能伪造曲线或用示例图冒充生产结果。

About 描述和 topics 只有用户明确要求仓库元数据也属于本次交付时才修改。描述用一句公开定义，topics 使用项目当前身份和实际能力，不用流行标签补造宿主专属身份。Release、CI、下载、Discussions 或贡献徽章只有对应生产者和点击目标真实存在、且会改变采用判断时才建议或加入。

## 6. 验证和发布

先为每项承诺绑定正式消费者：

| 承诺 | 最少证据 |
| --- | --- |
| 仓库准备 | 准确 Git 根、状态、分支、远端与默认分支 |
| 正文 | 公开读者合同、主要入口、删除测试与正文密度检查 |
| 视觉 | 实际打开的目标素材，以及 900px、360px、深浅主题观察 |
| 多语言 | 每个真实文件的完整章节、互链与正式 header 校验 |
| 项目导航 | 文档、贡献和反馈各自的真实目标、职责与可达结果 |
| 许可证 | 正式文本、范围说明、README 链接与 GitHub 识别 |
| Star History | 工作流成功、API 数量、输出分支、两个 raw SVG 和 README 消费 |
| About/topics | GitHub API 回读的准确描述和 topic 集合 |
| 发布 | 获准提交树、推送结果、远端 HEAD 与关键 blob |

视觉验收必须实际打开或渲染最终候选；脚本成功、SVG 能解析、文件存在或 alt text 正确只证明结构层。远程图片和徽章需要直接检查 HTTP 结果，GitHub 首页需要核对最终页面读取的是准备发布的同一文件。

README、许可证和纯仓库元数据不触发无关产品端到端测试。路由、脚本或公共测试合同发生变化时先运行目标测试；跨越多个活动消费者或目标测试暴露系统性影响时运行完整回归。关键测试先通过正式收集入口确认身份唯一。

发布消费 `repository-publication.md`。只暂存本次确认的依赖闭包；推送前重新读取远端分支，推送后核对远端 HEAD。Star History 需要远端工作流时，提交和推送只是中间状态，必须继续到远端图表和 README 消费成立。创建远端、改变可见性、强制推送、删除和来源不明的工作树变化不随 README 优化自动获得授权。

## 7. 交付报告

完成后按同一账本报告：

```text
仓库与发布状态：
README 动作与三层读者路径：
视觉与材料资格：
语言、项目导航、个人入口与仓库状态：
许可证与第三方范围：
Star History 生产和消费状态：
About、topics 与其它仓库元数据：
本地检查、实际渲染与远端证据：
未执行、不适用或受阻的事项：
```

只有各项分别取得对应证据后才说“完整优化完成”。某个外部环节受阻时保留其它已成立结果，并准确停在本地、提交、推送、工作流、raw 文件或 GitHub 渲染层。
