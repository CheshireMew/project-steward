# README 完整交付

用于用户要求“优化 README”“重写仓库主页”或交付完整 GitHub 首页时，把仓库准备、正文、视觉、多语言、许可证、Star History、GitHub Topics、验证和已有远端发布组织成一个结果。它只拥有编排顺序、结果账本、适用条件和停止位置；正文取舍、视觉方法、许可证选择、Star History 生成与仓库发布继续由各自 reference 唯一维护。

只问 README 现状、原因或建议时建立同一账本但保持只读。用户明确要求优化、重写、创建或完整处理 README 时，才执行账本中已经成立的写入动作。

## 1. 先冻结完整交付账本

在评价正文或生成素材前记录：

```text
准确项目根与上层 Git 边界：
当前是否已经初始化 Git：
工作区、索引、分支与并发变化：
远端所有者、仓库名、默认分支与可见性：
README 是否存在、当前动作与活动语言：
项目身份、第一采用读者与第一次成功入口：
宿主依赖证据、宿主中立结论与公开身份排除项：
公开安装入口、已验证的最短命令与实际安装验证等级：
项目活动真源与图片排除边界：
Logo 正式生产者、现有消费端、复用 / 派生 / 新建设计结论：
个人 profile 是否适用：
许可证文件、GitHub 识别与权利边界：
Star History 生产者、输出分支、raw 文件与消费端：
GitHub Topics 当前集合、项目事实依据与目标集合：
GitHub About、Issues、Discussions 与 Release 事实：
本次允许的本地写入、提交、推送和远端元数据动作：
需要单独确认的创建远端、可见性、删除、强推或法律选择：
最终停止位置：
```

检查目录是否位于父级 Git 工作树中；不能因为当前目录没有 `.git` 就创建嵌套仓库。用户要求完整优化且准确项目根尚未初始化时，只有当前请求明确包含初始化结果才进入 `repository-publication.md` 的初始化路径；否则报告缺口，不把“检查是否初始化”改写成未经授权的 `git init`。

README 不存在时选择新写；存在但读者路径、项目身份或公开事实错误时选择重写；事实正确但顺序和职责错误时选择重组；主要问题是重复与密度时选择压缩。一次交付只保留一个最终动作，不在新页面后面继续维护旧结构或兼容段落。

## 2. 完整优化的默认结果

用户明确要求 Project Steward 优化一个 README 时，默认结果不是只改几段文字，而是：

1. 仓库边界、README、公开身份和发布条件已经核对。
2. 第一采用读者能在首屏知道项目是什么、何时需要、交给它什么、会得到什么以及下一步做什么。
3. 项目存在公开安装入口时，`repository-publication.md` 已确认真实分发渠道和最短命令，并自动写入全部活动语言 README；命令存在与实际安装成功按真实证据分别说明。
4. 正文按采用、第一次成功和维护深入分层，没有把内部方法库复制成首页长文。
5. 正文和视觉概念只来自当前项目活动真源；判断 Logo 缺失前已经先调查代码、配置、正式资源声明与消费端。设计和写作不打开、查看、渲染、OCR、取色或分析任何图片，图片、链接和徽章只做结构、可达性与消费链校验。
6. profile 适用时，配置的完整语言页和贡献指南已经交付，项目导航、个人入口和仓库状态通过正式生成器进入每份 README；文档、贡献和反馈分别抵达真实且职责不同的目标，单个项目专属入口不成立时不影响其它组。
7. 许可证存在且范围准确；缺失时完成权利与采用目标判断，再按许可证方法要求取得具体方案确认并应用。
8. 现有公开 GitHub 仓库的完整 README 优化默认包含 Star History；正式生产链已经生成输出并被 README 消费，而不是只写了一份 YAML 或示例链接。
9. 公开 GitHub 仓库的 Topics 已经从项目当前身份、主要用户结果和真实能力生成最终集合；获得远端发布权限时写入并回读，而不是复制另一个仓库的标签。
10. 本地审计、素材结构和远端消费者分别取得证据；已有远端且本次确认包含发布时，精确提交、推送并核对远端结果。

用户只指出正文不说人话、术语太多、顺序难懂或看不出用途时，只改变正文的写作与验收。已经纳入完整优化的语言页、贡献指南、个人入口、仓库状态、许可证、Star History 和 GitHub Topics 继续作为同一个结果完成，除非用户明确退出其中某项；不能把对正文的纠正解释为把其它交付改成按需。

仓库不是 GitHub 项目、为私有仓库或没有现有远端时，不生成伪造徽章、空链接或假远端结果，并把依赖公开 GitHub 的交付标为不适用。目标是现有公开 GitHub 仓库但缺少权限、Actions 不可用或推送失败时，该项是受阻而不是可省略；工作流已派发但远端消费者尚未成立时标为异步未验证并停止，不等待它改变状态。其余仍能独立成立的 README 结果继续完成。

## 3. 正文不再充当活动方法镜像

README 是公开采用页面，不是 `SKILL.md`、reference、测试或变更日志的合并副本。内部治理能力新增、修正或细化，本身不构成修改 README 的理由。只有它改变了项目公开身份、第一采用读者、可执行入口、第一次成功、适用边界、维护入口或读者需要看到的证据时，才更新对应页面位置。

写作读取 `content-architecture.md`，并执行以下退出条件：

- 每项内部机制只有正式方法所有者和测试消费者，README 不成为第二个逐条消费者。
- 首页用少量稳定类别和真实请求入口概括能力；完整内部条件链接到 `SKILL.md` 或专项 reference，不改写成连续说明段落。
- 每个段落必须改变理解、信任、选择、操作或下一步；删除后无影响的文字退出。
- 同一节连续出现多段普通正文时，优先改成关系清楚的列表、请求示例、步骤、短表格或链接，而不是继续追加转折句。
- 自我进化的确定性测试验证活动所有者与路由，不要求新规则原文同时出现在 README。
- README 的测试只保护项目身份、读者路径、主要入口、许可证与致谢、公开素材、语言、状态区和维护导航等公开合同。

项目希望保留完整能力目录时，使用已有活动文档或新增有明确维护者入口的专项文档；README 只提供必要上下文和链接。不能用折叠块或 HTML 注释藏起一份仍被测试强制维护的第二套方法库。

## 4. 内容、视觉与多语言顺序

完整交付按固定顺序消费：

1. `content-architecture.md` 建立公开读者合同、入口台账、材料预算和最终章节职责。
2. 完整优化或涉及 Logo、hero 时，先冻结“项目是唯一真源、图片内容全部排除”的输入边界，再由 `visual-direction.md` 完成代码优先的正式身份源调查；没有这份结论不得判断 Logo 缺失或开始新设计。需要表达性视觉时再读取 `project-native-hero.md` 和 `github-readme-canvas.md`，素材制作只消费已经冻结的身份源结论、项目语义与几何合同。
3. 目标 owner 命中 `assets/readme-profile/profile.json` 时，由 `scripts/readme_header.py` 从项目名称、本地化一句公开定义、合格 Logo、真实语言文件、明确解析的项目导航目标、仓库身份和许可证文件生成完整首屏；不能临时改写内存中的 profile 绕过项目差异。
4. `scripts/audit_readme.py` 检查本地图片引用、SVG 结构、header、正文密度、明确传入的公开身份排除项，以及 Star History 是否位于许可证和第三方致谢之前；宿主中立项目把 `content-architecture.md` 核定的每个排除项用 `--forbid-public-term` 传给全部活动语言，不能只检查默认语言。审计器不替代宿主依赖事实核对、远程端点或素材结构检查，也不授权打开图片。

整页新写、重写或完整优化个人仓库时，同一 profile 中配置的语言属于同一个交付结果。缺少 `README.en.md`、`README.ja.md` 或其它配置语言时，它们是本次要创建的完整交付物，不是省略入口或判定 profile 不适用的依据。每份语言页来自同一公开事实、入口台账和章节职责，不能把默认语言完整交付、其它语言只放标题或自动跳转。同一份由项目事实生成的语言中性 hero 可以被多页引用；包含正文语言的 hero 必须分别交付并进行结构与消费链验证，不能通过查看图片来决定翻译或版式。

安装段落消费 `repository-publication.md` 已确认的公开分发身份和最短命令，不在 README 路径重新猜测包名或选择另一渠道。同一安装入口在全部活动语言页面保持命令完全一致，只翻译周围说明；不同平台确有不同命令时保留相同的平台边界和顺序。更新安装段落不自动触发整页重写，也不能覆盖其它正文、视觉、许可证或维护入口。

首屏固定顺序是：Logo、项目名称、一句普通读者能看懂的本地化介绍、语言与项目导航、个人入口、仓库状态，然后才进入第一个采用章节。Logo 是管理区中的第一个图片节点，必须是紧凑的项目标志或字标；全宽 hero、机制图、结果图和展示图不能作为 `identity_image` 传给生成器，`identity_image_width` 只接受 `1–480` 的整数。表达性视觉在完整首屏管理区和正向项目定义之后出现；如果它解释某个具体章节，就紧跟该章节的引入文字，不能抢在身份链之前。项目名称和一句话介绍必须保留为可选择、可翻译的 HTML 文本，不能只烘焙在图片里。语言组后用竖线追加文档、贡献和反馈，并逐项确定目标：文档读取当前项目的活动说明，由调用方通过正式项目导航参数交给生成器；贡献固定读取独立贡献指南；反馈读取已启用的正式渠道。

完整优化不是整理旧 README 已有内容，而是交付完整公开入口。旧页面缺少 Logo、名称、一句话介绍、配置语言页、活动文档入口、独立贡献指南、正式反馈入口、适用于 owner 的个人入口或目标仓库 Stars、Forks、许可证状态时，从项目事实、活动文件和正式 profile 补齐对应生产者与成品。找不到名为 logo 的文件、README 尚未引用图片或素材目录为空，都不能证明 Logo 缺失；必须先消费 `visual-direction.md` 返回的正式身份源结论。代码或配置已经定义标志时优先复用或确定性派生并建立同步验证，只有确认不存在正式生产者和可用消费端后才从项目事实新建设计。完整优化发现贡献指南缺失时，新增一份与当前项目规则一致的简洁 `CONTRIBUTING.md`，不把内部方法复制进去。只有仓库类型、反馈能力、许可证范围或 profile 适用性等目标事实本身不成立时，才省略对应入口并报告原因；不能因为旧 README 没写、旧素材不存在或消费者尚未更新就继续交付残缺首屏。

profile 的适用性只由目标 owner、目标项目的正式配置和用户明确要求决定，不由某个配置文件当前是否存在决定。项目已有首屏合同时只覆盖职责相同的组；例如项目自有语言合同不能顺带禁用 profile 的个人入口。新增根目录语言页或贡献指南前，检查目标仓库的文档分类、链接检查和 CI 路由；这些正式消费者若只认识原有文件，应在同一 README 任务中迁移到新文件集合，不能把消费者尚未更新作为放弃交付的理由。

## 5. 许可证、Star History 与仓库元数据

许可证存在时读取 `license-governance.md` 核对 SPDX、范围、第三方声明、README 摘要和 GitHub 识别；准确时保持现有许可证，不为了完成清单重复生成。许可证缺失、范围不明或需要重新授权时，先完成权利和目标方案，按许可证路径的确认边界实施。

Star History 是现有公开 GitHub 仓库完整 README 优化的默认交付项，自动读取 `github-star-history.md` 和 `repository-publication.md`，不等待第二次专项请求。只有用户明确退出，或目标客观上不是 GitHub 仓库、不是公开仓库、没有现有远端时才不适用；权限、Actions 或推送失败只能标为受阻，不能静默省略。本地调用器、远端工作流、API 星标数、输出分支、亮暗 SVG、raw 地址和 README `picture` 是一个连续链，但普通实施在工作流派发成功后停止并把后续层标为异步未验证；只有用户另行要求远端验收时才读取已经完成的链路。零星标仓库可以生成真实的零基线，不能伪造曲线或用示例图冒充生产结果。

README 包含 Star History 时，该章节必须位于许可证和第三方致谢章节之前；许可证与致谢可以合并或分开，但继续作为页面末尾的法律与来源边界。全部活动语言保持同一职责顺序。只有上段明确的不适用情形不生成章节；受阻时保留准确的未完成状态，不写空章节、示例图或必然失效的 raw 地址。

Topics 是公开 GitHub 仓库完整 README 优化的默认交付项。先从当前仓库的公开定义、第一采用读者、主要用户结果、真实输入输出、稳定技术生态和活动文件建立最终集合；现有准确 Topics 可以保留，已经失真或只属于旧身份的 Topics 必须退出。不能从个人 profile、流行标签或另一个仓库复制集合，也不能因为 Project Steward 被调用就添加 Project Steward、Codex 或其它宿主标签。`codex` 只有在 Codex 确实是项目当前公开的主要运行载体、安装入口或目标读者入口时才成立；`agent-skill` 等类别标签也必须由项目本体证明。

只读审计先运行 `python scripts/github_topics.py inspect --repository OWNER/REPOSITORY`，报告当前集合、默认分支 HEAD、目标集合和逐项事实依据；用户明确要求只改本地时，在交付报告中保留拟写入集合但不改变远端。工具只拥有仓库身份、并发保护、GitHub API 替换、回读和首页可见性验证；它不从 README 热词、仓库名或流行集合猜 Topics。项目事实到最终集合的语义判断只由本节拥有，调用方必须把已经核定的完整集合逐项传入 `--topic`。

用户要求优化、重写或完整处理 README，目标又是已有公开 GitHub 仓库且没有排除远端发布时，Topics 随同一完整交付自动写入，不再要求第二次专项确认。远端 README 身份提交完成后，先用 inspect 取得新鲜默认分支 HEAD，再运行 `python scripts/github_topics.py apply --repository OWNER/REPOSITORY --expected-head FULL_SHA --topic TOPIC ...`。apply 只在 HEAD、公开可见性和写入权限仍成立时通过 GitHub API 一次替换；随后重新读取仓库身份、HEAD 和准确 Topics，并从 GitHub 仓库主页 HTML 回读同一集合。只有命令成功返回 `api_verified`、`homepage_verified` 和 `verified` 均为 `true`，最终集合与逐项事实依据完整，才能关闭 Topics 交付项。不能用规则文字、测试中的预期集合、一次 PUT 成功或消费端手写结果代替该工具的真实输出。

仓库非公开、不是 GitHub 仓库、没有现有远端、缺少权限、远端发生并发变化，或者 API 与主页结果仍不一致时停在准确边界，其余 README 结果继续完成。Topics 工具失败后不得改用另一段临时 API 命令制造完成证据；先按它报告的身份、权限、并发、API 或主页层修复同一正式入口，再重新执行。

About 描述只有用户明确要求仓库描述也属于本次交付时才修改，并使用一句公开定义。Release、CI、下载、Discussions 或贡献徽章只有对应生产者和点击目标真实存在、且会改变采用判断时才建议或加入。

## 6. 验证和发布

先为每项承诺绑定正式消费者：

| 承诺 | 最少证据 |
| --- | --- |
| 仓库准备 | 准确 Git 根、状态、分支、远端与默认分支 |
| 公开安装入口 | 正式分发渠道的只读发现结果、全部活动语言 README 中一致的代码块；获得安装授权时再增加隔离环境的实际安装结果 |
| 正文 | 公开读者合同、主要入口、删除测试、正文密度检查；宿主中立时增加全部活动语言的公开身份排除审计 |
| 视觉 | 项目事实、语义概念、几何合同、素材源码结构、README 引用和远端消费的是同一候选；明确记录未进行人工画面判断 |
| 多语言 | 每个真实文件的完整章节、互链与正式 header 校验 |
| 项目导航 | 文档、贡献和反馈各自的真实目标、职责与可达结果 |
| 许可证 | 正式文本、范围说明、README 链接与 GitHub 识别 |
| Star History | 实施任务证明提交、推送与工作流派发；独立远端验收才证明 API 数量、输出分支、两个 raw SVG 和 README 消费 |
| GitHub Topics | 项目事实到最终集合的逐项对应、`scripts/github_topics.py apply` 的成功 JSON、GitHub API 准确回读、同一默认分支 HEAD 与仓库首页可见结果 |
| About 与其它元数据 | 用户明确纳入时，GitHub API 回读的准确描述或目标状态 |
| 发布 | 获准提交树、推送结果、远端 HEAD 与关键 blob |

视觉验收不得打开、查看、截图或渲染最终候选。SVG 通过 XML、`viewBox`、无障碍说明、元素与引用安全、几何边界和源码合同检查；栅格素材只检查格式、尺寸、内容身份和引用链。远程图片与徽章只核对 HTTP 状态、内容类型和内容身份，GitHub 首页只核对最终页面引用的是准备发布的同一文件。结构与消费链通过不能写成美观、清晰、对比度合格或主题适配；报告必须明确没有进行人工画面判断。

README、许可证和纯仓库元数据不触发无关产品端到端测试。路由、脚本或公共测试合同发生变化时先运行目标测试；跨越多个活动消费者或目标测试暴露系统性影响时运行完整回归。关键测试先通过正式收集入口确认身份唯一。

发布消费 `repository-publication.md`。只暂存本次确认的依赖闭包；推送前重新读取远端分支，推送成功后停止。Star History 需要远端工作流时，实施任务在派发后停止，把远端图表和 README 消费留给用户明确启动的后续验收。Topics 在推送前通过 `scripts/github_topics.py apply` 写入时，工具返回的 HEAD 和 API 集合进入交付账本；GitHub 首页刷新不保持任务等待。创建远端、改变可见性、强制推送、删除和来源不明的工作树变化不随 README 优化自动获得授权。
