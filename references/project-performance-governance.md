# 项目性能治理

用于项目综合审计中的“性能、资源与规模”维度。它负责生成完整检查范围、把用户结果映射到阶段、规模、资源和生命周期，识别跨边界工作放大，并规定性能修复怎样闭环。`hard-to-reproduce-diagnostics.md` 继续唯一负责竞争解释、区分实验、资源趋势和昂贵完整链；本方法不复制它的诊断流程，也不因发现性能风险自动获得项目写入、长时运行、安装依赖或改变用户数据的权限。

## 1. 先冻结性能合同和动作边界

只有持续运行、处理数据、存在实时或交互截止时间、使用昂贵资源，或者已经作出性能承诺的项目才适用。纯静态内容、没有运行时消费者且没有性能承诺的仓库可以标为不适用；缺少运行环境、依赖或代表性数据只会让验证深度停在静态审查或待运行验证，不能把适用维度改成不适用。

开始时记录：

```text
项目根、版本、工作树和正式运行入口：
用户要完成的结果，以及等待、卡顿、丢帧或资源占用怎样影响它：
已有延迟、吞吐、容量、实时截止时间或资源预算及其权威来源：
正式生产者 → 队列、存储、进程或设备边界 → 正式消费者 → 用户结果：
当前平台、硬件、运行时、模型、后端、数据根和缓存状态：
允许的静态检查、短探针、完整运行、长时运行和外部系统动作：
明确不得改变的用户数据、配置、数据库、缓存、设备与外部状态：
将产生的日志、profile、夹具和其它证据及其保留位置：
当前未知项和停止位置：
```

只读性能审计不能借“需要测量”改变项目状态。普通应用构造器、数据库封装或服务启动会自动迁移 schema、写运行缓存、创建任务、更新最近使用记录或改写配置时，不得把它直接指向用户真实数据根。优先使用项目正式只读模式、数据库只读连接、隔离数据根或经过内容身份核对的副本；复制、迁移、预热、生成大型夹具和连接真实设备或服务仍分别服从当前权限。测试需要清理证据时提前取得删除授权；没有授权就保留准确路径和责任，不用运行授权补造删除权限。

## 2. 建立阶段、规模和生命周期覆盖矩阵

先从正式功能、入口、后台任务、界面表面、持久状态和外部能力建立工作负载清单，再为每项适用结果组合以下维度。不能从已经发现的热点反推范围，也不能以一条 benchmark 代表整个产品。

| 维度 | 至少区分的状态 | 主要问题 |
| --- | --- | --- |
| 初始化阶段 | 新鲜进程、冷缓存、首次可用、惰性初始化或预热、后续热运行 | 启动成本被移到哪里，首次真实用户结果是否仍承担它 |
| 活动程度 | 空闲、正常活动、持续活动、突发输入、过载、解除压力后的恢复 | 常驻资源是否合理，输入超过消费能力时怎样降级和恢复 |
| 规模 | 普通输入、代表性大输入、大量对象或事件、长项目、长时间运行 | 单次成本是否随数量、内容或时间放大，增长是否有界 |
| 重复与并发 | 第一次与后续、单任务与批量、串行与并发、同资源竞争 | 缓存和复用是否真实命中，共享资源是否被重复创建或争用 |
| 生命周期 | 成功、失败、取消、重试、模型或配置切换、页面离开、关闭、重启恢复 | 每条路径是否停止生产、排空终态并释放资源 |
| 平台与后端 | 当前目标平台、实际 CPU/GPU、真实编解码器、provider 或外部进程 | 自动选择是否改变比较对象，结论是否只对准确环境成立 |

每个矩阵单元记录正式入口、代表性输入身份、期望用户结果、预算或截止时间、允许保留的资源、需要观察的指标和当前证据等级。只有会改变识别、测量、动作或验收的组合才单列；不为形式完整运行全排列。静态审查可以完成清单和风险分析，但没有新鲜运行证据时不得声称速度、吞吐、泄漏或真实硬件表现已经成立。

同一功能表面还要按会改变成本拓扑的操作形状拆分。属性原地修改、集合成员增加或删除、拆分或合并、重排或涟漪更新、关系变化和二级投影更新如果经过不同的生产者、提交边界或消费者，就各选择至少一个代表性操作；一个廉价操作通过不能代表这些结构操作。只有能够证明多个操作消费同一闭合变更集并产生同一种工作放大时才合并测量，不能用功能名称或共同界面入口替代这份证明。

冷、热和预热必须使用可区分的状态身份。新鲜进程不继承前一次的模块、线程、GPU 上下文、连接池、模型、页面、缓存或数据游标；热运行则明确列出允许复用的对象。空闲基线在首次可用之后取得，并说明是否已经打开默认页面、加载隐藏组件或执行自动预热。预热后的平台保持量、驱动保留或可回收缓存不能仅因没有回落到进程启动值就叫泄漏；只有稳态之后随次数或时间继续增长，并能关联到未释放所有者时，才升级为泄漏或无界增长。

## 3. 沿完整用户链计算工作放大

为核心结果建立端到端放大账本：

```text
阶段或边界：
输入对象、字节、事件或请求数量：
生产速率与触发频率：
本阶段每单位执行的查询、写入、复制、哈希、解码、序列化、推理或进程启动次数：
下游消费者数量和实际需要的投影：
队列、缓冲或持久积压的当前值与硬上界：
代表性单次成本 × 实际次数：
阻塞、丢弃、合并、重试或恢复的位置：
用户最终看到的延迟、吞吐与结果：
```

平均单次操作很快不表示系统成本低。每文件启动一个进程或加载一次模型、每条进度写数据库、每个事件重新读取完整任务、每个扫描项查询一次取消状态、每次预览重新哈希或解码完整媒体，都要乘以真实文件数、事件数、消费者数和触发频率。轮询间隔短于一次最坏扫描耗时时会自然形成重入或永久积压；只看到循环写成异步或放入线程池不能证明成本已经消失。

队列必须按完整生产链逐层枚举：操作系统或原生事件队列、回调缓冲、应用队列、线程池或执行器内部等待队列、按键合并映射、generation 或游标表、持久任务表、进程管道和界面请求协调器都可能分别无界。每层记录容量、生产和消费速率、满载策略、不可丢终态、可合并或可丢遥测、取消和关闭排空、解除压力后的恢复。某一层设置长度上限不能替其它层背书；以“最新值覆盖旧值”降级时，还要证明最终权威状态能通过快照或协调扫描恢复。

事件、进度、心跳和状态同步同时检查读放大与写放大。高频遥测可以按时间、数值变化和阶段变化合并，但权威终态不能丢失；取消检查应消费操作所有者的内存信号或其它有界边界，而不是在内层循环重复访问持久存储。批量状态同步优先从权威候选集合一次取得当前状态，只写真正变化的记录；界面优先消费事件本身能够证明的投影，只有终态、未知对象或合同要求时才重新取得完整聚合。

## 4. 按真实表面检查性能所有权

### 启动、导入和界面生命周期

- 从正式启动入口检查模块导入图、服务构造、数据库打开、迁移、默认页面、隐藏控件、媒体绑定、导航回调和完成回调。重型数值、媒体、模型或硬件库应由真实使用边界加载；惰性加载要把成本归到首次实际使用，不能从启动统计中消失后就当成已优化。
- 不可见不等于未实例化。隐藏播放器、预览器、面板和已经建立的绑定仍可能读取文件、解码媒体、订阅事件或创建昂贵运行时。只有明确的物化条件和销毁或复用合同才能证明它们不会在启动或无关页面活动。
- 自动预热要有用户收益、资源所有者、保留时间、页面离开和资源争用合同。预热模型不自动授权打开麦克风、摄像头、音频流、远程会话或正式处理输入；空闲释放后再次使用的恢复成本也进入矩阵。

### 批处理、数据库和后台循环

- 盘点定时扫描、恢复扫描、目录监听、索引、维护、同步和心跳循环。分别比较触发周期、最坏执行时间、重复遍历范围、每项数据库或网络访问、变化为空时的写入，以及服务空闲时是否仍持续工作。
- 数据库检查以正式查询的真实谓词、排序、连接和代表性数据量为准。取得实际查询计划，证明目标索引被选择且没有不必要的全表扫描、临时排序或重复查询；索引存在但未被使用不算修复。新增索引还要检查写入成本、重复索引和迁移影响，不能为一个读路径无限增加写放大。
- 原生文件事件、消息订阅或增量游标可以减少全量轮询，但必须有有界事件队列、溢出信号、去重或稳定期、关闭释放和低频权威协调扫描。事件化不是取消最终一致性，也不能把系统队列的无界增长移进应用。

### 模型、外部进程和共享昂贵资源

- 逐项记录进程、模型、GPU 上下文、解码器、连接池和设备会话的创建者、复用身份、切换条件、串行或并发限制、空闲释放、取消、崩溃恢复和关闭。逐项输入重新启动同一进程或加载同一模型时，计算固定启动成本怎样乘以批量规模。
- 常驻 worker 或模型复用必须有稳定协议和结果通道，不能从日志或 stdout 最后一行猜业务结果。模型切换、取消杀死进程、旧读取器迟到、进程崩溃和服务关闭分别验证；旧代结果不得进入新代任务，退出后核对孤儿进程和占用资源。
- 离线任务、实时任务和后台预热共享 GPU、provider、设备或排他执行槽时，明确准入、前台优先、暂停或释放、超时所有权和恢复调度。设置取消标志或创建前台线程不能证明资源已经交接。

### 实时回调和截止时间

- 音频、视频、输入、渲染或其它实时回调只承担有明确上界的搬运与状态更新。模型推理、媒体解码、文件或网络访问、数据库操作、进程启动、阻塞锁和随输入增长的内存分配不得隐藏在回调中；需要异步执行时使用预分配或有界缓冲，并定义满载时阻塞、丢弃旧输入、保留最新输入或降级的产品语义。
- 分别测量回调占用时间、排队等待、模型或处理耗时、输出提交和端到端用户延迟，并与真实块长、帧周期或交互截止时间比较。推理低于一个截止时间不能证明回调安全，回调很短也不能证明最终声音、画面或控制结果没有整体落后。
- 预热必须经过真实模型或后端路径，并和正式活动流隔离。启动流、设备打开或预热失败时也要释放已经取得的线程、缓冲、设备和模型租约；正常短跑不能替失败、过载和关闭路径背书。

### 数据、缓存、媒体和网络

- 为哈希、探测、解码、转换、序列化、上传和下载记录内容身份、物理对象、执行次数和正式消费者。另一个阶段已经完整解码或验证同一不可变内容时，可以让后续消费者复用带完整身份的回执；只知道路径、大小和修改时间不能证明内容相同。
- 缓存优化先冻结信任边界。新取得的外部输入、模型执行快照、运行时检查、发布或导入边界，以及内容允许原地改变的对象，需要按项目合同取得新鲜内容证明；同一任务内部、已经原子发布且不可变的对象可以复用。基于元数据的快速身份缓存只能加速候选选择，不能在元数据可伪造或粒度不足时冒充内容证明。
- 网络连接池、服务发现缓存和批量请求只有在身份、认证、过期、错误恢复与关闭合同成立时才复用。减少握手次数不能用过期端点、跨账号连接或吞掉失败换取。

### 资源趋势和关闭

同时观察 CPU、工作集与私有或提交内存、GPU 显存、线程、进程、句柄、连接、文件描述符、队列深度、磁盘与网络 I/O、数据库读写次数、缓存和临时目录体积。平台可见指标含义不同就分别报告，不能只用一个“内存”数字概括物理驻留、虚拟提交和设备保留。

由外部进程、worker、浏览器、编解码器或执行器共同交付结果时，资源账本按本轮拥有的完整进程树核算根进程、子进程和全部后代，不能用父进程工作集、配置的 worker 数或单进程估算替代。分别记录共享池或常驻服务基线、单任务增量、任务执行峰值、任务结束后的保留量、空闲回收后的稳定水平，以及正式关闭后的释放；共享进程只在一个所有者下计入一次。无法从启动记录、父子关系、所有权登记或其它权威来源证明进程归属时，相应资源总量保持未知，不能漏算脚本宿主、浏览器或媒体子进程，也不能把机器上的无关进程并入结果。

关闭顺序从停止生产者开始，再阻止新请求、取消或排空活动操作、提交不可丢终态、释放设备和进程，最后关闭执行器、数据库和事件分发。任何请求入口在执行器或服务关闭后仍能自动重启、提交新工作或写状态，说明关闭链尚未成立。成功、失败、取消、重试耗尽、页面离开、应用关闭和再次启动都检查相同资源所有者；超时只说明等待没有完成，不能把所有权改写为已经释放。

## 5. 建立可比较的测量证据

性能记录至少绑定代码或提交身份、配置、输入内容身份、当前平台和硬件、实际后端、进程与缓存状态、数据根、采样阶段、运行次数、统计方法和最终消费者。比较前只改变当前要判断的一个变量；冷与热、同步与异步、标准与高速路径、不同后端或不同模型不能混在一个百分比里。报告绝对值和同机相对变化，不能只写“提升若干倍”。

验收门槛与性能评价分开记录。权威预算被超过时是合同失败；预算内只证明该项门禁成立，不能自动推出整体性能健康。结果虽然在阈值内，但用户仍能感知等待、尾部延迟明显、余量很小，或者规模增长趋势会在代表性边界内很快耗尽预算时，把它报告为体验风险或优化候选，并同时写清门禁仍然通过，不能把风险改写成合同失败。没有权威预算时，保留实测事实、比较基线、用户影响假设和待确认的产品判断，不用个人体感把它宣告为缺陷，也不能用一个宽松阈值关闭已经存在的用户影响证据。

自动并发策略以已经声明的用户结果为选择目标，不能以 worker 数、平均利用率或总吞吐单独决定。对代表性规模同时记录总耗时、尾部延迟、启动与收尾固定成本、每个执行单元的实际利用和正式消费者结果。共享机器噪声较大时，可以让候选与标准路径在同一轮使用相同输入、后端和缓存条件，并同时要求独立的绝对安全上限与同机相对不退化；相对改善不能关闭已经超过的用户预算，两边都慢时正常容量仍保持未知或失败。

预算、历史回归界限和同机相对判据在候选运行前分别冻结并记录权威来源。候选失败后改变阈值，必须先把变化归类为产品合同改变还是验证器合同修正，保留原失败，再从新鲜可比条件重新运行；不能让已经看见的候选数字反向成为它自己的通过标准。

性能优化和容量合同变化必须分账。只有正式入口继续接受相同的代表性输入，并向正式消费者交付相同完整性、新鲜度和用户结果时，更低的延迟、资源或工作量才能记为原性能合同下的优化。缩小允许输入规模、降低原有容量上限、降低合同保证的结果完整性或新鲜度、减少合同保证的刷新频率，或者拒绝此前合法输入，只能形成容量限制、降级或产品合同变化，不能被记为性能优化。确实需要这些变化时，先由产品合同的权威来源确认新的输入范围、满载或降级语义、正式消费者和用户结果，再把原发现明确重新分类或经用户同意退出旧范围，并分别验证新合同成立和新合同下的性能；没有这项确认时，原性能发现仍然开放，较小工作负载下的更快数字只证明较小边界。

每项优化在写入前先把根因假设连接到一个能够直接观察的工作量，例如查询、哈希、复制、构造、序列化、缓存未命中、进程启动或传输字节次数，并记录它预计改变的测量边界。写入后先用同一正式入口、输入身份和冷、热或命中状态复测这项直接工作量及对应用户延迟，再运行宽泛回归；直接工作量没有按假设变化，或者延迟变化来自不同缓存、夹具、后端或消费者时，停止叠加优化，重新取得 profile 或查询计划并更新根因。不能用完整测试通过、其它热点变快或累计改动后的总时间替代这次因果核对。

指标名称必须对应真实测量边界。例如实时链分别称为回调时间、推理时间、排队时间和端到端延迟；服务启动、控制器构造、首个请求与首个用户可用结果也分别记录。平均值用于描述稳态，尾部、最大值、超限次数和资源斜率用于发现卡顿、过载和增长；一次最优结果不能代替代表性分布。

整套测试耗时只有在测试框架实际收集到的测试身份、参数化展开、夹具、并行方式、进程与缓存状态和测量边界一致时才能作性能比较。测试新增、删除、改名、改变选择范围或迁移执行路径后，本次套件结果只作为对应身份的正确性回归证据；即使总耗时下降，也不能据此声称产品或测试套件获得了性能提升。需要比较时冻结共同测试身份或建立独立代表性 benchmark，并分别报告未纳入比较的新增或退出测试。

运行实验前先用静态链、短探针和最小真实输入证明测量器读取了正确入口、对象和消费者。需要区分竞争原因、验证持续资源趋势、检查实时管线或运行昂贵完整链时，返回 `hard-to-reproduce-diagnostics.md`；需要大文件和长时日志时先消费 `production-storage-governance.md`。性能验证器改变缓存、迁移数据库、写全局运行状态、占用共享设备或留下后台任务时，先修复或隔离验证边界，不能把它造成的结果归到产品。

第一条计时前，列出本次审计启动的诊断、profile、扫描和发现进程并取得终态；递归产物发现使用已知证据根、正式清单、深度或数量上限，不启动无边界目录遍历。观测动作超时、外层停止等待或留下仍运行的自有进程树时，其重叠期间取得的全部性能数字失效，直到按准确所有权停止或隔离该进程树并重新核对资源。无法证明所有权的外部负载保持为独立环境变量，按 `hard-to-reproduce-diagnostics.md` 区分，不能擅自终止，也不能与审计自扰合并成产品结论。

## 6. 修复交接与二次性能复审

只读审计为每项发现分配稳定身份，记录原证据、用户影响、最早放大边界、建议所有者、验证条件和未知项。用户授权修复后，交给 `change-prevention.md` 与 `root-cause-remediation.md` 迁移唯一边界和全部调用点；本方法不直接把审计发现变成写入权限。

每项性能发现最终只能处于：**已解决 / 经新证据重新分类 / 经用户明确同意退出范围 / 受阻**。已解决至少需要：

1. 一个直接保护性能不变量的目标检查，例如队列有界、进度限频、没有启动时自动预热、查询计划选择目标索引、实时回调不执行重型工作、失败启动能够清理或关闭后没有孤儿进程；
2. 同一正式入口、代表性输入和当前目标平台上的用户链证据，证明优化后的生产者、边界、消费者和结果共同成立；
3. 正确性、取消、错误、恢复和资源所有权没有因提速退化；
4. 最后一次性能相关修改之后，从原性能覆盖矩阵重新生成一次二次性能复审。

二次性能复审专门检查修复本身是否新增了隐藏成本：新的原生或执行器队列是否无界，合并表或 generation 是否持续增长，驻留 worker 是否存在旧读取器和孤儿进程，事件限频是否丢终态，索引是否造成重复写入，缓存是否跨越信任边界，失败路径是否泄漏线程或设备，关闭后入口是否重启服务，以及验证器是否写入用户数据或全局缓存。发现同一根因下的新变体时并入原发现的迁移与验收；独立的新产品问题按综合审计权限另行登记，不能借“修复全部”无限扩张。

完整测试、静态检查或一次真实模型运行只能证明各自覆盖的层。结项从原发现账本逐项回读最后一次相关修改后的证据，不用累计测试数量、某个更快数字或其它发现的成功替开放项背书。

只读审计在覆盖矩阵、发现、证据等级和补证据入口完整后停止。静态风险不得写成已测性能，运行证据不得扩大到不同平台、模型或后端；没有用户可观察收益、资源预算或放大证据时，不为追求更小数字建议复杂优化。设计上有明确所有者、收益和释放策略的驻留资源不是自动缺陷，无法证明持续增长或用户影响时保留为待验证假设。
