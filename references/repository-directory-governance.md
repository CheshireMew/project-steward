# 项目目录治理

用于用户认为项目文件夹过多、想整理仓库根、询问哪些目录真实使用或已经过期，或者要求移动、归档、忽略、清理目录时。目标不是得到一次看起来更短的目录列表，而是让活动项目根只保留职责明确的内容，同时不破坏源码、运行数据、模型素材、开发工具和恢复能力。

## 1. 先冻结结果和权限

开始时分别记录：

```text
用户结果：解释现状 / 给出计划 / 整理 / 移动 / 归档 / 删除
检查根：用户要求盘点的准确目录
Git 根：检查根是否正好是仓库根，或位于另一个工作树中
活动消费者：构建、启动、测试、开发工具和人工制作流程
允许动作：只读检查、修改忽略规则、移动、归档、删除、提交、推送
停止位置：报告、待确认方案、本地完成或远端完成
```

这些动作分别授权。检查和计划保持只读；“整理一下”只覆盖用户已经看到并确认的准确处置方案，不能自动扩大为删除。删除文件或目录需要当前用户与项目规则允许，并在执行前列出准确目标。没有删除授权不等于获得归档授权；先保留准确候选，只有项目或用户确实要求历史保留时才提出归档，并在动作前说明归档位置、正式用途和 Git 影响。

开始盘点前保存当前根目录清单、Git 工作树与索引状态，以及本轮之外已经存在的修改。不能把用户原有改动、其它任务留下的变化或同步软件产生的文件归入本次清理，也不能用恢复命令把它们消掉。

### 任务产物按正式所有者和消费者归位

第一次写盘前先确定用户当前要求处理的准确项目根，再为本轮测试、生成、加工、验收和交付逐项记录正式生产者、正式消费者、路径所有者、保留期限和清理权限。需要临时根时消费 `change-prevention.md` 的受限执行路径合同，以正式消费者确定位置，不能由当前工作目录、下载目录、系统临时目录或某个碰巧可写的位置替代这项判断。

项目源码、交付物，以及项目测试、构建或正式项目工具会继续读取的夹具、快照、覆盖率、测试报告、staging、working copy 和中间文件，进入项目登记的受控源码、测试或运行根；没有合适目录时才在准确项目根内创建职责明确的子目录。生成的图片、音视频、代码、文档、重建或导出的工程和其它派生结果也按最终正式消费者归位，不能先散落到下载目录、全局工作目录或项目旁边的 `*-staging`、`*-output`，最后只把成品复制回来。

只被浏览器、调试器、执行器或机器环境消费的 profile、日志、桥接、截图、录像和诊断状态，可以进入用户确认的环境工具或临时根，不为了满足项目目录外观而迁回活动仓库或项目归档。已安装运行时、共享依赖缓存、由应用正式拥有并消费的用户数据继续按用户环境和产品合同管理；某次任务专用的对象必须记录本轮所有者和生命周期，不能只因位于共享根就冒充共享状态。无关项目不能因为可写而充当中转站。

启动生产者前，显式设置并核对工作目录、输出目录、临时目录和任务专用缓存最终采用的规范化真实路径。操作系统或外部工具强制写到预期根之外时，立即按正式消费者重新分类：项目消费者仍需要的对象迁入项目登记根并退出旧入口；环境消费者拥有的对象保留在已确认环境根并进入清理账本；没有正式所有者、消费者或可接受生命周期的对象使结果保持未完成，不能把“工具默认如此”当成例外。

用户提供且原本位于项目外的源文件可以继续留在原处；本轮创建的副本、修改版和派生结果仍按上述正式消费者归位。最终验收从本轮全部实际生产者重新生成产物清单，复查项目登记根、已知环境工作根和工具实际输出，证明项目外无所有者的任务产物为零，并且活动消费者不再引用错误旧路径。因缺少删除权限或宿主策略而保留的环境对象必须交付准确路径、生产者、所有者、清理状态和责任；它们不能被改称已经清理，也不能被塞进项目归档来制造零残留。只检查最终成品或只证明项目内存在副本，都不能关闭归位与残留账本。

## 2. 建立目录证据账本

在 Skill 根可用时，先运行只读盘点器：

```powershell
python scripts/inspect_project_tree.py <项目根>
```

目录很大且当前只需 Git 与结构证据时可以加 `--no-sizes`。脚本只报告物理目录、大小、文件数量、Git 跟踪与忽略现状，不判断目录是否正在使用，也不移动、归档或删除内容。

随后为每个需要处置的顶层路径补齐：

| 证据 | 要回答的问题 |
| --- | --- |
| 物理身份 | 是文件、真实目录、符号链接、目录联接还是其它重解析点；规范化目标在哪里 |
| 容量 | 文件数和大小是否完整取得；是否因权限、链接或扫描上限而不完整 |
| Git 状态 | 跟踪、未跟踪、修改、删除、忽略规则来源分别是什么 |
| 正式生产者 | 哪个安装、构建、运行、测试、下载、生成或人工流程创建它 |
| 正式消费者 | 哪个导入、配置、启动脚本、构建器、运行时、测试或人工工具读取它 |
| 路径所有者 | 路径来自代码、配置、环境变量、工具默认还是用户手工选择 |
| 生命周期 | 必须跟踪、仅本机长期保留、可重建、按次产生、历史保留或未知 |
| 目标职责 | 继续留在活动根、迁到唯一正式根、移出活动项目、归档或成为删除候选 |
| 证据强度 | 已确认、强推断、弱线索或未知 |

`git ls-files`、`git status`、`git check-ignore -v`、代码和配置搜索、包清单、启动与构建脚本、路径解析代码以及真实运行结果共同提供证据。最近修改时间、目录名、文件扩展名和大小只能筛选候选，不能单独证明用途。

## 3. 判断“真实使用”

按正式职责把目录归入以下类别；项目可以使用不同名称，但不能跳过职责判断：

1. **活动项目输入**：源码、配置、schema、迁移、测试、文档、构建和启动脚本，以及运行或发布必须消费的资源。
2. **活动本地状态**：数据库、会话、用户数据、运行时模型、下载素材或其它不应提交但当前功能会生产和消费的状态。
3. **依赖与工具链**：包管理器安装目录、解释器环境、SDK、工具缓存和由锁文件或安装入口重建的依赖。
4. **可再生产物**：构建输出、日志、测试报告、缓存、临时目录和由当前入口再次生成的中间物。
5. **制作工程与原始材料**：设计源文件、Live2D 或媒体工程、人工诊断工具等不会进入正式运行链、但仍由人工工作流使用的内容。
6. **历史材料**：旧提案、旧工作流、旧运行数据或已经退出活动消费者但仍有追溯价值的内容。
7. **未知**：缺少生产者、消费者或所有权证据，当前不能安全处置的内容。

确认“活动”至少需要一个可核对的生产或消费入口。静态搜索没有命中时，继续检查动态拼接路径、环境变量、配置加载、工作目录约定、插件发现、外部工具和人工流程；这些边界都排除后，才能把“未发现消费者”作为较强证据。

以下判断都不成立：

- 被 Git 跟踪，所以当前一定使用；
- 未跟踪或被忽略，所以可以删除；
- 名字含 `temp`、`old`、`data`、`build` 或日期，所以一定是临时文件；
- 很久没有修改，所以已经过期；
- 可以重新下载，所以当前操作可以直接删除；
- 目录为空，所以无需检查删除权限或生产者是否会再次创建。

目录被清理后又出现时，先定位再次创建它的正式生产者。构建、日志、测试或运行目录按合同重建，通常说明它是活动派生状态，不是上次移动失败；如果用户结果要求根目录长期保持简洁，应调整生产者拥有的输出根或接受一个明确、已忽略的稳定目录，不能循环删除结果。

## 4. 先设计最终目录职责

目录整理的用户结果通常包含两层：活动根更容易理解，以及每项内容以后仍由正确入口找到。先定义最终职责，再安排移动：

```text
活动项目根：仓库必须维护和日常开发直接使用的内容
本地状态根：运行时长期使用但不进入版本管理的内容
依赖与缓存根：由安装器、包管理器或工具拥有的可重建内容
制作工作根：人工制作工程和原始材料
归档根：活动入口不再读取、但需要保留的历史内容
```

不要求所有项目都采用相同物理布局。路径由外部工具硬编码、平台限制或打包合同决定时，可以留在根目录，但必须记录所有者、忽略规则和生命周期。目录数量不是唯一指标；职责不明、同一类内容散落多个根、运行时代码仍读旧位置，才是需要治理的问题。

一个目录先被集中到项目内的新文件夹、随后又被移到项目外，通常说明第一次只按内容名称分组，没有先确定“活动项目是否应拥有它”。未来应先确定活动消费者和最终根，再一次移动到目标位置。

## 5. `.gitignore` 只管理版本边界

`.gitignore` 不负责证明目录无用，也不负责整理物理位置。新增规则前先回答该目录为什么不应进入提交、谁仍会使用它、是否能在干净克隆中重建，以及规则会不会遮蔽同名源码或数据。

优先使用与意图一致的根定规则，例如 `/data/`、`/models/` 或 `/dist/`。只有确实希望在任意深度忽略同名目录时才使用未定根模式。Windows 和默认大小写不敏感的文件系统上，`Data` 一类宽泛规则可能同时影响 `data`；必须对实际目标和容易混淆的邻近路径分别运行：

```powershell
git check-ignore -v --no-index -- <路径>
```

规则修改后重新检查：目标路径命中了预期来源，必须跟踪的相邻路径没有被遮蔽，已经跟踪的文件不会因为新增规则自动退出索引。若忽略规则暴露出过去被意外隐藏的文件，应回到目录账本逐项分类，不能再增加一条更宽规则把问题藏回去。

## 6. 移动与归档必须迁移所有权

### 退役代码不因不能删除而自动归档

活动实现被替代、测试 helper 退出或迁移需要移除旧代码时，先判断 Git 历史已经提供可恢复证据，项目是否另有法律、审计、迁移或人工查阅需要。若删除尚未获准且没有独立保留要求，把对象保留在原位并列为准确删除候选；不得为了让旧实现退出活动入口而制造新的仓库归档，也不能用“已经归档”把仍在版本管理中的废弃实现描述成已经闭合。

仓库内归档必须有可核对的正式消费者、保留责任人和到期或复查条件，并明确不会被构建、测试、运行时、代码生成器或普通开发入口读取。‘以后可能有用’不能成为入库理由；Git 已经保留历史时，额外复制一份旧源码通常只增加搜索噪声、重复实现和同步负担。项目正式的决策记录、依法保留材料和有明确恢复流程的历史档案不因此被判为垃圾，但仍按各自生命周期治理。

确实获准归档时，除源到目标和完整性证据外，还要记录归档为何需要进入仓库、哪个入口消费、何时复查或退出，以及移动造成的 Git 删除和新增。最终交付必须披露全部仍被保留或已经归档的退役路径，不能等用户后来发现；没有获准删除或归档的准确候选继续标为未完成，不以新目录掩盖。

执行前建立准确清单：

```text
源绝对路径 → 目标绝对路径
当前类别与目标职责
生产者、消费者和路径真源
需要迁移的代码、配置、脚本、文档或人工入口
Git 预期变化：rename / add+delete / 仅本机移动 / 无变化
冲突与回滚位置
验证入口
```

在 Windows 上先解析源、目标父目录和重解析点的规范化绝对路径，证明它们位于用户批准的项目根或归档根内；使用同一种原生文件操作完成检查和移动，不把 PowerShell 枚举结果拼给另一个 shell 做递归操作。目标已存在、大小写折叠后重名或需要合并内容时停止，不能静默覆盖。

移动活动模型、数据、素材、工具或工程目录时，从路径唯一真源迁移所有生产者和消费者。新链成立后退出旧路径、旧回退、双读和同步副本；归档目录不得继续成为运行入口。只把文件搬到新位置、再用兼容查找保留旧根，会留下两个活动真源。

归档是可恢复操作，不等于改名后继续修改同一份内容。动作前保存来源清单；归档后逐项比较文件数量、字节数与哈希或直接逐字节核对，并记录归档位置。将已跟踪目录移出仓库会在 Git 中表现为删除；即使磁盘上仍有归档副本，也必须在执行前向用户说明这一版本管理结果，并遵守项目对删除的单独授权要求。

## 7. 删除只处理已经闭合的候选

删除前必须同时满足：

- 目标和递归范围准确列出并获得授权；
- 没有活动生产者、消费者、恢复入口或人工工作流仍需要它；
- 可再生产内容的正式重建入口存在，或用户接受不可恢复；
- 文件句柄、进程、同步程序和后台任务不会继续写入；
- 需要保留的内容已经在用户同意的位置完成可恢复归档；
- Git 删除、忽略规则和发布结果已经说明。

授权只覆盖清单中的准确对象。不要使用仓库根、用户目录、盘符根、未解析变量或宽泛通配符作为递归删除目标。空目录、清理后残留目录和整理过程中临时创建的目录仍受同一删除边界约束。

## 8. 按影响验证

纯目录说明和 `.gitignore` 元数据修改只需要结构、Git 与规则检查，不运行无关构建、浏览器或端到端测试。移动触及活动路径、模型、数据、打包输入或启动脚本时，升级为对应真实链：

```text
正式生产者或人工入口
→ 最终路径或存储边界
→ 正式消费者
→ 用户可观察结果
```

完成前至少重新取得：

1. 整理后的顶层目录、大小和职责账本。
2. 本轮前后 Git 工作树、索引、未跟踪和忽略状态，并与用户原有变化分开。
3. 每条新增忽略规则的来源和邻近路径反例。
4. 每个移动对象的新路径、旧路径退出、生产者与消费者结果。
5. 每个归档对象的清单与完整性核对。
6. 会自动重建的目录在一次相关入口后的实际位置和状态。
7. 未处理、证据不足或仍需删除授权的准确对象。

盘点器成功退出只证明它读取了报告中的路径；大小扫描不完整、Git 不可用、忽略来源未知或消费者未验证时，对应结论继续标为未知。最终报告先说明活动根为什么现在更清楚，再列出保留、迁移、归档、删除候选和仍未知内容，不用“文件夹减少了”替代运行链成立。
