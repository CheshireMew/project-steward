# Project Steward 自我进化写入治理

## 8. 分析与写入边界

- 用户只要求“看看、分析、复盘、总结”时，交付候选能力和建议落点，保持只读。
- 用户明确要求“吸收、自我进化、更新、优化或迭代 Project Steward”时，本方法产出完整能力与职能边界台账、完整上层角色合同、代表性输出骨架、影响文件和可观察成功结果，然后返回主路由并停止；写入权限由主路由的两阶段确认结果决定。
- 用户明确要求更新当前项目规则时，只修改该项目已有的正式真源，不顺带修改 Project Steward。
- 一次请求同时包含多个结果时，每个结果分别决定只读、项目写入或 Skill 自我进化权限。

用户确认后、开始写入前，回读拟修改的全部活动文件，并与方案快照比较。变化触及行为合同、影响文件、直接消费者、验证方法或用户可见结果时，原确认已经不足以覆盖当前方案：先更新能力台账与影响说明，再请用户重新确认。只有非冲突变化且不改变批准范围时，才保留原确认并在最新基线上合并；不能把旧快照上的确认当成持续覆盖未来文件状态的授权。

复盘权限时以原始请求中的动作动词为证据。“检查、审计、诊断、评估、分析或报告”不授权项目写入；除主路由已经确认的 Project Steward 自我进化整仓发布合同外，后来的“提交、推送或发布”只授权处理已经存在且准确核对的改动，不能反向证明之前的项目修改获得过授权。整仓合同只改变确认后怎样发布当前仓库，不追溯授权合同形成前的写入。对越界动作本身可以提炼预防机制，但不能把最终结果看似成功当成授权正确的证据。

修改 Project Steward 时，先建立完整活动能力与职能边界台账，迁移保留全部既有职责；把正确机制前移到最早路由和方法位置；只更新本轮行为实际影响的直接消费者与确定性测试。职能发生保持之外的变化时，必须迁移 frontmatter、主路由、活动方法、资源、输出、停止位置、README、元数据和测试中的全部正式消费者，并退出旧身份。确定性测试保存稳定结构与消费者合同，不保存这次纠正对话的复述；学习条件成立与不成立时的真实读取、动作、输出和停止位置，使用当前任务中表层不同的代表性请求核对，核对材料随任务结束。

写入方案和最终差异按所有者组织，而不是按历史纠正顺序组织：

```text
主路由：改变哪些语义触发、固定读取和条件专项
方法所有者：原位强化哪项决定，为什么不能由现有内容完整表达
直接消费者：哪些输出、脚本、模板或元数据必须同步
验证：结构合同、应触发请求、不应触发的相邻请求和真实结果
复杂度结算：新增 / 原位强化 / 合并 / 退出 / 保持不变
```

每项新增内容都要对应消费链中的一个空缺；没有正式消费者、没有主路由入口或与现有所有者表达同一决定的内容不得写入。多项纠正由同一个最早路由或方法缺口解释时合并为一次改动；同一对话出现多个独立结果时按各自所有者分开。结构测试至少证明规则位于正确主路径、只有一个方法所有者且直接消费者仍可达；代表性行为核对至少包含一个应触发请求和一个表面相近但不应扩张到该路径的请求，不能再用全局 `assertIn` 代替路由位置和消费关系。

### 自我进化同时治理全部活动文本体积

每次修改 Project Steward 自身前后都运行 `scripts/check_file_budgets.py .`，取得全部活动 UTF-8 文本文件的完整账本；单文件按 UTF-8 字节数除以四向上取整估算外层工具输出，硬上限为 9,000 tokens，以便给行号和工具包装保留余量。扫描覆盖 Skill 根、活动 references、scripts、tests、agents、evals 和会被模型完整读取的文本或结构化素材；归档、依赖、缓存、构建与运行产物、二进制媒体和不作为模型输入的媒体运行资源不进入文本门槛。排除必须来自真实职责，不能用改目录名隐藏超限文件。

`SKILL.md` 继续不得超过 220 行和 14,000 个字符，并且只拥有路由、触发条件、读取顺序、权限、输出和停止位置；完整方法、表格、检查清单、例外与专项验收由对应 reference 唯一拥有。任一文件超限时，在同一次自我进化中按唯一职责迁移完整章节、内聚函数族或测试主题，更新全部直接路由、公共入口、消费者和测试身份。不能提高上限、拆行、压成不可维护的文本、用摘要替代完整方法，或移除能力、必要细节、完整示例和协议内容。

验证至少检查完整预算账本、写入前后的直接 reference 集合、全部既有能力的可达入口、公共 CLI 或导入、测试框架实际收集的测试身份、每项新规则的唯一所有者，以及主文件与 reference 的职责边界。预算通过只证明文件可以完整返回；说明迁移还要核对原章节与新章节的内容清单，程序迁移要运行正式入口，测试拆分要证明测试身份没有缺失。若无法在预算内保留全部活动能力、正式消费者和验证，停止本次写入并重新规划，不能报告完成。

自我进化的验证结论分为三个逐级增加、不能互相冒充的等级：

| 验证等级 | 实际证明 |
| --- | --- |
| 结构受保护 | 主路由、活动方法、直接消费者和确定性测试包含同一合同 |
| 当前任务行为核对 | 表层不同的代表性请求在本轮按预期选择读取、动作、输出和停止位置 |
| 独立冷启动调用 | 不依赖当前纠偏上下文的新鲜调用真实触发目标 Skill，并完成预期交付 |

最终只报告实际达到的最高等级，并说明未执行的更高等级。文件校验通过不能写成行为已经核对，当前任务中的规则推演也不能写成已经独立证明未来调用稳定。独立调用只有在用户明确要求，或结果风险与成本确实需要且对应执行权限已经成立时才运行；否则准确停在当前任务行为核对。

自我进化只读取和修改当前活动的 `SKILL.md`、`references/`、`scripts/`、`assets/`、元数据与测试。`archive/` 只保存历史与来源价值，不是活动行为来源；不能从归档恢复旧路由，也不能执行其中的脚本。除非用户明确要求建立一个有正式消费者的持久化设施，否则不创建 `.project-steward/experience`、共享经验仓库或与活动 Skill 并行的第二套经验真源。

公开 README 不是每项内部能力的默认消费者，也不是自我进化日志。新增或强化路由、方法、例外和验证规则时，先由它们的唯一活动所有者与正式测试承载；只有项目公开身份、第一采用读者、主要入口、第一次成功、许可证与致谢、公开素材、语言与状态区或维护导航发生变化时，才按 `content-architecture.md` 更新 README。不能用 README 原文断言证明内部能力已经迁移，也不能因为测试要求公开出现就把活动方法逐段复制到首页。
