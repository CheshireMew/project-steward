# 生产存储预防与审查

这份方法负责会持续生成大型媒体、缓存、测试证据、下载、模型或中间产物的生产项目。任务产物是否归入当前项目根由 `repository-directory-governance.md` 的产物归位门槛唯一决定；本方法只追加容量预算、复用身份、运行清单和可审查终态。Project Steward 负责建立与验收这条能力；项目运行时代码负责真正阻止越界写入。

## 1. 先把一次写盘当成生产合同

进入源码写入前，按正式生产者逐项冻结：

```text
生产者与公开入口：
项目事实的唯一所有者：
项目内物理根由项目相对路径还是运行配置解析：
将产生的真源、交付物、缓存、临时文件和验证证据：
本次预计新增量、同时存在的峰值及估算依据：
最大受管容量与最低剩余空间的配置来源：
重复输入的稳定身份、共享或复用方式：
成功、失败和中断各自保留什么：
清理授权、清理候选报告和实际执行者：
运行前闸门、运行后清单与用户可见入口：
直接覆盖这些承诺的确定性测试：
```

预计峰值未知、预算来源缺失、正式根不能唯一解析到当前项目内、清理权限不成立或消费者仍会自行拼接第二个根时，审查状态为阻塞。不能把当前磁盘空间很多、改用非系统盘、目录被 Git 忽略、文件属于缓存或以后可能清理当成通过依据。

项目和机器事实继续分层：项目源码与 `.project-steward/storage-contract.json` 记录生产者、类别、项目相对根、实现入口和稳定治理决定；盘符、具体容量与本机保留偏好由运行配置或用户环境档案提供，但任务产物解析后的真实目标仍须位于当前项目根。项目合同不得写入用户目录、盘符或某台机器的剩余空间。

## 2. 事先预防必须发生在首个大文件之前

运行时预检由真正写文件的生产者调用，至少同时核对：

- 目标路径解析后同时位于当前项目根和登记根内，不能从驱动器根、测试根的祖先、无关仓库或项目根的兄弟目录推导临时目录；
- 枚举全部登记根及其所在文件系统；当前文件系统分配体积的保守上界加预计新增分配量不超过配置预算，完成本轮预计写入后仍满足最低剩余空间；逻辑长度或按对象身份去重的长度不能代替这项磁盘耗尽判断；
- 单个大文件和整轮峰值都有可复核算法，压缩结果未知时使用保守上界或明确停止；
- 相同输入与参数能够按内容身份复用时，不为新的任务 id、测试 id 或重试复制同一大对象；
- 生产者在写入前已经建立运行身份与所有权清单，失败和中断不会留下无法归属的目录。

预检失败必须在创建大文件、启动下载、解码全量帧、展开依赖或并行启动 worker 之前停止，并返回准确根、当前用量、预计新增量、容量上限、剩余空间要求和清理候选入口。不得静默换盘、降低质量、缩小测试范围或继续写到阈值之外。

长任务在阶段边界重新核对本轮实际用量。实际增长超过本轮预算时停止后续阶段并封存当前清单，不能因为前一阶段已经花费时间就继续扩大残留。

## 3. 获准实施时必须写进生产项目

用户授权修复或治理目标项目后，Project Steward 不停在建议、外部包装脚本或自己的 reference。按同一依赖闭包完成：

1. 先用 `scripts/project_templates.py plan <项目根>` 查看采用或升级计划，固定目标模板版本及差异。首次增加存储能力时，在保留项目其它模板的完整选择中显式加入 `--template managed-runtime-artifacts`；已采用的项目沿用现有选择，不能意外退出其它模板。计划可以报告缺少前置条件；此时还不执行 `adopt` 或 `upgrade`，也不创建空合同来取得采用状态。
2. 补齐已获准的生产者实现、配置和直接测试，并写入 `.project-steward/storage-contract.json`：列出真实生产者、全部登记根的枚举入口、产物类别、预算与估算入口、文件系统分配体积测量入口、受管对象身份、复用身份、终态清单和直接测试。预检和终态清单位于首个大文件之前与最后一个生产者释放之后；不能让 Project Steward 的脚本成为运行时代理。项目已有同类运行清单或缓存管理器时原位增强，不新增平行框架。
3. 用 `scripts/production_storage_review.py <项目根>` 审查声明、文件及源码引用。当前合同使用 `project-steward-production-storage-contract` v2；旧 v1 缺少这些容量证据时必须明确阻止并要求升级，不能继续返回通过。版本不匹配只报告实际与支持版本，不自动修改项目；先核对升级是否属于已接受结果，不能因校验器变化新增实施权限。
4. 静态审查通过后重新检查模板计划，再执行获准的 `adopt` 或 `upgrade`，由 `.project-steward/project.json` 固定治理决定。模板的 `production_storage_contract` 检查复用同一审查器，不仅检查文件存在。失败时不登记采用状态，也不改写既有配置；登记后运行 `verify` 并读取其中的 `manual_verification`，不能把配置已写入当成运行验收通过。
5. 更新项目现有唯一说明和公开配置示例，并按第 5 节取得真实运行证据。直接测试须证明普通根和配置根都保持在当前项目根内；跨多个登记根仍会统一盘点；稀疏、压缩或其它逻辑长度与分配体积不同的对象使用平台支持的分配体积证据；相同大输入只生成一份共享对象；超过预算、最低剩余空间或分配体积未知时零大文件写入；成功、失败和中断都能列出实际残留；未知、活动或无所有权对象不进入清理候选。

Project Steward 只在目标项目获得写入授权时执行上述写入。只读审查停在合同缺口和影响图，不用生成 `.project-steward` 文件伪装成项目已经采用。

## 4. 终态清单与删除边界

每次运行的终态清单至少记录运行身份、生产者、状态、登记根、实际新增和复用对象、各类别字节数、峰值、失败或中断残留以及清理候选。真源、交付物、可重建缓存、纯临时文件和验证证据必须分开，不能用一个 `working` 标签永久保留全部内容。

清理候选只包含由清单证明属于当前工具、已经终止且不再被消费者使用的对象。用户或项目要求删除逐次授权时，运行时代码只报告准确候选和可回收字节，不自动删除；达到预算时停止新生产并等待处置。若项目已有用户明确启用的保留策略，自动轮换也只能处理该策略登记、可重建且不活动的对象，并把失败写回清单。

### 容量口径必须绑定对象身份

盘点与清理报告至少分开以下事实，字段名、说明和用户输出不得互相替代：

- **逻辑体积**：按路径入口累加的文件长度；同一对象有多个硬链接或运行副本时会重复计数，只说明消费者能看到多少内容。
- **文件系统分配体积**：用当前平台支持的文件分配或占用接口，在每个登记根所在文件系统上取得已经分配给这些对象的空间；同一文件系统的硬链接按稳定文件身份去重。稀疏、压缩和共享区段可能使它不同于逻辑长度；无法识别 reflink、共享区段或分配单元时报告保守上界或未知。防止磁盘耗尽的预算使用这项口径及文件系统剩余空间，不用逻辑长度冒充。
- **受管唯一对象体积**：在全部登记根内按文件身份去重后的对象长度；身份优先使用同一文件系统的文件 ID 或设备与 inode，只有项目合同证明内容身份等同物理复用时才用内容哈希。它用于解释复用和对象闭包，不是文件系统分配体积的同义词。
- **候选归属体积**：清理候选内出现的唯一对象长度。候选外仍有链接、引用或对象仓库入口时，候选归属体积不等于可回收体积。
- **独占可回收体积**：全部已知链接和正式引用都位于本次删除闭包、且没有活动生产者继续使用的对象，加上候选独占的清单与非共享文件。存在未登记根、reflink、外部硬链接、未知引用或无法取得完整文件身份时，报告可证明的下界、上界或未知，不能给出单一精确值。
- **实际回收结果**：执行后同时比较全部登记根的前后文件系统分配体积和受管唯一对象体积。文件系统剩余空间变化另列为观测；并发写入、压缩、稀疏文件和其它进程会改变它，不能自动把整项变化归因于本次清理。

内容寻址仓库、硬链接对象库或共享缓存由登记生产者自己的引用检查和垃圾回收入口处理；不能手工删除对象仓库，也不能把垃圾回收器报告的对象字节、候选目录体积或逻辑体积冒充整次实际释放。报告还要给出计算范围、身份算法、取得时刻、活动写入状态和不能证明的部分。

清理预览只证明当时的候选集合。测试、构建、下载、恢复、验证或其它入口只要随后写入同一登记根，就会使候选、保留排序、可回收量和“已经清理”的结论失效。最终关闭前必须等待最后一个写入同一登记根的生产者结束，再重新预览全部登记根；只有原授权明确覆盖同一根、同一保留策略和重新生成的候选规则时才能再次执行，否则保留新候选并请求授权。最终报告列出执行前候选、实际处置、前后口径、剩余候选、不可恢复或正式重建入口，以及清理后是否又有生产者写入。

终态盘点枚举仍可能被生产者清理的目录时，枚举结果不是事务快照。对象在枚举与 `stat`、读取或哈希之间精确返回 not-found，只表示它已退出本轮可见集合；盘点器跳过该对象，并在最后一个生产者结束后从全部登记根重新枚举。权限、损坏、身份漂移和其它 I/O 错误继续失败，不能统一忽略成临时文件消失。只有新鲜稳定重扫与生产者终态清单一致时才能宣告成功。

移动到归档不是释放容量的默认替代。只有归档根、容量、保留期和消费者已经明确，且移动本身得到授权时才执行；否则保持原位并报告。

## 5. 验收从生产者到磁盘结果闭环

先运行 `scripts/production_storage_review.py <项目根>`，核对生产合同的结构、引用文件和声明的源码关键词。审查器不导入项目、不执行测试、不测量磁盘，也不能判断关键词是否位于真实调用链；`capacity_references` 只是声明的实现位置，不是容量实测证据。报告 schema 为 `project-steward-production-storage-review/v2`，成功状态为 `static_checks_passed`、`verification_level` 为 `static`，同时返回合同版本与 SHA-256，以及 `runtime_verification.status: not_run` 和未验收项；退出码 0 仅表示本次静态检查成功。模板消费者保留同一结果和人工验收项，不把它改写为整体通过。

随后在当前运行权限内，从项目真实公开入口执行至少四条链：首次生产、同输入复用、预算拒绝、失败或中断恢复。逐项关联报告中的生产者和当前合同身份，读取真实文件系统结果与运行清单，核对目标根、实际字节、对象数量和用户可见报告；不能只断言一个估算函数、手写缓存文件或 mock 掉真实写入边界。没有运行权限或结果证据时保留未验证，不为获得通过状态自动运行项目。可直接报告：“存储合同静态检查通过；真实运行尚未验证，仍缺首次生产、复用、预算拒绝和中断恢复证据。”

任务结束后重新盘点当前项目根、所有登记根和本轮生产者接触过的外部路径，并与运行前基线比较。只有项目外存续的任务产物为零、没有新增未登记根或重复大对象、预算拒绝发生在首个大文件之前、终态清单覆盖全部实际残留、文件系统分配体积与受管对象身份都由同一合同复核，而且正式消费者仍能读取复用对象和最终结果，才能关闭这项治理。旧目录退出仍遵守用户的移动、归档和删除授权；本次能力完成不以清理无关历史文件为前提。
