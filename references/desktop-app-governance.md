# 桌面应用治理

用于桌面应用的项目基线、改动前预防、综合审计和根因治理。它只补充窗口外壳、原生能力、关闭语义、持久化和实机验收；用户任务、业务界面和设计系统由已经选定的产品体验合同负责。

## 1. 先明确窗口外壳

每个顶层窗口或窗口呈现状态必须明确选择：

- `integrated`：关闭原生标题栏装饰，由应用内标题栏承担拖动、标题、窗口按钮和视觉边界。
- `native-explicit`：保留系统标题栏，并把它作为产品视觉的一部分接受。

自定义、品牌化或侧栏贯穿全高的应用默认采用 `integrated`。选择原生标题栏需要项目覆盖和理由；不能让框架默认白条在没有设计决定的情况下成为最终界面。

同一个窗口确实需要在紧凑栏、普通工作区、悬浮控制条或其它模式之间切换时，不把它描述成第三种外壳策略。为每个呈现状态分别选择上述一种策略，并由一个窗口呈现所有者统一切换；页面、按钮和业务状态不能各自修改边框、标题栏、置顶、尺寸和位置。

集成外壳的结构应当是：

```text
app-shell
├── titlebar
└── app-body
    ├── navigation
    └── main
        ├── content-header
        └── content
```

标题栏属于整个应用外壳。内容区分隔线只在 `main` 内绘制；侧栏自己的边界由侧栏或外壳唯一负责。这样可以避免内容标题的横线突出到侧栏，也避免在原生白条下再叠一层假标题栏。

应用内容延伸进系统标题栏时，品牌、导航和系统标题栏只占一份垂直预算；系统标题栏高度与标题按钮保留区属于同一个外壳布局合同，不能再用空白占位行重复预留。改变这份固定预算后，内容头、状态提示、媒体或其它依赖剩余高度的消费者都要重新布局和实机验收。

## 2. 窗口呈现状态与系统保留区

窗口外壳、尺寸和位置会随模式变化时，先建立窗口呈现状态矩阵：

| 呈现状态 | 边框与标题栏 | 外框尺寸或内容区尺寸 | 缩放、最大化、最小化与置顶 | 用户位置与锚点 | 拖动区与窗口按钮 | 系统保留区 |
| --- | --- | --- | --- | --- | --- | --- |
| | | | | | | |

矩阵中的外框尺寸是整个窗口占据的屏幕矩形；内容区尺寸是扣除边框、标题栏和系统装饰后，应用真正获得的布局空间。用户结果要求应用内容保持固定大小时，调整内容区尺寸；要求整个浮层占据固定范围时，调整外框尺寸。切换标题栏或边框后必须按当前状态重新计算，不能把一套尺寸当成另一套复用。

系统标题栏、最小化、最大化、关闭按钮和调整大小边缘是平台保留区。应用内容可以在明确采用集成标题栏时绘制到其背景下，但可交互文字和控件不能进入系统按钮的命中区域。保留区的高度和左右内缩由当前平台运行时取得，并按实际渲染缩放转换到布局坐标；不能把某台机器测得的像素写成所有显示器的常量。

采用集成标题栏时，让应用标题栏消费同一份高度，并用系统左右保留区保护交互内容，不再额外增加空白标题栏行。采用原生标题栏时，系统区域与应用内容是两个明确边界；框架如果仍让内容从窗口最上沿开始，就只预留实际原生标题栏高度，再由产品决定是否还需要职责不同的内容头，不能用两层近似导航重复表达同一关系。

用户移动窗口后，普通页面切换、展开面板和按钮点击默认保持当前锚点。只有首次出现、用户明确要求归位、当前显示器已经不可用或窗口完全落到工作区外时才重新放置。跨显示器切换要以目标显示器的工作区和缩放重新解释尺寸与坐标，不能在不同 DPI 的显示器之间直接复用未换算的位置。

## 3. 拖动区和窗口按钮

- 拖动区只覆盖没有交互控件的标题栏背景。
- 按钮、输入框、菜单和标签不能继承拖动行为。
- 调整大小边缘、拖动背景和交互控件分别拥有命中范围；窗口最上沿如果属于系统缩放边缘，就不能同时承诺为拖动区，应在其内侧提供连续、可发现的拖动背景。
- 最小化、最大化或还原、关闭按钮都映射到明确的原生窗口 API。
- 双击标题栏是否切换最大化由项目明确决定并实机验证。
- 窗口按钮在浅色、深色、聚焦、失焦、悬停和按下状态可辨认。
- 高 DPI、窗口缩放和不同 Windows 文本缩放下没有裁切或错位。

与拖动区同层的导航、菜单和窗口按钮必须用真实指针点击验证命中。程序化调用或自动化 `Invoke` 只能证明命令处理器可执行，不能证明原生非客户区、拖动区域和命中测试没有吞掉用户输入。

拖得动不表示外壳完成；窗口按钮、键盘可达、主题和边界都属于同一用户结果。

## 4. 原生能力与权限

为每个前端原生调用建立映射：

| 用户动作 | 前端调用 | 原生命令 | 能力或权限 | 成功结果 | 失败展示 |
| --- | --- | --- | --- | --- | --- |

调用名、配置权限和目标窗口必须对应。添加权限只能说明命令被允许，不能证明调用了正确 API、保存链完成或用户看到正确结果。

权限错误应在开发阶段由确定性检查捕获；运行时仍要以用户能理解的方式显示失败。不能把原生错误对象直接当成产品提示。

### 原生依赖供应、ABI 与进程隔离

桌面架构需要嵌入 Qt、MLT、FFmpeg 或其它预编译原生引擎时，先建立原生依赖合同，再冻结架构与版本。源码存在不能证明目标平台存在可用的构建 SDK 和运行时二进制，也不能证明二者 ABI、编译器、架构、调试/发布模式和补丁版本可以混用。开始上层实现前至少登记：

| 合同项 | 必须确认的事实 |
| --- | --- |
| 用户结果 | 哪项正式能力依赖该原生组件，失败会在哪个最终结果中暴露 |
| 权威供应 | 官方源码、构建 SDK、头文件、导入库、运行时二进制和插件从哪里取得，目标平台与架构是否齐全 |
| 版本与 ABI | 构建 SDK 和运行时的准确版本、编译器工具链、架构、配置、ABI 以及允许的组合 |
| 许可证与分发 | 实际启用组件的许可证、再分发条件和必须随包提供的声明 |
| 目录边界 | 插件目录、依赖库目录、数据目录、缓存目录和用户项目目录分别由谁拥有 |
| 进程级状态 | 环境变量、DLL 搜索路径、插件搜索路径、全局工厂和注册表由谁激活、何时恢复 |
| 验证链 | 原生组件怎样被真实数据加载，主界面和后续消费者怎样证明结果可用 |

只有运行时二进制而没有匹配的头文件、导入库或构建 SDK 时，结论是构建链尚未成立。应在写依赖它的产品代码前更换受支持版本、补齐权威供应或明确标记阻塞，不能先把计划写成“已集成”，再用宽松加载和版本猜测掩盖缺口。构建 SDK 与运行时补丁版本不同也不能只引用抽象兼容承诺；必须以实际加载、真实数据处理和下游消费者继续工作作为该组合的证据。

插件目录只包含插件。插件依赖的普通 DLL、编解码库和其它共享组件放在独立依赖目录，并对允许出现的文件集合做精确校验，不能把整个运行时目录塞进插件搜索路径后接受偶然加载。搜索顺序、回退目录和缺失插件的失败展示同样属于合同。

进程级环境变量、DLL 搜索路径、插件搜索路径、全局工厂和注册表必须由一个所有者以有界作用域激活。作用域要覆盖加载、打开、使用、关闭、重开和销毁，而不只覆盖构造调用；正常完成、异常、取消和部分初始化失败后都要精确恢复原状态。局部组件不能留下影响同一进程中后续预览、导出或其它原生消费者的残余配置。

真实验收至少重复执行以下顺序：

```text
记录进程级状态基线
→ 加载 → 打开 → 主界面消费真实数据
→ 关闭并重开原生对象
→ 后续导出或其它原生消费者继续完成用户结果
→ 销毁组件并关闭应用
→ 核对环境、搜索路径、插件集合和全局工厂已恢复
```

只调用一个原生函数、只看到 DLL 加载成功或只完成第一次预览，不能证明进程隔离成立。重复创建和销毁后还要检查崩溃、警告、资源泄漏、插件污染和后续消费者结果。若用户明确要求不打包，这些检查只做到开发运行时和当前机器的真实链路；干净机器、可再分发目录与安装层继续标记为未验证，不能擅自打包来补证据。

## 5. 屏幕捕获产品的自有窗口可见性

屏幕录制、截图或演示产品必须明确每个自有顶层窗口是否应进入最终捕获。主窗口、悬浮控制条、倒计时、区域选择器、提示层和后续创建的辅助窗口分别登记；不能只设置主窗口，就假设同一进程的其它窗口会自动继承。

需要排除时，在顶层窗口句柄已经创建后使用当前平台正式支持的窗口捕获可见性机制，并在窗口被重建时由同一所有者重新应用。Windows 的显示关联机制只接受当前进程拥有的顶层窗口，并受系统版本、桌面合成和捕获路径影响；它是产品捕获行为，不应描述成无法绕过的安全或数字版权保护。具体 API、支持版本和回退行为在实施时以当前官方合同为准。

真实验收必须经过产品正式捕获链：

```text
可识别的真实背景
→ 自有控制窗口覆盖在背景上
→ 正式捕获生产者录制
→ 正式编码与落盘完成
→ 从最终录制产物解码控制窗口所在区域
→ 看到背景而不是控制窗口
```

普通屏幕截图、窗口预览、捕获 API 返回成功或只检查窗口属性，都不能证明最终录制已经排除。其它端到端测试确实需要捕获应用自身时，可以提供明确、只用于测试的关闭开关；排除能力的专项测试必须使用生产默认值，不能带着该开关宣称通过。

## 6. 辅助进程、事件与终止生命周期

桌面应用启动采集器、编码器、索引器、渲染器或其它辅助进程时，进程所有权从创建成功就开始，不能等 IPC 连接完成后才建立。父进程身份、连接期限和连接前退出条件必须通过同一启动合同传入；父进程消失、连接超时或启动失败时，辅助进程应自行收口，不能无限等待或成为孤儿。

终止合同分开表达三类事实：

- **终止原因**：客户端主动关闭、后台声明的可恢复中断，或真实故障。
- **结果状态**：最终停止、恢复完成或失败。
- **传输收尾**：EOF、断管、取消中的 I/O、读取器结束和进程退出。

终止原因、结果状态和传输收尾不能互相覆盖。通用失败状态不能反向改写已经确定的结构化原因，EOF 也不能单独证明发生了故障。正确顺序是：

```text
登记结构化终止原因
→ 终止事件不可合并且完成交付
→ 读取器结束并等待事件消费完成
→ 订阅者和派生工作排空
→ 暴露进程终止与最终结果
```

辅助进程还承担 Agent、渲染、索引、转换或其它业务生产时，业务结果与上面的终止事实再次分开。生产者通过带版本、至多一次的结构化结果帧提交业务结论；stdout、stderr 和普通事件只进入日志，退出码只描述进程，EOF 只描述传输。结果帧缺失、重复或无法解析时由启动合同给出明确失败，消费者不能扫描最后一行、自然语言或日志关键词猜测成功。关闭要等待结果帧处理、完整日志落盘、终止事件交付、读取器和订阅者排空，再暴露最终状态。

主动停止导致的传输取消，只有在停止所有者已经生效且错误精确属于该次取消时才是正常收尾，并应在产生错误的边界消化；其它写入失败、超时和异常退出仍然保留为故障。客户端请求关闭只有在有界时间内以退出码 0 正常退出才算成功，超时后的强制终止和非零退出码属于清理失败，必须进入最终用户结果。

标准输出和标准错误的编码是进程协议的一部分。生产者明确写出哪种编码，启动器明确用同一种编码解码；生产代码和真实进程测试复用同一个启动合同，不能让测试绕过会产生乱码或参数漂移的正式入口。

至少验证以下竞争与失败顺序：

1. 终止事件先到、随后 EOF。
2. 先观察到传输关闭、随后读到终止事件。
3. 父进程在连接前消失或连接超时。
4. 主动停止正常零退出、停止超时和非零退出。
5. 真实辅助进程退出后没有孤儿，日志没有把正常收尾记成故障，正式消费者仍完成恢复或结果展示。
6. 真实生产者分别产生结构化业务结果和普通日志；日志内容即使包含成功或失败文字也不会改变业务结果，缺失或重复结果帧形成明确失败。

## 7. 界面线程与后台工作

桌面界面的事件循环只负责读取当前输入、完成有界校验、提交操作意图和呈现已经产生的状态。文件遍历、复制与大文件读写、网络和 provider 调用、媒体解码、索引或摘要重建、外部进程等待以及随输入规模增长的序列化都先作为潜在阻塞生产者登记；只有用代表性数据测得明确上界、并且最坏时长仍符合当前交互预算，才能留在界面线程。不能用开发机上“通常很快”、函数本身没有 `async`，或一次小夹具返回迅速证明不会阻塞。

需要后台执行时，界面处理器先冻结操作身份、generation、输入内容身份、目标对象和允许副作用，再交给一个生命周期足以覆盖实际工作的所有者。所有者负责排队、冲突串行、取消、进度和唯一终态；界面只禁用会与该操作冲突的控件，无关查看、移动窗口、输入和关闭入口继续响应。取消发生在任务开始前时不能创建工作目录或其它副作用；执行中取消或失败只收口本操作创建的临时对象和已登记结果，不能触碰其它任务或用户已有文件。

后台结果通过类型化通道返回，并原样携带操作身份与 generation。界面线程只有在目标仍存活、当前操作仍匹配且结果完整时才提交可见状态；迟到成功、失败和取消只能清理自己的旧任务。框架规定只能由界面线程创建、转换或释放的窗口、图像、字体、计时器和其它对象，不得在工作线程中构造或销毁；后台只生产框架允许跨线程传递的数据。窗口关闭和应用退出先停止接收新工作，再请求取消并排空已登记任务和结果投递，不能让信号源、目标对象或线程先被销毁后仍继续回调。

真实验收从自然界面入口使用受控但真实的代表性输入启动工作，保留正式文件、协议、媒体或进程边界，不 mock 掉正在验证的慢生产者。工作到达可观测阻塞点后，立即提交一次无冲突的界面输入，证明它在后台任务终态之前已经被事件循环处理；随后分别让任务正常完成、被新 generation 替代、取消以及关闭目标，核对正式消费者只接受匹配结果、部分产物按项目合同保全或收口、事件循环排空且终端没有未处理异常。只断言工作线程已创建、处理器很快返回、取消标志被设置或最终过一会儿出现结果，都不能单独证明界面仍可用和生命周期已经收口。

## 8. 延迟界面工作与对象生命周期

`callLater`、排队信号、零延迟或单次定时器、动画完成回调、防抖任务和 Future 完成处理器都可能在当前事件处理器返回后才执行。每项延迟界面工作必须有一个生命周期足以覆盖实际执行期的所有者，并明确对象替换、页面销毁、窗口关闭和应用退出时由谁取消、断开、排空或拒绝过期结果。把回调排进事件循环、让框架持有定时器，或者检查调度动作返回成功，都不能证明目标对象届时仍然存在。

所有者按工作职责选择：只服务当前页面或面板的工作随该对象销毁并停止；服务窗口或应用外壳的工作由更长寿命的所有者持有，并在触发时重新取得当前活动对象，不能保存已经退出页面的引用。语言或主题重载、路由替换、动态组件重建、面板关闭和窗口销毁都按生命周期替换处理；旧回调只能清理自己的旧状态，不能在新对象出现后继续写界面、配置或持久化状态。

涉及这类改动时，真实 smoke 至少执行：

```text
创建真实窗口和页面
→ 触发会排队或延迟执行的界面工作
→ 替换、重载或关闭其目标对象
→ 继续排空事件循环到工作已执行或被明确取消
→ 关闭应用并等待公开释放状态
→ 终端与界面没有销毁后访问、未处理异常或延迟写入
```

单元测试通过、窗口立即消失或进程退出码为零，都不能替代关闭后事件排空。框架关于对象已销毁、信号目标不存在、定时器仍活动或回调异常的警告，即使没有改变退出码，也属于该生命周期链的失败证据。

### 运行时表面清单与新鲜进程

桌面 smoke 不能只打开首个窗口。先从正式入口、窗口注册、路由、菜单、托盘、对话框和动态创建点建立运行时表面清单，至少包含主窗口、其它主要窗口、首次访问才创建的页面或面板、菜单与对话框，以及会覆盖当前界面的弹层。然后从产品自然入口在真实事件循环中逐项首次打开、关闭或离开、再次进入，并让每个表面的正式消费者读取真实状态；首屏成功不能替未访问表面背书。

运行时同时收集框架诊断。`ReferenceError`、未定义组件、属性、信号、主题或翻译、绑定循环、销毁后对象访问以及未处理回调异常，只要来自本轮实际表面和目标框架，就属于失败，即使进程最终退出码为零。普通信息或已证明无关的第三方告警可以分别解释，但不能用“应用没有崩溃”覆盖能够改变界面或生命周期的诊断。

`QApplication` 或等价应用单例、单实例锁、事件循环、进程环境、语言与主题注册表等进程级启动事实，必须在新进程中验证。测试套件复用已经创建或关闭过的应用对象、依赖执行顺序或残留全局状态，只能证明该复用状态；fresh-process smoke 要经过同一个生产 `main` 入口，完成启动、表面遍历、关闭和进程退出，不能用测试专用外壳重建第二套启动链。

## 9. 关闭语义

默认关闭合同是：

```text
用户请求关闭
  → 阻止重复关闭
  → 保存脏文档与项目状态
  → 处理外部修改冲突
  → 刷新或持久化必要原生状态
  → 等待成功或给出可操作失败
  → 请求窗口正常关闭
  → 进程退出
```

正常关闭和强制销毁是不同语义。只有确实要绕过关闭事件、清理和提示时才使用强制销毁，并为该决定建立单独合同；不能因为正常关闭链没有接通就换成 destroy。

自动化、验证脚本或发布前检查需要“关闭后立即重新打开”时，必须等待应用公开的释放完成或释放失败状态。私有 Future、内部 Promise、对象暂时消失和固定睡眠都不能证明文档、项目锁、浏览器、设备、辅助进程或持久化事务已经释放。只有公开状态表明正常关闭链完成且相应资源可重新取得后才能重开；公开失败状态要提供消费者可判断的原因，验证链据此停止或显式重试，不能继续调用打开入口制造第二条生命周期。公共关闭状态或方法迁移时，生产调用点、测试、自动化、验证与发布脚本必须在旧入口退出前一起迁移。

需要多窗口、托盘或后台驻留时，分别说明“关闭窗口”“退出应用”和“隐藏到后台”的用户结果。最后一个窗口消失不一定等于进程退出。

## 10. 持久化与恢复

核对：

- 文档内容、应用设置、窗口状态和缓存各自真源；
- 自动保存、手动保存、外部修改和关闭刷盘的顺序；
- 保存失败时窗口是否仍保持可恢复状态；
- 崩溃恢复副本是否会覆盖更新的磁盘内容；
- 再次启动是否由正式消费者读取刚才写入的状态。

关闭链测试必须先制造真实脏状态，再通过界面关闭，重新启动后读取；直接调用保存函数不等于关闭刷盘成立。

## 11. 实机验收

启动真实设备、媒体、窗口或输入生产者前，先列出它会改变的音频输出、屏幕内容、窗口焦点、键鼠状态、文件、网络、设备占用和后台进程，并选择满足同一合同的最低扰动输入。音频传输、编码和解码优先使用静音或不可听输入，振幅与信号质量离线验证；不得用持续刺耳的测试音充当默认端到端证据。用户对副作用提出异议时，立即停止本次启动的准确生产者，确认设备和后台任务已经释放，再从测试调用点、工作流和说明中退出该模式，不能把同一副作用降级后继续播放。

桌面外壳至少检查：

1. Windows 实际开发或生产窗口，不只看浏览器预览。
2. 每个窗口呈现状态的外壳、内容区尺寸、系统保留区和用户位置。
3. 每条活动状态转换至少完成一次 `A → B → A` 往返；高频往返再重复一次，确认没有累计位移、错位或状态残留。
4. 用户先把窗口拖到其它位置，再执行展开、收起、导航和主要按钮，确认不会无故归位。
5. 正常、最大化、还原、最小尺寸，以及同缩放和不同缩放的多显示器移动。
6. 项目承诺的系统缩放与文字缩放，至少覆盖 100% 和一个高缩放目标；目标环境使用 200% 时必须纳入。
7. 浅色和深色主题，聚焦和失焦。
8. 标题栏拖动、调整大小边缘、双击、系统快捷键，以及与拖动区同层控件的真实指针命中和窗口按钮。
9. 侧栏、标题栏、系统按钮保留区和内容分隔线的准确边界。
10. 关闭成功、保存失败、冲突、重复点击和再次启动；自动重开通过公开释放完成或失败状态推进，不等待私有任务或固定睡眠。
11. 屏幕捕获产品从最终录制产物验证所有应排除和应保留的自有窗口。
12. 有辅助进程时验证连接前所有权、终止事件顺序、订阅者排空、退出码、流编码和无孤儿进程。
13. 有后台界面工作时使用代表性真实输入证明事件循环在任务终态前仍能处理无冲突输入，正常完成、替代、取消和关闭只提交匹配结果并排空任务。
14. 有延迟界面工作时验证页面替换、语言或主题重载、窗口关闭后的事件排空，没有销毁后访问、过期回调或延迟写入。
15. 从自然入口遍历全部主要、延迟创建和覆盖型表面，首次进入与再次进入都没有运行时框架错误。
16. 进程级启动或单例状态通过同一个生产 `main` 入口在新进程中验证。
17. 终端与应用界面都没有权限报错或未处理异常。

截图只证明某个静态时刻。窗口行为需要真实输入和状态往返；系统保留区问题同时记录窗口、内容区、标题栏与控件矩形。关闭链需要真实操作与重启结果，捕获排除需要最终录制产物。

## 12. 输出

返回窗口外壳选择、呈现状态矩阵、外框与内容区边界、系统保留区、位置与拖动合同、原生权限映射、捕获可见性、辅助进程与终止合同、界面线程和后台工作所有权、延迟界面工作所有权、关闭链、持久化链、实机检查和仍未验证的平台。只完成静态检查时明确说明没有验证真实窗口。
