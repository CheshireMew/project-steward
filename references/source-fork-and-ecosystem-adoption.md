# 独立源码分叉与生态吸收治理

用于以外部项目源码为一次性起点建立独立产品，或者从上游核心、扩展、插件和工作流中选择性吸收成熟机制，同时明确不再自动跟随上游核心更新的改动。目标是保留可核对的源码血缘和授权责任，让目标项目取得产品、运行时、数据、版本和维护的完整所有权；参考来源不在分叉后继续成为隐藏核心。

普通的项目研究只负责讲懂来源和给出采用建议。用户只希望借鉴一个算法或局部行为、没有建立新产品身份时，继续使用改动前预防中的参考能力采用合同。只有源码会进入目标产品、目标要脱离上游发布节奏，或还要同时支持上游扩展生态时，才叠加本方法。检查和方案保持只读；复制源码、修改目标项目、安装依赖、运行、归档、删除、提交、打包和发布继续分别授权。

## 1. 先确定与上游的真实关系

同一个“基于某项目开发”至少可能表示四种不同合同，开始前只能选择已经由用户结果和目标架构证明的关系：

| 关系 | 上游在目标运行时中的地位 | 正确边界 |
| --- | --- | --- |
| 运行时依赖 | 目标安装或运行时继续调用上游包、服务或可执行文件 | 按外部依赖和兼容版本治理，不能声称已经独立 |
| 一次性源码分叉 | 固定来源版本进入目标仓库，之后由目标项目维护 | 上游只保留来源、许可证和历史身份，不继续拥有核心更新节奏 |
| 兼容适配器 | 目标原生核心独立，上游 API 或扩展通过边界外侧的可选适配器接入 | 适配器可依赖目标稳定接口，目标核心不得反向依赖适配器 |
| 机制借鉴 | 只采用行为、算法、测试思想或交互机制，不复制实现 | 目标按自身架构原生实现；仅因方法学习不把来源列为正在使用的依赖，也不自动产生 README 致谢 |

来源项目可同时以不同关系服务不同能力，例如核心使用一次性分叉、部分扩展只借鉴机制、公开扩展 API 由兼容适配器承接。必须逐项登记，不能用一个仓库级标签掩盖不同依赖方向。关系尚未确认时先交付选择合同；不能先复制源码或接通运行依赖，再把结果解释成用户已经接受的独立产品。

### 原始上游、fork 与 README 致谢

拿到 fork、镜像、压缩包或二次整理时，先沿仓库声明、许可证、包元数据、提交和文件差异追溯原始上游，并判断实际采用的内容由哪一层产生。只采用原始上游已有内容时，来源指向原仓库；实际采用 fork 的独有改动时，再把 fork 作为另一项来源。不能因为用户提供的是 fork，就用 fork 地址替代真正的原始上游。

采用台账必须在写入前区分：

- **直接复用或改编后再分发**：代码、脚本、模板、提示词、文档正文、示例、schema、数据、图片、音频、视频或其它资源被复制、翻译、改写、格式转换、抽取成新数据，或以仍可识别的表达进入目标项目。目标根 README 必须增加或更新“第三方资源与致谢”，列出准确上游链接、版权与许可证、复用范围和目标路径、修改性质，并链接保留完整许可证或 NOTICE 的详细说明；采用 fork 独有改动时再单列 fork。
- **方法学习后的独立实现**：只吸收高层方法、架构判断、视觉锚点、核心动作、工作流、测试思想或防止近似复刻的方法，由目标按自身架构重新实现，且没有复制来源 IP、代码、资源、示例或实质相同的表达。仅因这类研究不强制增加第三方致谢，也不能把来源写成目标依赖；明确引用、事实归因或其它许可义务仍按实际用途处理。

关系依据实际进入目标的内容，不依据“参考”“借鉴”“重写”之类自我描述。来源身份、许可或复用关系无法确认时，候选不得进入活动产物。

## 2. 冻结独立产品合同

一次性分叉开始前建立：

```text
目标产品和主要用户结果：
目标仓库、发布单元和命令身份：
公开产品名称与必须保持或迁移的技术标识：
核心包或模块命名空间：
配置、数据、缓存、日志和凭据边界：
任务、状态、持久化与恢复的唯一真源：
原生协议、扩展 API 和兼容适配器边界：
目标版本、发布节奏和支持平台：
上游来源版本、最后参与方式和退出条件：
以后如何发现、审计和选择性采用上游变化：
源码、构建产物、当前实例采用、打包与发布的停止位置：
```

独立不是换一个命令名或复制一份仓库。目标必须自己拥有产品决策、公共接口、任务或领域状态、数据目录、版本和失败收口；上游不能继续通过内部导入、共享配置、自动升级、默认数据路径、隐藏启动器或测试夹具决定核心行为。确实需要保持的协议或技术标识单独记录兼容原因和期限，不能为了字符串统一破坏外部合同，也不能让旧公开身份继续出现在活动用户入口。

## 3. 建立来源与采用台账

每项进入目标项目的第三方能力至少记录：

| 字段 | 必须回答 |
| --- | --- |
| 来源身份 | 原始上游及必要的 fork、包或制品，以及固定提交、版本和内容哈希 |
| 授权 | 许可证、版权、NOTICE、再分发与修改义务，无法确认时不得进入活动产物 |
| 用户结果 | 它在来源中解决什么问题，目标为什么需要 |
| 采用关系 | 运行时依赖、一次性源码分叉、兼容适配器、直接资源复用或机制借鉴 |
| 采用范围 | 实际进入的文件、模块、算法、状态约束、界面机制或测试 |
| 目标所有者 | 进入后由哪个目标模块、接口和维护责任接管 |
| 修改内容 | 为目标架构、协议、平台和生命周期做了什么改变 |
| 移植测试 | 哪些上游有效测试被保留，目标又增加哪些平台、恢复与用户链测试 |
| 拒绝部分 | 哪些能力、依赖、平台假设或数据模型不适用，以及原因 |
| 后续升级 | 默认不跟随、人工审计或有期限的外部兼容范围 |

台账描述实际进入的内容，不把整个上游仓库笼统列为来源。复制代码时同时使用许可证治理核对 Fork、NOTICE、版权和重新授权边界；只保留链接或包名不能代替适用许可证与内容身份。平台假设、临时存储、沙箱能力、后台生命周期或数据技术不符合目标合同时，应明确拒绝或在目标边界重做，不能因为上游实现成熟就把不匹配部分一并继承。

## 4. 核心内化与外围兼容只允许单向依赖

目标原生核心拥有业务任务、领域状态、持久化、恢复、模型或 provider 抽象、扩展 API 和用户结果。内化源码完成后，核心模块通过目标命名空间和目标公共接口交互；上游类型、全局状态、默认配置和恢复 helper 不得继续作为目标内部合同。

兼容适配器是独立版本的外围产品，只负责：

- 把已声明支持的上游扩展版本映射到目标稳定扩展 API；
- 在安装或启用前展示来源、版本和能力要求；
- 把不兼容版本在进入核心前明确拒绝；
- 保留兼容矩阵、迁移期限和删除或升级测试。

目标核心不能导入兼容包，不能为兼容包复制第二套任务状态、配置、持久化或结果解释，也不能让兼容测试夹具成为核心默认运行前提。兼容包可以作为目标 API 的消费者；删除兼容包后，目标原生 CLI、服务、数据和扩展仍应完整运行。外围渠道、集成和可选工作流同样不得因为功能丰富而进入核心启动链。

## 5. 分叉迁移面包含所有活动消费者

建立标识符和所有权清单，一次迁移：

```text
源码导入、包名、模块命名空间与公共导出
命令、帮助、版本、User-Agent、遥测与错误文案
配置键、环境变量、数据目录、缓存、日志和凭据位置
协议名称、schema、能力描述、扩展 API 与生成物来源
测试配置、模块别名、mock、fixture、测试 helper 与默认测试入口
构建脚本、原生宿主、资源清单、打包与发布配置
活动文档、示例、SDK 片段、迁移工具和真实用户链脚本
```

来源名称可以留在第三方通知、来源台账、明确历史材料和边界外侧兼容包中。活动核心中的旧命名、旧配置、旧恢复逻辑和旧工具链入口必须退出；测试、构建、文档和示例是正式消费者，不能从残留扫描中整体排除。宽泛搜索命中自然语言时逐项分类，不能为了得到零匹配删除来源和许可证证据。

上游有效测试与被吸收实现一起迁移，并增加目标自己的命名空间、平台、取消、失败、重启、恢复和协议测试。每项声明采用的能力都要进入目标默认测试入口，或者进入本轮明确必需且会单独运行的验收矩阵；测试文件存在但默认命令没有选择它，只能证明测试材料存在。迁移工具链本身发生失败时先修复配置、别名、fixture 或测试驱动，不能修改产品去迎合仍在消费旧身份的验证器。

## 6. 上游变化是新的采用事务

“不再跟随上游”意味着目标核心没有自动同步、定期合并或无审计升级通道。以后发现上游修复或新能力时，把它作为新的候选：

1. 固定新的来源身份并读取从当前已采用版本到候选版本的准确变化。
2. 重新判断用户结果、许可证、运行假设和目标缺口。
3. 选择拒绝、机制借鉴、局部移植或兼容适配器升级。
4. 由目标所有者按当前架构实施，更新来源台账、修改说明和移植测试。
5. 从目标正式入口完成新鲜验证，不把上游测试通过当成目标产品已经升级。

不能用长期合并分支、自动依赖更新或兼容包的内部需求重新建立上游对目标核心的所有权。紧急修复仍遵循同一关系，只能缩小候选范围，不能绕过来源、授权、目标所有者和回归证据。

## 7. 分层交付与真实验收

分别记录以下状态，任何一层不得替更高层背书：

| 层级 | 必须证明 |
| --- | --- |
| 源码独立 | 目标核心、接口、状态和命名空间已经成为唯一活动实现，旧核心不再被内部调用 |
| 默认测试 | 每项采用能力的有效测试与目标专项测试由默认入口或批准矩阵真实执行 |
| 普通构建 | 当前源码和资源产生可消费的普通构建输出 |
| 原生或生成产物 | 目标平台正式宿主、可执行文件或生成目录来自当前源码，依赖与资源闭包完整 |
| 兼容边界 | 移除兼容包不影响原生核心；声明支持的每个上游扩展版本经过自己的兼容矩阵 |
| 当前实例采用 | 正式消费者通过稳定运行入口选择目标产物，并满足双方版本、数据和生命周期不变量 |
| 打包与发布 | 获准的安装包、仓库提交、推送和发布分别完成并由真实入口核对 |

真实验收至少覆盖：

1. 从目标正常入口完成一个不加载兼容包的核心用户结果。
2. 由正式生产者生成任务、状态或其它结果，穿过目标自己的协议或持久化边界，被目标消费者读取。
3. 启用一个已声明兼容的扩展时，从暂存、确认到执行和结果消费经过边界外侧适配器；不兼容版本在启动核心工作前被拒绝。
4. 从活动源码、测试、配置、构建、文档、示例和生成物来源执行残留检查，逐项分类旧名称命中。
5. 核对来源台账、许可证和 NOTICE 与实际采用文件一致。
6. 用户没有授权生成原生产物、打包或发布时，让相应层保持未验证或受阻，明确停在源码、测试或普通构建，不运行旧产物冒充当前完成。

## 8. 输出与停止

第一段直接说明目标与上游属于哪种关系，独立性是否已经成立，以及当前实际完成到源码、产物、采用还是发布哪一层。随后交付：

1. 独立产品合同与核心所有者；
2. 来源、授权、采用、修改、测试和拒绝台账；
3. 核心、原生扩展与兼容适配器的依赖方向；
4. 全部活动消费者的迁移和旧路径退出；
5. 人工审计的上游升级政策；
6. 默认测试、普通构建、原生产物、当前实例采用、打包和发布的分层证据；
7. 尚未验证、受阻或需要用户决定的项目。

只要求分析或计划时到此停止。用户授权实施时才修改获准项目根，并在新边界完整承载原功能后退出旧核心、旧命名、旧配置、旧测试入口和内部兼容路径；归档、删除、提交、打包和发布继续服从各自权限。
