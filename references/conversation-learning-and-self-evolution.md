# 对话学习与自我进化

用于从历史对话、用户纠正、实施过程和最终结果中找出 Project Steward 今后应稳定具备的项目治理能力。跨项目可复用的机制更新 Project Steward 自身；项目事实继续由项目原有的代码、测试、规则和文档负责。

## 1. 先完整覆盖过程证据

开始读取前先冻结本次历史材料边界、准确任务身份和用户要求的时间范围。“这个会话”等只含当前任务；用户只要求最近若干消息时，以该范围关闭完整性，不自行升级为完整会话。先区分范围词和优先级词：“尤其”“重点”“特别关注”只改变检查顺序、深度和篇幅，只有“只”“仅”“排除”“不要看”等明确收窄表达才改变范围；强调一项不能排除其它结果。

其它任务链接、参考会话、附件、网页或外部材料，只有本次请求点名或用户确认扩展才纳入。不能因为链接仍在历史里就自动打开，也不能为了显得完整而递归遍历所有引用；只登记未展开指针、所服务结果及采用、排除或推翻状态。旧参考不永久扩张以后复盘范围。

用户明确收窄、撤回或重新扩展材料范围时，立即停止尚未执行的读取，并以最新明确要求重新冻结边界。随后被排除的内容标为“已读取但不参与本轮结论”，不能继续影响当前台账、能力判断或方案；从获准材料重算受影响判断。只有在新边界中登记后才恢复为证据；早先一次排除也不永久阻止用户重新纳入。

每个被纳入的来源分别进入来源—结果账本，不能只给整个材料集合写一个“已读取”状态：

| 来源与固定身份 | 预期范围、取得方式与覆盖游标 | EOF 或完整性 | 回答的事实与当前权威角色 | 实际采用的证据 | 排除的证据与理由 |
| --- | --- | --- | --- | --- | --- |
| | | 完整 / 不完整 / 不可取得 | | 无新问题也要登记 | |

在 Codex 读取完整会话或完整历史时，第一项取证动作固定运行本 Skill 根的 `scripts/read_codex_session.py`。它消费准确的 `CODEX_THREAD_ID` 或 `CODEX_SESSION_ID`，以兼容活动写入的共享只读句柄冻结末尾，只保留最后一个完整换行之前的记录，逐行校验 JSON 与内容身份，返回清单。不得先用普通文件读取、哈希命令、相似标题、最近时间或语义历史探测活动源。一次成功快照是本轮唯一记录真源；范围不变就不重开源。任一取证失败时，只报告脚本的单一结构化失败，不猜路径或换来源。语义历史只核对身份或补充投影；其它宿主选择能关闭范围的最强稳定来源。缺口未闭合即不可取得，不得声称完整。

先建立**公开对话账本**，按时间保留每一条用户可见的用户消息、批注或更正，以及助手 commentary 和 final。系统与开发者指令、隐藏推理、工具调用和工具输出不是公开对话。传输层的 `role=user` 不能单独证明是用户原话；宿主注入的环境、Skill、插件或上下文单列为上下文来源，不得作为用户请求、确认或动作授权，除非存在用户可见且可归因的消息事件或宿主作者元数据。**过程事件账本**按结果登记命令、等待、警告、失败、重试、文件变化、提交、推送和终态。事件身份与顺序必须覆盖完整，冗长载荷不整份灌入对话；判断依赖输出时，才从稳定来源把字段、页、行或字节区间读到可核对末尾。不能把“避免输出淹没”执行成删除失败、等待或范围变化。

对文件、差异、对话或 Git 历史发起可能无界的读取前，先取行数、字节数、分页能力或输出预算。只有已经证明能够在一次返回中完整容纳的来源才整份读取；否则固定身份分段覆盖到 EOF 或明确末尾。截断或未读即未完成。任何明确必选来源未完成时，不得声称“全部来源”“完整历史”；一个来源没有贡献新问题也必须交账。大结果按消费者收窄，证据读到边界。Git 仅在准确项目根直接存在 `.git` 且确需时读取，不能先在任意当前目录运行 Git。

完整性不等于当前权威性。每项会改变判断的来源还要记录它回答的是目标意图、当前实现还是历史原因，取得时刻，适用的项目状态、运行环境、分支、版本或提交，是否被用户接受或后续纠正，以及它能证明到哪一层。当前用户明确纠正和已接受合同决定目标行为；当前运行结果、源码、配置与测试只证明对应状态下的实现；Git 提交、旧截图和旧方案只证明其历史时点，不能因为内容更完整或更容易读取就恢复成当前目标。

来源冲突时不按单一“最新”或固定来源顺序粗暴覆盖。先按正在回答的问题比较适用范围：目标意图看当前明确要求与接受结果，当前实现看同一工作树、产物和运行入口，历史原因看对应提交与当时证据。无法取得可靠目标基线时，先形成一份可人工核对的行为合同，标明必须保持、明确改变、已经否定和仍未知的行为；不能从旧 Git、过期测试或一次稳定截图补造产品意图。

进入深度分析和能力比较前，先从时间扫描中列出每个用户最终结果并给出处置，防止醒目的专项吞掉其它结果：

| 用户结果 | 首次请求、追加或纠正 | 优先级与依据 | 处置 | 正式所有者或去向 | 当前证据 |
| --- | --- | --- | --- | --- | --- |
| | | | 现有能力已完整覆盖 / 现有能力未被消费 / 值得吸收的新缺口 / 项目事实 / 不持久化 | | |

每项结果都必须进入这份覆盖账本，即使结论只是“已有能力完整覆盖，本轮不修改”。已有专项方法、项目事实或一次性细节不能因为不需要新增规则就从复盘中消失；它们仍要有明确处置，之后才允许把写入范围收缩到真正缺失的能力。

开始分组前，先按时间恢复一次完整过程台账。台账覆盖当前会话和用户明确提供的历史材料中的：

```text
用户请求与结果变化
→ 判断、选择、授权与停止位置
→ 实际动作、命令、等待与外部状态
→ 警告、超时、重试、中断、返工与半成品
→ 用户纠正、确认、拒绝与最终证据
```

每条过程信号至少记录发生顺序、它试图服务的结果、当时可见状态、后续怎样证实或推翻，以及是否可能改变未来动作。然后把每条信号归入一个用户结果、多个结果共有的问题、仍未知的事项，或完成影响分析后确认无关的偶然信息。最终结果负责组织证据，不是预先筛掉过程细节的条件；“没有直接进入最终产物”本身不能证明一条信号不重要。

新的独立请求替换上一项尚未完成的结果时，也要保留切换时刻本身。若上一结果已经写入但尚未完成验证，交接状态至少包括已经写入或改变的对象、已经成立的证据、尚未验证的用户可见承诺、本轮启动的进程与残留，以及原权限和停止位置。新请求不授权继续或回退旧结果；完成这份最小交接后，为新结果重新建立材料边界、权限和停止位置。

用户在原结果尚未完成时补充图片、许可证、仓库可见性、配置迁移、性能或其它要求，先判断它是原结果的新增验收项还是明确替换它的新结果。新增验收项进入同一闭环账本，记录提出顺序、所属结果、授权、正式消费者、完成证据和仍缺项；后续计划只能重排执行顺序，不能覆盖较早仍有效的要求。准备回答“都做完了吗”或最终交付时，从最新材料边界中的全部仍有效请求重新生成完成清单，逐项回读证据，不能沿用某一版中间计划或只汇报最后处理的专项。

在把后续表述记为范围变化前，先区分基线纠正、同一结果增项和独立新结果。用户指出已经存在但先前误读的产品身份、环境事实、限制或目标，不是新增范围；它使基于错误基线的方案、估时与确认失效，相关返工归入假设或基线调查不足。只有在正确基线上增加新的验收承诺，才记入同一结果增项；输入职责、正式消费者或停止位置不同的要求建立独立新结果。耗时报告不得把基线纠正造成的返工归因于用户扩项，也不得把独立结果藏进原结果的实现时间。

警告、等待和超时必须恢复到足以解释实际状态。至少区分外层命令执行器超时、网络或构建工具自身超时、应用退出，以及原进程仍在运行；记录当时处于下载、配置、生成、编译、链接、安装、启动还是验证阶段，进程、日志和产物是否继续变化，是否已有退出码，以及正式消费者能否读取结果。只有这些事实才能判断应该继续观察、停止、修复后重试，还是避免与尚未结束的原任务重复运行。

过程盘点、能力搜索和结构验证包含多个探测时，先区分前后依赖、必需项与可选项，并在执行前核对各自前置条件。相互独立的探测只有在编排器能逐项保留成功输出、错误和退出状态时才可并行；任一探测使整个批次提前中止并遮蔽同批其它结果时，说明证据编排本身失败，不能据此认定其它探测也失败。保留已经取得且仍新鲜的结果，只单独补跑未返回或状态未知的项目。

完整过程台账是本轮分析工具，不是新的长期经验库。提炼完成后，只有会改变未来路由、动作、验收或停止位置的稳定机制进入活动 Skill 资源；项目事实进入项目已有真源；经过确认的用户与机器事实进入已获授权的用户环境档案；其余过程细节随本轮结束。

## 2. 再按用户最终结果分组

一段对话可能同时完成、失败或纠正多个结果。先识别每个用户真正要看到或使用的结果，再分别恢复：

```text
用户最终结果
→ 为得到它采用的决定和动作
→ 生产者、边界、消费者与实际产物
→ 用户接受、纠正或拒绝的内容
→ 最终证据和仍缺的证据
```

两个结果只有在输入职责、目标结果、正式消费者和停止位置都相同时才合并；发生在同一个文件、同一轮改动或同一主题下，不足以证明它们是同一结果。

调用一个 Skill、修改该 Skill 自身、修改目标项目和优化目标仓库的公开展示默认是四个独立结果。某条路径自带的提交、推送或工作流派发只属于该路径自己的结果，不能因为共用同一个 Skill、Git 工具或用户回合，就扩张到其它结果。

成功经验和暴露的问题都属于候选。用户明确认可、重复选择、可复现成功或最终用户链成立，可以证明成功机制；用户纠正、返工、半迁移、结果失效或验证缺口，可以证明现有机制缺失或错误。后来的明确纠正覆盖冲突的早期判断，但不会抹掉仍然成立的约束。

## 3. 对异常结果先做因果排序

任一结果包含失败、用户纠正、保护拦截、临时绕行或残留时，在选择主要学习主题前先读取 `root-cause-remediation.md`，并按固定层级建立因果台账：

```text
观察到的现象或结果
→ 直接触发或直接原因
→ 合法保护或约束
→ 最早有证据支持、且可由当前系统控制的架构或根所有权原因
→ 临时绕行
→ 残留或放大因素
```

每层分别记录证据、当时状态、它是否改变了用户结果，以及它与前后层的关系。保护规则准确阻止了不可保证的操作时，它是合法边界，不因为用户看见了报错就成为主要问题；保护规则本身错误时，才把它作为待治理原因。临时盘符、复制、缓存、重试、回退或其它绕行只说明问题如何被暂时避开；重复映射、孤儿文件、陈旧状态或误导性入口只说明绕行留下了什么。它们可以形成独立的清理结果，但不得覆盖更早的主要原因。

主要学习主题选择最早一个同时满足“证据成立、当前系统可控制、改变它会阻止同类结果”的原因。若只能证明直接原因，不能补造更深的架构解释；把更深层标为未知，并以直接原因作为当前主题。多个彼此独立的用户结果继续分组，例如根所有权错误和产品身份混淆可以同时成立，不能为了突出根因删掉另一个结果。

后续用户纠正或新证据改变主要原因时，现有能力台账、影响文件、代表性输出和验证方式都要重新生成；基于旧主要原因取得的确认随之失效，必须重新向用户确认后才能写入。不能把纠正只追加成次要备注，再继续执行旧方案。

## 4. 对每个结果同时提炼正反两面

逐组回答：

```text
什么做法已经被结果证明有效？
它为什么有效，依赖哪些条件？
哪个决定最早使结果偏离？
为什么原流程没有更早发现？
下一次应在哪个判断、动作或验收点预防？
```

“没有报错”不等于成功；正式生产者产生结果、结果经过真实边界、正式消费者读取并形成用户可观察结果，才是完整成功证据。终端出现警告也不自动等于失败，应结合产生阶段、退出状态、正式产物和用户链判断。先前的“已经完成”若被后续残留扫描、重启验证或真实消费者结果推翻，应以最后成立的证据重新归类，不能保留较早结论。验证工具、扫描器或审计命令自身失败时只能标为未知，不能把空输出或后续命令的成功当成零发现。验证器成功退出也不等于已覆盖预期对象；它实际读取的输入为空、过期，或被过滤与排除规则遗漏时，结论仍是未覆盖或未知，不是通过。

### 同时判断目标能力的职能边界

对每个结果完成正反提炼后，不只问“要不要增加一条规则”，还要判断目标 Skill 当前活动职能是否完整承载历史中反复出现的上层用户结果。职能边界判断使用以下台账：

```text
目标 Skill 当前承担什么：
历史中反复出现的用户最终结果：
哪些相邻能力构成同一个上层角色：
哪些只是单次需求或独立能力：
当前职能过窄、过宽还是适当：
建议保持、扩大或缩小：
默认能力与按需能力：
操作权限是否变化：
证据强度和仍需确认的假设：
```

正常成功经验和纠偏证据都可以进入这项判断，但强度必须分开。用户明确说出希望获得的上层结果、在不同任务中反复提出相邻结果、明确接受或重复选择同一种能力组合、正式生产者到最终消费者的用户链可复现成立，以及独立正式合同，都可以支持保持或扩大。用户没有继续纠正、没有回复或没有修改，一次结构检查通过，一次看起来顺利但没有最终消费者证据，或一条泛化的行业惯例，都不能单独算作长期接受或职能扩大的充分证据。

相邻能力只有共享输入职责、最早判断、核心对象或内容来源、上层用户结果和正式消费者时，才组合成一个完整上层角色。只共享主题、文件位置、界面表面或实现技术的能力继续独立；不能因为“可能有用”就把所有相邻领域并入一个 Skill。扩大后还要区分默认能力与按需能力：共同的首轮判断可以成为默认路径，昂贵研究、外部检索、生成、运行或专项实施继续由触发条件加载。

缩小职能必须有正向证据，例如用户明确排除某类结果、该能力反复误触发并与核心角色冲突，或职责已经迁入另一个有正式入口和消费者的能力。历史中没有出现某项能力、用户没有逐项列举、当前案例没有使用，均不足以证明它应当退出。一次对话只能证明一个单次需求时，把它留作候选或按需分支，不能立即改写整体定位。

能力范围与动作权限是两个合同。扩大一个 Skill 能判断、研究、设计或治理的结果，不自动增加联网、安装、运行、写文件、删除、提交、发布或其它改变状态的权限；这些动作继续由当前请求和宿主规则分别决定。后续纠正证明早期行为合同过窄时，重新建立整体行为合同，迁移 frontmatter、主路由、活动方法、资源、输出、停止位置、README、元数据和测试中的全部正式消费者，并退出旧身份；不能在旧定义后不断追加能力清单，留下两个并行活动角色。

方案阶段把这份完整上层角色合同作为一个整体进入一次整体确认，说明哪些能力属于同一角色、哪些仍独立、哪些默认执行、哪些按需触发以及动作权限是否变化。不要求用户不厌其烦地逐项补全可以由强证据推导出的相邻能力；证据不足或会实质改变角色的假设集中列出，再由用户确认。

如果多个问题在主要测试已经通过后，仍在末尾残留检查中依次出现，不要把每个补丁分别保存成经验。先判断这些问题能否由同一组派生维度提前生成：权限归属是否改变，状态处于哪个生命周期节点，数据经过哪种表示或分片，边界是否发生转向，以及用户入口最终选择了哪个运行产物。能够统一解释多个问题时，真正缺失的是事前方法没有生成这些同源变体；最早预防点应前移到接口和验收合同形成之前，而不是把“最后再多搜一遍”固化成新流程。

用户对“是否继续、何时交付、要不要每轮再确认”的纠正也是行为证据。若用户已经授权一个实现结果，并明确要求自行迭代到证据充分后停止，应提炼的是任务连续性合同：内部轮次不是新的授权边界，进度更新不等于最终交付，同一用户结果、同一受影响链和已冻结权限内的新证据可以直接进入下一轮；无关问题、新产品决定或需要新增权限的动作仍然停下。不能把这类纠正抽象成不受范围约束的“持续做更多”，也不能继续要求用户用“继续”维持一项尚未完成的同一任务。

用户追问“是不是卡住了”“为什么这么久”或“现在在做什么”时，把它视为过程透明度证据。先还原当时是在继续产生新证据、等待外部状态、执行必要验证、等待用户决定，还是已经把一个简单结果扩张成无关审计；不能仅从工具仍在运行推断沟通已经成立。能够跨项目保留的机制不是增加无意义播报，而是在工作扩展或状态变化时说明原因、完成检查点、当前状态、下一项可观察结果和输入需求。它既不能削减结果所需的真实验证，也不能用“流程需要”掩盖范围扩张。

用户要求解释每项工作为什么慢时，按用户结果建立耗时账本，而不是用整段会话的体感或测试总时长替代：

```text
用户结果：
主动检查与实现时间：
工具、构建和 CI 等待时间：
诊断、返工和重复验证时间：
等待用户决定或外部状态时间：
从请求到交付的墙钟时间：
可避免的瓶颈及下一次怎样消除：
时间证据来源与精度：
```

能取得命令起止、CI 时间戳、提交时间、消息时间或进程记录时分别计算，不把并行任务时长相加成墙钟时间，也不把外部等待说成实现耗时。历史没有可靠时间戳时，明确说明无法准确还原，只提供有证据的区间、相对占比或已观测命令耗时；不能为了回答完整而编造每项分钟数。

### 因果主题确定后，先恢复构成性细节

成功结果且没有失败、纠正、保护拦截、临时绕行或残留时，直接从已经证明有效的机制开始。存在这些信号时，必须先完成第 3 节的因果排序；只有主要原因对应的有效机制，以及确属另一个用户结果的独立次级问题，才进入具体能力比较。现象、失败绕行、残留、项目专名和偶然参数保留各自证据职责，不因醒目或出现得晚就升级成长期能力。

逐项记录：

```text
经过证据或因果判断的有效机制或独立结果：
它让未来治理者多注意什么、区分什么条件：
它会改变什么判断、动作、内容、交互、验证或停止位置：
构成性细节、可调参数和偶然细节分别是什么：
它与主要原因、独立次级结果、绕行或残留的关系：
```

项目路径、文件名、报错原句和一次阈值可以帮助还原机制，但只有替换后会漏认同类问题或选择错误动作的部分才是构成性细节。绕行或残留本身只有在形成独立、反复可识别的用户结果，并且存在不同的正确处理时，才作为次级能力候选；它们仍不能取代主要原因。

### 抽象前逐项比较当前具体能力

按 `SKILL.md` 的共同判断标准暂时遮住来源，逐项检查目标是否能认出同一条件、知道该细节为何重要，并作出同一治理选择、内容决定或验证。全部成立且活动流程确实会读取时，结论是**具体细节已经存在**；只有上位方法或相似术语时是**只有大方向**；目标尚无且通过价值门槛时是**值得吸收的新细节**；证据不足、只属于当前项目或不会改变未来结果时是**不吸收**。

涉及机器资源或项目运行链时，再比较触发条件与适用请求、实际动作与输出结果、唯一真源、活动入口和正式消费者、验证方式与停止位置，以及修改前适用请求、入口和消费者与修改后适用请求、入口和消费者。相似文字、reference 可达或结构测试通过不能代替具体处理；共享规则被缩窄仍属于回归。

### 先排除模型与宿主已经拥有的职责

候选机制如果主要用于补偿旧模型或旧工具不会选择上下文、理解任务、规划步骤、进行普通澄清、选择工具、协调 Agent、维持对话进度，或者为不同 AI 产品复制提示词格式、命令模板、工作流状态和适配目录，先核对当前模型、宿主和厂商工具已经公开提供且本轮实际可用的能力。当前原生边界已经能完成同一用户结果时，结论是**不吸收**；不能因为参考项目规模大、支持的厂商多或旧版本曾经需要这些设施，就在 Project Steward 内建立第二套编排器、集成注册表、扩展市场、持久工作流或模型操作说明。

模型负责语义理解、上下文选择、方案比较、步骤规划和工具选择；宿主与厂商运行时负责工具协议、Agent 编排、任务连续性和产品适配；项目真源负责业务事实、稳定身份、schema、权限、原子写入与恢复；Project Steward 只补充会改变治理决定和真实验收的跨项目方法。只有当前原生能力无法表达一项已经证明必要的持久项目合同、确定性边界或用户可观察保证时，才吸收这项最小缺口，并写清当前能力证据、缺失结果、唯一所有者、正式消费者和停止位置。模型偶尔犯错、提示词可以写得更长或理论上能够减少一次人工判断，都不能单独证明需要新的持久机制。

### 比较完成后再提炼共同路径与特殊维度

每项完成具体比较的经验再做两次互不替代的提炼：找一类请求共同需要的机制，再找只有特定条件成立时才会改变处理方式的特殊维度。这不是分类时的二选一；同一份证据、同一个用户结果可以同时支持共同机制和一个或多个特殊维度，再进入价值或归因门槛。

```text
共同机制：去掉专项名称和表面症状后，仍会改变哪类请求
适用的共同请求：哪些不同表面问题共享这条路径
最早共同决策点：最早在哪里识别、行动或验证
特殊条件：平台、版本、规模、顺序、生命周期或其它构成性条件
特殊条件改变什么：识别 / 观测 / 动作 / 验证 / 停止位置；内容与交互差异也在此说明
两层怎样共同消费：先执行哪段共同路径，何时叠加哪些特殊维度
各自唯一真源和消费者：共同规则与专项规则分别由谁维护、由谁读取
```

共同机制不能以某个专项症状命名并只服务该症状，否则共同路径会被特殊问题吞掉。特殊维度也不能被压缩成“按情况处理”；删掉某项条件后，如果 Agent 将无法发现问题、会选择不同动作、写出不同内容、使用错误证据或在错误位置停止，就保留足以重新识别和处理它的细节。一个结果同时符合多个特殊条件时可以组合消费，但每项决定只在一个真源维护。

如果一项所谓特殊条件并不改变识别、观测、动作、内容、交互、验证或停止位置，它只是当前案例背景，不进入活动能力。如果共同机制已经完整覆盖所有情形且不存在不同处理，也不为形式完整另建专项资料。完成这一步和后续价值门槛后才做历史责任归属；不能用目标 Skill 当时是否启用来决定哪些经验值得提炼。

## 5. 找到最早可改变结果的位置

依次检查：

1. 产品定位、主要用户和核心对象。
2. 内容、状态或数据的唯一真源。
3. 责任所有者、公共接口和调用方向。
4. 平台能力、权限、生命周期和失败收口。
5. 所有生产者、消费者、状态与调用点是否完整迁移。
6. 测试是否经过真实生产者与本次核心边界。
7. 用户最终能否看见或使用结果。

保存能够在这些位置改变未来行为的正向机制，不保存最后一次补丁。专项问题的具体机制由相应活动方法负责；本方法只判断它是否值得进入、应更新哪项能力以及未来怎样被消费。

## 6. 判断证据和可迁移性

| 证据 | 能证明什么 |
| --- | --- |
| 用户明确确认 | 目标、取舍或长期行为被直接确认 |
| 可复现成功 | 从真实入口可再次得到同一结果 |
| 源码、配置或产物 | 当前实现或状态确实存在 |
| 多项事实一致 | 可以形成较强推断，但仍可能缺最终链 |
| 信息不足 | 只能标为未知，不能补造 |

候选能力只有同时满足以下条件才更新 Project Steward：

- 能改变未来的路由、动作、输出、验证或停止位置；
- 去掉当前项目名、文件名、报错文字和偶然数值后仍成立；
- Project Steward 有明确的活动入口和正式消费者；
- 与现有能力相比，确实补足缺口或纠正了会产生错误结果的机制；
- 证据强度与规则强度相称。

只属于当前项目的产品决定、架构事实、文件边界、迁移状态和长期约束，应写回该项目已有的 `AGENTS.md`、设计文档、代码、配置或测试等真实来源。当前任务的报错、补丁、对话顺序、纠正原句和一次性核对留在本轮，不进入长期方法。

可迁移不等于越抽象越好。范围较窄的问题在以下任一条件成立时，仍应作为高频问题模式或专项方法保留：

- 在多个任务中经常发生，通用原则不足以让它被稳定发现；
- 单次发生就会造成严重数据、迁移、发布、平台或用户结果损失；
- 它有稳定因果链和可确定检测信号，能在早期直接拦住错误；
- 平台、版本、项目形态或生命周期阶段确实改变正确动作；
- 缺少具体步骤会让 Agent 再次停在表面修补或错误验证。

这类能力保留必要的触发条件、受影响边界、检测信号、正确动作、失败收口和真实验收。项目专名、偶然路径和一次报错文字仍然退出；决定行为的协议字段、平台限制、生命周期顺序和版本范围不能为了“通用”被抹掉。若稳定特殊问题已有独立消费者，原位强化该专项；没有消费者但确实需要不同方法时，才新增由主路由直接加载的问题模式。

### 最后判断历史责任归属

只有候选经验、共同机制、特殊维度、当前能力差距和持久化价值都已经判断后，才确认目标 Skill 在历史任务中的活动身份。它当时已被用户明确点名，或者宿主与项目规则允许自动路由且实际选中，并且相应主路径进入该用户结果时，才可能对当时动作负责：

| 当时状态 | 历史责任结论 | 当前自我进化动作 |
| --- | --- | --- |
| 已启用，活动能力无法表达正确行为 | 能力本身缺失 | 按已证明的共同机制或特殊维度补足唯一真源和正式消费者 |
| 已启用，正确规则存在但没有进入决定或动作 | 已有能力没有被执行 | 修复最早没有消费该规则的路由或动作门槛，迁移全部消费者，不增加同义原则 |
| 因用户约束、触发条件或任务边界从未启用 | 不能归因于目标 Skill | 不追究历史责任；候选仍按当前职能、能力差距和价值决定是否迭代。若目标应在未点名时自动触发，把项目规则、模板采用或触发策略作为独立结果确认 |

不能从“当前 Skill 现在已经有规则”反推它在历史任务中曾经活动，也不能因为当时未启用就拒绝一个已经证明的当前能力缺口。规则存在但未执行时，在当前任务用表层不同的代表性请求核对行为，并用确定性测试保护稳定结构；规则缺失时才新增机制或专项资料。

### 被否定内容只作为证据，不进入活动能力

被用户拒绝、被后续证据推翻、只为复现问题而保留，或仅在返工中出现的具体方案、提示词、动作、文案、布局、补丁和恢复办法，只用于定位当时缺失的判断。它们不得以案例、默认方法、候选模板、创作参考、few-shot 示例、活动资产或测试夹具的形式进入 Project Steward，也不能通过改名、摘要或抽象成类别标签继续影响后续输出。重复失败能够证明防护机制重要，但不能把失败内容本身升级成默认答案。

值得吸收时，只持久化最早决策点、选择所需事实、适用条件、正确行为边界、正式消费者和可观察验收。确定性测试使用与历史表面不同的代表性请求保护这份正确合同，不复刻被否定内容；需要保留原始失败材料作项目取证时，由项目已有历史或诊断设施负责，活动 Skill 不复制一份。

## 7. 映射到现有能力

为每个通过门槛的候选建立：

```text
用户结果：
目标行为基线、来源角色与适用状态：
目标 Skill 当时的启用、路由与实际消费证据：
当前语义触发条件与主路径：
固定必读方法所有者：
条件专项、适用证据与读取顺序：
动作门槛、正式消费者、验收与停止位置：
已证明有效的机制：
缺失或错误的机制：
最早预防点：
目标 Skill 当前承担什么：
历史中反复出现的用户最终结果：
哪些相邻能力构成同一个上层角色：
哪些只是单次需求或独立能力：
当前职能过窄、过宽还是适当：
建议保持、扩大或缩小：
默认能力与按需能力：
操作权限是否变化：
证据强度和仍需确认的假设：
主要原因、独立次级结果及绕行或残留的证据职责：
会改变未来治理的构成性细节：
当前具体能力结论：具体细节已经存在 / 只有大方向 / 值得吸收的新细节 / 不吸收：
共同机制及其适用请求：
最早共同决策点：
特殊条件及其改变的识别、观测、动作、验证或停止位置：
两层共同消费顺序：
各自唯一真源和正式消费者：
目标现有能力：
需要改变的主路由、方法、资源或验证：
未来怎样观察它已经生效：
```

先检查现有 `SKILL.md`、活动 reference、脚本、模板、测试和元数据，再为每项候选画出一条活动消费链：

```text
用户最终结果与语义触发
→ 主路径
→ 固定必读方法所有者
→ 有适用证据才叠加的条件专项
→ 动作门槛
→ 正式消费者与输出
→ 验收和停止位置
```

消费链必须给出实际证据，不能因为主文件出现了 reference 名称就判定规则已经参与决定。随后把候选归入以下一种状态：

| 状态 | 唯一改动位置 |
| --- | --- |
| 方法缺失或构成性细节不完整 | 原位强化负责该决定的唯一 reference，并迁移直接消费者 |
| 方法完整，但主路径没有固定加载 | 修改主路由的触发条件或读取顺序，不复制方法正文 |
| 路由已经加载，但动作绕过方法 | 修改最早动作门槛和实施入口，不增加同义原则 |
| 正式消费者或验收没有覆盖 | 修改对应消费者、输出或验证，并保留方法唯一真源 |
| 已经完整消费，或没有持久价值 | 不修改活动 Skill |

同一机制只能有一个方法所有者；主文件只负责把请求送到该所有者，测试只保护路由、所有权和消费合同。已有能力表达不完整时原位强化；只有出现边界清楚、会被主路由直接加载且不能由现有所有者内聚承载的新专项方法时才增加 reference。不能为一次对话建立孤立文件，也不能同时保留新旧两条路由。

模板只接收某类项目每次都应执行、无需临场重新判断的稳定默认。仍需根据项目结构和用户目标判断的方法进入 Project Steward 的主流程或专项方法，不借模板替代判断。抽象后的规则如果失去发现该问题所需的具体信号，应回退并补回构成性细节。


## 9. 分支或探索结束

用户准备合并、放弃、回滚或结束一条已经形成认识的分支或探索时，先按用户最终结果分组，再分别处置：

- 已完成且仍属于当前项目的事实，写回项目已有正式真源；
- 已证明可跨项目复用的机制，在用户要求自我进化时进入 Project Steward 能力候选；
- 已经稳定成某类项目默认的能力，进入模板候选；
- 只有来源价值的材料，保留项目已有历史指针；
- 没有形成结论的尝试、临时报错和纠正过程，随本轮结束。

先证明对应目标真实存在，再退出分支或临时材料。没有新结论的普通分支不生成长期记录，也不为了“有复盘”创建新的知识目录。
