# 对话学习与自我进化

用于从历史对话、用户纠正、实施过程和最终结果中找出 Project Steward 今后应稳定具备的项目治理能力。跨项目可复用的机制更新 Project Steward 自身；项目事实继续由项目原有的代码、测试、规则和文档负责。

## 1. 先完整覆盖过程证据

开始读取前先冻结本次历史材料边界。用户说“这个会话”“当前会话”或“这个任务”时，范围只包含承载本次请求的当前任务。当前任务中曾经出现的其它任务链接、参考会话、附件、网页或外部材料，要登记它们在当时服务哪个结果、是否被实际采用以及后来是否被推翻，但不能因为链接仍在历史里就自动打开并把其全部对话并入本轮。

只有本次学习请求明确点名另一项任务或材料，或者用户在看到边界后明确确认扩展，才把它加入本轮语料。用户早先为诊断、比较或实现提供过参考，只授权当时结果使用，不会跨结果永久扩张以后复盘的来源。若另一个任务只是当前 Agent 当时核对后判定无关的参考，这个“曾核对并排除”的动作属于当前过程证据，另一任务的内部历史仍不属于本轮。先记录准确边界和未展开的指针，再开始时间扫描；不能为了显得完整而递归遍历所有引用。

每个被纳入的来源同时记录预期范围、取得方式和完整性标记。工具返回截断提示、下一页游标、未读行区间或省略内容时，该来源仍是不完整状态；按页、游标或稳定行区间继续读取到 EOF 或明确末尾，再用于能力判断。大文件、长差异和大量搜索结果优先缩小到正式消费者、相关区段和可复核范围，不能因一次调用返回成功就假定全部内容已经进入上下文。

完整性不等于当前权威性。每项会改变判断的来源还要记录它回答的是目标意图、当前实现还是历史原因，取得时刻，适用的项目状态、运行环境、分支、版本或提交，是否被用户接受或后续纠正，以及它能证明到哪一层。当前用户明确纠正和已接受合同决定目标行为；当前运行结果、源码、配置与测试只证明对应状态下的实现；Git 提交、旧截图和旧方案只证明其历史时点，不能因为内容更完整或更容易读取就恢复成当前目标。

来源冲突时不按单一“最新”或固定来源顺序粗暴覆盖。先按正在回答的问题比较适用范围：目标意图看当前明确要求与接受结果，当前实现看同一工作树、产物和运行入口，历史原因看对应提交与当时证据。无法取得可靠目标基线时，先形成一份可人工核对的行为合同，标明必须保持、明确改变、已经否定和仍未知的行为；不能从旧 Git、过期测试或一次稳定截图补造产品意图。

开始分组前，先按时间恢复一次完整过程台账。台账覆盖当前会话和用户明确提供的历史材料中的：

```text
用户请求与结果变化
→ 判断、选择、授权与停止位置
→ 实际动作、命令、等待与外部状态
→ 警告、超时、重试、中断、返工与半成品
→ 用户纠正、确认、拒绝与最终证据
```

每条过程信号至少记录发生顺序、它试图服务的结果、当时可见状态、后续怎样证实或推翻，以及是否可能改变未来动作。然后把每条信号归入一个用户结果、多个结果共有的问题、仍未知的事项，或完成影响分析后确认无关的偶然信息。最终结果负责组织证据，不是预先筛掉过程细节的条件；“没有直接进入最终产物”本身不能证明一条信号不重要。

新的独立请求替换上一项尚未完成的结果时，也要保留切换时刻本身。若上一结果已经写入但尚未完成验证，交接状态至少包括已经写入或改变的对象、已经成立的证据、尚未验证的用户可见承诺、本轮启动的进程与残留，以及原权限和停止位置。新请求不授权继续或回退旧结果；完成这份最小交接后，为新结果重新建立材料边界、权限和停止位置。

警告、等待和超时必须恢复到足以解释实际状态。至少区分外层命令执行器超时、网络或构建工具自身超时、应用退出，以及原进程仍在运行；记录当时处于下载、配置、生成、编译、链接、安装、启动还是验证阶段，进程、日志和产物是否继续变化，是否已有退出码，以及正式消费者能否读取结果。只有这些事实才能判断应该继续观察、停止、修复后重试，还是避免与尚未结束的原任务重复运行。

过程盘点、能力搜索和结构验证包含多个探测时，先区分前后依赖、必需项与可选项，并在执行前核对各自前置条件。相互独立的探测只有在编排器能逐项保留成功输出、错误和退出状态时才可并行；任一探测使整个批次提前中止并遮蔽同批其它结果时，说明证据编排本身失败，不能据此认定其它探测也失败。保留已经取得且仍新鲜的结果，只单独补跑未返回或状态未知的项目。

完整过程台账是本轮分析工具，不是新的长期经验库。提炼完成后，只有会改变未来路由、动作、验收或停止位置的稳定机制进入活动 Skill 资源；项目事实进入项目已有真源；经过确认的用户与机器事实进入已获授权的用户环境档案；其余过程细节随本轮结束。

## 2. 再按用户最终结果分组

一段对话可能同时完成、失败或纠正多个结果。先识别每个用户真正要看到或使用的结果，再分别恢复：

```text
用户最终结果
→ 为得到它采用的决定和动作
→ 生产者、边界、消费者与实际产物
→ 用户接受、纠正或拒绝的内容
→ 最终证据和仍缺的证据
```

两个结果只有在输入职责、目标结果、正式消费者和停止位置都相同时才合并；发生在同一个文件、同一轮改动或同一主题下，不足以证明它们是同一结果。

成功经验和暴露的问题都属于候选。用户明确认可、重复选择、可复现成功或最终用户链成立，可以证明成功机制；用户纠正、返工、半迁移、结果失效或验证缺口，可以证明现有机制缺失或错误。后来的明确纠正覆盖冲突的早期判断，但不会抹掉仍然成立的约束。

## 3. 对每个结果同时提炼正反两面

逐组回答：

```text
什么做法已经被结果证明有效？
它为什么有效，依赖哪些条件？
哪个决定最早使结果偏离？
为什么原流程没有更早发现？
下一次应在哪个判断、动作或验收点预防？
这暴露的是 Project Steward 的已有能力没有执行，还是能力本身缺失？
```

“没有报错”不等于成功；正式生产者产生结果、结果经过真实边界、正式消费者读取并形成用户可观察结果，才是完整成功证据。终端出现警告也不自动等于失败，应结合产生阶段、退出状态、正式产物和用户链判断。先前的“已经完成”若被后续残留扫描、重启验证或真实消费者结果推翻，应以最后成立的证据重新归类，不能保留较早结论。验证工具、扫描器或审计命令自身失败时只能标为未知，不能把空输出或后续命令的成功当成零发现。验证器成功退出也不等于已覆盖预期对象；它实际读取的输入为空、过期，或被过滤与排除规则遗漏时，结论仍是未覆盖或未知，不是通过。

还要区分“能力本身缺失”和“已有能力没有被执行”。如果现有路由已经明确规定只读、写入权限或停止位置，但实际行动仍然越界，问题不在于缺少另一句同义原则。应找到最早没有消费该规则的路由或动作门槛，把合同前移到那里，移除冲突提示，在当前任务用表层不同的代表性请求核对行为，并用确定性测试保护稳定结构。只有现有活动能力确实无法表达正确动作时，才新增机制或专项资料。

如果多个问题在主要测试已经通过后，仍在末尾残留检查中依次出现，不要把每个补丁分别保存成经验。先判断这些问题能否由同一组派生维度提前生成：权限归属是否改变，状态处于哪个生命周期节点，数据经过哪种表示或分片，边界是否发生转向，以及用户入口最终选择了哪个运行产物。能够统一解释多个问题时，真正缺失的是事前方法没有生成这些同源变体；最早预防点应前移到接口和验收合同形成之前，而不是把“最后再多搜一遍”固化成新流程。

用户对“是否继续、何时交付、要不要每轮再确认”的纠正也是行为证据。若用户已经授权一个实现结果，并明确要求自行迭代到证据充分后停止，应提炼的是任务连续性合同：内部轮次不是新的授权边界，进度更新不等于最终交付，同一用户结果、同一受影响链和已冻结权限内的新证据可以直接进入下一轮；无关问题、新产品决定或需要新增权限的动作仍然停下。不能把这类纠正抽象成不受范围约束的“持续做更多”，也不能继续要求用户用“继续”维持一项尚未完成的同一任务。

用户追问“是不是卡住了”“为什么这么久”或“现在在做什么”时，把它视为过程透明度证据。先还原当时是在继续产生新证据、等待外部状态、执行必要验证、等待用户决定，还是已经把一个简单结果扩张成无关审计；不能仅从工具仍在运行推断沟通已经成立。能够跨项目保留的机制不是增加无意义播报，而是在工作扩展或状态变化时说明原因、完成检查点、当前状态、下一项可观察结果和输入需求。它既不能削减结果所需的真实验证，也不能用“流程需要”掩盖范围扩张。

### 同时提炼共同路径与特殊维度

每项通过候选门槛的经验都做两次互不替代的提炼：先找一类请求共同需要的机制，再找只有特定条件成立时才会改变处理方式的特殊维度。这不是分类时的二选一；同一份证据、同一个用户结果可以同时支持共同机制和一个或多个特殊维度。

```text
共同机制：去掉专项名称和表面症状后，仍会改变哪类请求
适用的共同请求：哪些不同表面问题共享这条路径
最早共同决策点：最早在哪里识别、行动或验证
特殊条件：平台、版本、规模、顺序、生命周期或其它构成性条件
特殊条件改变什么：识别 / 观测 / 动作 / 验证 / 停止位置
两层怎样共同消费：先执行哪段共同路径，何时叠加哪些特殊维度
各自唯一真源和消费者：共同规则与专项规则分别由谁维护、由谁读取
```

共同机制不能以某个专项症状命名并只服务该症状，否则共同路径会被特殊问题吞掉。特殊维度也不能被压缩成“按情况处理”；删掉某项条件后，如果 Agent 将无法发现问题、会选择不同动作、使用错误证据或在错误位置停止，就保留足以重新识别和处理它的细节。一个结果同时符合多个特殊条件时可以组合消费，但每项决定只在一个真源维护。

如果一项所谓特殊条件并不改变识别、观测、动作、验证或停止位置，它只是当前案例背景，不进入活动能力。如果共同机制已经完整覆盖所有情形且不存在不同动作，也不为形式完整另建专项资料。

## 4. 找到最早可改变结果的位置

依次检查：

1. 产品定位、主要用户和核心对象。
2. 内容、状态或数据的唯一真源。
3. 责任所有者、公共接口和调用方向。
4. 平台能力、权限、生命周期和失败收口。
5. 所有生产者、消费者、状态与调用点是否完整迁移。
6. 测试是否经过真实生产者与本次核心边界。
7. 用户最终能否看见或使用结果。

保存能够在这些位置改变未来行为的正向机制，不保存最后一次补丁。专项问题的具体机制由相应活动方法负责；本方法只判断它是否值得进入、应更新哪项能力以及未来怎样被消费。

## 5. 判断证据和可迁移性

| 证据 | 能证明什么 |
| --- | --- |
| 用户明确确认 | 目标、取舍或长期行为被直接确认 |
| 可复现成功 | 从真实入口可再次得到同一结果 |
| 源码、配置或产物 | 当前实现或状态确实存在 |
| 多项事实一致 | 可以形成较强推断，但仍可能缺最终链 |
| 信息不足 | 只能标为未知，不能补造 |

候选能力只有同时满足以下条件才更新 Project Steward：

- 能改变未来的路由、动作、输出、验证或停止位置；
- 去掉当前项目名、文件名、报错文字和偶然数值后仍成立；
- Project Steward 有明确的活动入口和正式消费者；
- 与现有能力相比，确实补足缺口或纠正了会产生错误结果的机制；
- 证据强度与规则强度相称。

只属于当前项目的产品决定、架构事实、文件边界、迁移状态和长期约束，应写回该项目已有的 `AGENTS.md`、设计文档、代码、配置或测试等真实来源。当前任务的报错、补丁、对话顺序、纠正原句和一次性核对留在本轮，不进入长期方法。

可迁移不等于越抽象越好。范围较窄的问题在以下任一条件成立时，仍应作为高频问题模式或专项方法保留：

- 在多个任务中经常发生，通用原则不足以让它被稳定发现；
- 单次发生就会造成严重数据、迁移、发布、平台或用户结果损失；
- 它有稳定因果链和可确定检测信号，能在早期直接拦住错误；
- 平台、版本、项目形态或生命周期阶段确实改变正确动作；
- 缺少具体步骤会让 Agent 再次停在表面修补或错误验证。

这类能力保留必要的触发条件、受影响边界、检测信号、正确动作、失败收口和真实验收。项目专名、偶然路径和一次报错文字仍然退出；决定行为的协议字段、平台限制、生命周期顺序和版本范围不能为了“通用”被抹掉。若稳定特殊问题已有独立消费者，原位强化该专项；没有消费者但确实需要不同方法时，才新增由主路由直接加载的问题模式。

### 被否定内容只作为证据，不进入活动能力

被用户拒绝、被后续证据推翻、只为复现问题而保留，或仅在返工中出现的具体方案、提示词、动作、文案、布局、补丁和恢复办法，只用于定位当时缺失的判断。它们不得以案例、默认方法、候选模板、创作参考、few-shot 示例、活动资产或测试夹具的形式进入 Project Steward，也不能通过改名、摘要或抽象成类别标签继续影响后续输出。重复失败能够证明防护机制重要，但不能把失败内容本身升级成默认答案。

值得吸收时，只持久化最早决策点、选择所需事实、适用条件、正确行为边界、正式消费者和可观察验收。确定性测试使用与历史表面不同的代表性请求保护这份正确合同，不复刻被否定内容；需要保留原始失败材料作项目取证时，由项目已有历史或诊断设施负责，活动 Skill 不复制一份。

## 6. 映射到现有能力

为每个通过门槛的候选建立：

```text
用户结果：
目标行为基线、来源角色与适用状态：
已证明有效的机制：
缺失或错误的机制：
最早预防点：
共同机制及其适用请求：
最早共同决策点：
特殊条件及其改变的识别、观测、动作、验证或停止位置：
两层共同消费顺序：
各自唯一真源和正式消费者：
目标现有能力：
需要改变的主路由、方法、资源或验证：
未来怎样观察它已经生效：
```

先检查现有 `SKILL.md`、活动 reference、脚本、模板、测试和元数据。已有能力表达不完整时原位强化；职责已有正确真源时修改该真源和所有消费者；只有出现边界清楚、会被主路由直接加载的新专项方法时才增加 reference。不能为一次对话建立孤立文件，也不能同时保留新旧两条路由。

模板只接收某类项目每次都应执行、无需临场重新判断的稳定默认。仍需根据项目结构和用户目标判断的方法进入 Project Steward 的主流程或专项方法，不借模板替代判断。抽象后的规则如果失去发现该问题所需的具体信号，应回退并补回构成性细节。

## 7. 分析与写入边界

- 用户只要求“看看、分析、复盘、总结”时，交付候选能力和建议落点，保持只读。
- 用户明确要求“吸收、自我进化、更新、优化或迭代 Project Steward”时，本方法产出完整能力台账、行为合同、代表性输出骨架、影响文件和可观察成功结果，然后返回主路由并停止；写入权限由主路由的两阶段确认结果决定。
- 用户明确要求更新当前项目规则时，只修改该项目已有的正式真源，不顺带修改 Project Steward。
- 一次请求同时包含多个结果时，每个结果分别决定只读、项目写入或 Skill 自我进化权限。

用户确认后、开始写入前，回读拟修改的全部活动文件，并与方案快照比较。变化触及行为合同、影响文件、直接消费者、验证方法或用户可见结果时，原确认已经不足以覆盖当前方案：先更新能力台账与影响说明，再请用户重新确认。只有非冲突变化且不改变批准范围时，才保留原确认并在最新基线上合并；不能把旧快照上的确认当成持续覆盖未来文件状态的授权。

复盘权限时以原始请求中的动作动词为证据。“检查、审计、诊断、评估、分析或报告”不授权项目写入；后来的“提交、推送或发布”只授权处理已经存在且准确核对的改动，不能反向证明之前的项目修改获得过授权。对越界动作本身可以提炼预防机制，但不能把最终结果看似成功当成授权正确的证据。

修改 Project Steward 时，先建立完整活动能力台账，迁移保留全部既有职责；把正确机制前移到最早路由和方法位置；只更新本轮行为实际影响的直接消费者与确定性测试。用户可见承诺变化时才更新 README，Skill 定位或默认入口变化时才更新元数据。确定性测试保存稳定结构与消费者合同，不保存这次纠正对话的复述；学习条件成立与不成立时的真实读取、动作、输出和停止位置，使用当前任务中表层不同的代表性请求核对，核对材料随任务结束。

自我进化只读取和修改当前活动的 `SKILL.md`、`references/`、`scripts/`、`assets/`、元数据与测试。`archive/` 只保存历史与来源价值，不是活动行为来源；不能从归档恢复旧路由，也不能执行其中的脚本。除非用户明确要求建立一个有正式消费者的持久化设施，否则不创建 `.project-steward/experience`、共享经验仓库或与活动 Skill 并行的第二套经验真源。

## 8. 分支或探索结束

用户准备合并、放弃、回滚或结束一条已经形成认识的分支或探索时，先按用户最终结果分组，再分别处置：

- 已完成且仍属于当前项目的事实，写回项目已有正式真源；
- 已证明可跨项目复用的机制，在用户要求自我进化时进入 Project Steward 能力候选；
- 已经稳定成某类项目默认的能力，进入模板候选；
- 只有来源价值的材料，保留项目已有历史指针；
- 没有形成结论的尝试、临时报错和纠正过程，随本轮结束。

先证明对应目标真实存在，再退出分支或临时材料。没有新结论的普通分支不生成长期记录，也不为了“有复盘”创建新的知识目录。
