# 用户环境档案与执行环境治理

用于建立、读取、核验和更新当前用户的机器环境档案，并在项目实施、构建、测试和排错中使用其中与当前任务有关的事实。环境档案解决“工具究竟在哪里、哪个命令对应哪个版本、包和缓存写到哪里、当前机器该使用哪种终端”这类反复出现的问题。

环境档案是用户级可变运行数据，不属于 Project Steward 源码，也不属于任何项目。Project Steward 保存方法、schema 和确定性工具；用户环境档案默认位于 Codex 用户目录下的 `project-steward/environment-profile.json`。用户提供其它准确位置时使用该位置。

## 1. 进入条件与停止位置

以下请求直接进入本专项：

- 建立、检查、解释或更新当前用户环境档案；
- 确认 Python、Node、Rust、Java、Android、Gradle、包目录、缓存目录或工具链位置；
- 判断当前机器应使用 PowerShell、Bash、WSL 或其它终端；
- 环境差异反复造成安装、构建、测试或启动失败；
- 判断长时间任务是真正失败、仍在运行，还是只有外层等待超时。

其它 Project Steward 路径只有在环境事实会改变本次命令、安装位置、构建方法、验证或停止位置时才读取档案中的相关部分。普通分析、README、许可证或纯架构讨论不为完整性展示扫描整台机器。

用户只要求查看时停在读取与解释。用户要求建立或更新档案时，先完成只读检测和变更计划；只有得到写入授权后才写入。安装、下载、修改系统环境变量和删除工具是独立动作，不由档案写入授权自动获得。

## 2. 唯一真源与数据边界

档案分开保存四类内容：

1. **用户确认的偏好**：首选终端、允许的安装根、下载根、临时目录和默认工具。自动检测不能覆盖这些决定。
2. **机器检测事实**：操作系统、架构、终端、可执行文件、版本、包目录、缓存目录、SDK 和工具链。
3. **运行要求**：某个工具正常工作前必须设置的非敏感环境变量及其值，例如独立的 Cargo 和 Rustup 根。
4. **核验信息**：检测器版本、最后核验时间以及每项事实来自哪个可执行文件或目录。

项目要求、依赖版本、构建参数和源码入口继续由项目规则、配置和脚本负责。一次报错、完整 `PATH`、进程列表、令牌、Cookie、账号、凭据和任意未列入合同的环境变量不进入档案。档案可以说明凭据由哪个系统保存，但不保存凭据内容。

档案 schema 的唯一真源是 `assets/user-environment/profile.schema.json`。确定性操作由 `scripts/user_environment_profile.py` 完成：

```powershell
python scripts/user_environment_profile.py inspect
python scripts/user_environment_profile.py plan
python scripts/user_environment_profile.py apply --write
python scripts/user_environment_profile.py verify
python scripts/user_environment_profile.py resolve --capability python
```

`inspect` 只读取已有档案。`plan` 重新检测允许列出的事实并显示创建、变化和失效条目，不写文件。`apply --write` 原子创建或更新档案，保留用户偏好。`verify` 核验记录的路径和工具是否仍可用。`resolve` 是正式消费入口，只返回当前任务所需能力的可执行文件、目录和必要环境变量。

## 3. 建立或更新档案

按以下顺序执行：

1. 确定准确档案路径和当前用户结果。
2. 读取已有档案；不存在时标为待创建，不把缺失当成损坏。
3. 读取用户已确认的安装、缓存和终端偏好。
4. 只检测允许列出的系统、终端、运行时、包根、缓存、SDK 和构建工具。
5. 把检测结果与已有档案比较，分别列出新增、变化、失效和仍然一致的条目。
6. 让用户看到写入位置、变化内容和停止位置。
7. 获得写入授权后运行 `apply --write`。
8. 运行 `verify`，再用 `resolve` 取出至少一个真实能力并让正式命令消费。

工具安装或用户偏好后来发生变化时，先完成产生变化的任务及其验证，再更新对应条目。检测不到某个工具时不猜路径，也不删除原记录；计划把它标为失效，写入时保留足以解释漂移的核验状态。

## 4. 选择终端和命令边界

终端选择依据当前操作系统、仓库正式入口和实际安装情况：

- Windows 上的盘符路径、注册表、Windows 进程、`.ps1`、`.bat`、Tauri、Android 和原生文件操作默认使用 PowerShell。
- 仓库正式入口明确是 Bash 脚本时，先确认实际 Bash 实现是 Git Bash、Cygwin、WSL 还是其它环境，再在该环境内完整执行。
- WSL 可执行文件存在不等于 Linux 子系统已经安装或可用。
- 同一个文件操作从路径解析到移动或删除使用同一终端完成，不能在 PowerShell 中枚举后拼接给另一个 shell。
- 多个同名命令存在时，以档案中经过核验的绝对可执行文件为准；`python`、`py` 和具体解释器路径不得视为同一个入口。

Project Steward 输出应直接说明当前任务选择哪个终端、为什么，以及相邻终端在什么条件下才使用，不输出没有决策作用的终端清单。

### Windows 工具启动前先确认执行表面

在 Windows 上首次调用 SDK、Qt 或其它可能同时提供脚本包装器、控制台程序和图形界面的工具时，先解析命令实际命中的绝对可执行文件，确认它是包装器还是原生目标，并确认启动后使用控制台输出还是打开可见窗口。即使只准备运行 `--help` 或 `--version`，也不能根据文件名猜测启动行为。

探测时优先使用已经核验的原生控制台程序，或直接运行一条有界、只读的实际验证命令。若唯一正式入口不可避免地会打开可见窗口，启动前先告诉用户会出现什么窗口、用途和停止方式，并限制进程、时间与副作用边界。不能让用于发现参数的探测意外弹窗并打断用户桌面。

## 5. 包、缓存与安装位置

记录的是正式消费者真正需要的路径：

- Python 的每个解释器、系统 `site-packages`、用户包目录、pip 入口和 pip 缓存；
- Node 的执行文件、npm 入口、全局包目录和 npm 缓存；
- Rust 的 Cargo、Rustup、工具链根、registry 与所需环境变量；
- Java、Android SDK、NDK、platform-tools、Gradle 用户目录和 wrapper 缓存；
- 用户确认的下载、临时文件和其它工具根。

档案不复制每个项目的虚拟环境或依赖清单。项目内部虚拟环境由项目负责；用户级解释器与缓存由环境档案负责。安装前先读取档案中的目标根和包管理器，安装后从真实入口验证，再更新档案。

## 6. 长时间任务、超时与停止条件

外层命令等待超时不能直接证明构建失败。发生超时、长时间无输出或用户询问是否继续时，依次检查：

1. 超时来自命令执行器、网络请求、构建工具还是应用本身。
2. 当前处于下载、配置、代码生成、编译、链接、安装、启动还是运行验证阶段。
3. 原进程和子进程是否仍存在，CPU、日志、输出目录或产物时间戳是否继续变化。
4. 命令是否已经给出退出码，正式产物是否生成，后续消费者能否读取。
5. 重新执行是否会与仍在运行的进程争用锁、缓存、端口或输出目录。

存在明确进展时继续监测原任务，不启动重复构建。只有出现成功退出且正式产物可消费、明确失败退出、进程已经消失且无产物、连续观察没有任何进展并取得足够诊断证据，或达到用户明确的时间与成本边界时才停止。

需要让长任务跨多次观察时，使用可返回进程标识、标准输出和错误日志的后台入口，定期读取新输出。不能用一次固定长等待替代状态观察，也不能把“工具调用返回超时”写成项目构建失败。

预计会超过一次观察或进度更新窗口的任务，不以单个前台阻塞调用启动。使用能够让出控制权、继续等待或后台运行的执行方式，保留可回读的进程身份、增量输出和退出状态。定期读取新进展；阶段、证据或预计停止位置发生变化时向用户说明，状态没有变化时不重复刷屏。这样既保持任务连续运行，也不会让用户只能看到长时间无回应。

### 长而嘈杂的命令先保全证据

命令预计会输出大量内容、运行超过一次观察窗口或需要跨轮继续判断时，在启动前建立一份可恢复的执行合同：

```text
本次执行尝试的稳定身份：
准确命令、工作目录、工具版本与输入身份：
稳定证据落点：工具原生报告 / 受控标准输出与错误日志 / 可回读结构化结果
启动器、根进程、子进程识别方式与所有者：
可能争用的端口、锁、缓存、设备或输出目录：
单独保存的退出状态及其正式语义：
允许重新执行的终态、资源释放和残留分类条件：
面向用户的有界摘要及其完整证据指针：
```

预计可能超过观察窗口的命令不能通过一个超时后无法恢复生产者身份的前台入口启动；应使用能够继续等待，或者能够从稳定记录重新取得执行身份、日志和退出结果的入口。临时执行句柄、单次工具返回和聊天上下文只用于观察，不是唯一证据。

外层等待结束或句柄失效后，按执行合同逐项取得根进程、已知子进程、日志增长、退出记录、正式产物和受占用资源。查询工具自身失败、只返回部分进程或没有输出时，只把对应证据标为状态未知，不能据此宣告原执行已经结束；一个进程不存在也不能覆盖其它已知进程的状态。原执行仍在运行或仍有进展时继续观察，不启动新的执行尝试。

只有取得正式终态，或者确认整个进程树已经结束、端口与锁等资源不再占用、产物和其它副作用已经分类且不会与新执行冲突后，才允许启动新的执行尝试。缺少退出状态但进程已经消失时，原结果仍标为未知；只有这项未知确实影响当前用户结果时才补跑必要项目。用户已经授权停止时，也只终止能够由执行合同证明属于本轮的准确进程，并在操作后重新核对进程、资源和残留。短小、低输出且能在一次调用内完整返回的命令继续直接执行，不增加日志仪式。

## 7. 真实验收

环境档案完成至少证明：

1. 正式检测器从当前机器取得真实工具和路径。
2. schema 与脚本消费者读取同一份档案。
3. `verify` 能发现不存在或漂移的路径。
4. `resolve` 返回的可执行文件被真实命令使用，并产生版本或能力结果。
5. 需要环境变量的工具由 `resolve` 返回同一组变量，设置后能够运行。
6. 检测过程没有保存允许列表之外的环境变量或凭据。
7. 项目配置、Skill 源码和用户档案之间没有复制同一可变事实。

完成后向用户说明档案位置、当前推荐终端、关键工具与包根、发现的漂移、实际消费证据和仍未核验的工具。没有写入授权时准确停在计划结果。
