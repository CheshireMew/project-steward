# 用户环境档案与执行环境治理

用于建立、读取、核验和更新当前用户的机器环境档案，并在项目实施、构建、测试和排错中使用其中与当前任务有关的事实。环境档案解决“工具究竟在哪里、哪个命令对应哪个版本、包和缓存写到哪里、当前机器该使用哪种终端”这类反复出现的问题。

环境档案是用户级可变运行数据，不属于 Project Steward 源码，也不属于任何项目。Project Steward 保存方法、schema 和确定性工具；用户环境档案默认位于 Codex 用户目录下的 `project-steward/environment-profile.json`。用户提供其它准确位置时使用该位置。

## 1. 进入条件与停止位置

以下请求直接进入本专项：

- 建立、检查、解释或更新当前用户环境档案；
- 确认 Python、Node、Rust、Java、Android、Gradle、包目录、缓存目录或工具链位置；
- 判断当前机器应使用 PowerShell、Bash、WSL 或其它终端；
- 环境差异反复造成安装、构建、测试或启动失败；
- 判断长时间任务是真正失败、仍在运行，还是只有外层等待超时。

其它 Project Steward 路径只有在环境事实会改变本次命令、安装位置、构建方法、验证或停止位置时才读取档案中的相关部分。普通分析、README、许可证或纯架构讨论不为完整性展示扫描整台机器。

用户只要求查看时停在读取与解释。用户要求建立或更新档案时，先完成只读检测和变更计划；只有得到写入授权后才写入。安装、下载、修改系统环境变量和删除工具是独立动作，不由档案写入授权自动获得。

## 2. 唯一真源与数据边界

档案分开保存四类内容：

1. **用户确认的偏好**：首选终端、允许的安装根、下载根、临时目录、默认工具，以及大型应用内容、项目、媒体和生成文件是否规避系统盘及其分类根目录。自动检测不能覆盖这些决定。
2. **机器检测事实**：操作系统、架构、终端、可执行文件、版本、包目录、缓存目录、SDK 和工具链。
3. **运行要求**：某个工具正常工作前必须设置的非敏感环境变量及其值，例如独立的 Cargo 和 Rustup 根。
4. **核验信息**：检测器版本、最后核验时间以及每项事实来自哪个可执行文件或目录。

项目要求、依赖版本、构建参数和源码入口继续由项目规则、配置和脚本负责。一次报错、完整 `PATH`、进程列表、令牌、Cookie、账号、凭据和任意未列入合同的环境变量不进入档案。档案可以说明凭据由哪个系统保存，但不保存凭据内容。

档案 schema 的唯一真源是 `assets/user-environment/profile.schema.json`。确定性操作由 `scripts/user_environment_profile.py` 完成：

```powershell
python scripts/user_environment_profile.py inspect
python scripts/user_environment_profile.py plan
python scripts/user_environment_profile.py apply --write
python scripts/user_environment_profile.py verify
python scripts/user_environment_profile.py resolve --capability python
python scripts/user_environment_profile.py resolve-storage --category media
```

`inspect` 只读取已有档案。`plan` 重新检测允许列出的事实并显示创建、变化和失效条目，不写文件。`apply --write` 原子创建或更新档案，保留用户偏好。`verify` 核验记录的路径、工具和大型内容根是否仍可用。`resolve` 是工具能力的正式消费入口，只返回当前任务所需能力的可执行文件、目录和必要环境变量；`resolve-storage` 是大型内容根的正式消费入口，按用户记录的分类优先级返回一个真实存在并满足系统盘策略的根。

## 3. 建立或更新档案

按以下顺序执行：

1. 确定准确档案路径和当前用户结果。
2. 读取已有档案；不存在时标为待创建，不把缺失当成损坏。
3. 读取用户已确认的安装、缓存、终端和大型内容存储偏好。
4. 只检测允许列出的系统、终端、运行时、包根、缓存、SDK 和构建工具。
5. 把检测结果与已有档案比较，分别列出新增、变化、失效和仍然一致的条目。
6. 让用户看到写入位置、变化内容和停止位置。
7. 获得写入授权后运行 `apply --write`。
8. 运行 `verify`，再用 `resolve` 取出至少一个真实能力并让正式命令消费。

工具安装或用户偏好后来发生变化时，先完成产生变化的任务及其验证，再更新对应条目。检测不到某个工具时不猜路径，也不删除原记录；计划把它标为失效，写入时保留足以解释漂移的核验状态。

## 4. 选择终端和命令边界

终端选择依据当前操作系统、仓库正式入口和实际安装情况：

- Windows 上的盘符路径、注册表、Windows 进程、`.ps1`、`.bat`、Tauri、Android 和原生文件操作默认使用 PowerShell。
- 仓库正式入口明确是 Bash 脚本时，先确认实际 Bash 实现是 Git Bash、Cygwin、WSL 还是其它环境，再在该环境内完整执行。
- WSL 可执行文件存在不等于 Linux 子系统已经安装或可用。
- 同一个文件操作从路径解析到移动或删除使用同一终端完成，不能在 PowerShell 中枚举后拼接给另一个 shell。
- 多个同名命令存在时，以档案中经过核验的绝对可执行文件为准；`python`、`py` 和具体解释器路径不得视为同一个入口。

Project Steward 输出应直接说明当前任务选择哪个终端、为什么，以及相邻终端在什么条件下才使用，不输出没有决策作用的终端清单。

### Windows 工具启动前先确认执行表面

在 Windows 上首次调用 SDK、Qt 或其它可能同时提供脚本包装器、控制台程序和图形界面的工具时，先解析命令实际命中的绝对可执行文件，确认它是包装器还是原生目标，并确认启动后使用控制台输出还是打开可见窗口。即使只准备运行 `--help` 或 `--version`，也不能根据文件名猜测启动行为。

探测时优先使用已经核验的原生控制台程序，或直接运行一条有界、只读的实际验证命令。若唯一正式入口不可避免地会打开可见窗口，启动前先告诉用户会出现什么窗口、用途和停止方式，并限制进程、时间与副作用边界。不能让用于发现参数的探测意外弹窗并打断用户桌面。

### PowerShell 证据不能由最后一条语句代替

PowerShell 的非终止错误、多语句脚本和管道可以在前面的探测失败后继续执行，整个进程最终表现出的退出状态也可能只对应最后一条成功语句。证据型命令不能据此把“查询失败后打印了空集合或零”解释成零发现。开始前为每个必需探测选择停止式错误处理，例如在受控作用域设置 `$ErrorActionPreference = "Stop"`，或者用 `try/catch` 明确保存该探测的成功、失败和错误；不能依赖整个脚本最后的 `$?`、`$LASTEXITCODE` 或最后一行文本反推前序命令状态。

派生数量、空集合、剩余对象和清理完成等摘要，只能在产生这些事实的权威查询已经独立成功后计算和输出。查询失败、命令不存在、只返回部分结果或没有可判定输出时，对应事实保持未知；同批其它独立探测已经成功且证据仍新鲜时继续保留，只补跑失败、未执行或状态未知的项目。用于验证这条边界的测试应让一个前序探测确定失败、后续普通语句能够成功，并证明最终消费者仍得到失败或未知而不是零。

### Windows 隐藏控制项不能由默认读取判定不存在

Windows 的 `Hidden` 属性会让默认目录枚举或不含隐藏项的读取省略对象。默认查询没有返回、`Get-Item` 未使用 `-Force` 时报告找不到路径，或资源管理器没有显示，都只证明该探测没有取得对象，不能证明准确字面量路径不存在，也不能据此把仓库、配置根或工具状态重新分类。

先冻结准确根和字面量子路径。判断 Git 仓库时，先用 `Test-Path -LiteralPath <root>\.git` 核对存在性；需要确认类型和属性时使用 `Get-Item -LiteralPath <root>\.git -Force`，或使用能够明确包含隐藏项的等价文件系统接口。只有隐藏项感知的直接检查证明准确项目根直接存在 `.git` 后，才调用 Git 取得工作树或发布证据；检查可靠地证明不存在时才按普通目录处理，检查失败或返回部分事实时保持未知。

若早先探测报告缺失，而隐藏项感知的直接检查随后证明对象存在，前者属于验证器假阴性：撤销由它产生的“对象不存在”结论，修正探测入口并重新计算受影响状态。不能为了让验证器看见对象而清除 `Hidden`、移动控制目录或改变项目状态；无关的隐藏文件也不会因为被发现就自动进入本次任务范围。

### Windows 文件系统别名只作为显式临时状态

资源管理器中两个盘符显示相同容量、卷标和内容时，先用 `subst`、`Get-PSDrive`、卷与挂载点信息，以及目标路径回读区分磁盘分区、`SUBST` 映射、PowerShell 驱动器、目录联接和符号链接。`SUBST` 和 PowerShell 驱动器不是新分区；符号链接与目录联接也不是新的物理存储。不能只凭资源管理器外观推断谁修改了分区，更不能在只需解除别名时调用分区、格式化或卷删除工具。

这些别名只在已经获准的诊断替代路径中使用，并在创建前记录准确别名、规范化真实目标、创建者或命令、生命周期、是否跨会话持久、清理授权和中断后的接管者。它们不会缩短正式消费者解析后的规范化真实路径，因此不进入项目的路径预算收益，也不能成为长路径问题的最终修复。临时别名是本轮运行状态，不写入用户环境档案成为长期机器事实；只有用户明确要求保留并且它确实是稳定环境能力时，才另行规划档案字段。

解除别名前先重新读取当前映射，只有别名与目标身份都和已确认对象完全一致时才执行对应的解除命令。清理不能只依赖创建命令中的 `finally`：外层等待超时、进程被终止或宿主中断后，接管者仍要从独立环境状态恢复映射身份。完成后分别验证别名已经消失、真实目标仍存在且内容未被移动或删除；这只证明别名生命周期收口，不证明创建它所绕过的正常入口或路径根因已经修复。

## 5. 包、缓存与安装位置

记录的是正式消费者真正需要的路径：

- Python 的每个解释器、系统 `site-packages`、用户包目录、pip 入口和 pip 缓存；
- Node 的执行文件、npm 入口、全局包目录和 npm 缓存；
- Rust 的 Cargo、Rustup、工具链根、registry 与所需环境变量；
- Java、Android SDK、NDK、platform-tools、Gradle 用户目录和 wrapper 缓存；
- 用户确认的下载、临时文件和其它工具根。

档案不复制每个项目的虚拟环境或依赖清单。项目内部虚拟环境由项目负责；用户级解释器与缓存由环境档案负责。安装前先读取档案中的目标根和包管理器，安装后从真实入口验证，再更新档案。

### 持久配置只能绑定稳定运行入口

项目、应用或 Skill 准备把外部可执行文件写入跨会话配置、默认工具或其它持久消费者时，在写配置前先判断入口的来源和生命周期：系统或用户级安装、用户确认的持久工具根、项目构建输出、缓存、下载解压目录、临时目录，或者只为本轮创建的包装器。至少记录运行入口所有者、来源版本或内容身份、预期保留期限、升级或替换方式、哪些构建或清理动作会使它失效，以及哪个正式消费者准备保存该路径。

文件存在且版本命令成功，只证明这个绝对路径在当前时刻可以执行。项目构建输出、缓存、下载解压目录或临时目录不会因此成为稳定安装；一次互操作测试通过也不能证明清理、重新构建、切换分支或下次会话后仍能使用。环境档案中的工具记录只接收能够作为机器能力稳定复用的入口；项目构建产物继续属于该项目的执行合同，不能因为当前机器能够找到它就写成用户级工具事实。

持久消费者只有在入口预期寿命覆盖配置承诺、所有者和升级方式明确，并由正式调用再次消费成功时，才写入长期绑定。消费者自己的配置若明确支持临时绑定，应同时保存临时状态、来源、失效条件和清理或重新选择入口；消费者不支持表达临时绑定时，不把临时路径伪装成普通长期配置，改用会话级参数、环境变量或调用入口完成当前验证。用户明确选择项目构建产物作为长期开发入口时，由项目配置保存该决定并说明重新构建或清理会使其失效，它仍不升级为稳定机器安装。

安装或复制到持久工具根、建立包装器、修改 PATH 和写入消费项目配置分别需要对应授权。没有安装或配置权限时，停在当前可执行证据和会话级消费结果，准确报告稳定运行入口与正式采用仍未完成；不能先持久绑定构建产物，再把以后可能失效降级成文档提醒。

### 大型应用内容、项目、媒体和生成文件

大型内容策略只管理默认根选择，不接管项目内部目录结构。档案分别记录 `application-content`、`project`、`media`、`generated-output` 和共同后备根；同一类别按用户记录顺序选择。具体项目名、工作区层级、素材组织、导出命名和长期项目决定继续由项目真源负责，不能把某个 MediaFlow、视频工程或一次生成目录写成所有项目共用的环境事实。

任务准备创建大型应用数据、工程状态、素材副本、代理、缓存、渲染中间物或生成结果时，正式调用 `resolve-storage --category <类别>`。用户档案要求规避系统盘时，写入档案和消费阶段都拒绝系统盘根；只返回真实存在的目录，不因目标盘空间看起来充足就猜一个未确认路径。没有记录可用根、系统盘身份未知或所有候选失效时，返回明确冲突并停在创建之前，由项目合同或用户决定新根。项目明确要求使用系统盘属于新的存储决定，需要先更新行为合同或用户偏好，不能由调用者静默绕过。

小型配置、平台强制文件和普通日志不因这项策略自动迁移。一个文件是否属于大型内容看它在正常生命周期中是否会形成持续增长的数据、工程、媒体或派生物，而不是只看本次样例大小。选定根后，项目生产者在其下创建自己的受控目录并返回规范化真实路径；后续消费者读取同一项目路径，不能再次选择另一根或把环境根当成项目最终目录。

### 跨启动器构建先统一目标有效身份

昂贵的原生预构建准备由包装器、任务运行器或子进程继续消费时，先建立目标有效构建身份，再启动第一次完整构建。身份至少包含源码与锁定依赖的内容身份、目标三元组、构建 profile、feature 集、工具链，以及目标实际选择的编译器、链接器、归档器、平台 SDK 或 API、目标专属配置和环境变量；会改变编译、链接、依赖探测或输出选择的 flags 也属于身份。项目专属值继续由项目配置或本轮执行合同保存，不写入用户环境档案成为机器级事实。

父入口、包装器和实际构建子进程分别记录规范化后的身份清单、最终命令和继承后环境。正常入口会覆盖、补充或重新解释某项输入时，以交接后的有效值为准；父进程里设置过某个变量不能证明子进程使用了同一值。目标名称相同、输出目录相同、缓存已经存在或日志显示命中部分增量结果，也不能证明它们属于同一构建身份。

预构建只有在后续子进程选择同一目标有效身份，并且正式消费者读取与该身份绑定的同一产物内容时才算真正复用。任一有效输入不同，就把父构建和子构建视为两个候选：在再次启动昂贵构建前定位第一个分歧的交接边界，由正常入口的唯一所有者统一身份，或者明确接受它们会生成不同产物和独立成本。不能先把不同身份产出的缓存称为预热成功，再用第二次完整构建掩盖交接缺陷。

需要跨轮观察或交付证据时，记录：

```text
源码、锁定依赖与目标产物种类：
父入口、包装器和子进程的目标有效身份清单：
第一个身份分歧及其唯一所有者：
预构建产物的路径、内容身份与完成状态：
后续子进程实际选择的构建身份和产物：
最终消费者读取结果：
结论：同一身份已复用 / 不同身份独立构建 / 状态未知
```

## 6. 长时间任务、超时与停止条件

外层命令等待超时不能直接证明构建失败。发生超时、长时间无输出或用户询问是否继续时，依次检查：

1. 超时来自命令执行器、网络请求、构建工具还是应用本身。
2. 当前处于下载、配置、代码生成、编译、链接、安装、启动还是运行验证阶段。
3. 原进程和子进程是否仍存在，CPU、日志、输出目录或产物时间戳是否继续变化。
4. 命令是否已经给出退出码，正式产物是否生成，后续消费者能否读取。
5. 重新执行是否会与仍在运行的进程争用锁、缓存、端口或输出目录。

存在明确进展时继续监测原任务，不启动重复构建。只有出现成功退出且正式产物可消费、明确失败退出、进程已经消失且无产物、连续观察没有任何进展并取得足够诊断证据，或达到用户明确的时间与成本边界时才停止。

需要让长任务跨多次观察时，使用可返回进程标识、标准输出和错误日志的后台入口，定期读取新输出。不能用一次固定长等待替代状态观察，也不能把“工具调用返回超时”写成项目构建失败。

预计会超过一次观察或进度更新窗口的任务，不以单个前台阻塞调用启动。使用能够让出控制权、继续等待或后台运行的执行方式，保留可回读的进程身份、增量输出和退出状态。定期读取新进展；阶段、证据或预计停止位置发生变化时向用户说明，状态没有变化时不重复刷屏。这样既保持任务连续运行，也不会让用户只能看到长时间无回应。

### 长而嘈杂的命令先保全证据

命令预计会输出大量内容、运行超过一次观察窗口或需要跨轮继续判断时，在启动前建立一份可恢复的执行合同：

```text
本次执行尝试的稳定身份：
准确命令、工作目录、工具版本与输入身份：
稳定证据落点：工具原生报告 / 受控标准输出与错误日志 / 可回读结构化结果
启动器、根进程、子进程识别方式与所有者：
可能争用的端口、锁、缓存、设备或输出目录：
单独保存的退出状态及其正式语义：
允许重新执行的终态、资源释放和残留分类条件：
面向用户的有界摘要及其完整证据指针：
```

预计可能超过观察窗口的命令不能通过一个超时后无法恢复生产者身份的前台入口启动；应使用能够继续等待，或者能够从稳定记录重新取得执行身份、日志和退出结果的入口。临时执行句柄、单次工具返回和聊天上下文只用于观察，不是唯一证据。

外层等待结束或句柄失效后，按执行合同逐项取得根进程、已知子进程、日志增长、退出记录、正式产物和受占用资源。查询工具自身失败、只返回部分进程或没有输出时，只把对应证据标为状态未知，不能据此宣告原执行已经结束；一个进程不存在也不能覆盖其它已知进程的状态。原执行仍在运行或仍有进展时继续观察，不启动新的执行尝试。

只有取得正式终态，或者确认整个进程树已经结束、端口与锁等资源不再占用、产物和其它副作用已经分类且不会与新执行冲突后，才允许启动新的执行尝试。缺少退出状态但进程已经消失时，原结果仍标为未知；只有这项未知确实影响当前用户结果时才补跑必要项目。用户已经授权停止时，也只终止能够由执行合同证明属于本轮的准确进程，并在操作后重新核对进程、资源和残留。短小、低输出且能在一次调用内完整返回的命令继续直接执行，不增加日志仪式。

### 终止前先区分进程存活与可枚举残留

停止、清理或再次提升终止权限前，先把目标判为“正在运行”“已经退出但仍可枚举的残留”或“状态未知”。任务管理器、进程 API 或命令行仍返回一行记录，只证明系统还能枚举该对象，不证明它仍有执行能力。结合等待或退出状态、线程与 CPU 时间是否增长、窗口或系统对话框、端口、文件锁、设备、子进程树以及其它受控资源的所有权判断；不同证据分别记录成功、失败或未知，不能让单项查询失败被空集合掩盖。

终止命令返回“访问被拒绝”只证明当前调用缺少终止权限，不证明目标仍然存活。再次触发 UAC、改用更强终止方式或处理父进程前，必须先证明目标确实正在运行且属于本轮；确认没有线程、窗口、端口、锁、子进程和持续变化的受控资源时，将仍可枚举的记录归为已退出残留，不重复提权，也不为清掉一行记录而终止父进程、宿主或整个会话。关键查询失败或证据互相冲突时保持状态未知，继续有界观察或交给系统会话结束后回收，不能对用户声称已经关闭，也不能把未知升级成更大范围的终止授权。

## 7. 真实验收

环境档案完成至少证明：

1. 正式检测器从当前机器取得真实工具和路径。
2. schema 与脚本消费者读取同一份档案。
3. `verify` 能发现不存在或漂移的路径。
4. `resolve` 返回的可执行文件被真实命令使用，并产生版本或能力结果。
5. 需要环境变量的工具由 `resolve` 返回同一组变量，设置后能够运行。
6. 检测过程没有保存允许列表之外的环境变量或凭据。
7. 项目配置、Skill 源码和用户档案之间没有复制同一可变事实。
8. 大型内容策略启用时，`apply --write` 生成的真实档案经过文件边界被 `resolve-storage` 消费，返回的根真实存在、符合系统盘策略，并由项目生产者而不是消费端手写路径。
9. 某个项目准备持久保存工具路径时，先证明该入口的所有者、来源、保留期限和升级方式符合配置承诺；当前可执行或版本输出不能替代稳定运行入口证据。
10. 构建、缓存、下载解压或临时产物只通过明确的会话级入口消费；消费者无法表达临时绑定且没有安装授权时，不写持久配置，并把正式采用状态报告为受阻。
11. 昂贵预构建准备跨父入口、包装器和子进程复用时，各层消费同一目标有效构建身份；只有后续子进程实际选择相同身份且最终消费者读取对应产物，才能把缓存或预构建标为已复用。

完成后向用户说明档案位置、当前推荐终端、关键工具与包根、持久或临时入口分类、发现的漂移、实际消费证据和仍未核验的工具。没有写入授权时准确停在计划结果。
