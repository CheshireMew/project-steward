# 项目研究与讲解

用于用户明确提供 GitHub 仓库、本地目录或源码包，希望先看懂项目价值、用途、内容、实现、使用方式、运行结果、维护状态或与其它项目的差别。上层已经选择本路径并确定动作权限；本方法只决定读取深度、解释顺序和停止位置。

## 1. 默认结果

默认把读者当作第一次听说该项目及其所属领域的人。先找出项目带来的价值变化：

```text
谁在什么情况下使用或依赖它
→ 原来缺少什么能力或结果
→ 通过项目能够完成什么
→ 最后得到什么可见变化
→ 这项变化为什么和什么时候有用
```

第一段直接说明这个结果及其意义。随后用一个具体场景展示用户会做什么、最后看到什么。常见事物的类比只在能够缩短理解、且项目自身的关键差别已经说清时补充。

第一段完成后，读者应当能够回答：

- 它解决什么问题；
- 用户最终得到什么；
- 为什么会需要它；
- 哪些情境会用到它。

用户只提供可运行软件、平台或框架的仓库、本地目录或源码包，并点名本 Skill 而没有提出更具体问题时，默认结果不是只讲用途。第一段和具体场景之后，还要交付一个足以解释主要价值怎样产生的**最小机制闭环**：

```text
用户动作 → 入口 → 决策或编排者 → 实际执行者 → 存储或外部边界 → 正式消费者 → 用户可见结果
```

同时用普通话说明谁决定下一步、谁真正执行，关键状态或产物保存在哪里，结果怎样回到用户，以及哪项失败保护、恢复或适配机制真正承担稳定性。内容或规则合集使用等价的读取者、动作、保存和交付链，不为了凑齐技术名词虚构运行架构。

项目类别、源码语言、框架、协议、目录和内部流程先用于研究。只有它们能够解释上述职责、边界、稳定机制，改变采用、使用或理解判断，或者用户明确追问时，才进入答案。框架名称和模块清单不能代替原理说明。

默认看懂仍不等于完整架构审计：只覆盖一条主要链和机制确实不同的必要分支，不穷举同类适配器、目录、接口或测试。上层已经选择实际效果、可靠性、上下文噪音、适用性或采用判断时，才提供对应结论；当前方法不自行扩大问题。

## 2. 来源和问题共同决定深度

先记录用户明确提供的来源和问题：

1. 本地目录或源码包以本地文件为唯一来源。没有 `.git` 时，历史和远程状态不从其它位置补齐。
2. GitHub URL 可以读取仓库文件。用户询问当前版本、维护状态、Stars、Issues 或 Releases 时，才读取相应实时官方页面，并记录查询日期。
3. 先读取项目根的 `AGENTS.md`、`CLAUDE.md` 或同类约束，再进行后续检查。
4. 将问题归入：默认看懂（含最小机制闭环）、开始使用、内容盘点、实现机制、实际效果、特定目标、亲自运行、维护现状、项目比较、完整能力吸收研究或详细报告。
5. 每次新增读取或命令都要能够改变当前答案；当前问题已经回答后停止。

连续追问沿用已经确定的项目根、材料边界和已验证事实，只补读能够回答新问题的内容。用户说明“我真正关心的是 X”时，以 X 重新评价项目怎样产生、保存或传输、维护、取回并最终交付结果，以及错误、过期和噪音怎样被处理。

## 3. 先判断项目怎样产生价值

项目类型只选择研究方法，不作为普通读者的固定开场：

- **可运行软件**：确认用户原来缺少什么、通过它能执行哪些动作、最后看到什么。
- **内容或规则合集**：确认谁读取这些文件、照着完成什么、最后产出什么；需要其它程序加载时，说明真实使用入口。
- **平台或框架**：确认用户能用它建立、连接或管理什么，以及从哪个入口得到结果。

项目同时包含多种类型时，以用户当前关心的结果为主。数量用于定位内容，不代替具体用途；正式内容、草稿、个人内容、示例和已弃用内容分别说明。

## 4. 读取最少够用的材料

默认按以下顺序读取：

1. 项目约束、README 和根目录分类，理解作者怎样描述项目及内容怎样分组。
2. 能代表主要用途的真实入口、主要处理、数据或外部边界和正式消费者，确认说明中的名称背后由谁决定、由谁执行、怎样形成用户结果。
3. 主要价值依赖多条执行原理不同的路径时，只补读会改变决策者、执行者、状态边界、失败收口或最终消费者的必要分支；同一合同下的同类适配器不逐项展开。
4. 用户询问“里面有什么”时，读取各项的名称、用途和状态，达到逐项解释所需的深度。
5. 当前答案仍缺少实现依据时，再读取包清单、构建配置、数据结构或其它调用点。

使用 `rg` 或同等快速搜索工具定位文件。已经能够用普通话说明项目解决什么问题、用户得到什么、什么时候有用，主要价值怎样经过最小机制闭环产生，并回答用户当前问题时停止；默认介绍到此不继续检查无关测试、CI、插件清单、发布流程和远程状态。

## 5. 按当前问题交付

### 默认看懂项目

读取项目说明和足以确认主要用途及最小机制闭环的代表文件。先说项目把用户从什么处境带到什么结果，再用具体场景说明用户会做什么、看到什么以及为什么有用；随后解释这项结果由谁决定、谁执行、经过什么状态或外部边界、由哪个正式消费者交给用户，以及真正承担正确性和稳定性的原理。

复杂平台先选择最能代表主要价值的一条主链。只有核心承诺依赖决策、执行、状态、失败收口或最终消费者明显不同的路径时，才追加必要分支，并说明它为什么不是主链中的普通变体。不要把完整目录、全部平台适配器或技术栈清单改写成“原理”。

源码用于证明机制，不自动成为逐文件架构讲解。项目宣传比源码更强、关键实现只存在于旧模块、或者本次没有运行时，在对应结论旁直接区分项目声明、源码实现、推断和实际观察，不能等用户追问限制才补边界。

### 怎样安装、配置、调用或开始使用

先用一句话确认采用后会得到什么，再读取项目自己的安装或使用说明、当前平台需要的配置和真实入口。说明必要前提、适合当前环境的步骤，以及首次成功时能够看到的结果。用户要求代为安装或运行时，上层动作权限成立后再执行并验证真实用户链。

### 里面有哪些东西

按用户要完成的事情分组：

- 主要项目不超过 30 个时，逐项说明“名称：谁使用、做什么、得到什么”。
- 超过 30 个时，先列出用途分组和组内名称，再展开最重要的内容；用户要求完整清单时再全部展开。
- 正式内容、草稿、个人内容、示例和已弃用内容保持各自状态。

### 怎样实现或架构是什么

可运行软件至少追踪一条与当前问题有关的代表路径；只有执行原理确实不同且会改变当前理解时才增加分支：

```text
用户动作 → 入口 → 决策或编排者 → 实际执行者 → 存储或外部边界 → 正式消费者 → 用户得到的结果
```

内容或规则合集说明谁读取文件、文件要求什么动作、结果保存或显示在哪里。先说清概念模型和职责分工，再说明真正承担正确性和稳定性的机制；实体身份、数据合并、更新、失败保护或信息损失会改变判断时继续检查。

### 亲自运行、复现或验证

用户明确要求真实验证时：

1. 按项目提供的方式启动程序或运行官方示例。
2. 从真实用户入口产生结果。
3. 确认结果经过项目真实的数据、存储或传输路径。
4. 确认用户使用的界面、命令或导出端能够读取结果。
5. 记录实际命令、环境条件和可观察结果。

运行成功只证明当前环境下链路可用；用户同时关心结果质量时，再按上层已选择的效果评估方法检查产物是否真的有用。

### 维护情况和当前状态

用户询问当前状态时，查询 GitHub 或其它官方来源中的 Releases、提交、Issues、支持环境和许可证，写明查询日期。本地源码包只说明副本自身状态，不代表当前远程状态。

### 比较项目

先用同一个用户问题分别解释每个项目，再比较用户结果、共同机制、使用条件和限制。Stars、功能数量和目录大小只有在它们会改变当前选择时才进入比较。

### 完整能力吸收研究

只有用户明确要求完整阅读参考项目，并判断哪些能力值得另一个目标项目吸收时，才进入本模式。普通项目介绍、一般比较和只问“它能做什么”继续读取最少够用的材料，不为形式完整穷举仓库。

先冻结完整覆盖边界，并把每个相关对象归入明确职责：

```text
研究根、版本或源码包身份：
用户要求覆盖的范围、明确排除项和仍未取得的证据：
规范真源、手工维护来源与派生视图：
生成器、构建入口、校验器及它们实际产生和读取的对象：
名称、别名、示例、目录和预览分别承担什么发现职责：
按输入、可观察结果、执行合同和正式消费者识别出的独立行为：
依赖的运行时、平台、时间、缓存、生命周期和宿主假设：
第三方来源、许可证、署名与再分发条件：
材料是原始上游还是 fork；fork 与原始上游各自新增了什么，实际拟采用内容来自哪一层：
采用关系是直接复用或改编后再分发，还是只学习方法并独立实现：
目标项目的用户结果与唯一边界：
候选能力在目标项目中属于核心对象、现有对象操作、获取渠道、视图或筛选、状态反馈还是可选集成：
它与哪个现有对象共享创建后的保存、查找、编辑、删除、恢复和交付生命周期：
来源项目的入口层级是否有目标项目自己的用户任务或产品合同支持：
```

“完整”只对这份冻结范围成立。目录、数据文件或演示代码明确由生成器产生时，读取生成来源、生成器和至少一个正式消费者；看似派生却没有可复现生成入口时，把它标为手工并行来源或未知风险，不能把两个来源同时带入目标项目。工具输出被截断、文件未读到末尾、运行入口无法确认或授权范围不明时，相应结论保持未知，不能用数量或命名规律补齐。

名称、别名和示例只负责发现，不能直接证明独立能力数量。两个条目只有在输入职责、可观察行为、执行合同、正式消费者、停止位置或会改变专业判断与结果的构成性细节确实不同时才算不同机制；同一行为的不同命名进入别名或索引候选。参考实现中已经成立的运行方式也只是来源事实，若它会在目标项目建立第二套状态、时间、缓存、恢复或宿主边界，应保留结果机制并拒绝原实现假设。

采用建议还要按实际进入目标的内容标明复用关系。代码、脚本、模板、正文、示例、schema、数据或媒体资源会被复制、改写、转换或抽取后随目标分发时，标为直接复用，并把原始上游、必要的 fork、许可证、目标路径和 README 致谢列入采用结果；只学习高层方法、视觉锚点、核心动作、工作流或反复刻方法并完全独立实现，且不复制来源 IP、示例、资源或代码时，标为方法学习，不把来源伪装成目标依赖。

映射前先为每项来源能力写清它让执行者多注意什么、区分什么条件，以及这些细节会改变什么选择、内容或验收。目标项目已经有相同职责、对象或入口，只能决定新能力应接到哪里，不能证明具体细节已经存在；按上层已经选定的共同判断标准遮住来源逐项比较，分别得出“具体细节已经存在、只有大方向、值得吸收的新细节、不吸收”。完成比较后才把共同机制和特殊维度映射到目标对象与生命周期。

随后把来源能力逐项映射到目标项目：

```text
来源能力与证据等级：项目声明 / 源码已实现 / 本次实际观察 / 推断
会改变未来判断、内容或验收的构成性细节：
目标具体能力结论：具体细节已经存在 / 只有大方向 / 值得吸收的新细节 / 不吸收：
目标项目当前缺少的用户结果：
目标项目已有且不能重复建立的职责：
目标项目中的职责类型和对应用户对象：
与现有对象共享的生命周期、行动和正式消费者：
整体采用 / 局部吸收 / 拒绝：
建议入口：现有统一入口 / 对象内行动 / 次级入口 / 独立工作区 / 不采用
独立主入口成立所需的目标侧证据：
建议的目标规范所有者与正式消费者：
需要保留的运行条件、来源和授权：
不采用的实现、名称、样例或平台假设及原因：
计划或实施前仍需确认的事实：
```

来源项目存在某个导航项、独立页面、显眼按钮、供应商配置或大量同类条目，只能证明来源产品怎样组织自身能力，不能证明目标项目也需要同级入口。候选能力产生的结果若在目标项目中与现有对象共享同一组保存、查找、编辑、删除、恢复和交付行为，默认建议接入现有对象路径，把差异表达为类型、元数据或对象内行动。只有目标项目自身已经证明用户有独立且反复发生的结果、关键决定、生命周期或恢复路径，而且现有入口无法自然承载时，才把独立主入口列为采用候选；证据不足时把入口层级列为待确认，不能用参考产品的界面替目标项目作决定。

只要求“看看有哪些值得吸收”时保持只读，交付来源覆盖、候选、拒绝项、证据强度和建议落点后停止。用户明确要求计划或实施时，把这份来源能力台账交给改动前预防；研究路径不自行创建目标 schema、资源、兼容层或演示实现，也不把参考项目的目录结构变成目标架构。

## 6. 用人话完成解释

- 先把项目名称翻译成用户原来面对的问题、能执行的动作、看得见的结果及其价值。
- 每个功能回答“用户做什么、最后得到什么”；区分使用者确有必要时再说明由谁使用。
- 用一个材料能够支持的具体场景串起主要用途，不把例子补写成项目事实。
- 解释原理时使用职责和因果关系：谁决定、谁执行、状态经过哪里、谁消费；框架名、协议名和目录名只在它们解释其中一项时出现。
- 同一观点的结论、原因和影响放在同一段；只有步骤、清单或多个对象需要比较时使用列表或表格。
- 专业名称方便搜索、安装、区分项目或继续理解时保留，并在第一次出现时说明它在当前场景中的作用。

普通用途说明直接陈述。证据层级会改变判断时，再区分：

- **项目文档声明**：README 或项目文档描述的预期；
- **源码已经实现**：代码存在对应处理，本次没有运行；
- **本次实际观察**：从真实入口和最终结果亲自看到；
- **根据现有材料推断**：由多项证据推出，同时指出未知部分。

网络来源使用可点击链接；本地源码使用绝对路径和行号。关键入口足以支持核对时保留最多三个，不把正文改写成证据目录。

## 7. 完成标准

第一段已经让零基础读者知道项目解决什么问题、用户最终得到什么、为什么和什么时候会需要它。只给仓库、本地目录或源码包的默认看懂结果，还必须让读者能够回答主要价值由谁决定、谁执行、经过什么状态或外部边界、由谁交付给用户，以及源码能证明到哪一层；复杂项目中机制确实不同且支撑核心承诺的必要分支已经说明。正文已经回答用户当前追问，所有额外材料都实际改变了理解、采用或使用判断。完整能力吸收研究还必须让每项采用或拒绝建议都能回到完整覆盖边界、独立行为、目标缺口、运行假设和授权证据，并停在用户批准的只读建议或交接位置。达到对应结果后返回上层主流程。
