# 项目研究与讲解

用于用户明确提供 GitHub 仓库、本地目录或源码包，希望先看懂项目价值、用途、内容、实现、使用方式、运行结果、维护状态或与其它项目的差别。上层已经选择本路径并确定动作权限；本方法只决定读取深度、解释顺序和停止位置。

## 1. 默认结果

默认把读者当作第一次听说该项目及其所属领域的人。先找出项目带来的价值变化：

```text
谁在什么情况下使用或依赖它
→ 原来缺少什么能力或结果
→ 通过项目能够完成什么
→ 最后得到什么可见变化
→ 这项变化为什么和什么时候有用
```

第一段直接说明这个结果及其意义。随后用一个具体场景展示用户会做什么、最后看到什么。常见事物的类比只在能够缩短理解、且项目自身的关键差别已经说清时补充。

第一段完成后，读者应当能够回答：

- 它解决什么问题；
- 用户最终得到什么；
- 为什么会需要它；
- 哪些情境会用到它。

项目类别、源码语言、框架、协议、目录和内部流程先用于研究。它们能够改变采用、使用或理解判断，或者用户明确追问时，再进入答案。

默认看懂项目只形成用途与使用情境说明。上层已经选择实际效果、可靠性、上下文噪音、适用性或采用判断时，才提供对应结论；当前方法不自行扩大问题。

## 2. 来源和问题共同决定深度

先记录用户明确提供的来源和问题：

1. 本地目录或源码包以本地文件为唯一来源。没有 `.git` 时，历史和远程状态不从其它位置补齐。
2. GitHub URL 可以读取仓库文件。用户询问当前版本、维护状态、Stars、Issues 或 Releases 时，才读取相应实时官方页面，并记录查询日期。
3. 先读取项目根的 `AGENTS.md`、`CLAUDE.md` 或同类约束，再进行后续检查。
4. 将问题归入：默认看懂、开始使用、内容盘点、实现机制、实际效果、特定目标、亲自运行、维护现状、项目比较或详细报告。
5. 每次新增读取或命令都要能够改变当前答案；当前问题已经回答后停止。

连续追问沿用已经确定的项目根、材料边界和已验证事实，只补读能够回答新问题的内容。用户说明“我真正关心的是 X”时，以 X 重新评价项目怎样产生、保存或传输、维护、取回并最终交付结果，以及错误、过期和噪音怎样被处理。

## 3. 先判断项目怎样产生价值

项目类型只选择研究方法，不作为普通读者的固定开场：

- **可运行软件**：确认用户原来缺少什么、通过它能执行哪些动作、最后看到什么。
- **内容或规则合集**：确认谁读取这些文件、照着完成什么、最后产出什么；需要其它程序加载时，说明真实使用入口。
- **平台或框架**：确认用户能用它建立、连接或管理什么，以及从哪个入口得到结果。

项目同时包含多种类型时，以用户当前关心的结果为主。数量用于定位内容，不代替具体用途；正式内容、草稿、个人内容、示例和已弃用内容分别说明。

## 4. 读取最少够用的材料

默认按以下顺序读取：

1. 项目约束、README 和根目录分类，理解作者怎样描述项目及内容怎样分组。
2. 能代表主要用途的入口文件或内容文件，确认说明中的名称背后实际做了什么。
3. 用户询问“里面有什么”时，读取各项的名称、用途和状态，达到逐项解释所需的深度。
4. 当前答案缺少实现依据时，再读取包清单、构建配置、源码入口、数据结构或调用点。

使用 `rg` 或同等快速搜索工具定位文件。已经能够用普通话说明项目解决什么问题、用户得到什么、什么时候有用，并回答用户当前问题时停止；默认介绍到此不继续检查测试、CI、插件清单、发布流程和远程状态。

## 5. 按当前问题交付

### 默认看懂项目

读取项目说明和足以确认主要用途的代表文件，先说项目把用户从什么处境带到什么结果，再用具体场景说明用户会做什么、看到什么以及为什么有用。源码用于核对用途，不自动成为目录或架构讲解。

### 怎样安装、配置、调用或开始使用

先用一句话确认采用后会得到什么，再读取项目自己的安装或使用说明、当前平台需要的配置和真实入口。说明必要前提、适合当前环境的步骤，以及首次成功时能够看到的结果。用户要求代为安装或运行时，上层动作权限成立后再执行并验证真实用户链。

### 里面有哪些东西

按用户要完成的事情分组：

- 主要项目不超过 30 个时，逐项说明“名称：谁使用、做什么、得到什么”。
- 超过 30 个时，先列出用途分组和组内名称，再展开最重要的内容；用户要求完整清单时再全部展开。
- 正式内容、草稿、个人内容、示例和已弃用内容保持各自状态。

### 怎样实现或架构是什么

可运行软件只追踪一条与当前问题有关的代表路径：

```text
用户动作 → 入口 → 主要处理 → 数据或外部服务 → 用户得到的结果
```

内容或规则合集说明谁读取文件、文件要求什么动作、结果保存或显示在哪里。先说清概念模型，再说明真正承担正确性和稳定性的机制；实体身份、数据合并、更新、失败保护或信息损失会改变判断时继续检查。

### 亲自运行、复现或验证

用户明确要求真实验证时：

1. 按项目提供的方式启动程序或运行官方示例。
2. 从真实用户入口产生结果。
3. 确认结果经过项目真实的数据、存储或传输路径。
4. 确认用户使用的界面、命令或导出端能够读取结果。
5. 记录实际命令、环境条件和可观察结果。

运行成功只证明当前环境下链路可用；用户同时关心结果质量时，再按上层已选择的效果评估方法检查产物是否真的有用。

### 维护情况和当前状态

用户询问当前状态时，查询 GitHub 或其它官方来源中的 Releases、提交、Issues、支持环境和许可证，写明查询日期。本地源码包只说明副本自身状态，不代表当前远程状态。

### 比较项目

先用同一个用户问题分别解释每个项目，再比较用户结果、共同机制、使用条件和限制。Stars、功能数量和目录大小只有在它们会改变当前选择时才进入比较。

## 6. 用人话完成解释

- 先把项目名称翻译成用户原来面对的问题、能执行的动作、看得见的结果及其价值。
- 每个功能回答“用户做什么、最后得到什么”；区分使用者确有必要时再说明由谁使用。
- 用一个材料能够支持的具体场景串起主要用途，不把例子补写成项目事实。
- 同一观点的结论、原因和影响放在同一段；只有步骤、清单或多个对象需要比较时使用列表或表格。
- 专业名称方便搜索、安装、区分项目或继续理解时保留，并在第一次出现时说明它在当前场景中的作用。

普通用途说明直接陈述。证据层级会改变判断时，再区分：

- **项目文档声明**：README 或项目文档描述的预期；
- **源码已经实现**：代码存在对应处理，本次没有运行；
- **本次实际观察**：从真实入口和最终结果亲自看到；
- **根据现有材料推断**：由多项证据推出，同时指出未知部分。

网络来源使用可点击链接；本地源码使用绝对路径和行号。关键入口足以支持核对时保留最多三个，不把正文改写成证据目录。

## 7. 完成标准

第一段已经让零基础读者知道项目解决什么问题、用户最终得到什么、为什么和什么时候会需要它；正文已经回答用户当前追问；所有额外材料都实际改变了理解、采用或使用判断。达到这些结果后返回上层主流程。
