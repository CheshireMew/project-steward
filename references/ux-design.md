# 数字产品用户体验设计

用于理解用户与使用情境、定义或重做产品体验、建立用户旅程、信息架构、导航、任务流、参考产品研究和体验验证。它决定产品应该怎样被理解和使用；具体视觉、组件、响应式、动效与实施验收由上层主路径另行选择。

## 1. 先确定设计问题和证据强度

```text
产品希望产生什么用户价值：
主要用户在什么情境下使用：
用户要完成什么、得到什么：
当前体验怎样运作：
已有用户证据和产品事实：
需要验证的假设：
业务、技术、平台与合规限制：
本轮允许改变什么：
交付与停止位置：
```

把输入分成五类：用户直接表达或观察到的证据、行为与结果数据、已确认的产品事实、对原因的解释性假设、准备采用的设计决定。数据可以证明发生了什么，不能单独解释为什么；个别反馈可以暴露问题，不能自动代表全部用户。

没有足够研究时，不虚构精细画像、需求比例和行为动机。低风险局部设计可以在明确假设下继续；会改变核心用户、产品价值或主流程的未知项，先说明需要怎样的访谈、观察、数据或原型验证。

## 2. 用情境和结果理解用户

只记录会改变设计的用户差异：触发原因、目标、已有知识、使用频率、设备与环境、时间压力、输入能力、可访问性需要、协作关系和错误代价。人口属性只有在它确实改变内容、行为或约束时才进入设计。

用用户语言说明体验结果：用户在某个情境下，要对什么对象完成什么，并怎样知道已经成功。把产品目标和用户结果分别写清；两者冲突时不使用转化指标掩盖用户成本。

## 3. 建立完整的当前体验

用户旅程从触发开始，不从某个页面截图开始。按需要覆盖：了解与进入、首次使用、核心任务、等待与跨会话、完成与交付、重复使用、协作、失败恢复、离开再返回。通知、权限、文件、邮件、外部跳转和人工支持会改变任务结果时，也属于旅程的一部分。

为每个关键阶段记录：

```text
用户目标与预期：
当前入口和必要信息：
用户操作的对象与行动：
系统反馈和等待：
完成结果与下一步：
失败、取消、撤销和恢复：
证据、问题与未知项：
```

问题优先回到最早失效关系：用户结果、对象模型、流程与决策、信息架构、内容与状态、交互方式，最后才是视觉表现。不要用新增说明文字补偿错误的任务结构。

## 4. 设计对象模型和信息架构

先列用户真正识别和操作的对象、对象之间的关系，以及用户对它们使用的名词和动词。产品内部数据结构可以支持实现，但不能迫使用户学习系统表名、处理阶段或工程术语。

信息架构按用户寻找和完成任务的方式组织。为每个入口、导航项、页面、区域和弹层写清职责、可找到的内容、允许的行动、前后关系和退出结果。职责重复时合并；需要跨层跳转时保持对象身份、上下文和返回位置。

分类、搜索、筛选、历史记录和最近使用解决不同的查找问题，不因产品内容多就全部加入。验证结构时使用真实任务和真实内容判断用户会去哪里找，而不是只检查栏目名称是否整齐。

## 5. 设计任务流、状态与控制

先形成最短成功路径，再增加真实需要的分支：

```text
自然入口
→ 必要输入与关键决定
→ 系统可可靠自动完成的步骤
→ 持续可见的对象、范围与进度
→ 用户能理解和使用的结果
→ 下一步、重复使用或安全退出
```

只有会改变输出、成本、风险或不可逆结果的决定留在主路径。默认值能可靠工作时，高级设置进入次级层；后台准备只在影响等待、可用性或失败恢复时显示状态，不变成要求用户理解的前置任务。

为等待、完成和失败分别定义可见生命周期。完成状态只在用户仍需要确认结果、继续行动或回看历史时保留；结果已经自然出现在工作对象中且无需决定时，完成提示及时退出或压缩，避免后台步骤反过来成为持续占位的主要内容。

每个关键行动定义开始条件、即时反馈、进行状态、成功结果、失败解释、重试、取消、撤销、重复执行和跨会话恢复。高频用户可以获得快捷键、批量操作和可记忆设置，但首次用户仍能发现主路径。

## 6. 研究参考产品，而不收集外观

这些情况适合主动研究当前参考：用户要求对标；目标平台存在强惯例；同类任务有成熟模式；团队需要比较结构性方向；某项现行产品行为或规范会改变方案。局部样式微调、已有真源足够或研究不会改变决定时不联网。

围绕任务搜索“用户怎样完成某件事”，而不是只搜行业名称和界面截图。来源优先级为：用户提供的当前产品证据；参考产品官方帮助、产品页和发布说明；目标平台当前规范；能够补充真实操作过程的可靠演示或评测。版本相关结论记录来源和时间，无法确认时标为证据缺口。

使用同一组问题比较少量参考：

```text
主要用户和任务是否相近：
对象怎样命名和组织：
用户怎样进入并开始：
默认路径、直接操作和高级选项怎样分层：
系统怎样表达进度、结果、失败和恢复：
首次使用与高频使用怎样兼顾：
移动、桌面或网页惯例怎样体现：
这种关系降低什么成本、引入什么代价：
本产品应采用、调整还是不采用，为什么：
```

借鉴的是任务关系、信息组织、交互语义、反馈、渐进披露和视觉层级。参考产品的品牌外观、专有内容、功能规模和商业模式不自动迁入当前产品。

## 7. 定义目标体验

目标体验至少说明：核心用户结果、目标旅程、对象模型、信息架构、最短成功路径、关键决策与默认值、状态与恢复、首次和重复使用、效率与可访问性、跨平台不变量，以及仍需验证的高风险假设。

设计原则必须能改变具体决定，例如“用户选择内容后立即进入工作状态，后台准备只表达进度”。“简洁、直观、高级”不能单独成为原则。功能、页面和控件只有在目标旅程中承担职责时才进入方案。

体验结构确定后，把用户、任务、对象关系、信息架构、状态与风险返回上层主路径，由其决定是否继续形成界面方向或具体规格。

## 8. 选择合适的验证

按风险验证最早的不确定关系：概念是否值得、对象和分类是否能被理解、流程是否能完成、交互是否可用、实现是否与设计一致。不要用高保真画面测试一个尚未成立的产品概念，也不要用偏好投票代替任务完成。

验证合同写清目标用户、真实情境、任务、允许提供的信息、成功标准、观察指标和停止条件。常用证据包括任务完成、理解偏差、犹豫和错误、完成时间、恢复能力、重复使用效率、可访问性与主观信心；只选择会改变设计的指标。

Agent 自己的流程走查只能发现启发式问题。没有真实目标用户参与时，不声称已经完成用户研究或可用性验证；输出应区分已证实结果、当前推演和下一步验证。

## 9. 输出与停止

- 体验定义：用户、情境、结果、证据与假设、当前旅程、目标旅程、信息架构、流程和验证；
- 参考研究：研究问题、当前来源、共同比较、可迁移关系、代价与推荐；
- 结构方案：对象模型、导航、任务流、状态、内容和跨平台不变量；
- 验证方案：风险假设、参与者条件、任务、观察指标、通过标准和迭代决定。

只输出当前请求需要的层级。形成用户需要的判断、方案或验证合同后停止，不自动扩张到完整市场研究、品牌战略、功能路线图、代码实施或长期运营。
