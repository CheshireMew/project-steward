# 架构内聚、耦合与重复治理

用于检查或治理高内聚低耦合、重复或相近实现、上帝类、上帝模块和职责过度集中的文件。目标不是把大文件机械拆小，而是让每项业务决定只有一个清楚的所有者，让变更只影响真正相关的部分。

## 1. 先明确被检查的用户结果

记录：

```text
项目的主要用户结果：
本次检查覆盖的模块和平台：
当前用户动作到最终结果的核心链：
用户只要诊断，还是也要求实施治理：
```

代码行数、函数数、依赖数和文件大小只用于筛选候选。一个大文件可能只负责一个完整领域而保持高内聚；一个很小的文件也可能同时决定多个领域或制造隐蔽双真源。结论必须由职责、变化原因、状态生命周期、调用关系和真实影响共同支持。

按照主路由已经选定的模式执行：诊断模式只交付证据、职责图、优先级和最终迁移方案；治理模式才建立新边界、迁移调用点并验证旧架构退出。本方法不重新解释用户措辞，也不改变上层已经冻结的写入权限和停止位置。

## 2. 建立职责与依赖图

候选清单同时按物理文件和逻辑所有者建立。逻辑所有者包括同一个 `partial class`、同一类型的扩展分片、共同实现一个类型或模块的头文件与实现文件、生成器及其分片输出，以及通过单一共享状态和公共表面组成的中心对象。筛选指标要同时报告单文件值和聚合值；不能把一个中心简单拆成多个文件后，让每个文件分别低于阈值就判定治理完成。生成代码和生成器分开标记，避免把机械输出误判成多个独立业务所有者。

对候选中心文件、类型或对象记录：

| 维度 | 要回答的问题 |
| --- | --- |
| 用户结果 | 它参与哪些彼此独立的最终结果 |
| 职责簇 | 函数、状态和命令能按哪些业务责任分组 |
| 变化原因 | 哪些互不相关的需求都会修改它 |
| 状态生命周期 | 哪些状态一起创建、更新、持久化和退出 |
| 公共表面 | 它向外暴露多少成员，消费者实际使用哪些组合 |
| 扇入与扇出 | 多少调用者依赖它，它又直接依赖多少边界 |
| 跨层调用 | 展示层是否直接决定原生、存储或领域行为 |
| 真源 | 同一事实、合同或转换是否由多处维护 |
| 测试缝 | 能否独立验证职责，还是必须启动整个中心 |
| 变更波及 | 修改一项职责会迫使哪些无关模块重测或同步修改 |

同时从关键消费者反向检查。中心对象拥有很多成员并不一定有害；如果一个主要消费者必须读取几乎全部成员、同时绕过中心直接调用下层，通常说明组合边界和领域边界都不清楚。

## 3. 判断上帝模块

出现以下组合时，可以认定为职责集中问题：

- 同一文件或对象拥有多个生命周期不同、失败方式不同的领域；
- 多种互不相关的需求都必须修改它；
- 它同时负责协调流程、保存状态、执行业务规则、访问平台和组织界面；
- 公共表面持续膨胀，消费者依赖大量成员而无法只依赖一个领域接口；
- 测试必须构造大量无关状态，或者一个修改触发大范围无关回归；
- 新模块虽已出现，旧中心仍包办全部转发、状态和兼容判断。
- 物理文件已经变小，但聚合后的逻辑所有者仍暴露全部状态、依赖和互不相关的变化原因。

只有“行数很多”时标为候选，不直接下结论。职责属于同一领域、共享同一生命周期、一起变化且能通过窄接口被消费时，保留为一个较大内聚模块可能更合理。

## 4. 识别真正的重复

同时做文本相似和语义重复检查。语义重复包括：

- 两处根据同一输入作出同一业务决定；
- 前后端、平台层或多个状态对象分别维护同一事实；
- 多个 helper 以不同名字完成相同转换、校验或恢复；
- 两套类型、命令或事件表达同一合同；
- 新旧实现并行，调用者根据场景选择不同真源；
- 多处复制同一状态机或错误映射，之后必须同步修改。

只有输入职责、业务责任、输出合同、消费者和停止位置都相同时才合并。代码长得相似但属于不同领域、具有不同失败语义或未来变化原因时，保留独立实现；可以共享更低层的纯机制，但不能强行共享业务所有权。

自动化文本扫描只生成候选，不直接产生“有重复”或“无重复”的结论。审查候选时至少区分声明与定义、接口与实现、生成器与生成物、协议两端必须存在的表示，以及真正由多处维护的业务决定。声明和对应定义、同一生成链的输出或语言固定样板可以从语义重复组排除；两端长期手写并会独立漂移的协议表示仍应追到唯一合同真源。报告“真实重复为零”时，必须说明候选已按这些角色归类，而不是只引用窗口哈希或文本相似度。

## 5. 设计最终边界

先决定每个职责簇的唯一所有者：

```text
领域或生命周期
→ 唯一状态与业务决定
→ 窄公共接口
→ 明确消费者
→ 可独立验证的用户结果
```

中心层只保留组合与流程协调，不重新拥有领域状态和规则。展示层负责呈现和交互；领域模块负责业务语义；平台边界负责文件、原生能力或远程调用。跨语言合同有一个可生成或可核对的真源，不由两端长期手写两份等价定义。

迁移计划逐项列出：

- 新的领域所有者和公共接口；
- 所有生产者、消费者、事件、状态和测试调用点；
- 数据与生命周期迁移；
- 旧类型、旧 helper、旧导出、旧转发、旧恢复逻辑和兼容层的退出条件；
- 依赖方向与循环依赖的处理；
- 必须保持的用户行为。

把函数移动到多个文件但保留一个暴露全部成员的巨型 facade，不算完成；新旧 API 同时活动、旧中心继续保存同一状态或消费者仍绕过新边界，也不算完成。

## 6. 实施与退出

用户只要求检查时，交付证据、职责图、优先级和最终迁移方案后停止。用户要求治理时：

1. 先用测试或真实链保住现有用户结果。
2. 建立新领域所有者和窄接口。
3. 一次迁移全部调用者、状态、事件、持久化和平台适配。
4. 让组合层只负责组装，不保留第二份决定。
5. 新链完整成立后退出旧实现和公共表面。
6. 搜索旧名称、旧导入、直接跨层调用和并行合同残留。
7. 把防回归检查接到正式质量入口，并按逻辑所有者重新聚合指标；门槛用于重新筛出候选，不能用任意行数替代职责判断。

不得按行数平均切文件，也不得为了降低单文件数字制造只含一层转发的碎片模块。

## 7. 真实验证

至少验证：

1. 职责与依赖图中的每个最终所有者都能从正式入口被消费。
2. 关键用户链经过真实生产者、边界和消费者。
3. 公共表面只暴露当前消费者需要的领域能力。
4. 旧导入、旧类型、旧 helper、旧转发和直接跨层调用已经退出。
5. 依赖方向符合目标边界且没有新增循环。
6. 语义重复扫描不再发现并行的业务决定或真源。
7. 修改一个领域时，无关领域不再被迫同步修改或构造。
8. 必须保持的用户行为、平台行为和失败恢复仍成立。
9. 拆分后按逻辑所有者重算职责、公共表面和依赖，`partial class`、头文件与实现文件或其它物理分片没有让中心对象靠文件数量规避检查。

核心链测试不能由消费者手写假数据代替生产者输出，也不能 mock 掉本次正在验证的领域或平台边界。

## 8. 输出

第一段直接回答当前项目是否达到高内聚低耦合，是否存在应合并的语义重复，以及哪些文件、类型或对象属于上帝模块。随后按优先级给出：

1. 问题与证据，不用文件大小代替根因。
2. 当前职责、调用和真源关系。
3. 应合并与不应合并的实现及理由。
4. 最终领域所有者、接口和迁移顺序。
5. 旧架构退出条件。
6. 真实测试与用户可观察验收。

同一根因的多个症状合并报告；只有证据不同、修复所有者不同或用户结果不同的问题才分开。
