# 架构内聚、耦合与重复治理

用于检查或治理高内聚低耦合、重复或相近实现、上帝类、上帝模块和职责过度集中的文件。目标不是把大文件机械拆小，而是让每项业务决定只有一个清楚的所有者，让变更只影响真正相关的部分。

## 1. 先明确被检查的用户结果

记录：

```text
项目的主要用户结果：
本次检查覆盖的模块和平台：
当前用户动作到最终结果的核心链：
用户只要诊断，还是也要求实施治理：
```

代码行数、函数数、依赖数和文件大小只用于筛选候选。一个大文件可能只负责一个完整领域而保持高内聚；一个很小的文件也可能同时决定多个领域或制造隐蔽双真源。结论必须由职责、变化原因、状态生命周期、调用关系和真实影响共同支持。

按照主路由已经选定的模式执行：诊断模式只交付证据、职责图、优先级和最终迁移方案；治理模式才建立新边界、迁移调用点并验证旧架构退出。本方法不重新解释用户措辞，也不改变上层已经冻结的写入权限和停止位置。

诊断结果可能被后续治理继续消费时，为每项发现分配稳定发现身份，并记录原证据、目标所有者、旧路径退出条件、结构验收和必须保持的用户行为。用户随后要求治理“全部”或“上述”问题时，直接消费这份发现清单；根因合并、职责重新划分或文件改名只能更新对应关系，不能重新挑选一份更容易完成的问题集合。

同一问题类型、关键词、目录位置或代码形态，不等于同一根因或同一迁移边界。只有最早错误事实、最终所有者、受影响的生产者到消费者链和旧路径退出条件都相同时，多个症状才合并为一项发现；任一项不同就继续独立建账。治理中复扫到的新命中只有在这四项仍然成立时才进入当前迁移范围，否则只记录为独立问题并停在原授权边界。

### 冻结审计基线与度量来源

第一次取得候选指标时，同时冻结它所对应的实际内容，不能只记一个脱离来源的行数或成员数：

```text
发现身份：
审计来源：当前工作树 / 指定提交 / 指定产物
内容身份：取得时刻、版本或哈希
聚合定义：单文件 / 类型 / 逻辑所有者，以及包含的成员或分片
既有未提交变化：
```

审计脏工作树时，基线是审计当时磁盘上的实际内容，不能用 Git HEAD 替代。候选、其分片或聚合定义在审计后被其它工作改变时，旧基线失效；重新度量并建立新基线，或把不同来源分别报告，不能把不可比数值拼成前后变化。

所有前后值都要绑定各自的内容身份，并能追溯到同一审计基线和同一聚合定义。最终报告分开写清“审计快照到当前状态”“本任务实际改动”和“相对 Git 的差异”；无法证明某项变化由本任务产生时，只报告现状，不把它算成本任务减少的职责、代码或依赖。

## 2. 建立职责与依赖图

候选清单同时按物理文件和逻辑所有者建立。逻辑所有者包括同一个 `partial class`、同一类型的扩展分片、共同实现一个类型或模块的头文件与实现文件、生成器及其分片输出，以及通过单一共享状态和公共表面组成的中心对象。筛选指标要同时报告单文件值和聚合值；不能把一个中心简单拆成多个文件后，让每个文件分别低于阈值就判定治理完成。生成代码和生成器分开标记，避免把机械输出误判成多个独立业务所有者。

对候选中心文件、类型或对象记录：

| 维度 | 要回答的问题 |
| --- | --- |
| 用户结果 | 它参与哪些彼此独立的最终结果 |
| 职责簇 | 函数、状态和命令能按哪些业务责任分组 |
| 变化原因 | 哪些互不相关的需求都会修改它 |
| 状态生命周期 | 哪些状态一起创建、更新、持久化和退出 |
| 公共表面 | 它向外暴露多少成员，消费者实际使用哪些组合 |
| 扇入与扇出 | 多少调用者依赖它，它又直接依赖多少边界 |
| 跨层调用 | 展示层是否直接决定原生、存储或领域行为 |
| 真源 | 同一事实、合同或转换是否由多处维护 |
| 测试缝 | 能否独立验证职责，还是必须启动整个中心 |
| 变更波及 | 修改一项职责会迫使哪些无关模块重测或同步修改 |

同时从关键消费者反向检查。中心对象拥有很多成员并不一定有害；如果一个主要消费者必须读取几乎全部成员、同时绕过中心直接调用下层，通常说明组合边界和领域边界都不清楚。

### 文件图与聚合图分别验收

同一组实际导入、调用或绑定至少生成文件图和聚合图两种投影。文件图保留准确源码身份；聚合图按项目已经声明的目录层、包、组件或逻辑所有者合并节点，并为每一层写出允许的单向依赖。两张图分别检查非法边、环和强连通分量：文件图无环不能替目录或包无环，聚合图成环也不能凭一个未成环的文件例子排除。再从正式运行入口核对活动源码可达性；测试、生成物和归档按各自消费者单独建账，不能替活动生产路径成立。

硬编码扫描只生成候选。跨消费者表达章节身份、数量、链接、资源版本、超时政策或其它共享业务事实时，追到一个可执行真源并让其余位置派生；只服务一个局部呈现、测量结果、动画曲线或媒体调优，且没有同步变化义务时，保留在所属模块。相同字面量和“可以抽成常量”都不能单独证明应合并。

## 3. 判断上帝模块

出现以下组合时，可以认定为职责集中问题：

- 同一文件或对象拥有多个生命周期不同、失败方式不同的领域；
- 多种互不相关的需求都必须修改它；
- 它同时负责协调流程、保存状态、执行业务规则、访问平台和组织界面；
- 公共表面持续膨胀，消费者依赖大量成员而无法只依赖一个领域接口；
- 测试必须构造大量无关状态，或者一个修改触发大范围无关回归；
- 新模块虽已出现，旧中心仍包办全部转发、状态和兼容判断。
- 物理文件已经变小，但聚合后的逻辑所有者仍暴露全部状态、依赖和互不相关的变化原因。

只有“行数很多”时标为候选，不直接下结论。职责属于同一领域、共享同一生命周期、一起变化且能通过窄接口被消费时，保留为一个较大内聚模块可能更合理。

## 4. 识别真正的重复

同时做文本相似和语义重复检查。语义重复包括：

- 两处根据同一输入作出同一业务决定；
- 前后端、平台层或多个状态对象分别维护同一事实；
- 多个 helper 以不同名字完成相同转换、校验或恢复；
- 两套类型、命令或事件表达同一合同；
- 新旧实现并行，调用者根据场景选择不同真源；
- 多处复制同一状态机或错误映射，之后必须同步修改。

只有输入职责、业务责任、输出合同、消费者和停止位置都相同时才合并。代码长得相似但属于不同领域、具有不同失败语义或未来变化原因时，保留独立实现；可以共享更低层的纯机制，但不能强行共享业务所有权。

自动化文本扫描只生成候选，不直接产生“有重复”或“无重复”的结论。审查候选时至少区分声明与定义、接口与实现、生成器与生成物、协议两端必须存在的表示，以及真正由多处维护的业务决定。声明和对应定义、同一生成链的输出或语言固定样板可以从语义重复组排除；两端长期手写并会独立漂移的协议表示仍应追到唯一合同真源。报告“真实重复为零”时，必须说明候选已按这些角色归类，而不是只引用窗口哈希或文本相似度。

### 过度设计候选必须用等价合同证明

以下形态进入过度设计候选：只有一个正式实现和一个消费者的接口或工厂；只做转发且不拥有策略、状态、失败收口或生命周期的 wrapper、基类与文件；没有活动消费者的 flag、配置、扩展点和兼容分支；重复语言、运行时、数据库、浏览器或操作系统原生能力的自建代码；与现有依赖或原生能力重叠的新依赖。它们只是筛选信号，不能因文件小、层数多、依赖多或可以删行就直接判为问题。

每项候选记录稳定发现身份、受影响的用户结果、当前机制及维护成本、可替代能力的来源证据、必须保持的输入输出、错误、生命周期、平台与消费者合同，以及迁移和旧路径退出条件。只有替代路径完整闭合相同合同，当前层又没有独立责任或已证明消费者时，才认定为可收敛；相邻能力、最短代码和净删除行数不能充当等价证明。诊断授权只交付发现与最终迁移方案，治理授权才实施替换并验证旧机制退出。

### 适配器族先拆开共同政策与合法变体

爬虫、provider、导入器、平台适配器或其它同族实现只有部分相似时，不把整个方法作为最小比较单元，也不在“全部合并”和“全部复制”之间二选一。先建立变体账本：

```text
重复实现族与正式入口
→ 共同业务政策及顺序：生命周期、去重、停止、数量上限、错误收口、结果规范化
→ 只有适配器知道的来源事实：获取、选择器、解析、平台调用
→ 会改变生命周期或失败语义的真实例外
→ 最终族级所有者、窄适配器接口和正式消费者
```

相同政策、默认值和执行顺序由一个族级流程、策略或组合所有者维护；适配器接口只返回来源事实或执行平台专用动作，不能重新决定共同政策。标准适配器不得通过覆写重新复制去重、停止、限制、错误或规范化流程；只有证据证明其输入职责、生命周期或失败语义不同，才保留显式例外，并写清适用条件、独立所有者和退出条件。不要为了复用建立只有一层转发的基类，也不要把来源专用解析塞进共同所有者。

验收从正式入口分别运行一个标准适配器和每类真实例外，证明共同政策由同一所有者执行、来源事实仍由对应适配器提供、结果合同和失败收口正确。再用一个表面不同的标准适配器核对新增来源无需复制共同流程，并让架构门禁阻止标准适配器重新覆写不变量；基类存在、文本减少或单独调用 hook 都不能代替这条链。

### 测试专用影子实现不算生产覆盖

测试引用一个 helper，而生产入口调用名称不同但职责相近的另一份实现时，先核对可达性，不能因测试通过或两段代码当前结果相同就认定生产实现已被覆盖。为候选建立“同一业务决定 → 生产入口实际到达的实现 → 测试入口实际到达的实现 → 正式唯一所有者 → 迁移或保留决定”账本。只被测试、样例或验证器引用的实现，如果重新决定生产转换、校验、切分、恢复或错误语义，就是测试专用影子实现；测试数据构造器只有在不复制这些业务决定时才是合法夹具。

治理时让生产入口与测试共同消费正式唯一所有者，并让至少一项测试从生产公共入口或其真实上游到达该所有者；随后退出影子 helper、重复夹具逻辑和只为旧测试保留的导出。单元测试可以直接验证最终领域所有者，但不能用只存在于测试侧的相近实现替代生产可达性证据。残留检查同时比较生产引用集合和测试引用集合；“只有测试引用”是需要解释的候选，不自动等于可删除，也不自动等于已经覆盖生产。

### 公共协议表面的存活与唯一语义

事件、DTO、payload、状态快照、回调、信号或跨进程消息一旦进入公共表面，逐项建立存活账本，不能只证明类型可构造、序列化能通过或测试里仍有引用：

```text
事件或字段，包括线名称、类型和版本
→ 唯一语义所有者
→ 稳定操作身份与代次
→ 正式生产者
→ 传输或存储边界
→ 生产消费者及其用户可观察结果
→ 出现的生命周期阶段
→ 权威事实 / 必要投影 / 有明确消费者与保留期的诊断信息 / 死表面
→ 保留、统一或退出决定
→ 真实链验证和旧标识残留证据
```

结构测试、迁移测试和说明文档仍属于接口迁移时必须同步的消费者，但它们不能单独证明一个运行时事件或字段有存活价值。没有生产消费者和用户结果的表面退出；诊断或遥测表面只有在点名正式消费者、用途与保留期后才保留。必要投影只能从权威事实生成，不能重新决定业务状态或成为第二真源。

仓内调用点为零只能作为有界内部符号的退出证据，不能证明 HTTP、WebSocket、IPC、CLI、插件入口、框架注册、公共导出或其它仓外可达表面已经死亡。对这些表面还要核对正式注册与路由、机器可读发现或 schema、活动文档与示例、SDK 或扩展合同、版本与发布承诺，以及已知外部消费者；框架注册只能证明仍可到达，也不能反向证明仍有实际用途。无法界定消费者范围或取得外部合同证据时，该表面的退出只能标为未知或受阻，不能因仓内搜索无命中就删除、改名或宣告原功能已经迁移。

同一语义事实贯穿开始、更新、完成、失败、取消和清理时，使用同一个字段名称、类型、操作身份和版本含义。两个字段互为别名、同一阶段发送两个等价事件，或新旧消费者各读一种名称，都是并行合同，不是兼容性成果。迁移必须同时覆盖生产者、schema 或共享词汇、传输与存储、全部生产消费者、文档、示例和测试；新链成立后退出旧字段、旧事件、旧别名、旧默认值和旧恢复分支，并按准确标识做残留扫描。

验收从正式生产者触发每个保留表面，让实际事件、传输或存储边界和生产消费者形成对应的用户结果；不能由消费者测试手写 payload，也不能只断言字段存在。涉及交错回调、失败或取消清理时，存活账本先决定应保留的合同，再由并发、所有权与顺序诊断证明每个操作只影响自己的身份与代次。

## 5. 设计最终边界

先决定每个职责簇的唯一所有者：

```text
领域或生命周期
→ 唯一状态与业务决定
→ 窄公共接口
→ 明确消费者
→ 可独立验证的用户结果
```

中心层只保留组合与流程协调，不重新拥有领域状态和规则。展示层负责呈现和交互；领域模块负责业务语义；平台边界负责文件、原生能力或远程调用。跨语言合同有一个可生成或可核对的真源，不由两端长期手写两份等价定义。

### Repository 边界按聚合所有权验收

把 SQL、ORM 查询或文件读写从 manager、service 或 controller 移进名为 repository 的文件，只证明物理位置改变，不证明领域已经解耦。逐个 repository 建立所有权账本：

```text
repository 与公共接口
→ 拥有的聚合、稳定身份和写入不变量
→ 直接读写的表、集合、文件或索引
→ 明确拥有的只读投影及其一致性语义
→ 事务、重启恢复、批处理和释放生命周期
→ 正式应用服务与其它消费者
→ 允许和禁止的跨聚合依赖
```

聚合 repository 不能隐藏查询另一个聚合并据此决定其领域规则，也不能把自身 `.repository`、连接、游标或表级 helper 暴露给 controller、service 或其它 repository。需要跨聚合事实时，由窄公共接口、注入的 resolver、明确命名的查询服务或应用服务组合结果；这些边界必须保留原来成立的事务、重启恢复、批处理和生命周期不变量，不能为了消除依赖而丢掉合法语义。

显式只读投影可以组合多个聚合或表，但必须公开表明它是查询模型，列出来源、时点或一致性语义，不写回来源聚合，也不成为任何聚合的第二业务真源。验收不能按“一张表一个 repository”机械判断，而要证明每个写入决定只有一个聚合所有者、跨聚合读取经过已声明接口、应用层没有穿透 `.repository`，并以代表性事务、重启或恢复链证明拆分没有破坏生命周期。

### 宽公共表面和组合根迁移保留合同身份

拆分宽 facade、控制器或组合根时，不能只列出受影响文件和最终类名。修改前建立成员与协作者迁移账本：

```text
旧方法、属性、信号、事件、回调、导出或构造参数
→ 最终领域所有者或组合对象字段
→ 生产代码、跨语言绑定、测试、脚本和验证器中的正式消费者
→ 必须保持同一实例的协作者及其身份约束
→ 允许机械迁移的前提
→ 新调用证据和旧成员退出证据
```

迁移包含可变事实或业务草稿时，再建立写入所有权闭合账本：

```text
可变事实或业务草稿及其稳定身份
→ 旧层的全部写入、默认值重算、定时保存、恢复和生命周期回调
→ 最终权威所有者及其提交、持久化和活动运行时消费者
→ 旧层获准保留的瞬态展示状态、类型化意图和只读投影
→ 同一活动实例的装配身份
→ 旧写入退出、真实入口提交和关闭重开证据
```

新建模型、helper 或 bridge 只证明新边界能够被表达，不证明状态权威已经迁移。旧展示层仍能给业务字段赋值、补默认值、定时保存、关闭刷盘或从持久状态恢复时，事实仍有两个所有者；这些写入必须进入最终所有者，展示层只提交类型化意图并读取投影。焦点、悬停、临时布局和纯绘制缓存等不影响业务结果的瞬态展示状态可以留在界面，不能为了追求零赋值机械迁走。完成验收先按写入、保存、恢复和生命周期调用形态扫描旧层，再从真实用户入口修改一次事实，让同一个正式模型实例经过提交、活动运行时消费、关闭和重开；只构造新模型、检查属性存在或让测试直接调用 setter 都不能证明权威迁移完成。

成员表面必须按实际使用方式盘点。消费者继续导入同一个根类型，却仍调用旧成员、连接旧信号、读取旧属性或使用字符串绑定，也属于未迁移；只搜索旧类型名、文件名或导入不能发现这类残留。跨语言界面要同时记录两端的成员路径和通知语义，测试、示例和验证工具与生产调用点使用同一最终合同。

多个独立参数被服务图、上下文或其它组合对象替代时，账本还要记录对象身份不变量。例如配置、事件总线、存储、provider、生命周期所有者或锁必须来自哪一个活动对象图，哪些消费者必须共享同一实例。批量改写只能处理能从当前调用点无歧义取得这些协作者的情况；不能根据其它调用点常见的局部变量名补造依赖，也不能为通过构造检查临时创建第二个实例。来源缺失或身份关系不清楚的调用点必须单独迁移。

修改后先按旧成员的调用、属性、信号和字符串绑定形式做跨语言残留检查，再让每种不同的调用点形态实际构造或运行，并从正式组合根产生的对象核对身份不变量。动态绑定、通配导入、反射或跨语言绑定会削弱静态分析；编译和 lint 通过只能证明其实际覆盖的符号，不能替代这些调用形态和身份检查。完整回归用于确认行为保持，成员残留与身份检查用于证明接口迁移完成，两者不能互相冒充。

### 可选能力按独立支持面拆分公共合同

把宽 facade、动态成员探测或乐观兼容判断替换成正式接口前，先建立能力合同采用账本：

| 实现或消费者 | 核心必需合同 | 独立可选能力 | 支持与不可用证据 | 生命周期和失败语义 | 迁移状态与旧回退退出条件 |
| --- | --- | --- | --- | --- | --- |
| | | | | | |

核心必需合同只保留全部正式实现都必须履行、缺失时核心用户结果就不能成立的成员。可选能力能够被独立支持、独立配置、独立失效，或者拥有不同生命周期和失败收口时，分别建立窄接口或能力端口；只有证据证明它们总由同一实现共同提供、共同变化并共享可用性、生命周期和失败语义时才允许聚合。组合根或特定消费者可以为方便组合多个窄端口，但这种组合不能反向成为每个实现都必须满足的宽前提。按成员是否存在进行探测、成员缺失时返回乐观默认，或在多个调用点各自猜测能力可用性，都属于待退出的旧兼容路径，不是正式能力模型。

迁移继续消费 `change-prevention.md` 对全部正式契约消费者的闭包要求，逐项覆盖生产实现、平台适配器、组合根、测试替身和 fixture。测试替身声明自己扮演某个正式核心实现却缺少必需成员时，修正替身或共享夹具；它本来只模拟一项可选能力时，让测试只注入对应窄端口并保留“部分能力”身份。不能为了让旧替身继续通过而恢复产品动态回退，也不能用一个能力齐全的共享假对象掩盖正式实现之间真实存在的支持差异。

无论替身模拟的是核心合同还是可选能力，接口、端口或依赖签名变化后，故障注入替身必须先按最终合同完成参数、协作者和对象身份绑定，并证明执行已经到达原定故障注入阶段。由旧签名、缺失参数、错误构造或替身初始化引发的提前异常，只能判为验证器迁移失败，不能作为事务、回滚、恢复或失败语义的证据；产品适配器在正式入口按最终合同拒绝真实无效输入，仍是产品合同失败，不因本规则被重分类。修正替身后，仍要让目标边界按预定故障类别失败，并由正式恢复消费者核对原状态、稳定身份和后置条件，不能把“测试重新变绿”替代这条失败链。

验收至少包含一个完整能力实现、一个只支持部分可选能力的实现和一个不支持该可选能力的实现。三者都从正式组合或消费入口运行：核心路径不因可选能力缺失而被误判失效；部分实现只暴露实际能力；缺失能力进入明确的不可用或不适用结果；旧成员探测、乐观默认和兼容分支已经按准确标识退出。每行采用账本还要由相应的构造、调用或测试收集证据证明实际参与验证，不能只因类型声明存在就标为已迁移。

### 多入口操作共享一份绑定与请求收口

同一操作同时由通用执行入口、CLI 简写、桌面动作、后台恢复、RPC 或验证脚本发起时，为每项操作建立一份合同账本：稳定操作身份、同步或长任务属性、阶段或 handler 所有者、请求 schema 与默认值、必要的请求身份和关联信息、幂等或恢复语义、全部第一方入口，以及正式结果消费者。操作身份到这些语义的绑定只有一个可执行真源；其它注册表、帮助文本、能力描述和界面列表只能由它投影或与它做启动时集合相等检查，不能分别维护会漂移的子集。

所有第一方入口在序列化或传输前经过同一个请求收口边界，由该边界补齐和校验通用 envelope，例如请求身份、关联身份、操作代次、幂等信息和协议版本；入口专用 preparer 只负责把用户输入转换为操作参数，不能各自重写通用 envelope。长任务属性、handler 绑定和 preparer 或快照如果分属不同生成物，启动检查必须证明操作集合及稳定身份完全一致，缺项、孤儿项和重复绑定立即失败。

验收至少从一个第一方简写或界面动作发起代表性操作，让请求经过正式收口、传输或存储、handler、结果边界和最终消费者，并检查关联信息在完整链中保持一致。只调用通用 execute、直接构造已完成请求，或只验证注册表里存在操作名，不能证明其它第一方入口消费了同一合同。

### 让异步工作流按业务阶段闭环

同一用户工作流包含多个业务阶段，并且一个阶段的输入校验、任务命令生成、结果应用和展示更新分散在多个中心服务、控制器或分派器时，把它作为职责扩散检查。稳定信号包括：新增一个阶段需要同时修改启动任务的中央分支、执行注册、结果消费的另一组中央分支和界面控制器；阶段名称或参数在字典、持久化记录和界面中重复解释；中央协调器既决定下一步流程，又知道每个阶段怎样构造命令和怎样把结果写回领域状态。只包含一个简单异步调用、没有阶段语义和结果回写分支的流程不为形式完整增加阶段框架。

最终边界按以下顺序建立：

```text
用户动作
→ 阶段所有者校验输入并生成类型化命令
→ 任务边界持久化命令并交给对应执行器
→ 执行器只负责外部、平台或计算操作并产生类型化结果
→ 同一阶段所有者消费正式结果并提交领域状态
→ 展示投影从已提交状态生成可观察结果
→ 当前界面消费该投影
```

阶段所有者拥有该阶段从业务输入到结果应用的闭环，但不接管平台执行；执行器不反向决定领域状态；展示投影不重新解释任务参数。组合根只装配阶段所有者、执行器、存储和投影，通用分派器只按稳定类型找到所有者，不保留阶段专用判断。持久化或传输的命令必须是正式生产者实际生成的严格合同，计算字段、展示字段和调度元数据不能混入后再要求下游猜测或剔除。

验收从真实用户动作取得本轮命令身份，让该命令经过正式序列化与存储、对应执行器、类型化结果、阶段结果应用和当前展示投影。阶段注册表必须覆盖正式命令或阶段集合；新增一个阶段不应再修改多个中央业务分支；架构守卫应阻止中央协调器重新出现阶段逻辑、展示层依赖宽控制器，以及已经退出的 facade、旧命令字典或结果分派入口重新活动。只验证阶段处理函数、直接构造结果或让界面读取手写状态，不能证明这条闭环成立。

迁移计划逐项列出：

- 新的领域所有者和公共接口；
- 所有生产者、消费者、事件、状态和测试调用点；
- 数据与生命周期迁移；
- 旧类型、旧 helper、旧导出、旧转发、旧恢复逻辑和兼容层的退出条件；
- 依赖方向与循环依赖的处理；
- 必须保持的用户行为。

迁移顺序由唯一真源和依赖图决定，不由文件大小或修改难度决定。先建立被多条上层链共同依赖、负责数据、状态或合同决定的最终所有者，再向应用编排、展示和外部入口迁移消费者；实际项目没有固定的层名顺序，以当前依赖方向为准。每迁移一个边界，都要让该边界的全部调用点改用最终接口并退出对应旧公共表面，不能为了让后续阶段暂时运行而留下内部兼容层。

把函数移动到多个文件但保留一个暴露全部成员的巨型 facade，不算完成；新旧 API 同时活动、旧中心继续保存同一状态或消费者仍绕过新边界，也不算完成。

## 6. 实施与退出

用户只要求检查时，交付证据、职责图、优先级和最终迁移方案后停止。用户要求治理时：

1. 先用测试或真实链保住现有用户结果。
2. 建立新领域所有者和窄接口。
3. 一次迁移全部调用者、状态、事件、持久化和平台适配。
4. 让组合层只负责组装，不保留第二份决定。
5. 新链完整成立后退出旧实现和公共表面。
6. 搜索旧名称、旧导入、直接跨层调用和并行合同残留。
7. 把防回归检查接到正式质量入口，并按逻辑所有者重新聚合指标；门槛用于重新筛出候选，不能用任意行数替代职责判断。

每项残留扫描在运行前先写出语义闭合条件：本发现禁止存在的所有权或依赖方向、必须覆盖的源码与合同来源、允许存在的最终边界，以及每种命中怎样归入旧架构、最终实现、自然语言误报或范围外独立问题。文件名、`globals`、`fetch`、目录层级或旧标识符只能帮助发现候选；零匹配只有在扫描器成功覆盖预期输入、允许边界已经逐项核对且语义重复也已检查后，才能证明这一项结构退出。

架构门禁或残留扫描器会在测试常量、规则表或诊断说明中声明被禁止的旧标识符时，把规则定义控制面与被检查的活动对象分开。输入合同同时记录活动源码、脚本、验证器和公共合同等目标根，保存禁用标识符的规则文件，以及每项精确排除的理由；规则定义中的哨兵文本不能被当成活动调用，但测试或脚本中的真实导入、成员访问和字符串绑定仍然属于正式消费者，不能为了消除自命中而排除整个测试目录或脚本目录。优先使用能够区分声明文本与活动语义的结构化扫描；必须排除规则定义文件时，用另一个表面不同的代表性目标注入同类残留，证明扫描器仍会失败，再移除注入并取得零发现。

结构化门禁还要声明被禁止事实的准确语义单元和语言作用域，例如模块顶层绑定、类型成员、函数局部变量、导入、调用或字符串绑定；一个作用域中的禁令不能凭相近命名扩张到另一个作用域。每条门禁都用一个真实违规夹具和一个文本相近但语义合法的夹具成对验证：前者证明不会漏报，后者证明不会误报；两者还要与实际目标根使用同一解析和选择路径。解析器没有覆盖项目实际使用的动态绑定或语言结构时，对应边界保持未知，不能用局部 AST 成功宣称整体通过。

### 测试依赖和失败作用域随成员迁移

拆分前把测试对私有方法、模块常量、monkeypatch、fixture 和内部状态的访问加入成员迁移账本，标明它验证的是公共行为、最终所有者的领域规则、结构不变量，还是过期耦合。公共行为改从正式入口到达；领域规则只经最终所有者的窄接口验证；结构测试点名准确不变量。不能为旧测试恢复私有兼容层，也不能只改 monkeypatch 路径使其变绿。

同时冻结代码移动前的失败作用域：每项输入在哪里捕获异常、记录错误、重试、继续或中止，事务与清理覆盖什么。重构后以代表性失败证明逐项失败没有升级成整批失败、必须中止的错误没有被吞掉，且后续合法项仍按原合同处理。只有迁移确实改变生产者、合同、边界或消费者的断言和夹具才同步修改，并映射到稳定发现身份和已冻结的目标行为基线；无关断言、并发改动或目标仍未知的失败保持原状，不能用脏工作树当前文字、一次运行结果或“让测试变绿”反向改写目标行为。

不得按行数平均切文件，也不得为了降低单文件数字制造只含一层转发的碎片模块。

## 7. 真实验证

至少验证：

1. 职责与依赖图中的每个最终所有者都能从正式入口被消费。
2. 关键用户链经过真实生产者、边界和消费者。
3. 公共表面只暴露当前消费者需要的领域能力。
4. 旧导入、旧类型、旧 helper、旧转发和直接跨层调用已经退出。
5. 依赖方向符合目标边界且没有新增循环。
6. 语义重复扫描不再发现并行的业务决定或真源。
7. 修改一个领域时，无关领域不再被迫同步修改或构造。
8. 必须保持的用户行为、平台行为和失败恢复仍成立。
9. 拆分后按逻辑所有者重算职责、公共表面和依赖，`partial class`、头文件与实现文件或其它物理分片没有让中心对象靠文件数量规避检查。
10. 仓外可达的公共表面已经取得消费者存活或退出证据，未知外部合同没有被仓内零引用替代。
11. 每项残留扫描的实际输入、允许边界与命中分类都符合预先定义的语义闭合条件。
12. 测试改动逐项对应本轮发现和目标行为，无关断言没有因同文件或同套件被顺带改写。
13. 每个 repository 的聚合、写入不变量和允许投影都有明确所有者，跨聚合事实不经内部 repository 穿透。
14. 关键测试实际到达生产唯一所有者，测试专用影子实现已经退出或被证明只是无业务决定的夹具。
15. 操作绑定和通用请求 envelope 只有一个可执行真源，至少一个第一方简写或界面入口完成真实链。
16. 同族适配器的共同政策只有一个所有者，标准适配器不覆写不变量，真实例外保留自己的生命周期与失败语义。
17. 架构门禁按准确语义作用域检查，并由违规与合法近似夹具分别证明不会漏报和误报。

核心链测试不能由消费者手写假数据代替生产者输出，也不能 mock 掉本次正在验证的领域或平台边界。

治理结束时按稳定发现身份逐项结账。结构发现只有在最终所有者被活动消费者使用、旧公共表面和禁止依赖已经退出、逻辑所有者重新聚合后的职责与依赖符合目标，并且这些证据产生于最后一次相关修改之后，才可标为已解决。完整回归和真实用户链证明行为保持，不能替代结构收口；反过来，结构扫描通过也不能替代用户行为。发现被重新分类时要指出原结论依赖的职责、生命周期、公共表面或真源条件为何不再成立；退出范围必须有用户明确决定。存在开放、未知或受阻项时，结论必须如实保留，不能宣称全部治理完成。

## 8. 输出

第一段直接回答当前项目是否达到高内聚低耦合，是否存在应合并的语义重复，以及哪些文件、类型或对象属于上帝模块。随后按优先级给出：

1. 问题与证据，不用文件大小代替根因。
2. 当前职责、调用和真源关系。
3. 应合并与不应合并的实现及理由。
4. 最终领域所有者、接口和迁移顺序。
5. 旧架构退出条件。
6. 真实测试与用户可观察验收。
7. 原始发现逐项对应的已解决、重新分类、用户确认退出范围或受阻状态，以及各自的新鲜证据。
8. 同源变体的闭合条件、扫描覆盖与命中分类，以及只记录而未纳入治理的独立问题。
9. 每项新增架构门禁的真实违规夹具、合法近似夹具和实际目标输入结果；缺少成对自测时只报告现状扫描，不宣称已经防回归。
