# 项目综合审计

只在用户明确要求全面检查、健康判断、风险排序或综合审计时使用。本方法只读，适用于普通文件夹、源码包、本地 Git 仓库和远程仓库。

## 输入与停止位置

输入是准确项目根、用户目标和当前规则。输出是项目事实、治理基线、关键风险、证据强度和建议顺序。交付后停止，不写项目配置、不修改源码、不初始化 Git，也不自动进入专项分支。

用户要求“全部问题”“所有问题”或“全面检查”时，开始前建立覆盖合同：

```text
审计根、版本或工作树状态：
确认存在的项目形态与平台：
需要覆盖的用户结果和主要生产链：
将读取的源码、配置、文档与仓库边界：
获准实际运行的入口、成功路径、失败与恢复路径：
可验证的构建、产物、部署或发布层：
需要核对的本地、实时远端与外部能力证据平面：
当前明确无法取得的证据：
```

“全部”只表示在这份冻结范围内完成了高价值事实、同源变体和残留证据检查，不表示未知平台、未获准运行的命令或不可访问的外部系统已经无问题。最终输出必须同时列出已覆盖范围和仍未覆盖的证据；后续取得的新入口或新权限只扩展相应部分，不能反向把早先结论描述成无条件完整。

## 1. 建立项目事实

读取与结论直接有关的材料：

- 项目规则、现有项目配置、目录边界和平台；
- README、包元数据、启动入口、主要源码与真实示例；
- 精确根 Git 状态、默认分支和远程地址；项目根没有 `.git` 时标为普通项目；
- 构建、测试、发布、迁移和恢复入口；
- 现有许可证、NOTICE、版权与第三方内容；
- 可运行项目的日志入口、存储和查看方式。

只有工具位置、包或缓存根、终端、SDK 或长任务状态会改变审计结论时，才读取已有用户环境档案中的相关条目，并由绝对可执行文件、版本或目录核验。没有环境档案不是项目缺陷，也不能为完成综合审计自动创建或更新档案。

### 分开本地与实时远端事实

项目配置了远端仓库，并且公开交付、远端检查、许可证、默认分支或发布状态会改变审计结论时，分别建立以下证据平面：

```text
工作树与本地提交：
本地缓存的远端跟踪引用及最后更新时间：
实时远端默认分支与 HEAD：
对应提交的远端检查或工作流：
当前 release、标签与可下载制品：
各项取得时刻、身份与访问条件：
```

本地 `refs/remotes/*`、历史 CI 徽章、上一次抓取结果和本地已有许可证，只证明各自时点的状态，不能代替实时远端。当前审计范围包含公开或远端交付且网络可访问时，使用仓库托管方的只读接口或正式客户端取得实时状态；无法访问、没有权限或没有取得准确提交身份时标为待确认，不能把“没有读到”写成“远端不存在”。实时远端与本地不一致时，先说明差异和证据时刻，不在只读审计中自动拉取、合并或改写工作树。

写清：

```text
项目是什么：
主要用户：
第一项可观察价值：
内容或状态真源：
主要生产链：
当前平台：
当前模板：
当前公开状态：
最强证据：
```

源码存在只证明包含实现；配置声明只证明作者作出声明；测试通过只证明测试覆盖的边界；真实产物和用户链才能证明最终结果。

“不存在后端”“没有持久化”“没有发布能力”等负面结论也需要范围证据：检查项目根内的服务入口、依赖与脚本、部署或进程配置、环境读取、网络调用、数据存储和正式运行入口，再说明结论限定在哪个根、版本和平台。没有发现常见目录只能形成线索，不能单独证明某一层不存在；确认产品本来不需要该层时，将其列为非问题，不为了形式完整建议新增架构。

## 2. 审计治理基线

检查：

- 项目是否有一个准确根，普通文件夹是否被错误当成必须 Git；
- 项目配置固定的模板版本是否能从注册表解析；
- 当前项目类型和技术栈是否与模板选择一致；
- 项目覆盖与偏离是否有理由、影响和复查条件；
- 模板、源码、测试和文档之间是否已经漂移；
- 当前项目的长期决定是否位于会被真实开发流程读取的规则、文档、配置、代码或测试中；
- 没有项目配置时，是否仍有清楚的项目规则与真实边界。

没有采用模板不是自动缺陷。只有重复决策、跨项目缺陷或维护边界确实需要时，才建议采用。

没有 Project Steward 配置不是自动缺陷。项目反复依赖同一结论但没有任何正式真源，或者文档、代码和测试表达互相冲突时，才把它列为治理问题。

## 3. 审计产品与真源

检查：

- 项目定位和主要用户结果是否与实际实现一致；
- 磁盘文件、数据库、远程服务、缓存或生成副本中谁是唯一真源；
- 状态恢复、自动保存、迁移和同步是否会产生双真源；
- 普通用户路径和高级能力是否在界面与架构中正确分层；
- 平台差异是否是明确合同，而不是遗漏。

发现多个可写副本时，指出最早分叉和最终应由谁负责，不在综合审计中直接迁移。

### 验证外部默认能力的现实可用性

云服务、公共 API 或其它外部能力承担首次成功路径、默认能力，或者项目承诺匿名、免费、零配置即可使用时，不能只从配置项、测试替身、旧文档或接口名称推断它当前可用。先读取当前官方合同、身份与额度要求；它们存在冲突或不完整时明确记录。当前规则与用户请求允许运行，并且该能力会改变主要用户结果时，再使用项目自己的有界连接测试、正式 provider 入口或真实消费者验证，不另写一条绕过产品配置和错误映射的探测链。

结果至少记录取得时间、服务与端点身份、匿名或账号条件、项目实际配置、返回状态和正式消费者怎样展示。认证、额度、价格、区域、速率或服务端失败只证明这些准确条件下的当前路径；不能从一次 `401`、`402`、超时或官方资料冲突扩大成服务永久关闭，也不能用另一个账号、测试开关或手工请求的成功替默认入口背书。未获运行授权时只报告合同证据和现实可用性仍未验证。

## 4. 审计架构链

为最重要的用户结果建立：

```text
用户动作 → 生产者 → 边界 → 持久化或传输 → 消费者 → 可观察结果
```

检查：

- 前端、后端、原生层和远程服务的责任是否清楚；
- 公共类型、命令、事件和状态是否已经半迁移；
- 错误、取消、重试、冲突和关闭是否通过同一边界；
- 旧 helper、旧入口、旧数据源和兼容层是否仍在活动；
- 测试是否穿过本次声称验证的核心边界。
- 外部 CLI 是否允许配置完整命令字符串或原始 argv，从而覆盖适配器拥有的工作目录、隔离、权限、设置、输出或工具能力；
- 中心文件或对象是否同时拥有多个生命周期和变化原因；
- 公共表面是否迫使消费者依赖大量无关能力；
- 同一业务决定、状态、合同或转换是否存在语义重复；
- 依赖方向是否清楚，是否出现循环、跨层直连或巨型转发中心。

只看到一个函数正确或一个界面静态截图，不能把整条链标为健康。

代码行数、函数数和依赖数只用于筛选候选，不能单独证明上帝模块。用户明确要求检查高内聚低耦合、重复实现或上帝文件时，由主路由直接加载架构专项方法，建立完整职责、依赖、真源和变化原因图；综合审计这里只保留项目级结论和优先级。

## 5. 审计数据与生命周期

按适用场景检查：

- schema 版本和迁移是否单向、可重试并立即重写；
- 协议或 schema 迁移是否分别覆盖当前版本新建状态、由旧版本真实生产或保存的历史状态、迁移失败后仍可恢复的原状态，以及迁移后由当前消费者关闭并重新打开的结果；只验证当前版本新数据不能证明既有用户数据可用；
- 迁移后的实际序列化文件、数据库记录或线上消息是否由正式校验器对照 schema、存储或线协议检查，包括字段省略与显式 `null` 的差异；内存模型有效不能替代落地表示有效；
- 保存、外部修改、冲突、删除、恢复和回收站是否有明确语义；
- 启动恢复、后台任务、关闭刷盘、进程退出和再次启动是否连通；
- 凭据、缓存、恢复副本和用户内容是否各在正确边界；
- 多窗口、多设备或多平台是否会并行写同一真源。

高风险数据链缺少真实迁移或重启测试时，标记为待验证，不用单元测试替代。

## 6. 审计用户界面和平台外壳

项目存在真实用户界面时做轻量健康检查；后端、CLI 和库项目跳过。检查：

- 核心用户任务、自然入口、主要结果与恢复是否清楚；
- 顶层布局、标题栏、侧栏、内容区、边界和滚动是否有唯一所有者；
- 控件数量与交互语义、空与加载与成功与失败状态是否完整；
- 视觉方向是否来自项目身份、内容、平台和一个活动设计系统真源；
- 原生窗口、浏览器预览和移动端是否各用正确边界；
- 主题、缩放、目标视口、输入方式和平台状态是否可用；
- 调用的原生命令是否具有对应权限；
- 错误是否转换成用户能理解和处理的提示；
- 关键操作能否从界面抵达最终结果。
- 界面事件处理器是否同步执行随输入增长的文件、网络、provider、媒体、进程或序列化工作；转入后台的工作是否有操作身份、取消、迟到结果拒绝和关闭排空。

综合审计可以使用现有截图和真实运行证据；没有用户要求复现时，不为扩大证据自动安装或运行项目。发现系统性体验问题时建议进入产品体验专项，不在综合审计中展开完整页面规格。

## 7. 审计构建、测试和发布

检查：

- 当前开发、生产和平台构建入口是否真实可用；
- 开发服务器、编译器、链接器、运行时和应用各自产生的输出是否按阶段、退出状态与用户结果分级；
- 核心测试使用真实生产者还是消费端假数据；
- Windows、Android、Web 或其它正式目标是否有与发布风险匹配的检查，并把相关源码、配置和依赖映射到实际目标、构建 profile、feature 与条件编译分支；宿主测试或默认目标通过不能证明未参与该次编译的目标专属代码；
- 生成物是否来自当前源码，而不是旧缓存；
- 用户入口与它启动的子进程是否解析到同一构建计划中的产物、包导出、依赖和资源；内容清单的允许文件集合是否与运行目录实际集合完全相等，缺失、改变和额外陈旧文件是否都会被拒绝；
- 本地提交、远程分支、制品和用户下载之间是否有可核对边界。

### 公开验证器必须实际进入保证链

README、项目规则、CI、发布流程或维护文档中公开宣称的验证脚本、性能检查和真实用户链工具本身也是审计对象。先盘点每个入口的实际命令、当前接口、代表性输入、正式消费者和它声称保证的用户结果，再核对 CI 或人工流程究竟执行了主流程，还是只做语法检查、导入、文件存在或帮助输出。

在当前运行权限和成本边界允许时，让每个会影响审计结论的验证器使用代表性输入真正执行，并核对它实际选择的内容身份和退出语义。lint 或成功导入只能证明脚本能够被解析；验证器仍调用已经退出的接口、私有状态或旧产物时，这是保证链自身的缺陷，即使产品测试全部通过也不能把该能力标为已覆盖。CI 应实际执行适用的验证器，或者明确把它标为人工且当前未覆盖；未来计划、注释和文档声明不能冒充当前执行证据。未获运行授权或缺少外部前置条件时保留为待确认，不在只读审计中修改脚本。

公开包装器本身也是正式消费者，必须实际执行，不能只绕过它运行内部子检查。它的超时预算要覆盖代表性输入下必需子检查的实际稳定时长，以及启动、报告落盘、关闭和清理余量；外层执行器的等待预算还要覆盖包装器自身收尾。子检查已经打印通过，但包装器随后超时、清理失败或非零退出时，整条公开验证链仍是失败或待确认，不能摘取内部成功当作公开入口通过。预算来自可观察阶段和代表性运行证据，不靠任意放大掩盖挂起；持续无进展时仍按长任务合同诊断并收口。

运行构建、测试、预览或真实浏览器必须已经获得当前规则和用户请求允许。单独的“允许运行 build”只授权执行构建及生成它正常产生的产物，不把只读审计改成项目修复；构建失败形成审计证据，修改源码、配置、测试或工作流仍需已有修复授权或另行确认。构建成功也只证明该构建入口和产物边界，不能代替未运行的失败恢复、交互或最终用户链。用户没有授权生成或打包时，审计应确认过期产物不会被静默选用，并把原生产物闭包与冷目录消费标为未验证；未来 CI 计划不能冒充当前已经生成和消费的证据。

构建命令存在不表示当前能构建；历史 CI 徽章不表示当前分支通过。终端出现 `warning` 不自动等于构建失败，也不自动等于可以忽略：先确认消息的生产者、完整上下文、命令最终状态、正式产物和用户链是否受影响，再决定解释、观察或治理。

工具调用或外层等待超时也不自动等于构建失败。审计证据必须区分执行器停止等待、原进程仍在运行、构建工具明确失败和应用已经退出，并说明当时阶段、进程、日志或产物是否继续变化、最终退出状态和消费者结果。没有这些证据时标为待确认，不用重复启动同一构建来制造新的状态。

### 分开功能、合并和发布就绪度

审计涉及交付状态时分别给出三项结论，不能用其中一项替代另一项：

- **功能可用**：当前工作状态下，正式生产者、真实边界、消费者和用户结果已经成立；它不自动证明待合并内容完整或仓库可复现。
- **可合并**：候选变更范围准确，生产代码、测试、验证与发布脚本、文档等正式消费者已经迁移，针对同一份当前内容的必需检查通过，并且没有已知旧入口或未归属变化；它不自动证明制品和远端发布链成立。
- **可发布**：干净检出能够重建并消费当前制品，发布配置、许可证、README、版本、远端检查和用户取得结果的路径均符合本次发布合同。

某一层不适用时说明原因；证据不足时标为待确认。历史测试通过、局部补跑或功能演示不能拼接成更高一层就绪结论。

## 8. 审计 README、许可证和日志

README 检查第一屏、证据、首次成功路径、主要入口、限制和维护信息。许可证检查代码、内容、数据、素材和第三方条款是否覆盖准确。日志只判断是否适用、是否有稳定入口、关键操作能否关联，以及是否有真实消费者。

需要逐段重写、许可证选择或逐字段日志审计时，建议进入对应专项路径；综合审计不实施。

## 9. 证据等级

- **已证实**：项目文件、配置解析、真实命令、运行结果或用户可见结果直接支持。
- **较强推断**：多个事实一致，但缺少最终运行、平台或权利证明。
- **待确认**：缺少用户目标、项目环境、历史状态或真实消费者。

每个问题同时说明证据位置、影响用户结果和建议路径。没有证据的通用最佳实践不进入优先级。

## 10. 输出

### 综合审计必须交付修复交接账本

综合审计本身必须交付一份可由后续普通修复任务直接消费的账本，不能只给按严重程度排列的文字摘要，再依赖后续任务重新解释范围。每项确认发现和仍待确认的高影响事实使用稳定发现编号；编号绑定审计根、版本或工作树内容身份和问题语义，不绑定临时行号、排序位置或措辞。审计后文件移动、风险顺序改变或取得新证据时沿用同一编号；证据证明原判断错误时更新状态和理由，不删除原发现来制造全部闭环。

每项账本至少写清：

```text
稳定发现编号与简短标题：
审计根、版本或工作树内容身份：
证据位置、来源身份、取得时刻与证据等级：
根因及当前唯一责任边界：
受影响的生产者、传输或存储边界、正式消费者与用户结果：
应迁移到的目标所有者或真实边界：
```

状态按发现和证据平面分别成立。源码在本地修好，只能关闭本地实现条件；实时远端、发布制品、外部服务或最终消费者仍是旧状态时，相应平面继续开放或待确认，不能把某一平面的完成折叠成整个发现已经解决。测试总数、一次完整回归或其它发现的真实用户链通过，也不能替代该发现列出的逐项完成证据。只有全部适用完成条件都由当前内容身份的新鲜证据满足，或者按上列状态得到明确重新分类、退出范围或受阻结论，后续任务才能关闭该发现；仍有开放或待确认项时不得宣称“全部问题已经解决”、可合并或可发布。
