# 项目综合审计

只在用户明确要求按实施计划核对完成度、全面检查、健康判断、风险排序或综合审计时使用。审计阶段只读，适用于普通文件夹、源码包、本地 Git 仓库和远程仓库；用户同时授权修复时，由发现对应的专项方法实施，修复后再回到本方法全新复查。

## 输入与停止位置

输入是准确项目根、用户目标和当前规则。输出是项目事实、治理基线、关键风险、证据强度和建议顺序。交付后停止，不写项目配置、不修改源码、不初始化 Git，也不自动进入专项分支。

用户要求“全部问题”“所有问题”或“全面检查”时，开始前建立覆盖合同：

```text
审计根、版本或工作树状态：
确认存在的项目形态与平台：
全部适用维度及其适用性依据：
需要覆盖的用户结果和主要生产链：
正式功能、用户入口、界面表面与公开能力清单：
将读取的源码、配置、文档与仓库边界：
获准实际运行的入口、成功路径、失败与恢复路径：
可验证的构建、产物、部署或发布层：
需要核对的本地、实时远端与外部能力证据平面：
需要核对的 GitHub 上传候选、索引、历史与实时远端内容边界：
当前明确无法取得的证据：
```

“全部”只表示在这份冻结范围内完成了高价值事实、同源变体和残留证据检查，不表示未知平台、未获准运行的命令或不可访问的外部系统已经无问题。最终输出必须同时列出已覆盖范围和仍未覆盖的证据；后续取得的新入口或新权限只扩展相应部分，不能反向把早先结论描述成无条件完整。

## 实施计划符合性审计

用户询问某份实施计划、迁移计划或验收清单是否已经全部完成时，审计范围来自计划本身，而不是当前代码看起来已经实现了什么。开始前冻结计划内容身份、项目状态、明确排除项和证据平面；计划后来发生会改变规范要求、验收方法或用户结果的变化时，旧账本失效，按新身份重新提取。不能从现有源码、测试名称或已经发现的问题反推计划范围。

从原计划提取每一项规范性要求、验收标准、公开方法或事件、schema 字段、平台目标、失败与取消语义以及旧路径退出要求，并给出稳定计划条目身份和原文定位。示例、解释和背景只有在计划明确把它们写成约束时才进入完成条件；有意偏离必须记录批准它的当前权威、理由和替代验收，不能由实现者默认为完成。

每个计划条目使用同一份符合性记录：

```text
稳定计划条目身份、原文定位与计划内容身份：
规范要求、验收标准与明确排除项：
当前唯一责任所有者和真实边界：
实际实现位置及全部正式调用点：
生产者 → 传输或存储边界 → 消费者 → 用户可观察结果：
预期关键测试身份与实际收集身份：
当前内容身份的新鲜运行证据：
本地、CI、目标平台实机和外部服务证据平面：
经权威批准的有意偏离、理由与替代验收：
状态：已实现且已验证 / 已实现但未验证 / 缺失 / 明确排除 / 受阻
```

源码、配置、测试和报告都是计划条目的消费者或证据，不能代替计划真源。完整测试通过不能替没有映射关系的计划条目背书；源码里存在测试方法也不能代替测试框架实际收集的唯一身份。删除旧字段、旧类型、旧 helper、兼容分支或恢复逻辑等负向要求，还要用语义残留扫描、正式调用点退出和真实消费者证据证明旧架构已经不存在，不能只证明新路径可用。

证据按本地代码与运行、CI、目标平台实机和外部服务分别成立。一层通过不能补足另一层；没有计划要求或项目规则明确排除的证据平面标为明确排除并给出依据，暂时无法取得则标为已实现但未验证或受阻。只有每个计划条目都有闭合状态，且所有未取得的证据平面被如实分开，才可以宣告该计划在冻结范围内全部完成。

用户同时授权“发现遗漏就继续改”时，每轮修复后都从原始计划和当前已接受合同重新生成全新符合性账本，不得复制上一轮的完成标记、只复查刚修过的问题或用累计测试总数回填。新账本再次发现同一冻结范围内的遗漏时继续进入对应专项修复；出现独立的新产品决定、范围扩张或新增权限需求时停止。实施计划审计只覆盖计划范围，不因名称里有“全部”自动扩张为下方全部项目维度；只有用户另行要求全面项目审计，或计划内发现证明存在跨维度系统性影响时，才叠加综合覆盖账本。

## 0. 先建立维度覆盖账本

综合审计先证明每个适用项目维度都查过，再报告发现了什么。不能从已经发现的问题反推审查范围，也不能因为某个维度没有发现问题就省略它。一个维度出现过一条发现、跑过一条测试或读取过一个文件，只能证明触达过该点，不自动证明整个维度已经审查。

先按项目形态建立以下维度矩阵；通用维度必须进入账本，条件维度在对应表面、承诺或风险存在时进入。项目没有某个表面时仍要给出不适用依据，不能直接删掉该行：

| 项目维度 | 必须核对的对象 | 适用规则 |
| --- | --- | --- |
| 产品定位与用户结果 | 主要用户、正式能力、第一项价值、产品承诺、核心对象和成功标准 | 通用 |
| 功能与缺陷 | 全部正式功能、公开入口、正常分支、错误、取消、重试、恢复和最终结果 | 通用 |
| 代码质量 | 静态检查、类型、可读性、死代码、异常处理、依赖使用、可测试性和维护成本 | 有源码时适用 |
| 架构、内聚与重复 | 真源、责任边界、依赖方向、公共表面、语义重复、半迁移和上帝模块候选 | 有源码或可分析结构时适用 |
| 数据、持久化与生命周期 | schema、保存、自动保存、迁移、外部修改、冲突、关闭、崩溃、重启恢复与清理 | 存在持久或跨进程状态时适用 |
| 界面视觉 | 全部窗口、页面、面板、菜单、对话框和覆盖层的布局、层级、排版、颜色、图标、设计系统与视觉状态 | 存在 GUI 时适用 |
| 交互与完整用户旅程 | 首次启动、发现入口、主要任务、反馈、进度、取消、撤销、错误理解、恢复、重开和最终交付 | 通用；按 GUI、CLI、API 或库的真实入口变化 |
| 无障碍、键盘与国际化 | 焦点顺序、键盘路径、对比度、辅助技术语义、缩放、长文本、编码和语言切换 | 存在面向人的交互或多语言承诺时适用 |
| 性能、资源与规模 | 启动、核心操作延迟、吞吐、CPU、内存、GPU、I/O、缓存与临时文件增长、泄漏、大项目和长时间运行 | 对持续运行、处理数据或有性能承诺的项目适用 |
| 兼容性与环境 | 正式平台、版本、依赖、路径、编码、权限、硬件、GPU、编解码器、网络、离线和外部服务条件 | 存在相应支持声明或运行依赖时适用 |
| 构建、测试与 CI | 开发与生产构建、测试层级、真实生产者、验证器、目标平台、缓存身份和 CI 实际执行 | 有可执行、构建或发布项目时适用 |
| 安装、升级与发布 | 安装、首次启动、升级、数据迁移、回滚或恢复、卸载影响、干净检出、制品、GitHub 实际上传内容和远端发布 | 项目向用户或其它系统交付时适用 |
| 日志与诊断 | 关键操作关联、错误上下文、日志入口、落盘、轮转、查看、导出和实际消费者 | 有运行时行为时适用 |
| 文档、示例与许可证 | 首次成功路径、能力与限制、维护入口、示例真实性、许可证范围和第三方材料 | 通用；没有第三方材料也要记录检查依据 |
| 外部集成、隐私与安全边界 | 凭据、网络数据、遥测、外部 CLI/API、下载或更新、用户内容边界和最小必要权限 | 存在相应边界时适用；本地应用按真实风险控制深度 |

每个维度使用同一份覆盖记录：

```text
维度与适用性依据：
预期检查对象和完整清单来源：
实际检查的方法、输入、版本与范围：
取得的静态、运行或用户可见证据：
覆盖状态：已审查 / 部分审查 / 未审查 / 不适用
未覆盖对象、原因与补证据入口：
由哪个专项方法承担加深检查：
```

- **已审查**：已经从权威清单覆盖该维度全部适用对象，并达到本维度要求的静态、运行或用户可见证据；允许结论为“未发现问题”。
- **部分审查**：只完成抽样、静态阅读、单个平台、单一状态或局部运行，或者有正式对象因权限、环境、成本或外部条件没有检查。
- **未审查**：没有足以说明该维度实际经过检查的证据。没有发现和工具零输出都不能改变这个状态。
- **不适用**：项目形态、正式入口与产品承诺共同证明该表面不存在；暂时无法运行、没有安装依赖或没有取得账号只能标为部分审查或未审查。

只有全部适用维度均为“已审查”，最终结果才可以称为完成的全面审查。任一适用维度仍是部分审查或未审查时，标题和结论必须明确写成受限综合审查或部分审查，并保留补齐入口。覆盖账本和问题账本是两个结果：前者回答“每项是否查了”，后者回答“查出了什么”，二者不能互相替代。

## 1. 建立项目事实

读取与结论直接有关的材料：

- 项目规则、现有项目配置、目录边界和平台；
- README、包元数据、启动入口、主要源码与真实示例；
- 精确根 Git 状态、默认分支和远程地址；项目根没有 `.git` 时标为普通项目；
- 构建、测试、发布、迁移和恢复入口；
- 现有许可证、NOTICE、版权与第三方内容；
- 可运行项目的日志入口、存储和查看方式。

只有工具位置、包或缓存根、终端、SDK 或长任务状态会改变审计结论时，才读取已有用户环境档案中的相关条目，并由绝对可执行文件、版本或目录核验。没有环境档案不是项目缺陷，也不能为完成综合审计自动创建或更新档案。

### 分开本地与实时远端事实

项目配置了远端仓库，并且公开交付、远端检查、许可证、默认分支或发布状态会改变审计结论时，分别建立以下证据平面：

```text
工作树与本地提交：
本地缓存的远端跟踪引用及最后更新时间：
实时远端默认分支与 HEAD：
对应提交的远端检查或工作流：
当前 release、标签与可下载制品：
各项取得时刻、身份与访问条件：
```

本地 `refs/remotes/*`、历史 CI 徽章、上一次抓取结果和本地已有许可证，只证明各自时点的状态，不能代替实时远端。当前审计范围包含公开或远端交付且网络可访问时，使用仓库托管方的只读接口或正式客户端取得实时状态；无法访问、没有权限或没有取得准确提交身份时标为待确认，不能把“没有读到”写成“远端不存在”。实时远端与本地不一致时，先说明差异和证据时刻，不在只读审计中自动拉取、合并或改写工作树。

写清：

```text
项目是什么：
主要用户：
第一项可观察价值：
内容或状态真源：
主要生产链：
当前平台：
当前模板：
当前公开状态：
最强证据：
```

源码存在只证明包含实现；配置声明只证明作者作出声明；测试通过只证明测试覆盖的边界；真实产物和用户链才能证明最终结果。

“不存在后端”“没有持久化”“没有发布能力”等负面结论也需要范围证据：检查项目根内的服务入口、依赖与脚本、部署或进程配置、环境读取、网络调用、数据存储和正式运行入口，再说明结论限定在哪个根、版本和平台。没有发现常见目录只能形成线索，不能单独证明某一层不存在；确认产品本来不需要该层时，将其列为非问题，不为了形式完整建议新增架构。

## 2. 审计治理基线

检查：

- 项目是否有一个准确根，普通文件夹是否被错误当成必须 Git；
- 项目配置固定的模板版本是否能从注册表解析；
- 当前项目类型和技术栈是否与模板选择一致；
- 项目覆盖与偏离是否有理由、影响和复查条件；
- 模板、源码、测试和文档之间是否已经漂移；
- 当前项目的长期决定是否位于会被真实开发流程读取的规则、文档、配置、代码或测试中；
- 没有项目配置时，是否仍有清楚的项目规则与真实边界。

没有采用模板不是自动缺陷。只有重复决策、跨项目缺陷或维护边界确实需要时，才建议采用。

没有 Project Steward 配置不是自动缺陷。项目反复依赖同一结论但没有任何正式真源，或者文档、代码和测试表达互相冲突时，才把它列为治理问题。

## 3. 审计产品与真源

检查：

- 项目定位和主要用户结果是否与实际实现一致；
- 磁盘文件、数据库、远程服务、缓存或生成副本中谁是唯一真源；
- 状态恢复、自动保存、迁移和同步是否会产生双真源；
- 普通用户路径和高级能力是否在界面与架构中正确分层；
- 平台差异是否是明确合同，而不是遗漏。

发现多个可写副本时，指出最早分叉和最终应由谁负责，不在综合审计中直接迁移。

### 验证外部默认能力的现实可用性

云服务、公共 API 或其它外部能力承担首次成功路径、默认能力，或者项目承诺匿名、免费、零配置即可使用时，不能只从配置项、测试替身、旧文档或接口名称推断它当前可用。先读取当前官方合同、身份与额度要求；它们存在冲突或不完整时明确记录。当前规则与用户请求允许运行，并且该能力会改变主要用户结果时，再使用项目自己的有界连接测试、正式 provider 入口或真实消费者验证，不另写一条绕过产品配置和错误映射的探测链。

结果至少记录取得时间、服务与端点身份、匿名或账号条件、项目实际配置、返回状态和正式消费者怎样展示。认证、额度、价格、区域、速率或服务端失败只证明这些准确条件下的当前路径；不能从一次 `401`、`402`、超时或官方资料冲突扩大成服务永久关闭，也不能用另一个账号、测试开关或手工请求的成功替默认入口背书。未获运行授权时只报告合同证据和现实可用性仍未验证。

## 4. 审计功能与缺陷

先从正式界面、菜单、快捷键、CLI 或 API 能力描述、设置、文档承诺、自动化入口和现有测试中建立功能清单，再核对这些来源是否一致。源码目录和测试名称只能帮助发现候选，不能单独决定产品实际有哪些功能；同一能力的多个入口应保留入口差异，但不重复计成多个用户结果。

每项正式功能至少记录：

```text
功能和稳定身份：
自然用户入口与其它公开入口：
正式生产者、边界、消费者和最终结果：
正常、空、错误、取消、重试、恢复与重开中哪些状态适用：
实际检查方法与证据：
功能状态：成立 / 有缺陷 / 部分审查 / 未审查 / 不适用
```

核心任务、高频任务、会写用户数据或会产生交付物的功能必须经过真实入口和代表性输入；其它公开功能也必须至少完成静态链路核对并由相应测试、能力描述或运行证据支持。只运行现有测试不能证明功能已经全部盘点，因为测试可能没有覆盖尚未建测、未被收集或已经从验证器中漂移的入口。综合审计也不承诺证明“项目不存在任何未知 Bug”；它承诺的是清单内每项功能都留下检查状态，未检查对象不会被成功结果隐藏。

## 5. 审计架构链

为最重要的用户结果建立：

```text
用户动作 → 生产者 → 边界 → 持久化或传输 → 消费者 → 可观察结果
```

检查：

- 前端、后端、原生层和远程服务的责任是否清楚；
- 公共类型、命令、事件和状态是否已经半迁移；
- 错误、取消、重试、冲突和关闭是否通过同一边界；
- 旧 helper、旧入口、旧数据源和兼容层是否仍在活动；
- 测试是否穿过本次声称验证的核心边界。
- 外部 CLI 是否允许配置完整命令字符串或原始 argv，从而覆盖适配器拥有的工作目录、隔离、权限、设置、输出或工具能力；
- 中心文件或对象是否同时拥有多个生命周期和变化原因；
- 公共表面是否迫使消费者依赖大量无关能力；
- 同一业务决定、状态、合同或转换是否存在语义重复；
- 依赖方向是否清楚，是否出现循环、跨层直连或巨型转发中心。

只看到一个函数正确或一个界面静态截图，不能把整条链标为健康。

代码行数、函数数和依赖数只用于筛选候选，不能单独证明上帝模块。用户明确要求检查高内聚低耦合、重复实现或上帝文件时，由主路由直接加载架构专项方法，建立完整职责、依赖、真源和变化原因图；综合审计这里只保留项目级结论和优先级。

## 6. 审计数据与生命周期

按适用场景检查：

- schema 版本和迁移是否单向、可重试并立即重写；
- 协议或 schema 迁移是否分别覆盖当前版本新建状态、由旧版本真实生产或保存的历史状态、迁移失败后仍可恢复的原状态，以及迁移后由当前消费者关闭并重新打开的结果；只验证当前版本新数据不能证明既有用户数据可用；
- 迁移后的实际序列化文件、数据库记录或线上消息是否由正式校验器对照 schema、存储或线协议检查，包括字段省略与显式 `null` 的差异；内存模型有效不能替代落地表示有效；
- 保存、外部修改、冲突、删除、恢复和回收站是否有明确语义；
- 启动恢复、后台任务、关闭刷盘、进程退出和再次启动是否连通；
- 凭据、缓存、恢复副本和用户内容是否各在正确边界；
- 多窗口、多设备或多平台是否会并行写同一真源。

高风险数据链缺少真实迁移或重启测试时，标记为待验证，不用单元测试替代。

## 7. 审计用户界面与完整体验

项目存在真实用户界面时，直接加载 `product-experience-governance.md`、`ux-design.md`、`interface-experience-quality.md` 和 `implementation-review.md`；桌面应用再加载 `desktop-app-governance.md`，响应式网页或多视口界面再加载 `layout-responsive.md`。后端、CLI 和库项目不检查不存在的 GUI，但仍审计各自真实入口的可发现性、反馈、错误理解和完整用户旅程。界面存在时不得把本节降级为轻量抽查。

先建立全部窗口、页面、延迟面板、菜单、对话框、覆盖层和主要状态的界面表面清单，再从首次启动到核心结果建立用户旅程清单。逐项检查：

- 核心用户任务、自然入口、主要结果与恢复是否清楚；
- 顶层布局、标题栏、侧栏、内容区、边界和滚动是否有唯一所有者；
- 信息层级、密度、间距、排版、颜色、图标、焦点与主要行动是否清楚且一致；
- 控件数量与交互语义，以及初始、空、加载、进行中、成功、失败、禁用、离线、取消和恢复状态是否完整；
- 视觉方向是否来自项目身份、内容、平台和一个活动设计系统真源，并覆盖全部表面而不是只看主窗口；
- 原生窗口、浏览器预览和移动端是否各用正确边界；
- 主题、缩放、目标视口、窗口尺寸、DPI、多显示器、长文本、语言、输入方式和平台状态是否可用；
- 鼠标、触摸、键盘、快捷键和焦点顺序是否能完成主要任务，无障碍语义与对比度是否符合项目承诺；
- 调用的原生命令是否具有对应权限；
- 错误是否转换成用户能理解和处理的提示；
- 关键操作能否从界面抵达最终结果，并具有进度、取消、撤销、重试或恢复中适用的反馈；
- 首次启动、首次成功、正常编辑或操作、保存、关闭、重开、失败恢复和最终交付是否形成连续旅程；
- 界面事件处理器是否同步执行随输入增长的文件、网络、provider、媒体、进程或序列化工作；转入后台的工作是否有操作身份、取消、迟到结果拒绝和关闭排空。

综合审计可以使用现有截图和真实运行证据；截图必须实际打开并按目标显示比例检查，文件存在或渲染数量正确不等于 UI 已审查。没有运行权限或环境不足时，不为扩大证据自动安装或运行项目，但相应界面和旅程只能标为部分审查或未审查。综合审计负责检查完整表面与旅程；只有用户要求重新设计或实施时才进入页面规格和修改。

## 8. 审计性能、资源与规模

按项目的真实工作负载建立规模矩阵，至少覆盖普通输入、代表性大输入、长时间运行或重复操作中适用的场景。检查启动和首个可用结果、核心交互或请求延迟、批量吞吐、CPU、内存、GPU、磁盘和网络、缓存与临时目录增长、资源释放、并发争用以及退化和恢复。媒体、编辑器、后台服务和数据处理项目还要检查长项目、多对象、连续预览或处理、重复打开关闭和取消后的资源状态。

已有 benchmark 数字只有在输入身份、环境、版本、采样阶段和用户结果可比时才可采用。小夹具、单帧、短时运行和“开发机感觉流畅”不能替代表性规模；只能静态识别热点而没有实际测量时，本维度标为部分审查。性能工具或指标没有正式生产者、没有覆盖目标阶段或与用户结果冲突时，先把指标本身列为审计发现。

## 9. 审计兼容性、安装与外部边界

先从项目公开承诺和实际构建目标列出支持矩阵，再检查适用的操作系统与版本、运行时和依赖、CPU/GPU 与驱动、编解码器、区域和编码、Unicode 与长路径、DPI 与输入方式、权限、代理与离线、外部 CLI/API 及其凭据或额度。只在当前开发机通过不能证明其它正式支持目标；没有声明支持的任意平台也不因理论可运行而进入缺陷范围。

面向用户或其它系统交付时，继续检查安装、首次启动、升级与数据迁移、失败回滚或恢复、卸载对用户数据的影响、干净检出或安装后的真实入口，以及当前发布制品是否对应当前源码。自动更新、下载、遥测、云服务或外部工具存在时，按真实风险检查凭据、用户内容、网络数据、来源身份和最小必要权限；本地桌面应用不为形式完整扩张成与产品风险无关的安全专项。

## 10. 审计构建、测试和发布

检查：

- 当前开发、生产和平台构建入口是否真实可用；
- 开发服务器、编译器、链接器、运行时和应用各自产生的输出是否按阶段、退出状态与用户结果分级；
- 核心测试使用真实生产者还是消费端假数据；
- Windows、Android、Web 或其它正式目标是否有与发布风险匹配的检查，并把相关源码、配置和依赖映射到实际目标、构建 profile、feature 与条件编译分支；宿主测试或默认目标通过不能证明未参与该次编译的目标专属代码；
- 生成物是否来自当前源码，而不是旧缓存；
- 用户入口与它启动的子进程是否解析到同一构建计划中的产物、包导出、依赖和资源；内容清单的允许文件集合是否与运行目录实际集合完全相等，缺失、改变和额外陈旧文件是否都会被拒绝；
- 本地提交、远程分支、制品和用户下载之间是否有可核对边界。

### GitHub 仓库必须审计实际上传边界

准确项目根已经连接 GitHub、存在 GitHub 上的公开或私有交付，或者当前项目明确计划初始化 GitHub 仓库时，读取 `repository-publication.md` 的“审计 GitHub 上传边界”。综合审计只消费这份共享方法并报告发现，不在这里建立第二套敏感文件或目录黑名单。

检查对象至少分开本地物理文件与拟上传候选、Git 索引、当前已跟踪树、本地提交和可达历史、实时 GitHub 默认分支、其它活动分支与标签；项目实际使用 Git LFS、Release 资产或 Actions 制品交付文件时，再加入对应公开表面。被忽略和未跟踪内容用于判断未来候选与本地隐私边界，不得被误报成已经上传；本地 `origin/*` 也不能代替实时 GitHub 内容。

每个实际或候选路径都要从干净克隆交付合同核对正式生产者、消费者、生命周期和上传必要性。缓存、构建输出、日志、数据库、备份、下载依赖、编辑器状态、原始制作材料、重复产物和大文件只是重点候选；没有消费者证据才说明它不应进入仓库，不能按名称、扩展名、大小或是否为二进制直接定性。已经跟踪或在历史中存在也不证明必要。

隐私检查覆盖凭据与环境配置、私钥和证书、本机路径与账号或主机身份、用户内容、数据库、日志、转储、会话、备份、真实测试数据，以及文档、截图、媒体元数据、压缩包和二进制容器中的私人或内部内容；同时核对 Git 提交作者姓名与邮箱的公开暴露。扫描器必须实际消费待判断的索引、提交对象、适用历史或实时远端内容，并记录版本、输入、排除与退出状态。工具缺失、输入为空、历史未取得、远端不可访问或二进制未覆盖时，本维度只能标为部分审查或待确认，不能报告“没有隐私文件”。

数据库、日志、备份、运行状态和生成结果要同时记录上传必要性与内容敏感性，不能把两者合并成一个严重程度判断。扩展名、文件大小、二进制格式或存在真实运行记录只能把它们列为检查候选；没有正式消费者证明“不应上传”，只有安全投影、权威来源或等价直接证据才能证明其中包含真实凭据、私人用户内容、内部数据，或者已经证明不敏感。无法安全核对内容时标为未知，不把未知自动升级成敏感，也不因为仓库应保持整洁就补造隐私结论。

默认分支当前树没有发现不能清除其它分支、标签或 Git 历史中的既有暴露；工作区删除、`.gitignore` 命中或新提交移除也不能证明 GitHub 已经清除。审计发现真实凭据时，把撤销或轮换列为第一处置；取消跟踪、移动、归档、删除、历史重写、强制推送和远端制品清理分别进入仓库发布或目录治理的获准修复路径。只读综合审计不修改 `.gitignore`、不初始化 Git、不改变索引、不创建远端，也不清理历史。

发现需要历史清理时，由 `repository-publication.md` 唯一拥有当前树、本地引用、实时远端活动历史、旧 SHA 缓存、PR、fork 和其它克隆的分层合同。修复交接账本必须写明用户已经接受的准确清理层；只有确认敏感且对应层属于接受结果时，服务器缓存或托管方工单才进入完成条件。不能在修复后因为发现一个未获准、非必要或尚未证明相关的外部残留，反向扩大原发现并把已经成立的项目结果改成受阻。

交付时为每项发现写明证据平面、路径与内容身份、隐私类别、必要性、正式消费者、当前本地与 GitHub 暴露状态、证据缺口及所需处置权限。只有预期上传清单、真实索引或提交树、实时远端树和适用历史均由有效检查覆盖，才可以把 GitHub 上传边界标为已审查。

### 公开验证器必须实际进入保证链

README、项目规则、CI、发布流程或维护文档中公开宣称的验证脚本、性能检查和真实用户链工具本身也是审计对象。先盘点每个入口的实际命令、当前接口、代表性输入、正式消费者和它声称保证的用户结果，再核对 CI 或人工流程究竟执行了主流程，还是只做语法检查、导入、文件存在或帮助输出。

在当前运行权限和成本边界允许时，让每个会影响审计结论的验证器使用代表性输入真正执行，并核对它实际选择的内容身份和退出语义。lint 或成功导入只能证明脚本能够被解析；验证器仍调用已经退出的接口、私有状态或旧产物时，这是保证链自身的缺陷，即使产品测试全部通过也不能把该能力标为已覆盖。CI 应实际执行适用的验证器，或者明确把它标为人工且当前未覆盖；未来计划、注释和文档声明不能冒充当前执行证据。未获运行授权或缺少外部前置条件时保留为待确认，不在只读审计中修改脚本。

公开包装器本身也是正式消费者，必须实际执行，不能只绕过它运行内部子检查。它的超时预算要覆盖代表性输入下必需子检查的实际稳定时长，以及启动、报告落盘、关闭和清理余量；外层执行器的等待预算还要覆盖包装器自身收尾。子检查已经打印通过，但包装器随后超时、清理失败或非零退出时，整条公开验证链仍是失败或待确认，不能摘取内部成功当作公开入口通过。预算来自可观察阶段和代表性运行证据，不靠任意放大掩盖挂起；持续无进展时仍按长任务合同诊断并收口。

运行构建、测试、预览或真实浏览器必须已经获得当前规则和用户请求允许。单独的“允许运行 build”只授权执行构建及生成它正常产生的产物，不把只读审计改成项目修复；构建失败形成审计证据，修改源码、配置、测试或工作流仍需已有修复授权或另行确认。构建成功也只证明该构建入口和产物边界，不能代替未运行的失败恢复、交互或最终用户链。用户没有授权生成或打包时，审计应确认过期产物不会被静默选用，并把原生产物闭包与冷目录消费标为未验证；未来 CI 计划不能冒充当前已经生成和消费的证据。

构建命令存在不表示当前能构建；历史 CI 徽章不表示当前分支通过。终端出现 `warning` 不自动等于构建失败，也不自动等于可以忽略：先确认消息的生产者、完整上下文、命令最终状态、正式产物和用户链是否受影响，再决定解释、观察或治理。

工具调用或外层等待超时也不自动等于构建失败。审计证据必须区分执行器停止等待、原进程仍在运行、构建工具明确失败和应用已经退出，并说明当时阶段、进程、日志或产物是否继续变化、最终退出状态和消费者结果。没有这些证据时标为待确认，不用重复启动同一构建来制造新的状态。

### 分开功能、合并和发布就绪度

审计涉及交付状态时分别给出三项结论，不能用其中一项替代另一项：

- **功能可用**：当前工作状态下，正式生产者、真实边界、消费者和用户结果已经成立；它不自动证明待合并内容完整或仓库可复现。
- **可合并**：候选变更范围准确，生产代码、测试、验证与发布脚本、文档等正式消费者已经迁移，针对同一份当前内容的必需检查通过，并且没有已知旧入口或未归属变化；它不自动证明制品和远端发布链成立。
- **可发布**：干净检出能够重建并消费当前制品，发布配置、许可证、README、版本、远端检查和用户取得结果的路径均符合本次发布合同。

某一层不适用时说明原因；证据不足时标为待确认。历史测试通过、局部补跑或功能演示不能拼接成更高一层就绪结论。

## 11. 审计 README、许可证和日志

README 检查第一屏、证据、首次成功路径、主要入口、限制和维护信息。许可证检查代码、内容、数据、素材和第三方条款是否覆盖准确。日志只判断是否适用、是否有稳定入口、关键操作能否关联，以及是否有真实消费者。

需要逐段重写、许可证选择或逐字段日志审计时，建议进入对应专项路径；综合审计不实施。

## 12. 证据等级

- **已证实**：项目文件、配置解析、真实命令、运行结果或用户可见结果直接支持。
- **较强推断**：多个事实一致，但缺少最终运行、平台或权利证明。
- **待确认**：缺少用户目标、项目环境、历史状态或真实消费者。

每个问题同时说明证据位置、影响用户结果和建议路径。没有证据的通用最佳实践不进入优先级。

## 13. 输出

### 综合审计必须交付修复交接账本

综合审计本身必须交付一份可由后续普通修复任务直接消费的账本，不能只给按严重程度排列的文字摘要，再依赖后续任务重新解释范围。每项确认发现和仍待确认的高影响事实使用稳定发现编号；编号绑定审计根、版本或工作树内容身份和问题语义，不绑定临时行号、排序位置或措辞。审计后文件移动、风险顺序改变或取得新证据时沿用同一编号；证据证明原判断错误时更新状态和理由，不删除原发现来制造全部闭环。

每项账本至少写清：

```text
稳定发现编号与简短标题：
审计根、版本或工作树内容身份：
证据位置、来源身份、取得时刻与证据等级：
根因及当前唯一责任边界：
受影响的生产者、传输或存储边界、正式消费者与用户结果：
应迁移到的目标所有者或真实边界：
逐项完成条件及必须取得的生产、边界、消费和可观察证据：
本地工作树、本地提交、实时远端、发布制品或其它适用证据平面的独立状态：
当前状态：开放 / 待确认 / 经新证据重新分类 / 经用户明确同意退出范围 / 受阻 / 已解决
```
