# 仓库建立与发布

这份方法用于把一个本地项目建立成 Git 仓库、完整初始化 GitHub 仓库、准备 GitHub 主页并在明确授权后发布。它把本地整理、Git 提交、GitHub 远端创建和推送分成独立权限，避免“初始化”被误解成“已经公开”；同时由同一上传边界审计决定哪些内容可以进入 Git 与 GitHub。

## 1. 先冻结目标和停止位置

开始前用一句话写清：

```text
本地目录：
当前是否为 Git 仓库：
目标 GitHub 所有者与仓库名：
目标可见性：
目标默认分支：
本次交付路径：直接更新默认分支 / 候选分支与 PR / 只建提交 / 其它
交付后允许存在的本地分支：
交付后允许存在的远端分支：
长期贡献路径：允许直接推送 / 只经 PR / 尚未决定
分支保护或 ruleset 目标状态：
分支删除与例外授权：
本次允许的动作：
本次明确不做的动作：
停止位置：
```

“不要为本次改动创建其它分支”只描述本次交付路径；“所有分支都进入 main，最后只保留 main”还声明了交付后的最终分支集合。遇到“不要其它分支”“都提送到 main”等可能同时指向两层的说法，必须结合上下文把本次交付路径与最终分支集合分别写清；无法唯一确定时只约束本次交付，不据此删除已有分支或改变保护规则。

最终分支集合必须分别枚举当前本地分支和实时远端分支，并核对其它 worktree、自动生成的展示分支或发布分支等正式消费者。长期贡献路径与分支保护目标是另外两项决定：当前一次直接推送可以与今后只经 PR 并存，但必须安排在保护生效之前；如果交付路径、最终分支集合、正式消费者和保护目标互相冲突，在任何删除或远端设置变更前停止。列出最终集合不替代准确分支的删除授权，也不把分支保护加入普通推送权限。

“先给本地预览”是明确的停止条件：可以修改用户要求的仓库文件并生成预览，但不创建提交、不创建远程仓库、不推送、不改变可见性。用户之后明确要求推送时，从已经验收的本地状态继续，不重做内容设计。

调用 Project Steward、允许修改目标项目或确认治理方案，都不自动授权提交和推送该目标项目。普通项目只有在用户明确要求提交或推送，或者一个独立专项路径已经把精确提交与推送写入其确认结果时，才进入发布链。停止位置只是提交或候选分支推送时，只处理获准依赖闭包并在推送成功后停止，不等待 GitHub Actions、部署或其它远端验证；用户明确要求准确改动进入默认分支时，该结果同时覆盖为通过保护规则所必需的候选分支、PR、准确候选 required checks 和允许的非破坏性合并，但不授权修复失败或改变远端设置。创建远端、改变可见性、删除、改写历史、强制推送和无关工作树变化仍分别授权。Project Steward 自我进化使用下一节的整仓发布合同；Star History 使用其叶子方法的独立展示优化合同，两者都不能为普通目标项目补造发布权限。

“公开仓库”“改成 public”或“让别人能看到”只授权把已经准确确认的目标远端改变为公开可见，并回读该可见性结果；它不会把本地产品升级成发布候选，也不自动授权推送尚未发布的工作区内容。公开前可以只读核对实时远端身份、当前已上传内容、提交身份和本节上传边界；发现隐私、凭据、未知内容或需要修改 README、许可证与仓库元数据时，先报告并分别取得处置权限，不能用“公开”补造写入。

公开可见性本身不包含安装器或自动更新器、签名、打包与 Release 工作流、GitHub Pages、分支保护、Topics、Star History、README 重设计、CI 改造、部署或远端运行等待。只有用户把其中准确结果单独加入本次合同后才实施，并分别遵守其验证与停止位置；不能为了让“公开”显得完整而建设一整套发布基础设施。

### 推送前先冻结自动远端后果

推送授权只覆盖准确引用更新以及与它相容的普通远端检查，不能让自动化替未获授权的发布结果取得权限。在任何推送前，从最终候选内容、准确推送事件和目标引用建立自动远端后果账本：展开候选提交中的 workflow 触发器、引用过滤、被调用的本地或可取得的复用 workflow 与 action，并读取当前权限下能够确认的远端 ruleset、hook、应用或其它自动生产者。权限声明、工作流名称和历史运行只能筛选候选；以实际触发条件、步骤和写入目标判断后果。无法取得且可能改变本轮停止位置的自动化保持未知。

逐项把后果分类为普通测试、文档检查或质量门，或者打包与签名、创建或更新 Release 与标签、部署、发布包或镜像、写入其它分支或仓库，以及调用外部发布系统。普通检查在用户未明确禁止远端运行时可以随已授权推送异步触发，推送成功后按既有停止位置报告而不等待。其余每项都是独立远端结果；不能因为它由 push 自动触发，就把它降为普通推送的内部步骤。

把账本与本次允许动作、明确禁止项和停止位置逐项对账。自动结果已经获得准确授权时，记录其生产者和异步边界后继续；未获授权、与“不要打包”“不要部署”等禁止项冲突，或未知状态使合规性无法成立时，停在推送前并说明不可分离的后果。不能擅自修改工作流、改推其它引用、临时禁用远端规则或选择另一交付路径来绕过。候选中的自动化、目标引用或远端生产者发生变化时，旧账本和相关确认失效，推送前重新冻结。

如果普通项目的推送请求承接同一对话中刚完成且已经验证的本地改动，先检查证据新鲜度：验收后工作树是否又变化、准备提交的差异是否仍是同一范围、当前分支与远端是否分叉、原验证是否覆盖最终提交内容。证据仍新鲜时复用已有验证，不重新运行整套开发流程；出现新增改动、冲突、生成物变化或验证结果已过时时，只重跑受影响检查和必要用户链。普通推送授权只覆盖核对后的准确范围，不追溯授权此前产生项目修改，也不自动包含同一工作树中的无关改动。

### 远端结果先通过目标前置门

本次停止位置包含推送、远端分支更新、PR 或默认分支结果时，在任何暂存、创建提交或其它本地历史变化前，先从真实 Git 边界解析准确远端、目标引用与可用上游，回读远端身份与当前 HEAD，并把用户是否单独要求本地提交写入交付合同。远端或目标引用缺失、无法唯一确定或不可取得时，远端结果受阻；仍可完成用户明确要求且不会改变状态的检查，但若用户没有独立授权“只创建本地提交”，停在暂存前，保持工作区、索引和本地提交图不变。

推送请求不能把“本地先提交也有用”作为默认降级，也不授权创建远端、猜仓库、选择可见性或改为其它交付路径。已经由只读事实证明当前没有可推送目标时，不执行已知必然失败的 push 来取得重复报错；报告缺少的远端身份、已完成检查、未发生的暂存、提交与推送，以及继续所需的远端地址、创建远端授权或明确本地提交结果。用户明确只要本地提交，或允许远端受阻时仍交付本地提交，才按本地提交合同继续并把远端保持为未改变。

### Project Steward 自我进化使用整仓发布合同

用户已经确认 Project Steward 自我进化方案、仓库存在当前跟踪远端且没有选择只改本地时，整个当前工作区是一个不可拆分的发布范围。开始写入前读取完整工作区状态与相关差异；工作区不干净不是跳过文件、缩小历史调查或拒绝修改的理由。发布范围包含提交前存在的全部已跟踪修改、未跟踪文件和现有删除，不按任务、来源、文件或内容片段选择性排除；当前分支本地尚未推送提交也会随同一次推送到达远端，动作前必须准确列出并核对。

根据整个工作区的实际影响范围建立验证账本，并在最后一次相关修改后完成相应检查。发现真实凭据、未获授权的新删除、验证失败、无法解释且可能覆盖用户意图的变化，或者任何一项不能安全进入同一提交时，保留完整工作区并停止；不能遗漏该项、退回最小依赖闭包或发布一个看似干净的子集。现有删除属于待发布状态，允许提交它不等于授权本轮再实施新的删除。

检查通过后使用 `git add -A` 暂存整个工作区，核对索引覆盖动作前全部已跟踪修改、未跟踪文件和现有删除，工作区没有未暂存或新出现的遗漏，再把本轮工作区变化创建为一个新提交。提交后若工作区再次变化，该提交不再满足整仓合同；在推送前重新建立完整候选、补齐受影响验证并使最终提交覆盖全部变化，不把新增内容留在本地。

只向当前跟踪分支执行非强制推送；不创建远端、不改变可见性、不改写已发布历史。推送前核对工作区没有遗漏；推送命令成功后立即停止，不再执行状态回读，也不等待 GitHub Actions 或其它远端消费者。分叉、认证失败、分支保护拒绝或远端变化时保持完整本地状态并报告，不拆分工作区绕过阻塞。

### 本地提交与远端状态分层交付

提交、推送、创建远端、部署或打包前，先说明本次动作会改变哪一层以及明确不会改变哪一层。当前分支已经领先远端而本轮还要创建新提交时，动作前说明未推送提交会从多少变为多少、已有提交与新提交分别服务哪个获准结果；本次推送会把已有未推送提交一并带到远端时，先列出准确提交集合并确认它们都属于获准发布范围，不能只用最后一个提交概括远端将得到的内容。

每次状态改变后从权威 Git 状态取得并按固定顺序交付：

```text
项目工作结果：
工作区与索引：
本地分支、本轮新增提交及各自用途：
相对上游的 ahead / behind：
远端分支与 HEAD 的实际核对：
尚未执行或尚未验证的推送、打包、部署与远端检查：
```

“产品修改完成”“已提交到本地分支”“候选分支推送成功”“默认分支已包含改动”和“远端结果已经验证”分别成立。普通实施停在候选分支推送成功并把 Actions 或部署标为异步，不把未等待的远端结果写成已经验证；停止位置明确是默认分支时，只有准确候选的必需检查通过、合并成功且远端默认分支包含该结果，用户要求的发布表面才成立。用户只授权提交时明确说明远端没有变化；只有用户明确要求远端验收时，或默认分支结果本身需要远端门槛时，才重新取得远端 HEAD、检查和合并状态。

### 跨项目根的发布状态分别成立

同一个用户结果涉及两个以上准确项目根时，先消费改动前预防形成的跨根交付账本，再开始任何暂存动作。逐根核对目录身份、职责、本轮变化、正式验证器及其实际输入、是否直接存在 Git 仓库、当前分支、远端和用户授予的发布动作。普通目录、Git 仓库、已提交、已推送和远端已验证是各根自己的状态；一个根的仓库能力、提交或远端 HEAD 不能替另一个根成立。

发布候选只属于当前获准发布的准确项目根。其它项目根提供了正式合同、同步输入或互操作依赖，只证明技术关系存在，不能自动让那个根的文件获得暂存、提交或推送授权；也不能把项目根 A 已推送、项目根 B 仍是普通目录或只有本地修改，概括成“整个跨项目结果已经推送”。用户说“推送到 main”时，必须先把准确目标根与它的候选范围对应起来；存在两个以上可能目标且历史没有唯一指向时，在暂存前说明各根状态并取得准确目标。

跨根结果的交付状态使用同一份独立矩阵：

```text
准确项目根：
本轮职责与获准结果：
本地变化和正式验证：
跨项目互操作证据：
是否为 Git 仓库及准确仓库根：
候选、提交和分支：
推送与远端验证：
仍只存在于本机或尚未验证的结果：
```

共享合同消费者若承诺在干净克隆中构建、测试或运行，仓库必须跟踪可重建该承诺的同步快照、来源身份和同步入口，或者明确声明并验证可取得的外部依赖。正式消费者测试不能静默读取相邻项目的绝对路径；这类路径只允许出现在显式跨项目集成测试的输入中，并且不能用该测试在当前开发机通过，替代当前仓库自己的干净克隆合同。

### 混合工作树先求获准依赖闭包

本节适用于普通项目发布。已经进入 Project Steward 自我进化整仓发布合同时，直接执行上面的整仓范围、验证、`git add -A` 和失败收口，不用本节把工作区重新拆成最小依赖闭包。

工作树同时包含本次结果、用户原有修改、其它任务、生成物、归档或删除时，发布候选从本次获准的用户结果开始，而不是从“当前所有能一起通过测试的文件”开始。先把已获准路径和内容片段映射到正式消费者，再沿导入、schema、构建、运行和迁移关系求出让该结果独立成立的最小依赖闭包；每项依赖同时记录来源、职责和授权状态。依赖对于编译或运行是必需的，只证明它属于技术闭包，不会让用户原有或来源不明的改动自动获得暂存与发布授权；完整工作树一起通过测试也只能证明组合兼容，不能证明组合范围已经获准。

闭包只包含来源明确且已经获准的内容时，可以按准确路径或内容片段建立候选并验证。闭包一旦需要未获准改动、无法归因的文件、受单独删除规则约束的退出路径，或必须把其它独立用户结果一起发布，立即在暂存前停止，向用户列出准确对象、依赖原因、现有验证和扩大后的远端结果，由用户决定扩大范围、另行拆分还是保持本地。不能把整个脏工作树改称“当前整合状态”来绕过确认，也不能因为拆分困难就执行 `git add -A`。只有用户看到准确清单后明确授权整个工作树，并且项目的删除、归档和发布规则分别满足时，全部纳入才成为合法候选。

在运行最终检查前，为最终候选内容建立验证账本：

```text
候选身份：工作树基线、待暂存路径及内容身份
范围归属：每项变化服务哪个获准结果、来源是谁、是否已经获得发布授权
依赖闭包：候选独立成立需要哪些输入，哪些未获准或未知依赖会阻塞暂存
变化事实：每类源码、配置、媒体、测试、文档、生成物或删除改变了什么
正式消费者：构建器、运行时、用户界面、维护者、远端检查或部署分别消费什么
检查覆盖：每项检查预期读取什么，实际选择了哪些路径、内容身份、过滤和排除项
新鲜证据：最后一次相关变化之后，哪项检查或真实用户链验证了该消费者
失效条件：哪些后续修改、生成动作、冲突或外部变化会使证据失效
```

验证强度由变化实际影响的消费者决定，不能只挑最快或最容易通过的命令。可见界面、媒体或交互发生变化时，需要从最终候选对应的真实入口经过正式状态和资源边界到可观察结果；类型检查或构建成功不能代替这条用户链。只改文档、许可证或仓库元数据时也不机械重跑无关产品回归，但必须验证相应渲染、识别或维护入口。最后一次相关变化发生在旧验证之后时，只使受影响证据失效，并在暂存或提交前补齐。

本地候选在提交或推送前验证失败时，立即冻结当前发布候选。用户只说“提交”“推送”或“推到 main”，只授权发布已经核对且达到发布条件的现有改动，不授权为了消除失败而修改源码、配置、测试、工作流或生成逻辑。只有原请求明确包含“持续修到可以发布”这类修复结果，或用户看到失败证据后另行授权，才进入修复。没有修复授权时，保留准确命令、输入身份、退出状态和失败产物，说明候选尚未达到发布条件并停止；不暂存、不提交、不推送。

得到修复授权后，继续消费原验证账本，不把一次修复当成全部证据清零。只让修复实际触及的代码、配置、测试基础设施、生成物及其正式消费者证据失效；仍与最终候选一致的新鲜通过结果继续有效。优先重跑原失败检查、受修复影响的消费者和必要用户链。只有修复改变测试收集、共享夹具、全局配置、公共边界，或者项目规则明确要求完整回归时，才重跑整套检查；不能为了得到一份整齐的新日志而丢弃仍然有效的昂贵证据。

开始前还要读取项目规则对删除、归档、生成物和提交的额外限制。若项目规则要求删除前单独征求同意，通用的“提交”“推送到 main”或“发布”不能代替删除授权；在暂存、提交或推送前准确列出所有待删除路径及理由，未获同意的删除从本次范围移除，或按用户已同意的归档方式处理。不能先提交删除再把远程发布当成用户已经接受。

## 2. 用干净克隆确定仓库边界

用户要让另一台机器、服务器或新环境从仓库直接构建、部署或运行同一结果时，先建立干净克隆交付合同，再判断哪些文件应进入仓库：

```text
仓库承诺交付的用户结果：
新环境从哪个提交和入口开始：
允许依赖的外部服务与环境变量：
安装、构建、启动或部署命令：
正式运行根、基础路径和平台条件：
最终应看见或取得什么：
本轮能够真实验证到哪一层：
```

随后按正式消费者分类，而不是按文件扩展名、当前差异或个人习惯分类：

1. **必须跟踪的输入**：源码、锁文件、构建与部署配置、迁移或 schema、运行期静态资源，以及仓库明确承诺提供的 Skill、模板、文档或维护能力。某项能力是否在当前任务中被调用，不能决定它是否属于仓库产品。
2. **可重新生成的输出**：构建目录、缓存、测试报告和本地预览产物通常由已跟踪输入生成；仓库若明确承诺预构建发布物，则它转为正式交付物，并需要来源、新旧判定和消费者验证。
3. **本地原始材料与归档**：只有在构建、运行、维护或仓库公开承诺会正式消费时才进入交付；“以后可能有用”不能代替消费者。
4. **机器状态与外部依赖**：凭据、个人缓存、已安装工具和本机配置不伪装成仓库内容；需要的版本、变量与服务通过项目正式配置和文档表达。

已被 Git 跟踪、尚未跟踪、命中忽略规则或当前页面能够从开发机读取，都只是现状信号，不能单独证明应纳入或排除。运行素材即使是二进制文件，也可能是构建或网站的必需输入；源码目录即使很重要，也可能只是不会进入发布结果的本地原始材料。

在用户允许实际运行验证时，从不继承当前脏工作树、缓存和依赖目录的新鲜检出开始，使用项目锁定的安装入口完成构建，再从正式静态根、受支持的基础路径或真实启动入口交给最终消费者。干净检出、构建成功、服务启动和用户结果分别记录；其中任一层没有运行就标为未验证，不能用当前工作区的成功拼成干净克隆成功。

### 自动同步公开安装入口

准备发布项目或完整交付 README 时，只要项目存在面向第一采用读者的公开安装入口，就把安装命令作为发布结果的一部分自动同步到 README。范围不限于 Skill：根据项目正式清单、锁文件、构建与发布配置、包注册表、GitHub Release、容器镜像或源码安装入口确定真实分发渠道，再选择该读者完成第一次安装所需的最短命令；不能根据仓库名、目录名或惯例猜测尚未发布的包、镜像、资产或命令。项目同时支持多个读者或平台且命令实质不同时，分别保留成立条件和对应命令，不把一个平台的入口写成通用答案。

写入前先用不会安装到用户环境的公开元数据、包查询、仓库发现、发布资产检查或工具自带的 list、dry-run、help 等入口确认名称、版本边界和命令形态。实际安装、下载依赖或运行安装脚本仍需当前请求授权；获得授权时在隔离目录或干净环境执行，并把正式产物交给真实消费者。只完成发现检查时，README 可以陈述已经证明的公开入口，但交付报告必须把“命令存在”和“实际安装成功”分开。公开入口不存在、尚未发布或检查失败时不写占位命令，也不把计划中的渠道表述为已经可安装。

确认命令后，在提交前自动创建或更新每份活动语言 README 的安装段落：已有安装或 Installation 段落原位更新，不重复追加；缺少段落时放在项目定义之后、第一次使用之前；README 尚不存在而公开采用页面属于本次发布结果时创建。命令使用标明 shell 的代码块，周围只保留完成第一次成功所需的说明，README 其它内容继续由原有职责和当前写入范围决定。安装段落、项目清单与发布配置进入同一次获准发布闭包，不能让 README 指向未进入该提交的未来状态。

提交前让全部活动语言 README、包、Release、镜像、源码入口或 Skills CLI 等正式安装消费者消费同一候选，并在推送成功后停止。普通发布任务不等待 GitHub 页面、Actions 或远端安装消费者刷新；它只报告本地安装入口已验证、提交已推送和远端消费仍是异步状态。用户另行明确要求远端验收时，再从准确提交回读页面与正式分发身份；任一项变化或失败时，只把对应远端入口标为未完成，不能反向重跑无关本地检查。

## 3. 审计 GitHub 上传边界

完整初始化 GitHub 仓库、准备首次提交、提交或推送现有改动，以及项目综合审计需要判断是否已经向 GitHub 上传隐私或非必要文件时，共用本节作为唯一检查方法。先从第 2 节的干净克隆交付合同得到仓库应交付的用户结果和预期内容清单，再检查实际 Git 与 GitHub 表面；不能从 `.gitignore`、文件名、扩展名或当前默认分支看起来正常，推断整个上传边界安全且必要。

### 分开每个实际内容平面

开始前冻结准确仓库根、目标 GitHub 仓库、取得时间和以下适用平面，每个平面分别记录内容身份、检查范围和不可取得的证据：

```text
本地物理文件：包括未跟踪与被忽略内容，用于发现候选和本地状态，不等于准备上传
本次获准候选：由用户结果和依赖闭包得到的明确路径或内容片段
Git 索引：下一次提交实际会取得的内容
本地提交与可达历史：当前 HEAD、适用分支、标签及仍可取得的历史对象
实时 GitHub：默认分支、其它活动分支与标签的实际树和可达历史
其它公开制品：项目实际使用的 Git LFS、Release 资产或 Actions 制品；不存在时不扩张检查
```

本地 `origin/*`、工作区当前文件和 GitHub 默认分支分别只证明自己的状态。要回答“已经上传了什么”，必须通过实时 GitHub 只读接口取得准确远端引用和内容身份；网络、权限、树截断、历史深度或扫描器覆盖不足时，把对应平面标为未知或部分审查，不能用本地缓存补成零发现。新目录尚未初始化 Git 时仍先建立本地物理文件与拟上传候选，初始化产生 `.git` 后再补索引和提交平面。

### 用正式消费者判断必要性

为候选和已经上传的每个路径记录正式生产者、干净克隆中的消费者、生命周期和公开必要性，并归入下列一种职责：

1. 必须跟踪的项目输入或公开交付物；
2. 只应留在本机的用户内容、机器配置或运行状态；
3. 能从已跟踪输入稳定重建的缓存、依赖、测试或构建输出；
4. 仍由人工制作流程使用、但不属于仓库交付的原始材料；
5. 已退出活动消费者、仅有历史或归档价值的内容；
6. 生产者、消费者或权利边界尚不明确的未知内容。

已被跟踪、体积较小、位于源码目录或以前曾经提交都不能证明必要；二进制、大文件、锁文件、运行素材和生成文件也不能仅凭类别自动排除。只有正式构建、运行、维护、许可证或用户取得结果的消费者能够证明它应该进入 GitHub。未知项不能被自动加入忽略规则或上传清单。

### 检查隐私与敏感内容

隐私检查至少覆盖真实凭据与环境配置、私钥和证书、本机绝对路径与账号或主机身份、用户内容、数据库、日志、崩溃转储、会话、备份、导出、测试夹具中的真实数据，以及文档、截图、媒体元数据、压缩包和二进制容器中可能包含的私人或内部内容。首次提交前还要检查提交作者姓名与邮箱是否符合用户希望公开的身份；提交元数据不是普通文件，但同样会随 Git 历史进入 GitHub。

文件名和路径模式只能筛选候选。对准备提交的准确索引、已经提交的对象和适用历史运行内容或密钥扫描器，并记录工具身份、版本、输入集合、排除规则、退出状态与未覆盖的二进制或归档边界。扫描器成功运行且零匹配只证明它实际读取的集合；工具缺失、命令失败、历史未取得、输入为空或被默认过滤时结论是未知。测试值必须与真实凭据明显不同，不能为了验证扫描器写入看似真实的秘密。

检查过程只输出路径、内容身份、规则类别、脱敏位置和处置状态。凭据、用户内容和其它私人原文必须在进入终端输出、工具结果、对话、报告或日志前脱敏；不能为了证明发现而打印原值、前后缀或可逆编码。

同一份上传边界账本至少包含：

```text
证据平面、路径与内容身份：
生产者、正式消费者与干净克隆职责：
必要性：必须上传 / 仅本机 / 可重建 / 制作材料 / 历史材料 / 未知
隐私或敏感类别与脱敏证据：
当前 Git 状态与实时 GitHub 暴露状态：
建议处置及其所需授权：保留 / 忽略 / 取消跟踪 / 移出候选 / 归档 / 轮换凭据 / 清理历史
检查工具、实际输入、排除项与证据等级：
```

发现真实凭据时先停止一切会继续传播内容的提交和推送，并把撤销或轮换凭据作为第一处置；从当前工作区删除或加入 `.gitignore` 不会撤销秘密，也不会清除索引、本地历史或 GitHub。`.gitignore` 只影响尚未跟踪的匹配路径，不能让已跟踪文件自动退出索引。取消跟踪、移动、归档、删除、改写历史、强制推送和清理 GitHub 制品分别遵守当前权限，不能由一次只读审计自动执行。

首次初始化中存在隐私、非必要或未知候选时，完整初始化事务停在上传前，不创建一个随后可能被误推送的半成品远端。修正候选、忽略规则、索引或历史后，重新对最终内容身份运行本节检查；只有获准清单、索引、提交树和实时远端树在各自阶段一致，才能把相应上传边界标为通过。

### 历史清理先冻结类别、结果层和引用平面

已经上传的数据库、日志、备份、运行状态或生成结果需要退出仓库时，先分别判断**上传必要性**和**内容敏感性**。没有干净克隆消费者只能证明文件不应进入仓库；扩展名、二进制格式、包含真实运行记录或工具使用了 `--sensitive-data-removal` 等选项，都不能反向证明内容属于凭据、隐私或其它敏感数据。内容分类至少分开可撤销或轮换的真实凭据、已经证明包含私人或内部内容的数据、已经证明不敏感的运行或样例数据，以及尚未安全核对的未知内容。未知项保持待确认并在输出前脱敏，不为了取得一个更严重的结论读取或展示私人原文。

随后从用户接受的结果冻结准确清理层，不能让工具残留或后续探测自动扩大完成条件：

```text
内容类别及证据：仓库整洁 / 已确认私人内容 / 真实凭据 / 未知
准确路径、历史旧路径与内容身份：
第 1 层——当前工作树、索引和新提交不再包含目标：
第 2 层——获准的本地分支、标签与其它引用不再可达目标：
第 3 层——实时远端活动分支、标签和新鲜克隆不再可达目标：
第 4 层——旧提交 SHA 缓存、PR 引用、fork、其它克隆或托管方存储不再提供目标：
本次明确授权到哪一层，哪些层明确不做：
```

准确清理范围来自语义所有权账本：按生产者、正式消费者、生命周期、所属根目录和历史别名定义同一份路径集合。文件名、扩展名或正则扫描只能提供候选，不能成为过滤范围的权威；当前物理文件、忽略规则、源码验证器、当前树和获准历史必须消费同一范围身份，不能各自维护近似黑名单。

删除当前文件、改写本地历史、强制更新准确远端引用、协调 PR 或 fork、联系托管方清理缓存和服务器对象是不同动作。用户只批准从当前树或公开活动历史移除时，不自动获得清理其它克隆、提交工单或把第 4 层作为项目完成条件的权限；反过来，已经确认敏感且用户明确要求彻底清除时，也不能用新鲜克隆干净替代第 4 层。真实凭据仍先撤销或轮换，历史清理只减少后续暴露，不恢复凭据可信度。

执行历史改写前，取得实时远端全部适用分支与标签、当前远端 HEAD、本地 ahead / behind、待保留的未推送提交、准确路径及所有历史名称，并枚举本地引用的名称和对象类型。历史工具可能在敏感数据模式下主动抓取远端、覆盖本地引用或拒绝非新鲜仓库；先核对该版本的真实行为，让全部获准本地结果进入可恢复的提交或其它已批准保全边界，再决定正常抓取、显式禁用抓取或停止。普通 commit 引用之外的 tree 等快照引用可能继续持有目标 blob；工具警告跳过它们时逐项过滤准确树或保持为明确未清理状态，不能直接删除来源不明的引用，也不能从主分支已重写推断全部对象不可达。

本地引用还要按所有者和生命周期分成仓库公开引用、历史工具备份引用、活动宿主或工作区的回滚引用，以及所有者未知的引用。引用名称前缀和一次删除成功只能提供线索；通过创建者、宿主状态、更新时间、对象类型和删除后的再生行为确认。仓库公开历史、新鲜克隆与宿主本地运行状态分别成立：活动宿主会重建的引用仍会让第 2 层的本地全引用结论不成立，但不会反向否定已经验证的第 3 层；宿主仍运行时一次零引用只是带取得时间的瞬时快照，不能成为持续保证。

删除宿主或工具引用仍需用户明确授权，并且只处理身份和所有者已经确认的准确引用。用户只要求公开历史干净时，保留不上传且不改变公开可达性的宿主引用并报告其职责；用户明确要求本地宿主引用退出时，先让创建者停止或转到不再持有该仓库的执行边界，再删除并记录宿主状态、取得时间和立即回读结果。当前宿主无法停用或删除后仍会再生时，把持续为零标为当前不可保证，交付远端与新鲜克隆已经成立的层并停止；不能循环删除、扩大到未知引用，或把瞬时清空冒充持久结果。

更新远端前重新读取目标引用，并对每个获准改写的活动引用使用精确租约或等价条件更新；远端已变化就中止。完成后分别检查当前树、所有获准本地引用和对象类型、垃圾回收后的目标对象、实时远端活动引用，以及从远端准确提交取得的新鲜镜像或克隆。只有验证器实际读取这些平面，零路径或零对象才成立。若合同包含第 4 层，再单独检查已知旧 SHA、PR、fork 和托管方缓存，并按已确认的敏感类别与外部沟通权限决定是否联系托管方。

旧 SHA 仍能通过缓存直链读取，只证明第 4 层尚有服务器残留；当接受结果只到第 3 层、内容未被证明敏感或用户没有要求服务器彻底清除时，应准确报告该残留，但不能据此把已经完成的仓库结果改写成受阻，也不能要求用户提交支持工单。托管方只为特定敏感数据提供服务器清理时，把其资格要求、工单和最终清除验证留在第 4 层；非敏感仓库整洁问题在获准层通过后结束。
