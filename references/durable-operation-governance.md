# 持久操作治理

用于导出、复制、保存、下载、同步、最终化和其它在用户动作被接受后仍可能取消、失败、崩溃恢复或跨重启继续交付结果的操作，也用于队列、调度器、重试器或多个观察者可能重复接受同一次自动触发的任务，以及常驻有状态服务中会被多个命令发现、共享和释放的会话、项目上下文或资源。目标是让一次用户意图、一次物理执行和一个最终可见结果属于同一条可追踪链；自动触发则把一次正式发生、一次物理执行和一个最终可见结果纳入同样边界；共享资源则让每次准入、在途使用和最终关闭由同一个生命周期所有者协调，不让前置校验、文件命名、调度扫描、恢复扫描、资源注册表或界面提示各自形成第二套事实。

普通内存内计算、失败后无需追踪且不会留下外部结果的瞬时操作不使用本方法。是否需要持久事务由用户结果、失败后果和恢复要求决定，不能为了形式完整给所有按钮增加账本。常驻服务中的普通命令即使不需要持久事务，只要它使用可被并发释放的共享对象，就只消费本方法的准入、排空和关闭合同，不为每条命令补造任务账本。

## 1. 先定义操作接受点

区分两类校验：

- 在接受操作前完成：调用身份、授权、参数结构、操作类型、账本可写性，以及能否取得本次操作唯一租约。
- 在接受操作后由本次事务负责：当前输入文件是否仍存在、采集清单是否仍有效、远程对象是否变化、渲染请求能否构建、生产者能否启动，以及执行中的资源和设备是否可用。

用户动作一旦越过接受点，后续失败就必须属于这次操作。标准顺序是：

```text
用户动作
→ 身份、授权、结构与操作准入
→ 分配操作身份和目标意图
→ 持久化 pending
→ 重新读取并校验当前输入
→ 正式生产者执行
→ 物理结果完成或证据保全
→ 持久化唯一终态
→ 正式消费者读取
→ 用户实际看见结果
→ 明确确认已交付
```

不能先完成所有易失败的输入重校验，再在成功路径中补建事务。这样会让“用户已经发起、但前置条件刚好失效”的操作绕过账本、恢复和可见结果。取消发生在接受点之前可以不建立事务；发生在接受点之后必须结束同一事务。

越过接受点后，`pending` 还必须早于本次操作产生的任何外部可观察副作用。创建父目录或临时目录、分配临时文件、写入备份或恢复副本、改变权限与元数据、更新索引、版本变更清单或其它辅助状态，都属于事务的物理执行，不得伪装成“准备工作”发生在落账之前。接受前只允许不会改变外部状态的准入与只读探测；全部物理副作用由同一执行所有者在事务内产生，并能由操作身份和物理事实恢复或判定冲突。

### 冲突型换版先计划再提交

重新绑定对象、迁移持久状态或批量替换会遇到多个合法目标、同名记录、路径占用或其它必须由用户决定的冲突时，先建立严格的 `plan → commit` 边界。无冲突的瞬时内存修改不使用这套流程，不为了统一形式增加摘要和事务。

1. `plan` 只读地重新取得源、目标和受影响记录的准确身份与当前版本，返回完整影响集合、每项冲突、允许选择，以及覆盖整份计划的不可变摘要。
2. `commit` 必须同时收到原计划摘要和每一项冲突的明确决定；不得提供 `allow_conflicts`、尽力而为或隐式偏好来跳过选择。
3. 任何写入前再次读取源、目标和受影响记录，并与计划中的身份、版本和内容基线逐项比较；任一对象漂移就拒绝整份计划并重新生成，不能只重算发生变化的局部后继续使用旧摘要。
4. 计划仍有效且决定完整后，才越过操作接受点；随后由本方法既有的 `pending → 正式生产者 → 物理事实 → 唯一终态 → 可见确认` 链拥有全部副作用。

### 固化执行计划并分开进度语义

排队、后台、分块、并发或可重试操作的结果会受用户选择、输入范围、生产者版本或运行配置影响时，在接受点把这些决定固化为不可变执行计划，并与操作身份一起持久化。计划至少记录目标对象、正式输入身份、只包含会改变结果的内容相关修订或指纹、用户已选配置、生产者与版本、计划工作单元和重新计划条件。执行者、恢复者和显式重试从这份计划读取决定，不得在真正执行时重新读取已经可能变化的全局设置并悄悄改变同一次用户意图。

执行前仍要重新取得当前输入，但只与计划声明的内容相关身份比较。波形、缩略图、缓存、观察进度或其它不参与结果的派生状态不能让计划失效；反过来，任何会改变输出的输入、范围、排序、配置或生产者版本漂移都必须拒绝原计划并重新计划，不能用一个宽泛的项目更新时间同时制造误冲突和漏冲突。

进度是执行批次对这份计划的投影，不是任意子步骤最后上报的数字：

- 整体进度属于一个执行批次，由唯一聚合器根据计划工作单元计算，在该批次内只能单调前进；工作量无法可靠估计时明确显示不确定进度，不编造百分比。
- 阶段进度属于带稳定身份的当前步骤，可以在进入新阶段时从零开始，但必须和整体进度分开存储、传输和展示；单个阶段到达 100% 不等于操作成功。
- 多个并发生产者只上报各自工作单元、完成量和阶段状态，由聚合器统一加权；较晚启动的模型加载、分块或子任务不能把已有整体进度覆盖回零。
- 成功、失败、取消、冲突和中断仍只由唯一终态决定。显式重试创建新的执行批次和自己的进度序列，消费者必须能区分它与原批次，不能把两次尝试拼成一条看似倒退的进度。

### 有界批次必须证明积压能够排空

队列、调度器、重试器或恢复扫描使用数量上限、分页、时间预算或时间窗口时，这些限制只是一次执行的资源边界，不是业务完成边界。开始前定义权威候选集合、资格条件及其版本、稳定顺序、批次上限、尾批规则、失败与过期语义、重新进入条件和唯一调度所有者。一次批次至少保留候选范围或快照身份、本批选中身份、成功提交、明确终态、仍可重试、剩余数量或未知状态，以及下一次触发；只返回本批结果、只记录成功数量或查询达到上限，不能证明积压已经排空。

批次游标或高水位只能越过已经提交，或者按照正式合同进入失败、取消、过期、隔离等明确终态的记录。严格顺序不允许越过前方空洞；允许乱序时使用逐记录状态、租约或确认边界，不能用一个全局最大 ID 猜测此前对象都已处理。查询、计数或分页失败时，剩余量保持未知，不能投影为零。超过时间窗口的对象也必须进入可观察终态或带重新进入条件的延期状态，不能仅因过滤条件变化从待处理集合中消失。

处理期间的新到达对象与本轮冻结候选分开定代，下一轮按稳定公平顺序取得；持续新流量不能让既有积压长期饥饿。单条永久失败按合同重试后进入明确失败或隔离终态，并让后续合格对象继续，但不得为推进游标静默吞掉失败。只有权威候选查询成功、当前代全部对象已有可解释状态且没有待触发尾批时，才能报告“积压已排空”；“本批完成”和“整体排空”始终是两个结论。

## 2. 身份、命名空间和输出分配

持久操作身份至少包含：

```text
物理命名空间或存储根
+ 业务对象身份
+ 操作或事务身份
```

自动触发还要有独立于执行批次的稳定发生身份，例如“调度定义身份 + 定义版本 + 计划发生时刻”或消息系统提供的正式幂等键。多个进程、调度器或恢复扫描看到同一发生身份时，只能有一个观察者在同一事务中写入发生记录、创建任务并推进调度游标；先查再写、内存锁或事后去重都不能证明不会产生重复副作用。

发生身份回答“这是不是同一次触发”，执行批次回答“这次由哪一次尝试运行”。首次执行、显式重试和恢复后的继续观察使用不同批次身份，并记录各自开始、终止原因和终态。进程崩溃或连接丢失后，无法证明生产者尚未产生副作用时，把原批次结束为中断或等价的非成功终态；不得自动重放同一批次。用户或正式策略允许重试时创建新批次，同时保留与原发生身份和原批次的关联。

只使用逻辑对象 ID 和事务 ID，无法隔离被复制、克隆、恢复到另一目录或位于不同账号、卷和工作区的对象。恢复去重、确认和冲突判断都要包含能够区分真实存储位置的命名空间身份。

输出名、序号和临时路径由事务边界内的唯一分配器负责。失败、取消和被保全的尝试是否消耗名称属于正式合同；消费者、界面和测试不得根据成功数量重新实现分配规则。它们应记录动作前已有事务身份，动作后从新事务读取实际路径。

临时文件名必须由事务身份唯一确定，并与正式目标位于满足原子发布要求的边界。路径解析要验证仍在允许的存储根内，不能把账本中的相对路径直接当成可信绝对路径。

## 3. 物理事实先于账本声明

账本终态只能描述已经发生的物理事实：

- 发布成功：正式目标已完成、可读取，并通过当前结果所需的校验。
- 失败但有产物：部分产物已经原样移到确定的恢复位置，再记录保全路径和失败原因。
- 失败且无产物：已确认正式目标、精确临时目标和恢复位置均没有可交付媒体，再记录无产物终态。
- 冲突：正式目标、临时产物或恢复产物同时存在且无法唯一解释时，全部保持原样并记录冲突，不能猜测哪一个应覆盖。

不能先写“已经保全”再移动文件，也不能由原生生产者或下层库擅自删除失败证据。物理移动、刷盘、哈希或媒体校验失败时，事务保持能够继续恢复的状态。

### 生产者报错后按物理事实协调

生产者返回错误、连接中断或确认超时，只能说明调用边界没有取得可信完成结果，不能单独证明物理操作没有发生。凡生产者可能先改变文件、远程对象、索引或其它正式目标，再在返回、确认或后续记录阶段失败，执行计划必须预先定义可读取的成功后置条件、确定未发生的证据和冲突条件。完成所有者收到错误后，以操作身份、执行前基线和正式目标重新读取物理事实，并且只产生以下一种协调结果：

- 正式目标已经符合本次计划的身份、内容和完整性条件：从权威事实重建同一结果合同，作为本次执行的完成结果；
- 已经证明正式目标、临时目标和恢复位置都没有本次副作用：形成无产物失败；
- 只完成部分副作用、事实身份不匹配或无法排除其它生产者：保持证据并进入未决或冲突，不猜测成功，也不把原批次再执行一次。

协调器不能用进程内布尔值、异常类型或“通常在写入前报错”替代后置条件，也不能为了确认而再次调用有副作用的生产者。选定协调结果后，必须把它交给既有的唯一结果接收边界并立即结束当前完成路径；不得继续落入通用错误处理，再追加失败、成功或第二次清理。显式重试仍创建新的执行批次，并保留与原批次及协调结果的关系。

操作完成由一个唯一所有者接收显式结果并写入一次终态。成功、失败、取消、冲突或中断不能由多个清理分支、析构逻辑、`finally`、默认布尔值或“没有观察到错误”分别推断；即时准入后失败也必须把明确失败结果交给同一个完成入口，不能先记录失败再由兜底路径追加成功。账本终态、结构化完成事件和操作日志必须消费同一结果身份；出现两个终态或相互矛盾的完成记录时，事务保持待解释，不能选择最后一条覆盖。

### 所有完成路径在同一结果合同内收口

操作已经为正式结果声明类型、schema 或校验器，不等于生产者返回的值已经被任务生命周期接受。实现前从任务注册表、状态机和恢复入口列出实际存在的完成路径矩阵，例如即时同步、队列 worker、后台线程或进程、延期回调或聚合、显式重试和重启恢复；只列出项目真实拥有的路径，不为形式完整补造分支。每条路径都要记录正式生产者、结果合同、唯一结果接收边界、合同失败对应的终态，以及执行器能否继续处理后续操作。

所有正式生产者的返回值都先进入同一个结果接收边界。结果校验必须位于当前操作生命周期所有者的异常边界内，在正式生产者返回后、接受成功或写入终态之前执行；校验失败形成稳定的结果合同失败终态，不能逃逸并结束 worker 主循环，不能让操作留在 `running` 或等价非终态，也不能由外层清理改写成成功或追加第二终态。同步、后台、延期、聚合、重试和恢复路径不得分别复制校验与错误映射；延期标记只转移完成责任，后续正式结果仍回到同一个接收边界。

验收从正式任务入口注册一个受控但真实的结果生产者，让它返回违反当前结果合同的值；随后由账本等待唯一失败终态，让正式消费者读取稳定错误类别，再通过同一执行器提交一个合法操作并证明它正常完成。项目拥有多种完成路径时，对每种实际路径重复这条生产者到终态链。直接调用校验器、由消费端手写坏结果、只断言异常被捕获，或者只证明下一条任务被接受，都不能证明结果合同、持久终态和执行器存活已经共同收口。

原生任务、后台线程或远程请求尚未完成释放时，不得检查、移动或宣告其产物终态。超时只说明等待没有完成，不转移资源所有权；无法证明生产者已经退出时，事务保持 `pending` 或等价的未决状态。

### 完整结果集合一起发布或撤回

一项操作会同时产生主文件、旁路文件、质量报告、证明材料、索引、历史记录或其它由用户共同消费的结果时，在执行前定义完整结果集合及每个成员的正式消费者。全部成员共享同一操作身份、输入身份和发布决定；主文件存在不能代表整个结果已经完成。

成功终态只能在结果集合的所有必需成员完成校验、原子发布并由权威记录登记后产生。任一成员失败、身份不匹配或仍被生产者占用时，整个集合保持未决或失败；已经产生的成员一起撤回到同一恢复位置或按合同保全，不能只删除主文件、留下旁路结果，也不能保留成功历史记录指向已经撤回的产物。可选成员必须在合同里事先标明，不能在失败后临时降级为可选来保住成功状态。

### 验证运行证据的保留生命周期

测试、性能、审计和真实用户链会产生用例目录、日志、截图、报告或其它运行证据时，把每次运行当成有明确身份的持久操作，而不是测试结束后的无主临时文件。运行开始前，在受控证据根内先写入由工具拥有的清单，至少记录运行身份、明确类别、生产者与所有者身份、进程或执行批次身份、开始时刻、输入内容身份和 `running` 状态；类别由调用合同明确提供，不能从目录名或成功数量猜测。

清单的终态只在正式生产者结束、全部证据完成写入、相关文件句柄和消费者已经关闭后，由唯一所有者写为成功、失败或中断。进程消失不自动等于中断；恢复者还要证明原所有者及其子生产者已经结束且证据不再变化。证明成立后，遗留的 `running` 才能转换为中断，不能把未知运行归为成功或直接清理。

保留策略必须在运行前定义类别与选择规则，并在跨进程生命周期锁内执行。常见合同可以保留全部失败与中断运行，并让每个明确类别只保留最近一次完整成功；较早成功只有在更新的成功终态和完整证据已经持久提交后才成为清理候选。若用例具有由正式运行器提供的稳定身份和可信终态，失败运行可以只保留失败与未完成用例的独立证据；否则保留整个失败运行，不能根据缺失目录或日志文字猜测哪些用例成功。

轮换不得触碰仍在运行、状态未知、缺少工具所有权标记、位于未登记根或由其它工具管理的对象。实体清理继续服从当前用户、项目和环境的删除或归档权限；没有权限时只报告候选，不执行删除。Windows 打开文件、权限、同步占用或其它清理失败要作为独立保留错误写回清单或报告，等待后续安全重试，不能把原测试终态改成失败或为了得到干净目录扩大删除范围。

### 证据消费绑定明确运行身份

验证命令、性能比较或多轮抽样结束后，调用者必须保存每次调用返回的明确运行身份或同等清单引用。后续报告消费者按类别 + 运行身份 + 工具所有权标记解析当前或归档位置，并回读清单核对输入内容身份和终态；保留策略移动目录不能改变证据身份。不能按目录修改时间、排序后的“最新目录”、文件名猜测或扫描成功数量选择本轮证据，因为轮换、归档、时钟差异和较晚写入摘要都会改变物理顺序。

聚合只接受当前调用显式传入的运行身份集合。每个成员都要存在、属于预期类别和所有者、已经达到可信终态，并与本轮输入身份一致；任何成员缺失、仍在运行或身份不匹配时，聚合保持不完整或未知，不能用未匹配的旧运行补位。聚合报告是派生证据，不是运行清单的替代真源；它必须列出完整输入运行身份集合、各成员终态、统计口径和生成时刻，使消费者能够从聚合结果返回每一份原始证据。

## 4. 恢复动作和可见确认

终态恢复动作应自包含：

- 物理命名空间；
- 业务对象身份；
- 事务身份与操作类型；
- 终态类型；
- 正式目标或保全路径；
- 失败原因；
- 用户需要采取的行动。

它不能依赖仍然有效的输入文件、采集清单、缓存页面或当前进程内对象。应用重启后持续重放账本中未确认的可见恢复动作、消息和行动入口，不重放结果不确定的业务生产者；直到正式消费者已经读取、界面完成布局、消息和行动入口实际可见，再记录确认。把消息赋值给视图模型不等于用户已经看见。

每个可见恢复动作还要有稳定的动作身份、当前执行批次或 generation，以及可观察的 busy 状态。用户重复点击、两个窗口同时触发或重放消息再次到达时，只能加入同一活动尝试并读取其结果，或者在同一原子边界被确定性拒绝；不得启动第二个恢复生产者。界面在执行中禁用会产生新尝试的入口，但禁用只是投影，幂等或拒绝仍由持久边界保证。

取消请求必须携带恢复动作身份和目标 generation，边界在生效前重新读取当前活动尝试与是否仍需恢复。只允许取消匹配且仍在运行的尝试；较早界面、超时回调或重复触发留下的取消，不得命中新 generation，更不能取消、回滚或覆盖已经完成的替代结果。完成、失败与取消继续进入同一唯一终态和可见确认链。

长错误、恢复路径和行动按钮必须在低高度或窄视口中仍然可达。状态区域可以有界滚动，但不能把保存、重试、打开目录或确认按钮挤出窗口。

## 5. 并发和唯一所有权

同一业务对象的采集、最终化、预览、导出、复制和恢复如果会修改同一媒体或账本，应通过一个可等待的租约或等价所有权边界串行化。锁只保护一次写入不足以证明整个原生操作不会与恢复并发。

### 执行拓扑改变后重新证明共享状态所有权

把正式生产者从界面线程移到 worker、把同步路径改成后台任务、让原本同一执行器中的操作进入不同线程或进程，或者新增能够同时到达同一服务的入口时，旧的“天然串行”结论立即失效。操作队列只证明经过同一仲裁边界的工作按其合同调度，不能证明仲裁器自身的可变状态、它调用的共享服务与原生引擎、延迟回调或绕过该入口的恢复路径能够被并发进入。

实施前重新建立执行拓扑与共享状态矩阵：每个生产者的实际执行上下文、可能重叠的接受区间、共享可变状态或原生资源、线程亲和与可重入合同、准入或排他的唯一所有者，以及关闭时等待谁结束。每个跨上下文共享对象必须选择一种完整所有权：由单一执行上下文拥有并通过消息收口，或者由覆盖整个在途使用区间的锁、租约或等价边界保护；只锁队列更新、状态切换或一次调用，不能替仍在运行的底层操作提供排他性。操作身份、generation 和终态隔离继续负责关联结果，不能冒充执行互斥。

对象、服务或其所有者跨线程、进程或 executor 迁移时，还要枚举内部已经创建的框架资源和子对象，包括计时器、读取器、套接字、订阅、回调和句柄。每项必须由框架合同证明会随所有者正式迁移，或在原上下文停止并在目标上下文重建；不能只移动外层对象。启动、停止、销毁和等待归属允许访问该资源的同一执行上下文，跨上下文启动、停止或销毁警告属于失败。

验收从两个真实正式入口发起不同操作，用受控屏障让它们在共享边界前形成重叠，证明共享服务或原生资源的最大在途进入数符合合同，两项操作仍各自得到唯一终态，旧取消或较晚回调不会命中另一项，关闭会等待真正的持有者排空。直接并发调用锁 helper、只观察队列顺序或把测试改成串行，不能证明执行拓扑已经安全。

### 可发现会话与共享资源先取得准入租约

常驻服务通过注册表、会话表、项目表或连接映射公开共享对象时，“能够查到对象”不等于调用者已经取得安全使用权。发现、准入计数和关闭门槛由同一个注册表所有者负责，标准顺序是：

```text
在注册表所有者的同一原子边界内验证对象仍可发现且未关闭
→ 增加活动使用者并返回共享准入租约
→ 命令在租约内完成全部读取、写入和结果发布
→ 释放方在同一边界把对象移出可发现集合并标记为 `closing`
→ 拒绝新准入，等待已经发放的共享准入租约归零
→ 取得对象的独占写入或关闭权
→ 排空依赖该对象的工作并释放持久状态、句柄和原生资源
```

不能查表后返回裸对象，再由调用者晚些时候加锁；释放方可能在这两个动作之间关闭对象。命令在内部派生会越过自身返回点继续使用对象的工作时，派生工作必须在原命令释放前取得自己的租约，不能借父命令已经准入推断以后仍安全。释放等待超时只说明旧使用者尚未排空，状态保持 `closing` 且所有权未知；不能丢失引用、重新加入发现表、强行关闭仍在使用的资源或让另一个关闭者接管。

共享准入只保护对象仍然存活，不替代业务写入、设备或其它排他资源自己的窄锁。多个只读或互不冲突的命令应能够同时持有共享租约；不能用一把覆盖会话整个生命期的排他锁把全部命令串行化，也不能让后台长任务仅因先取得普通准入就阻塞不依赖同一排他资源的前台动作。

关闭计划再把后台工作按实际依赖的资源域分类。读取项目状态的工作必须在项目资源释放前排空或明确结束；只依赖应用级网络、传输或调度资源的工作由各自生命周期所有者停止接收、取消、排空和关闭，不能用一个全局执行器统一等待或统一取消后猜测谁还会读取已经释放的项目。每类任务都记录它持有的准入租约、排他资源和释放顺序，项目关闭不等待与项目无关的网络工作，应用关闭也不能越过仍在读取项目状态的工作直接释放项目。

### 唯一运行权先于恢复和调度

有状态 daemon、后台服务、调度器或本地服务端可能由两个进程同时启动时，命名端点、服务锁、租约或平台服务管理器给出的唯一运行权必须先于任何会改变持久状态的初始化。构造对象、打开传输端或读取只读配置不能顺带恢复任务、推进调度游标、标记中断、重新排队或发布状态；标准顺序是：

```text
创建不触发持久状态变化的进程外壳
→ 竞争并取得权威端点或服务租约
→ 确认本进程是唯一活动实例
→ 初始化状态服务、恢复任务和启动调度
→ 接受客户端并产生新的状态变化
```

竞争失败的进程只能关闭自己为竞争创建的端点、句柄和内存对象，不能打开恢复链后再靠绑定失败或析构逻辑回滚；恢复已经产生的状态变化通常无法与胜者并发动作安全区分。服务 `start` 必须幂等，端点绑定或后续初始化失败时由同一所有者关闭本次资源，并在未取得运行权时保证账本、任务状态、重试次数和调度游标逐字节或逐记录不变。运行权在服务存活期间丢失时，先停止接受新工作并排空或明确中断本实例拥有的工作，再允许新实例恢复，不能让两个恢复者短暂重叠。

多个进程需要从第一次访问同一资源起协调时，同步命名空间必须直接由规范化资源身份和合同版本确定，并在任何参与者创建侧边锁文件、状态目录或业务副作用之前取得。侧边锁文件可以记录诊断或所有者，但不能把“侧边锁文件已经存在”作为其它进程加入同一同步边界的前提；只读参与者也不能为了协调创建业务状态。首次启动时同时进入的读写进程必须竞争同一平台租约或命名端点。

每个线程、任务、事件读取器和订阅分发器都要有：

- 创建者和唯一释放者；
- 可等待的完成信号；
- 取消后的排空路径；
- 失败怎样进入当前事务；
- 关闭时谁等待它真正结束。

权威状态和致命错误使用无损路径；高频遥测可以使用有界、合并或丢旧值的路径。不能为了防止慢订阅者阻塞而丢失状态转换，也不能通过逃逸任务或超时回调让关闭看似完成。

## 6. 真实验收

至少覆盖：

1. 从真实用户动作或正式 API 接受一次操作，确认 `pending` 在易失败输入重校验之前已经存在。
2. 正式生产者实际生成结果，结果经过真实文件、远程、进程或原生边界。
3. 正式消费者从账本读取该事务的实际身份和路径，不预测名称、不按成功数量推算。
4. 成功结果可用；取消和失败没有发布正式目标，已有历史结果未被覆盖。
5. 有产物失败先完成物理保全，再出现终态；无产物失败不会声称存在可恢复媒体。
6. 进程中断后由新进程恢复账本并重放未确认的可见恢复动作，不重放结果不确定的业务生产者；用户看到结果后精确确认该事务。
7. 复制或克隆到另一物理命名空间的对象不会互相吞掉恢复动作。
8. 关闭等待生产者、读取器和分发器真正结束；没有后台工作继续修改已经宣告完成的事务。
9. 两个独立调度观察者同时处理同一发生身份，只产生一条发生记录和一个初始任务；原子边界失败时三者都不留下半写状态。
10. 生产者在结果不确定时崩溃或断开，原批次不会被恢复逻辑静默重放；显式重试产生可区分的新批次，并由同一消费者读取两次尝试的关系和结果。
11. 在 `pending` 前后以及每类辅助副作用前后注入失败，证明落账前没有目录、临时文件、备份、元数据或变更清单残留，落账后的残留能由同一操作恢复或判定冲突。
12. 成功、即时失败、取消、冲突和中断分别只产生一个与账本一致的结构化终态；日志反向扫描不会发现同一操作先失败后成功、重复完成或由清理路径补写的矛盾结果。
13. 多输出操作只有在全部必需成员和权威记录共同发布后成功；任一成员失败会让已经产生的主文件、旁路文件、报告和历史记录按同一操作身份一起撤回或保全。
14. 两个进程同时结束验证运行和执行保留选择时，生命周期锁保证活跃运行不被清理；全部失败与中断仍可读取，每个明确类别最多保留合同指定的最近成功。
15. 新成功尚未完整落盘、原所有者仍活动或清理遇到打开文件时，旧成功证据仍然保留；清理错误可见且不会改写测试本身的成功或失败终态。
16. 证据根中没有工具所有权标记的目录保持原样；用例级裁剪只在正式运行器提供稳定用例身份和可信终态时发生。
17. 排队后改变全局默认配置不会改变已经接受的执行计划；内容相关输入漂移会拒绝原计划，而只更新缓存、缩略图或其它派生状态不会制造误冲突。
18. 真实事件流跨过至少两个阶段并包含并发工作单元时，整体进度始终单调，阶段进度可以随阶段身份重置，任何阶段的 100% 都不会提前产生成功终态。
19. 显式重试使用新的执行批次和独立进度序列，正式消费者仍能读出两次尝试与同一用户意图的关系，不把第二次从零开始显示成原任务倒退。
20. 用受控屏障让两个独立进程同时竞争同一权威端点，并预置至少一个非终态持久任务；只有胜者执行一次恢复和调度，失败竞争者退出后任务状态、重试次数和调度游标不变，同一个正式消费者从胜者端点读取恢复结果。同一测试从不存在任何侧边锁文件的状态启动读写进程，二者仍命中同一同步身份，失败竞争者和只读者不创建业务状态。
21. 同一恢复动作被连续点击、两个窗口同时触发或旧消息重放时，只加入或拒绝同一活动 generation；旧取消不能影响新尝试或已经完成的替代结果。
22. 连续产生多次同类别验证并触发归档后，聚合器只消费调用者显式交付的运行身份集合；目录修改时间或归档位置变化不会换入旧报告，缺失成员会让聚合保持不完整并列出准确身份。
23. 用受控屏障让一个正式命令取得共享准入租约后暂停，再开始释放；对象先退出可发现集合，新命令被拒绝，已有命令仍可完成，最后一个租约释放后才取得独占关闭权并释放资源。
24. 两个互不冲突的正式命令能够同时使用同一活动对象；后台任务另行取得自己的租约后，前台命令不会被会话生命期排他锁阻塞。关闭时项目作用域工作先排空，应用或网络作用域工作由自己的所有者收口，任何任务都不读取已经释放的资源。
25. 对每种实际完成路径，让正式生产者返回违反结果合同的值，证明账本得到唯一稳定失败且没有 `running` 残留；随后由同一执行器完成一个合法操作，不能以直接调用校验器或只观察新任务已入队代替执行器存活证据。
26. 预置超过两个批次上限且带尾批的积压，由正式调度入口连续运行，证明处理顺序是完整批次、完整批次、尾批，每个初始对象恰好进入一个可解释终态；第一批成功时消费者仍显示准确剩余量而不是整体完成。
27. 在批次提交和游标推进的各个边界注入中断并重启，证明已提交对象不会重复产生副作用，未提交对象不会因高水位、分页或时间窗口被跳过，尾批仍会重新获得调度。
28. 在旧积压处理期间持续加入新对象，证明冻结候选与新一代身份清楚、既有对象不会饥饿；再让一条对象永久失败或过期，证明它进入可观察的失败、隔离或延期状态，后续对象仍能处理且游标没有静默吞掉空洞。
29. 让权威候选查询、剩余计数或下一页读取失败，证明正式消费者报告剩余未知和准确失败位置，不把零、当前批数量或最后成功游标伪装成积压已经排空。
30. 让正式生产者在完整应用物理结果后返回受控错误，证明完成所有者从后置条件重建同一结果、生产者只执行一次且账本只有一个成功终态；再分别让错误发生在副作用前和部分副作用后，证明前者得到唯一无产物失败，后者保持未决或冲突，任何路径都不会先失败后成功、再次执行原批次或落入第二个完成分支。
31. 把拥有计时器、读取器、套接字、订阅或回调的真实对象迁移到目标执行上下文，证明每项内部资源随所有者正式迁移或在原上下文停止后重建；启动、停止、等待和销毁都没有跨上下文警告。

测试先读取动作前的事务身份集合，再等待唯一的新终态，并从该事务解析实际目标。不要建立第二个时钟、文件编号器、状态机或恢复解释器充当断言真源。消费端手写事务对象只能测试消费者，不能证明完整操作链。

## 7. 输出

第一段直接说明操作的接受点、最早错误边界和最终事务所有者。随后给出：

1. 身份、命名空间和输出分配真源；
