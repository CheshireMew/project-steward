# 持久操作治理

用于导出、复制、保存、下载、同步、最终化和其它在用户动作被接受后仍可能取消、失败、崩溃恢复或跨重启继续交付结果的操作，也用于队列、调度器、重试器或多个观察者可能重复接受同一次自动触发的任务。目标是让一次用户意图、一次物理执行和一个最终可见结果属于同一条可追踪链；自动触发则把一次正式发生、一次物理执行和一个最终可见结果纳入同样边界，不让前置校验、文件命名、调度扫描、恢复扫描或界面提示各自形成第二套事实。

普通内存内计算、失败后无需追踪且不会留下外部结果的瞬时操作不使用本方法。是否需要持久事务由用户结果、失败后果和恢复要求决定，不能为了形式完整给所有按钮增加账本。

## 1. 先定义操作接受点

区分两类校验：

- 在接受操作前完成：调用身份、授权、参数结构、操作类型、账本可写性，以及能否取得本次操作唯一租约。
- 在接受操作后由本次事务负责：当前输入文件是否仍存在、采集清单是否仍有效、远程对象是否变化、渲染请求能否构建、生产者能否启动，以及执行中的资源和设备是否可用。

用户动作一旦越过接受点，后续失败就必须属于这次操作。标准顺序是：

```text
用户动作
→ 身份、授权、结构与操作准入
→ 分配操作身份和目标意图
→ 持久化 pending
→ 重新读取并校验当前输入
→ 正式生产者执行
→ 物理结果完成或证据保全
→ 持久化唯一终态
→ 正式消费者读取
→ 用户实际看见结果
→ 明确确认已交付
```

不能先完成所有易失败的输入重校验，再在成功路径中补建事务。这样会让“用户已经发起、但前置条件刚好失效”的操作绕过账本、恢复和可见结果。取消发生在接受点之前可以不建立事务；发生在接受点之后必须结束同一事务。

越过接受点后，`pending` 还必须早于本次操作产生的任何外部可观察副作用。创建父目录或临时目录、分配临时文件、写入备份或恢复副本、改变权限与元数据、更新索引、版本变更清单或其它辅助状态，都属于事务的物理执行，不得伪装成“准备工作”发生在落账之前。接受前只允许不会改变外部状态的准入与只读探测；全部物理副作用由同一执行所有者在事务内产生，并能由操作身份和物理事实恢复或判定冲突。

### 冲突型换版先计划再提交

重新绑定对象、迁移持久状态或批量替换会遇到多个合法目标、同名记录、路径占用或其它必须由用户决定的冲突时，先建立严格的 `plan → commit` 边界。无冲突的瞬时内存修改不使用这套流程，不为了统一形式增加摘要和事务。

1. `plan` 只读地重新取得源、目标和受影响记录的准确身份与当前版本，返回完整影响集合、每项冲突、允许选择，以及覆盖整份计划的不可变摘要。
2. `commit` 必须同时收到原计划摘要和每一项冲突的明确决定；不得提供 `allow_conflicts`、尽力而为或隐式偏好来跳过选择。
3. 任何写入前再次读取源、目标和受影响记录，并与计划中的身份、版本和内容基线逐项比较；任一对象漂移就拒绝整份计划并重新生成，不能只重算发生变化的局部后继续使用旧摘要。
4. 计划仍有效且决定完整后，才越过操作接受点；随后由本方法既有的 `pending → 正式生产者 → 物理事实 → 唯一终态 → 可见确认` 链拥有全部副作用。

## 2. 身份、命名空间和输出分配

持久操作身份至少包含：

```text
物理命名空间或存储根
+ 业务对象身份
+ 操作或事务身份
```

自动触发还要有独立于执行批次的稳定发生身份，例如“调度定义身份 + 定义版本 + 计划发生时刻”或消息系统提供的正式幂等键。多个进程、调度器或恢复扫描看到同一发生身份时，只能有一个观察者在同一事务中写入发生记录、创建任务并推进调度游标；先查再写、内存锁或事后去重都不能证明不会产生重复副作用。

发生身份回答“这是不是同一次触发”，执行批次回答“这次由哪一次尝试运行”。首次执行、显式重试和恢复后的继续观察使用不同批次身份，并记录各自开始、终止原因和终态。进程崩溃或连接丢失后，无法证明生产者尚未产生副作用时，把原批次结束为中断或等价的非成功终态；不得自动重放同一批次。用户或正式策略允许重试时创建新批次，同时保留与原发生身份和原批次的关联。

只使用逻辑对象 ID 和事务 ID，无法隔离被复制、克隆、恢复到另一目录或位于不同账号、卷和工作区的对象。恢复去重、确认和冲突判断都要包含能够区分真实存储位置的命名空间身份。

输出名、序号和临时路径由事务边界内的唯一分配器负责。失败、取消和被保全的尝试是否消耗名称属于正式合同；消费者、界面和测试不得根据成功数量重新实现分配规则。它们应记录动作前已有事务身份，动作后从新事务读取实际路径。

临时文件名必须由事务身份唯一确定，并与正式目标位于满足原子发布要求的边界。路径解析要验证仍在允许的存储根内，不能把账本中的相对路径直接当成可信绝对路径。

## 3. 物理事实先于账本声明

账本终态只能描述已经发生的物理事实：

- 发布成功：正式目标已完成、可读取，并通过当前结果所需的校验。
- 失败但有产物：部分产物已经原样移到确定的恢复位置，再记录保全路径和失败原因。
- 失败且无产物：已确认正式目标、精确临时目标和恢复位置均没有可交付媒体，再记录无产物终态。
- 冲突：正式目标、临时产物或恢复产物同时存在且无法唯一解释时，全部保持原样并记录冲突，不能猜测哪一个应覆盖。

不能先写“已经保全”再移动文件，也不能由原生生产者或下层库擅自删除失败证据。物理移动、刷盘、哈希或媒体校验失败时，事务保持能够继续恢复的状态。

操作完成由一个唯一所有者接收显式结果并写入一次终态。成功、失败、取消、冲突或中断不能由多个清理分支、析构逻辑、`finally`、默认布尔值或“没有观察到错误”分别推断；即时准入后失败也必须把明确失败结果交给同一个完成入口，不能先记录失败再由兜底路径追加成功。账本终态、结构化完成事件和操作日志必须消费同一结果身份；出现两个终态或相互矛盾的完成记录时，事务保持待解释，不能选择最后一条覆盖。

原生任务、后台线程或远程请求尚未完成释放时，不得检查、移动或宣告其产物终态。超时只说明等待没有完成，不转移资源所有权；无法证明生产者已经退出时，事务保持 `pending` 或等价的未决状态。

### 完整结果集合一起发布或撤回

一项操作会同时产生主文件、旁路文件、质量报告、证明材料、索引、历史记录或其它由用户共同消费的结果时，在执行前定义完整结果集合及每个成员的正式消费者。全部成员共享同一操作身份、输入身份和发布决定；主文件存在不能代表整个结果已经完成。

成功终态只能在结果集合的所有必需成员完成校验、原子发布并由权威记录登记后产生。任一成员失败、身份不匹配或仍被生产者占用时，整个集合保持未决或失败；已经产生的成员一起撤回到同一恢复位置或按合同保全，不能只删除主文件、留下旁路结果，也不能保留成功历史记录指向已经撤回的产物。可选成员必须在合同里事先标明，不能在失败后临时降级为可选来保住成功状态。

### 验证运行证据的保留生命周期

测试、性能、审计和真实用户链会产生用例目录、日志、截图、报告或其它运行证据时，把每次运行当成有明确身份的持久操作，而不是测试结束后的无主临时文件。运行开始前，在受控证据根内先写入由工具拥有的清单，至少记录运行身份、明确类别、生产者与所有者身份、进程或执行批次身份、开始时刻、输入内容身份和 `running` 状态；类别由调用合同明确提供，不能从目录名或成功数量猜测。

清单的终态只在正式生产者结束、全部证据完成写入、相关文件句柄和消费者已经关闭后，由唯一所有者写为成功、失败或中断。进程消失不自动等于中断；恢复者还要证明原所有者及其子生产者已经结束且证据不再变化。证明成立后，遗留的 `running` 才能转换为中断，不能把未知运行归为成功或直接清理。

保留策略必须在运行前定义类别与选择规则，并在跨进程生命周期锁内执行。常见合同可以保留全部失败与中断运行，并让每个明确类别只保留最近一次完整成功；较早成功只有在更新的成功终态和完整证据已经持久提交后才成为清理候选。若用例具有由正式运行器提供的稳定身份和可信终态，失败运行可以只保留失败与未完成用例的独立证据；否则保留整个失败运行，不能根据缺失目录或日志文字猜测哪些用例成功。

轮换不得触碰仍在运行、状态未知、缺少工具所有权标记、位于未登记根或由其它工具管理的对象。实体清理继续服从当前用户、项目和环境的删除或归档权限；没有权限时只报告候选，不执行删除。Windows 打开文件、权限、同步占用或其它清理失败要作为独立保留错误写回清单或报告，等待后续安全重试，不能把原测试终态改成失败或为了得到干净目录扩大删除范围。

## 4. 恢复动作和可见确认

终态恢复动作应自包含：

- 物理命名空间；
- 业务对象身份；
- 事务身份与操作类型；
- 终态类型；
- 正式目标或保全路径；
- 失败原因；
- 用户需要采取的行动。

它不能依赖仍然有效的输入文件、采集清单、缓存页面或当前进程内对象。应用重启后持续重放账本中未确认的可见恢复动作、消息和行动入口，不重放结果不确定的业务生产者；直到正式消费者已经读取、界面完成布局、消息和行动入口实际可见，再记录确认。把消息赋值给视图模型不等于用户已经看见。

长错误、恢复路径和行动按钮必须在低高度或窄视口中仍然可达。状态区域可以有界滚动，但不能把保存、重试、打开目录或确认按钮挤出窗口。

## 5. 并发和唯一所有权

同一业务对象的采集、最终化、预览、导出、复制和恢复如果会修改同一媒体或账本，应通过一个可等待的租约或等价所有权边界串行化。锁只保护一次写入不足以证明整个原生操作不会与恢复并发。

每个线程、任务、事件读取器和订阅分发器都要有：

- 创建者和唯一释放者；
- 可等待的完成信号；
- 取消后的排空路径；
- 失败怎样进入当前事务；
- 关闭时谁等待它真正结束。

权威状态和致命错误使用无损路径；高频遥测可以使用有界、合并或丢旧值的路径。不能为了防止慢订阅者阻塞而丢失状态转换，也不能通过逃逸任务或超时回调让关闭看似完成。

## 6. 真实验收

至少覆盖：

1. 从真实用户动作或正式 API 接受一次操作，确认 `pending` 在易失败输入重校验之前已经存在。
2. 正式生产者实际生成结果，结果经过真实文件、远程、进程或原生边界。
3. 正式消费者从账本读取该事务的实际身份和路径，不预测名称、不按成功数量推算。
4. 成功结果可用；取消和失败没有发布正式目标，已有历史结果未被覆盖。
5. 有产物失败先完成物理保全，再出现终态；无产物失败不会声称存在可恢复媒体。
6. 进程中断后由新进程恢复账本并重放未确认的可见恢复动作，不重放结果不确定的业务生产者；用户看到结果后精确确认该事务。
7. 复制或克隆到另一物理命名空间的对象不会互相吞掉恢复动作。
8. 关闭等待生产者、读取器和分发器真正结束；没有后台工作继续修改已经宣告完成的事务。
9. 两个独立调度观察者同时处理同一发生身份，只产生一条发生记录和一个初始任务；原子边界失败时三者都不留下半写状态。
10. 生产者在结果不确定时崩溃或断开，原批次不会被恢复逻辑静默重放；显式重试产生可区分的新批次，并由同一消费者读取两次尝试的关系和结果。
11. 在 `pending` 前后以及每类辅助副作用前后注入失败，证明落账前没有目录、临时文件、备份、元数据或变更清单残留，落账后的残留能由同一操作恢复或判定冲突。
12. 成功、即时失败、取消、冲突和中断分别只产生一个与账本一致的结构化终态；日志反向扫描不会发现同一操作先失败后成功、重复完成或由清理路径补写的矛盾结果。
13. 多输出操作只有在全部必需成员和权威记录共同发布后成功；任一成员失败会让已经产生的主文件、旁路文件、报告和历史记录按同一操作身份一起撤回或保全。
14. 两个进程同时结束验证运行和执行保留选择时，生命周期锁保证活跃运行不被清理；全部失败与中断仍可读取，每个明确类别最多保留合同指定的最近成功。
15. 新成功尚未完整落盘、原所有者仍活动或清理遇到打开文件时，旧成功证据仍然保留；清理错误可见且不会改写测试本身的成功或失败终态。
16. 证据根中没有工具所有权标记的目录保持原样；用例级裁剪只在正式运行器提供稳定用例身份和可信终态时发生。

测试先读取动作前的事务身份集合，再等待唯一的新终态，并从该事务解析实际目标。不要建立第二个时钟、文件编号器、状态机或恢复解释器充当断言真源。消费端手写事务对象只能测试消费者，不能证明完整操作链。

## 7. 输出

第一段直接说明操作的接受点、最早错误边界和最终事务所有者。随后给出：

1. 身份、命名空间和输出分配真源；
2. `pending`、执行、物理结果、终态和可见确认顺序；
3. 取消、失败、冲突、重试和跨重启恢复；
4. 并发租约与后台任务所有权；
5. 完整结果集合，以及运行证据的身份、保留、轮换和清理错误；
6. 所有生产者、消费者、状态和旧路径的迁移范围；
7. 真实事务、真实产物和最终用户结果的验收证据。

用户只要求诊断时停在证据与最终方案；要求修复时一次迁移全部调用点，并退出旧账本、旧分配器、旧恢复动作、旧测试 helper 和并行解释逻辑。
