# 模板演进

用于把已经稳定成某类项目默认约束的治理能力加入项目模板，或修改已有模板的检测、默认决策和验收合同。仍需结合具体情境选择的方法留在 Project Steward 的主流程或专项资料。只有用户明确要求更新模板时进入本方法。

## 1. 准入证据

一项经验至少满足一个条件：

- 同类缺陷在两个独立项目或两个独立实现中重复出现；
- 一个真实用户链证明当前模板缺少会稳定导致失败的构成性边界；
- 框架或平台的正式合同改变，现有检查已经失真；
- 用户明确把某个长期项目决策指定为模板默认。

一次报错文本、临时补丁、当前文件名、项目专名和偶然目录结构不能证明一项能力应成为模板默认。正确做法与失败教训使用同一门槛；只有当前项目需要的做法留在项目真实来源，能够跨项目使用但仍需情境判断的做法通过对话学习更新 Project Steward。历史材料已经提炼时，以通过能力门槛的候选为输入，不把原始纠正过程再次写进模板。

## 2. 选择最早层级

把经验放到最早且最窄的正确层：

| 层 | 适用范围 |
| --- | --- |
| base | 几乎所有软件项目都成立 |
| surface | 只对具有某种真实产品表面的项目成立，例如数字产品界面 |
| archetype | 同一种项目形态共同成立 |
| stack | 只由某个具体技术栈决定 |
| capability | 只在启用某项能力时成立 |
| project override | 只属于当前项目 |

用户任务、完整界面合同和设计系统真源属于数字产品表面；桌面标题栏和关闭生命周期属于桌面应用形态；Tauri capability 权限名和配置位置属于 Tauri 技术栈；某个产品的侧栏宽度只属于项目。

没有可靠文件、依赖或配置可以确定某项领域能力时，把模板注册为 `explicit_only`。它仍可被用户、现有项目配置或另一个模板依赖选择，但 `inspect` 不根据项目名、相似目录或当前案例专名猜测。无法可靠自动识别不是制造弱信号的理由。

## 3. 写成模板合同

每项新增内容写成：

```text
用户或系统应得到的结果：
最早需要作出的决策：
稳定不变量：
可以确定性检测的信号：
需要人工或真实运行验证的链：
不适用条件：
```

优先增加正向默认、检测和完成证据。硬禁止只用于权限、协议、数据完整性或会实质改变结果的边界，不能把一次纠偏原句复制进模板。

模板正文保存稳定行为、检测和验收，不保存对话历史、项目专名或外部经验条目指针。准入依据留在本次演进证据中；模板长期有效性由注册表版本、真实消费者、外部项目验证和后续升级链共同证明。

高频问题只有在主流程会按条件读取、能够指出最早预防点并具有真实验收证据时才进入模式库。不能为了覆盖更多案例增加每次都执行的细碎检查。

## 4. 版本和迁移

模板使用语义版本：

- 修正文案且行为不变：补丁版本。
- 新增检查、默认决策或向后可解释字段：次版本。
- 改变项目默认、删除字段或需要项目选择：主版本。

更新模板内容后同步：

1. 模板文件中的版本。
2. 注册表版本、文件哈希和目录版本。
3. 脚本消费者。
4. 固定测试夹具。
5. 适用平台方法。

旧项目配置保持固定版本并显示漂移。迁移由 `plan` 解释，由 `upgrade` 一次完成；活动源码不保留“旧版也这样解释”的兼容分支。

## 5. 行为验收

至少验证：

1. 原有模板仍能完成原有触发请求。
2. 新缺陷在不符合的外部项目中会被检查捕获。
3. 符合合同的外部项目能通过确定性检查。
4. 项目覆盖不会静默抹掉失败。
5. 旧配置显示准确版本差异，升级后重新读取成功。
6. 注册表哈希与模板真实字节一致。
7. 当前任务路径、报错句和项目专名没有进入运行模板。
8. 模板规则仍与当前 Project Steward 方法、平台合同和适用范围一致。

最后运行结构校验和旧名称残留检查，分别报告结构、真实实例化、确定性消费和平台运行的验证等级。
