# CI 执行治理

用于项目级改动、迁移、发布保证或反复出现的 CI 成本问题。它把已经成立的验收义务转换成尽早失败、资源隔离、可复用且能够精准重跑的执行计划。普通单个 CI 报错仍按当前开发任务处理；没有项目级结果、跨边界迁移或持续成本问题时，不为它启动完整治理。

本方法只拥有 CI 的执行拓扑、环境缓存、资源分组、分片、阶段顺序、失败范围和耗时证据。`change-prevention.md` 继续决定某项检查是否适用，`derived-artifact-governance.md` 继续拥有产品派生产物及其语义缓存，`hard-to-reproduce-diagnostics.md` 继续拥有竞争解释、瞬态证据和根因判断。不能在工作流里复制这些方法的产品合同、缓存算法或失败解释。

## 1. 先生成一份验证计划

从本轮变化事实、用户承诺和受影响边界生成唯一验证计划，再让本地入口与全部 CI 作业消费它。不能让每个 workflow、脚本和矩阵表达式分别用路径猜测验证范围。

```text
候选提交、变化事实和内容身份：
本轮用户承诺及正式消费者：
适用且必需 / 辅助 / 范围外的检查：
每项检查的实际收集身份和入口：
资源档位、目标平台和依赖阶段：
预期成本、缓存边界和失效条件：
失败归属、允许的重跑范围和完成门槛：
```

### 完整入口必须与验收义务对账

用户、项目规则、发布合同或公开验证器清单已经分别规定验证结果时，先形成不依赖命令名称的验收义务集合，再展开名为 `full`、`all`、“完整”或类似总入口的机器可读阶段与实际子命令，逐项建立“由总入口覆盖 / 必须单独运行 / 范围外”的映射。总入口名称、历史口头约定或一次成功退出不能证明它包含真实用户链、性能、视觉、交接、目标平台或其它独立验证族；无法安全展开时，把覆盖关系标为未知并停在计划阶段，不能先运行后补猜。

测试前，验证计划列出总入口实际覆盖的义务和仍需单独运行的义务，记录入口、候选身份、前置、失败归属和证据位置，并计算合并后的关键路径预算、阶段顺序及完整套件次数。父入口在同一候选上完整运行子入口并保留同等退出状态和证据时，最终只运行父入口；子入口只用于冻结前聚焦诊断，不再重复取得最终资格。总入口漏掉的独立义务起初就单列，不能在用户确认预算或完整运行结束后静默追加。候选、规则、清单或入口变化并重新冻结后，从同一验收义务集合重新展开和对账，旧的覆盖映射与预算确认随之失效。

### 本地测试前只消费已经完成的远端失败

每个验证阶段在启动第一条本地测试前，至多一次读取公开仓库最近一项已经完成的失败运行；一次验证阶段包含同一逻辑改动批次的聚焦测试、修复和精准复跑，不在每个 spec、分片或内部轮次前重新访问远端。只消费能够映射到当前分支、候选提交、公共合同或本轮受影响边界的失败，并先归类为产品、测试驱动或夹具、基础设施或外部环境、最终断言；较早成功、排队、运行、取消和跳过状态不进入本地完成门槛。远端不可访问或没有已完成失败时记录未知或无适用失败，继续按当前变化事实选择本地检查，不能把远端查询本身变成测试前置阻塞。

普通实施默认只验证当前机器和当前操作系统，即使仓库公开声明跨平台支持。其它平台的既有失败可以形成待处理证据，但不在当前机器伪造平台结果，也不启动对应矩阵；只有用户明确要求另一平台、当前结果本身就是跨平台迁移，或者正在进行发布候选验收时，才把准确目标平台加入本轮执行计划。提交或推送触发的新 GitHub Actions、部署和公开仓库检查属于异步证据：记录已触发或未知后停止，不轮询、不等待、不因它们仍在运行而保持当前任务打开。用户另行明确要求监控、排查或完成远端 CI 时，才建立以准确 run 和提交为目标的独立结果。

活跃开发的完整覆盖率、完整端到端矩阵、性能与视觉矩阵、打包、签名和发布检查不是普通小改动的默认消费者。它们只在用户明确要求、经权威来源确认的代码冻结或发布候选，或聚焦检查已经证明公共合同、测试收集或共享基础设施受到系统性影响时进入。

### 阶段资格、累计预算与全量验证上限

项目阶段默认是活跃开发。只有用户明确确认，或项目正式发布真源已经把准确候选内容身份标为冻结或发布候选，才取得对应阶段资格；实现者不能因为局部检查通过、待办看似清空、准备提交或计划运行完整测试而自行宣布“代码冻结”。源码、配置、测试执行器、共享夹具、验证计划或候选内容身份发生相关变化时，冻结资格和依赖它取得的昂贵验证授权立即失效，必须由同一权威来源重新冻结，不能沿用先前确认。

启动本阶段第一条测试前，按关键路径累计全部计划检查的预计墙钟时间，包含环境准备、数据生成、启动、关闭、清理以及计划允许的一次重跑；并行项按关键路径计算，不把总计算量伪装成墙钟时间。先消费用户或项目已有预算；没有既定预算时，累计预计超过十五分钟就作为长验证，在第一条测试前一次性报告候选命令、目的、范围、历史耗时依据和累计预计并取得用户确认。多条各自短于十五分钟的命令不能绕过累计门槛；后来增加检查或重跑使累计预计越过已确认预算时，旧确认立即失效，新增动作开始前重新确认。

同一用户结果和同一冻结候选最多先运行一次获准的完整仓库套件。它失败后只做聚焦诊断、获准修复和受影响检查；只有准确候选再次由权威来源冻结，并且用户重新确认完整验证的命令与累计预算时，才允许最后一次完整套件复跑。第二次完整套件仍失败、再次改变候选，或又出现需要修改验证控制面的新事实时停止并重新规划，不启动第三次完整套件。完整套件上限不能反向让原本不适用的全量验证取得运行资格。

每次测试运行都绑定启动时的准确候选内容身份。运行期间只要相关源码、配置、测试、夹具、验证器或验证计划发生变化，从变化发生时起，该运行只能作为诊断证据：尚未开始的阶段立即停止，之后产生的结果不得关闭当前候选，也不能把变化前后的输出拼成同一次通过。重新运行前只收口能够证明由旧运行拥有的进程与资源，并为新候选建立新的运行身份；不能让旧进程、临时目录或部分产物进入新证据。

远端运行身份由候选 SHA、验证计划、基准或 merge-ref、权限与信任边界、正式消费者共同组成。`push` 与同仓 PR 的身份等价时，昂贵验证只保留一个规范运行，另一事件复用它的必需检查；基准内容、fork 权限、secrets、merge-ref 或消费者不同则分别运行。取消组可以收口被新提交取代或同身份重复的运行，不能取消不同信任或基准合同；required check 名称指向规范结果。

用户或项目规则明确要求最终完整套件，只证明该验证族适用于最终候选，不会绕过阶段资格、累计预算、候选冻结、命令范围或完整套件次数上限。尚未满足这些门槛时先完成资格与计划，不用“最终必须运行”提前启动。

计划的机器可读输出应当成为后续作业的唯一选择输入。文档、许可证、致谢和纯仓库元数据变化只选择相应维护入口；公共合同、核心运行时、跨平台能力、跨仓库边界和发布承诺才选择对应的目标测试、平台冒烟、合同或完整用户链。计划生成器本身必须报告实际读取的差异基线、候选路径和规则版本，空输入或未知基线不能被解释成“无需验证”。

每个能够独立适用、失败、缓存或重跑的昂贵验证族都要有自己的机器可读选择输出和质量门归属，不能为了少写条件把跨平台源码构建、项目或数据交接、发布验收等不同边界捆进一个总开关。一个验证族不适用时只退出该族，其它必需结果继续成立；质量门也逐项读取同一计划输出，不能再从总范围反推哪些昂贵作业本应运行。

计划生成器、分类清单、工作流条件和质量门属于验证控制面。控制面变化必须失败关闭：先运行规则自检和代表性路径矩阵，再选择它可能改变的全部验证族；不能让正在被修改的旧规则决定自己无需接受某个分支。代表性矩阵至少覆盖纯维护、普通核心、每个独立昂贵边界、混合变化、未知路径和空基线，并核对每项机器输出及质量门条件。

大规模迁移或测试重构后，重新从当前测试框架的实际收集结果和真实资源调用生成计划。旧目录、旧 marker、旧测试数量和重构前的耗时记录只能作为迁移输入，不能继续决定当前分组。

### 测试命令先展开再取得运行资格

每条候选测试命令在启动测试进程前，先展开 package script、包装器、默认 glob、项目配置、分片和过滤参数，取得它实际会收集的唯一测试身份以及各自会启动或消费的外部 CLI、真实子进程、浏览器、桌面运行时、原生能力、网络服务和持久状态。优先使用框架的仅收集入口、验证计划清单或静态配置解析；取得清单所需的预检不得执行测试正文。命令名称、所属目录、`unit`、`test`、`coverage` 等标签和维护者印象都不能代替实际展开结果。

测试的正式启动身份还要包含实际 runner 或包装入口、唯一测试节点或选择器、参数、工作目录、环境增量、动态库、插件与运行时模块搜索根、隔离根和可见界面。新增测试缝前，用不执行正文的短探针确认 runner 的转译方式、模块解析、支持语法和运行时全局；新模块必须能被正式入口实际加载。runner 注入的环境、运行时与搜索路径都属于测试合同；直接双击或从终端运行 runner 生成的桌面测试可执行文件不能替代正式入口，除非已证明身份相同。正文相同、文件存在或裸进程成功，都不能证明它消费了正式测试环境。

Windows 桌面测试可能在进入 `main()` 和测试框架日志之前就因 DLL、插件或运行时模块缺失而由系统加载器弹出模态错误框，使批处理没有标准输出却一直等待。自动执行前应通过正式 runner 证明依赖闭包，或者在构建输出旁准备由该构建身份拥有的开发运行时，再从正式入口启动；不能把裸 GUI 测试可执行文件当成方便的探针。用户要求“不打包”只排除安装包和可分发目录，不排除让构建树测试可重复运行所需的开发运行时准备；桌面原生依赖、搜索路径和分发边界仍由 `desktop-app-governance.md` 负责，本方法不规定把全部运行库一律复制到输出目录。

把每个收集身份映射到本轮变化事实、用户承诺、受影响生产者或正式消费者，并明确标为必需、辅助或范围外。候选命令只有在实际收集集合完全落入获准的必需与辅助范围后才有运行资格；只要混入范围外身份，就改用测试框架正式支持的文件、节点、资源档位或分片过滤，或者选择更窄的正式入口。无法安全展开或无法从混合入口排除范围外测试时，停在清单与证据缺口，不得先执行整库命令再事后解释哪些测试无关。测试使用临时配置、假模型、本地替身、不联网或隔离账号只能降低执行风险，不能让与本轮受影响链无关的外部集成取得运行资格。

候选检查会启动外部 CLI、浏览器、桌面运行时、真实 API、网络服务或其它可能让用户意外的外部资源时，在启动前向用户说明本轮变化事实、取得运行资格的具体测试身份、资源类型和预计耗时；长验证仍按上一节单独确认。隔离目录、假服务、无网络或临时账号只说明风险控制，不能代替为什么该检查直接覆盖本轮改动。已经启动后再解释警告也不能追认运行资格；无法在启动前完成这份映射就不运行。

修改测试执行器、共享配置、收集规则或验证计划时，也不自动让全部产品测试变成相关测试。先运行控制面自己的规则测试，再从每项被改变的收集语义、资源路由、隔离方式和失败传播中选择能够区分新旧行为的代表性节点。只有这些证据证明影响无法按正式身份和资源档位界定，或者改动确实改变全局收集与执行合同，才扩大到受影响的完整验证族；完整仓库套件仍须满足本节的范围映射、活跃开发阶段限制和长验证确认门槛。

### 昂贵验证器先证明自己的适用合同

性能、视觉、长时、规模、真实进程或其它昂贵验证器在生成大数据、启动完整运行时或进入长循环前，先用不执行昂贵正文的预检核对：准确命令与选择器、实际非空收集身份、当前夹具与数据 schema、正式消费者依赖的 DOM 或协议合同、规模参数、停止条件和结果解析入口。随后只用能够区分当前合同的最小样本跑一次短探针，证明验证器确实读取预期生产者和消费者；预检或短探针失败时不得先构造代表性大规模输入，也不能把验证器失败写成产品失败。

验证器不兼容需要修改时，先取得测试基础设施写入权限，并把验证器修复计入同一累计预算。一次验证器修复后只允许一次精确短探针复跑；若又出现第二个不同的过时假设、夹具漂移、选择器失配或结果解析不兼容，就把该验证器标为当前候选不适用，形成独立的测试基础设施发现并停止当前昂贵验证循环。产品结论保持未验证，重新规划或取得用户对专项治理和新预算的明确授权后才能继续；不能边修验证器边反复生成大数据，直到偶然进入绿色。

## 2. 按成本和信息量排列阶段

阶段依赖由它能证明的事实决定，不按形式完整串成同一条长流水线：

1. **工作流预检**：配置语法、表达式、作业输出合同、缓存身份、命令入口和测试收集能够在产品测试前确定失败。
2. **便宜的确定性检查**：格式、静态合同、架构预算、迁移残留和直接单元或合同检查。
3. **目标平台冷启动冒烟**：从新鲜进程、状态、缓存和输出位置启动准确运行分支，尽早证明原生、浏览器、设备或其它平台能力能够独立建立。
4. **受影响测试与资源分片**：按验证计划运行会经过本轮边界的轻量和重型测试。
5. **昂贵合同与真实用户链**：只在前置事实成立后运行，并承担不能由便宜检查替代的最终承诺。
6. **质量门**：读取同一候选提交下全部必需作业的正式结果，不通过作业名称、总数或较早提交猜测完成。

目标平台冒烟如果代表昂贵合同依赖的同一冷启动分支，就必须位于合同之前。冒烟失败时保留新鲜状态、阶段和边界证据；不能把它移到昂贵测试之后、增加预热或复用前一作业状态来恢复绿色，因为这些动作会隐藏正式链的冷启动依赖。只有冒烟不再经过同一能力，或者验收承诺已经改变时才重新安排位置。

互不依赖的便宜检查可以并行；存在前后依赖时让后续只在前置成功后启动。早失败节省的是注定无效的后续计算，不得通过跳过正式消费者或降低完成门槛取得。

### 生成产物的生产者必须先于消费者

为每条安装、打包、测试、发布或运行命令列出它在干净 runner 上必须已经存在的文件、目录和能力。任何未被仓库跟踪、由构建生成、通常被忽略或来自另一作业的输入，都要记录正式生产者、内容身份、传递边界和第一个消费者：

```text
必需生成输入与来源身份：
正式生产者步骤及其前置输入：
同一作业路径或上游 artifact 传递边界：
第一个安装、打包、测试或运行消费者：
干净 runner 的初始缺失状态：
生产失败、跳过或取得错误身份时的停止位置：
```

构建清单中的强制包含目录、资源复制、代码生成输出、前端或原生构建目录和由另一语言安装器读取的静态资源，都是阶段依赖信号，不是当前开发机已经准备好的普通文件。消费者只能在同一执行图中的生产者成功后运行，或者从明确依赖的上游作业取得经过内容身份校验的 artifact；不能依赖本机残留、未声明的缓存、另一个不传递产物的作业或早先人工运行。预先生成一次后消费者成功，只证明该内容可消费，不能证明工作流在冷检出中的顺序正确。

工作流预检从不包含这些输出的新鲜检出或等价隔离状态核对依赖图，确认每个必需生成输入都有唯一上游、路径和失败传播，且消费者不会在生产者之前进入。阶段顺序发生变化后，至少让目标 runner 从当前提交执行到第一个消费者；只有远端或等价冷环境实际跨过生产、传递和消费边界，才能关闭该编排缺陷。产品产物的语义身份、失效和装配仍由 `derived-artifact-governance.md` 负责，本节只拥有 CI 中的生产顺序和传递事实。

多包或工作区仓库在内部公共合同变化后，把根级测试入口、包级 test script、局部测试配置与 alias、源码树和构建输出视为可能指向不同内容身份的执行边界。逐个记录命令的工作目录、实际加载的包与测试配置、模块或 alias 最终解析到的绝对目标和内容身份，并明确该入口应读取本轮源码还是由本轮生产者生成的输出。根级测试通过、构建步骤已经运行或目标路径存在，都不能证明包级 runner 没有读取旧 `dist`、另一份副本或错误层级；必须在干净 runner 中从实际包入口启动，证明正式消费者解析并读取的是验证计划声明的当前合同身份。产品产物的语义正确性仍归派生产物方法，本节只验证各执行入口实际选择的内容身份。

本地最终入口与 CI 消费同一验证计划，但不需要伪装成同一台机器能够执行所有平台。存在资源分层时，提供一个能够报告差异基线、计划、阶段、命令、隔离目录、耗时和证据位置的本地唯一入口，不再把无资源边界的整库命令当作最终验收入口。它只执行当前机器与授权允许的必需阶段，并把必须留给目标 runner、远端服务或其它平台的验证族明确报告为异步或待证明；本地完整通过不能被写成这些边界已经通过，也不会为了等待这些边界而占住普通实施任务。

## 3. 缓存执行环境，不混入产品缓存

先测量依赖解析、下载、安装、原生准备和测试本身各自耗时。环境准备在关键路径中占有稳定且显著成本，并且完整环境能够在同一平台上安全迁移时，可以缓存完整语言或依赖环境；环境不可迁移、包含机器绑定路径或恢复后无法验证时，只缓存包下载、编译下载物或其它可复现输入。

完整环境缓存键至少绑定：

```text
操作系统与架构
+ 解释器或运行时的准确版本和 ABI
+ 依赖锁文件内容身份
+ 会改变已安装结果的安装器或构建选项
```

缓存同时保存状态清单。恢复后先核对实际解释器、平台、架构、锁文件身份、关键可执行文件和依赖完整性，再刷新当前候选源码的 editable 或等价安装并执行依赖一致性检查。缓存命中输出为空、缺失、真假值或未知时按动作提供者的正式输出合同解析；不能把非空字符串、记忆中的默认值或某个平台的偶然表现当成布尔事实。

只有缓存键与当前平台、锁定输入和构建来源完全一致，状态清单也通过恢复校验的精确命中，才允许跳过对应的环境或构建生产步骤。部分命中、回退键、缺失清单、未知输出或恢复内容不完整时必须重新生产；即使生产步骤被跳过，当前候选提交的正式测试、冒烟和消费者验证仍然执行。不能为了利用缓存而保留一个不再被任何消费者需要的安装或构建步骤。

语言依赖环境与原生 SDK、浏览器、媒体运行时、模型、驱动或其它重型能力分别建缓存。每层键只包含实际改变该层结果的版本、锁文件、平台和构建输入；不要让业务源码的普通变化使稳定依赖环境失效，也不要让语言环境命中掩盖原生运行时仍需准备。凭据、个人配置、活动任务状态和产品产生的数据不得进入共享缓存。

首次冷运行与后续热运行分别记录。并行作业在冷缓存时可能同时准备同一环境；只有平台和缓存服务确实支持安全的唯一发布或写入竞争时才依赖共享保存，否则把准备阶段提升为显式上游作业或接受准确的冷启动成本。命中只证明环境恢复，不能替代当前提交的测试和用户结果。

## 4. 用资源合同分层测试

测试分层依据测试真实启动、连接或消费的能力，而不是所属目录、模块名称或维护者印象。建立一个资源清单，把测试框架实际收集的唯一节点身份映射到最低必要资源档位，例如普通语言运行时、原生库、桌面界面、浏览器、媒体工具、外部进程或在线服务。资源类别只在会改变准备、隔离、并行或失败处理时保留。

不要为了形式给大量测试机械添加多套 marker。同一资源事实由一份清单或同等唯一生产者维护；marker 只有已经是测试框架的稳定正式输入时才作为该清单的来源之一，不能与目录规则、文件名单和 workflow 条件并行维护多份分类。

每次收集后证明：

- 每个预期节点恰好属于一个执行档位，分区完整且互斥；
- 没有重复身份、未分类节点、过期清单项或意外排除；
- 轻量档位不安装、启动或暴露重型能力，并在测试意外请求它们时明确失败；
- 重型档位只准备该组实际消费的能力，不用“可能需要”让所有作业安装完整桌面、浏览器或媒体环境；
- 参数化和生成测试按实际节点计入，文件数不能冒充执行节点数。

资源清单不是永久人工名单。测试入口、fixture、共享 helper 或运行时依赖变化时，分类验证必须暴露漂移；大迁移后以最新收集与真实调用重新建立基线，不能为了保持原分片稳定而保留旧归属。

每条可能并发执行的命令拥有独立的测试、项目、媒体、服务状态、端口和临时工作根。受路径预算约束的平台先从正式消费者的最窄限制和工程内最长合法后缀反推执行根长度，把可读的日志与报告证据根和尽量短的执行根分开；不能因为证据目录便于理解，就让深层嵌套的运行产物继续在其中生成。

后台进程和常驻服务的通用实例身份与关闭仍由 `root-cause-remediation.md` 负责；CI 入口只应用这条边界：为每条命令记录状态根、发现记录、进程身份和启动时间，结束时只审计并收口由该命令正式登记的实例。进程名称相同、启动时间接近或恰好在测试期间出现，都不能证明它由测试拥有；位于用户默认状态根或身份不匹配的进程保持不动并单独报告。进程在审计期间正常退出属于可接受竞争，检查器必须把“已退出”和“身份不属于本轮”与清理失败区分开。

### 并发数由最紧瓶颈余量决定

并发计划先枚举当前平台会限制一轮验证的有限资源：CPU、物理内存、虚拟或提交内存及其系统上限、进程和句柄、端口、临时与持久存储、显存或设备会话，以及外部服务配额。只保留会改变本轮并发的维度，但必须使用操作系统或正式运行时表达的真实容量语义；物理内存仍然充足不能证明提交内存、页面文件、句柄、端口或显存还有可分配空间。

对每种候选资源档位测量共享基线、代表性命令在启动、核心操作与关闭阶段的峰值，以及失败后仍由本轮登记实例占用的资源。先从总容量减去系统与用户保留量、共享基线和已确认的活动占用，再用剩余余量除以单个并发单元的保守峰值；最终并发数取 CPU、隔离条件和全部有限资源结果中的最小值。项目可以保存经过当前平台实测的阈值，但阈值必须由这份容量合同生成和刷新，不能把某台机器的固定数字写成跨项目方法。

每条并发命令在开始和结束时都回读本轮登记的进程树、服务实例及适用资源增量。测试断言通过但登记实例没有退出，说明产品断言可以成立，当前命令的资源收口门槛仍然失败；后续分片不能把这部分占用当成可用余量，也不能继续提高并发。多个无关测试同时出现分配、页面文件、句柄、端口或设备会话错误，而同一节点隔离运行通过时，先核对登记实例泄漏和真实瓶颈余量，再判断产品并发、测试隔离或基础设施；不能先修改无关产品逻辑，也不能用全局串行长期遮住生命周期缺口。

并发决策至少用一组表驱动案例证明：CPU 和物理内存充足但另一项资源余量不足时降低并发；命令退出后登记实例仍占用资源时阻止下一阶段沿用旧容量；全部资源在保留量之上时才允许选择更高并发。真实 runner 报告同时列出限制并发的资源、容量来源、保留量、代表性峰值、最终工作数和运行后的登记实例，而不是只输出一个 worker 数字。

## 5. 按历史耗时分片

同一资源档位内，保存各测试节点在可比平台和配置下的历史耗时，使用稳定统计量形成权重，再按权重平衡分片。测试文件字节数、测试函数数量和一次偶然运行不能代表耗时；参数化节点、初始化成本和共享 fixture 要按实际执行模型计量。

新节点没有历史时使用公开的保守默认权重，取得足够样本后再替换。间歇超时、失败中止和环境排队不能直接混入正常测试权重；先分开测试执行时间、环境准备时间和基础设施等待。平台成本明显不同时分别维护权重，不能用一个平台的历史强行平衡其它平台。

精确分片身份由候选内容、收集输入、按序节点清单、选择规则、分片算法与配置、耗时权重、环境和命令共同组成；分片编号与总数不是身份。新增、删除、改名测试，或收集、权重、配置变化后，同编号分片已经是新分片，不得称为原样重跑。此时分别运行旧候选的疑似失败节点和当前候选重新计算的实际分片。

作业总超时未记录当前节点时，只有执行器确定串行、节点顺序已冻结且逐节点日志刷新语义已知，才能由最后完成节点推断下一节点；否则当前节点保持未知，并在后续验证器增加节点开始标记或心跳。

并行数同时受上一节的最紧瓶颈余量、资源隔离和总成本约束。纯计算或独立语言测试可以并行；共享原生运行时、设备、浏览器配置、端口、缓存或输出目录的测试只有在所有权和隔离成立时才并行。优化同时报告最慢分片的墙钟时间、全部分片的总计算量和冷启动成本，不能只让作业数增加后宣称更快。

并发失败后先判断正在验证的是产品并发合同，还是测试自身只在无竞争资源或稳定时间预算下成立。前者必须修复产品、夹具或隔离边界并继续并发验证，不能通过串行隐藏；后者可以把测试框架实际收集到的最窄节点身份移入显式串行通道，并从并行分片排除同一身份。参数化测试使用稳定的节点前缀覆盖预期参数实例，不能扩大到整个文件或套件；串行通道仍属于同一验证计划和完成门槛，不能成为遗漏测试的旁路。

## 6. 在昂贵阶段前验证工作流边界

工作流预检至少覆盖本轮实际使用的边界：

- action 或上游步骤输出的缺失、空字符串、真假值和错误值语义；
- 作业条件与验证计划输出能否选择预期分支；
- 缓存键、恢复路径和状态清单能否在目标 runner 解析；
- 命令从 workflow 声明的工作目录，以与 CI 相同的 shell、模块或包入口启动；
- 路径大小写、分隔符、模块搜索路径和参数转义在目标平台不依赖当前开发机的偶然环境；
- 测试收集实际非空并与计划身份一致。

本地静态检查只能证明它实际解释的部分。跨平台入口和 action 输出语义如果无法在本地等价模拟，就用最小 runner 作业先取得证据，再允许昂贵作业依赖它。某条命令在一个终端直接运行成功，不能证明不同工作目录、shell 或模块解析规则下仍是同一入口。

## 7. 失败后只重跑有证据的范围

第一次失败保留候选提交、计划身份、runner、作业、步骤、测试节点、环境准备、缓存状态、日志和产物。状态页与 watcher 只是可能截断名称的展示投影；失败身份必须从机器可读接口还原准确 SHA、run、attempt、job、check、日志和产物。先把失败归入工作流编排、基础设施或外部环境、测试驱动或夹具、正式产品链、最终断言中的最早一层，再决定修复与重跑。

只有存在真实瞬态依据时，允许在相同提交、输入、runner 和命令下做一次原样重跑。重跑范围限于失败作业及依赖其结果的质量门；已经成功、证据仍新鲜且不依赖失败产物的作业不重新运行完整工作流。一次原样重跑再次失败，或者第一次已经提供确定性证据时，停止重跑并修复最早错误边界。不能用通用 retry、提高次数或延长所有超时把稳定缺陷变成绿色概率。

修复后先重跑原失败检查、修复触及的消费者和对应质量门。只有修复改变公共合同、全局配置、测试收集、共享夹具、执行环境或其它作业的正式输入，才扩大到受影响作业；只有项目规则或用户承诺要求时才重新运行完整工作流。较早成功证据与修复后结果可以共同使用的前提，是修复没有触及它们的生产者、输入、环境或消费者。

早期冒烟暴露真实产品或冷启动缺陷时，修复产品或测试边界并重新走同一冷链；不能把失败归咎于“冒烟太早”后移除它。如果相同失败在本地或 CI 稳定复现，就不再消耗一次瞬态重跑。

## 8. 用实际耗时解释瓶颈

每次优化至少保留可比较的前后证据：

```text
候选提交、runner、工作负载和缓存状态：
排队与启动：
依赖恢复、下载与安装：
原生、浏览器或其它重型准备：
测试收集与各资源档位：
各分片耗时、最长关键路径与总计算量：
合同、用户链、产物上传和质量门：
冷运行、热运行及失败范围重跑：
当前最大瓶颈、证据和下一项值得优化的边界：
限制并发的资源、容量来源、保留量、代表性峰值与最终工作数：
本地已执行与明确交给 CI 的验证族：
本轮登记、退出和仍存的后台实例：
```

用户询问为什么慢时，直接说明时间花在排队、环境、测试、原生准备、外部服务还是重复重跑，并区分墙钟时间与总计算量。测试节点多、作业多或日志长只是现象；只有阶段计时和关键路径能够证明瓶颈。优化使核心测试变快但把主要时间移到系统包安装、runner 排队或产物传输时，应如实报告新的主导阶段，不继续机械拆分测试。

阶段账本之外，还要统计应用构造、资源发现、缓存或清理扫描、运行时启动、连接建立和关闭等生命周期边界在一轮验证中实际执行多少次，用“执行次数 × 代表性阶段成本”判断被重复放大的总成本。对代表命令分别测量启动或构造、核心操作、关闭或清理，不能因为单个节点不在最慢列表中就忽略每个进程、场景或分片都会支付的固定成本。

若重复阶段属于真实产品入口，且普通用户也会承担该成本，应修复产品所有权、受管理命名空间或生命周期边界，不能靠跨命令共享实例、复用污染状态、跳过关闭或删除覆盖把成本藏在测试外。若成本只来自测试编排，在保持资源隔离和正式入口不变的前提下合并重复准备。修复后用同一账本重测代表节点和受影响档位，刷新历史耗时权重后再重新分片；旧权重不能继续替已经变化的执行模型做平衡。

## 9. 完成与停止

普通实施任务在当前机器的必需目标检查通过、获准提交与非强制推送完成时停止。推送触发的 GitHub Actions、部署或其它远端验证只报告提交身份和异步状态，不主动取得 run 后持续轮询；它们尚未结束不会阻止本地实施结果交付，也不能被写成已经通过。

只有用户明确要求监控或完成 CI、发布候选合同明确要求远端成功，或者当前任务专门诊断 CI 时，才从当前候选提交核对准确必需作业。停止位置只是普通提交或候选分支推送时，普通的提交和推送动作仍在触发远端运行后释放当前任务；停止位置明确是候选进入默认分支时，required checks 是该已授权结果的前置门。仍在排队、运行、取消、跳过原因未知或属于较早提交的结果只能报告为未完成；可选作业和无关外部失败单独报告。

最终输出至少包含：

```text
本轮为什么进入 CI 执行治理：
唯一验证计划及适用 / 范围外检查：
阶段顺序与最早失败门：
环境缓存层、键、恢复验证、冷 / 热结果：
资源分区的完整与互斥证据：
耗时分片、关键路径和总计算量：
各次失败的最早层、修复和实际重跑范围：
当前候选提交上的必需作业与质量门：
本地测试前消费的最近已完成远端失败及分类：
当前机器、明确范围外的平台与原因：
推送后异步运行且本任务没有等待的远端检查：
尚未验证、受阻或明确范围外的结果：
```

只为验证真实计划生成、缓存恢复、资源分区、阶段选择和失败范围等稳定合同建立测试；不为每条说明制作镜像断言，也不建立多套 marker 分类来证明治理文字存在。优化在必需承诺全部成立、当前最大瓶颈已经位于本轮范围外，或继续变化不再带来可测收益时停止，不为了让流程显得完整继续增加作业、分类和测试。
