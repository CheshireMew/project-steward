# README 内容写作与结构

用于 README 只读审计和整页模式。主路由只选择 README 子类型、写入权限、读取顺序和停止位置；本方法统一核定项目身份、宿主角色、材料资格、公开读者合同和首页读者变化，再决定每个章节要让读者新增什么理解或行动、怎样把合格项目事实转换成读者能够判断和行动的信息，以及哪些内容应保留、移动、改写、合并或删除。完成后返回已选择的 README 子类型，不决定视觉风格，也不改变该子类型的写入权限和停止位置。

仅素材模式不使用本方法重组正文。README 以长期可用的事实说明、真实入口和可核对结果为目标。社交平台的钩子库、情绪化痛点、传播模板、宣发节奏和作者记忆服务另一类成品，不进入本方法。

## 1. 确认本次写作动作

在已选子类型内判断当前动作：

- **审计**：判断现有内容是否帮助目标读者理解、信任和行动，只给建议。
- **新写**：从仓库事实建立第一版完整阅读路径。
- **重写**：核心事实或读者路径需要改变，重新组织表达。
- **重组**：事实基本正确，但章节职责、顺序或证据位置不合理。
- **压缩**：删去重复和低价值内容，不损失必要事实与操作路径。

动作不是新的路由。只读审计仍然不写文件；整页模式仍按用户授权修改并停在本地预览。

## 2. 先建立读者与事实合同

评价或起草文字前，先建立公开事实与材料资格。现有 README、专项文档、示例、内部图片、截图、流程图和生成物只作为候选材料；它们必须能够对应产生时的项目状态、当前活动真源和准备承担的公开职责，才能进入正文或视觉。用户已经指出过时、版本不明、与当前真源冲突或职责无法成立的材料，标为过时或未验证，退出公开事实、证据池、视觉证据等级和复用候选。文件能够读取、图片能够渲染或审计脚本通过都不能改变这项资格。

随后使用已经核定的当前项目事实建立公开读者合同：

```text
第一采用读者：最可能判断“这是否适合我”的人，以及他实际需要的专业程度
首页读者变化：读者看完首屏与首个核心章节后，新增哪项理解、形成哪项判断或知道怎样开始
项目本体与运行载体：仓库实际交付什么，谁会加载或使用它，当前宿主是否只是兼容与安装信息
项目身份真源与宿主角色：哪些活动事实定义项目，宿主信息实际改变什么
到访情境：他遇到了什么、想完成什么
交给项目什么：一句请求、文件、链接、数据、命令或其它真实输入
可观察结果：使用后能看到、拿到或完成什么
第一步：无需先理解内部实现就能采取的下一行动
后续读者：安装者、开发者、维护者和贡献者需要到哪里继续
场景证据：前段每个使用场景分别对应哪条活动入口、真实输入、交付和停止位置
公开事实与合格材料：哪些当前事实和材料可以进入正文或视觉，哪些已退出及原因
```

项目真实入口、输入、输出和停止位置共同确定项目本体。项目同时面向普通使用者和技术维护者时，首屏、首个核心章节和第一次成功路径服务普通采用者，安装原理、内部机制、目录、脚本和维护资料进入后续层。第一次真实使用本身要求技术知识时，第一层使用相应技术语言并说明当前用途。

把公开读者合同展开为当前页面的写作输入：

1. **第一采用读者**：谁最可能来到主页，他已经知道什么、不需要预先知道什么，目前要判断或完成什么。
2. **首页读者变化**：他看完首屏与首个核心章节后，应该新增哪项理解、形成哪项判断或知道怎样开始。
3. **项目本体与运行载体**：仓库实际交付的是应用、库、模板、Skill、方法包还是其它对象，谁会加载或使用它，当前宿主、插件或分发目录是否只是兼容与安装信息。
4. **到访情境**：什么具体处境会让他意识到这个项目与自己有关。
5. **用户输入**：他需要提供、选择、安装、输入或说出什么。
6. **可观察结果**：项目完成后，他能够看到、拿到、使用或确认什么变化。
7. **第一行动**：读者在尚未理解内部实现时也能采取的下一步。
8. **后续读者**：安装者、开发者、维护者和贡献者分别需要哪些准确细节，以及这些内容应在首次采用路径之后的什么位置出现。
9. **场景证据**：前段每个使用场景对应哪个仍活动的触发入口、真实输入、交付结果和停止位置。
10. **事实真源**：上层已经核定哪些当前事实和材料能够证明上述内容，哪些只是推断、未来计划、过时或未验证的候选。

本方法只从上层核定的当前事实和合格材料中写作：

1. 当前用户要求和纠正决定公开目标与已经否定的内容；
2. 当前活动核心定义、源码、配置、测试和真实入口证明对应状态下的项目身份与实现；
3. 当前真实界面、输出和端到端结果证明已经生效的可观察能力；
4. 现有 README、专项文档、示例、截图、流程图和其它内部产物只提供查找线索，只有已经对应到当前真源、适用项目状态和公开职责的部分才能进入正文；
5. 用户要求核查，或某项承诺必须依赖当前外部事实时，再使用已经核实的对应外部来源。

配置声明证明设计存在，实际行为和输出证明能力已经生效，未来计划以计划身份出现。项目真实入口、接受的输入、交付和停止位置共同定义项目用途与目标读者；项目名称、仓库类别和宿主元数据只用于发现相关事实。上层已经确定 Skill、插件和方法包的通用工作流身份与宿主适配边界；本方法只决定这些事实在读者路径中的位置，不用宿主名称重选项目本体。

仓库中的类型名、路由名、合同字段、目录和测试术语先作为事实与证据理解；只有它们会改变第一采用读者的选择或行动时才进入前段正文。修改已有 README 时，保留准确的项目术语、作者语气和已经自然清楚的表达，不为统一风格把它们改成通用文案。

## 3. 分开确定主页主身份与独立使用入口

主页主身份决定读者首先记住什么；独立使用入口决定读者分别怎样开始不同的主要任务。两者分别建立，不能用主特色替其它不同结果决定去留。

### 主页主身份

在内部写清：

```text
第一采用读者及到访情境：
首页读者变化：
项目本体、实际加载者与运行载体的关系：
他需要交给项目什么或说出什么：
首先承诺的可观察结果：
一句不用内部分类也能成立的项目定义：
能让读者想象使用过程的具体场景：
该场景对应的活动入口、真实输入、交付和停止位置：
最值得记住的能力、机制或差异：
直接支持它的事实与证据：
只起支撑作用的其它能力：
首屏、首个核心章节和主要成功路径怎样共同兑现：
```

先用字面身份说清项目本体。项目是 Skill、插件、模板、库或方法包时，明确谁会加载什么、用它处理哪些已支持请求。首页围绕一个主要读者变化建立项目定义和 hero；其它独立用户结果通过真实入口继续呈现。主页主身份直接使用上层已经核定的项目身份。宿主信息只有在上层已经证明会改变入口、输入、动作或结果时，才进入对应的兼容、安装或限制位置。

首层先兑现首页读者变化，再按“项目是什么 → 当前支持的主要工作流 → 直接入口”组织。一个主要意图明显占据主页时，用“谁在什么情况下，把什么交给项目，得到什么”展开该入口；多个并列意图共同构成项目时，先给字面身份和真实范围，再由请求示例分别呈现输入与交付。动作分支写成“条件 → 动作 → 交付 → 停止位置”，权限与兼容信息在改变对应操作时出现一次。

用户在当前任务中明确指出的重点决定内容层级，功能事实由仓库证据验证。证据支持一个具体、可验证的第一价值时，将它作为主页重心；其它独立用户结果继续保留对应入口。

### 独立使用入口台账

新写 README 时从项目当前支持的主要用户结果建立台账；修改已有 README 时同时记录现有入口。写正文前逐项记录：

| 字段 | 要回答的问题 |
| --- | --- |
| 用户意图 | 读者要完成什么独立结果 |
| 支持证据 | 当前源码、配置、文档、测试或真实行为是否仍支持 |
| 当前入口 | README 里现有的命令、提示词、连续步骤或明确链接 |
| 第一次成功 | 读者执行后首先能观察到什么 |
| 新位置 | 原位保留、移动保留、合并保留、新增，或有依据地省略 |

触发条件、必需输入、最终结果或下一消费者不同的任务，先按不同意图保留。功能名称相近、位于同一段、共享工具或都能写成代码块，不足以把它们合并。功能列表只说明“能做什么”；只有读者能够据此开始的命令、提示词、连续步骤或明确链接才算入口。

进入采用层的每个请求示例或使用场景都要回指台账中的活动意图，并同时保留该意图真实接受的输入、实际交付和停止位置。项目名称、功能标签或某类项目可能遇到的常见故障不能替代这条证据链；没有真实用户材料支持时，直接展示项目接受的请求，不虚构用户处境。

每项仍受支持、面向当前主要读者并会影响首次采用的独立主要意图，在新页面中保留至少一个可执行入口。主意图使用一条连续的完整成功路径；其它独立主要意图可以使用较短的命令、提示词或专项文档链接，不必复制完整教程。入口数量由真实用户意图决定，不预设固定数量。

只有下列情况才省略入口，并在当前材料预算中记录依据：

- 项目已经不再支持对应结果；
- 它只服务当前主页目标读者之外的少数场景，且已有稳定专项入口；
- 它与另一个入口的触发、输入、结果和停止位置等价，合并后读者仍能完成原任务；
- 用户明确要求当前主页不再承载该结果。

用户要求新增或提高某项特色时，先调整主页主身份和相关入口的层级，再按台账核对其它意图的新位置。没有上述省略依据的入口继续保留或移动，不用新特色原位替换。

### 首屏语言、项目导航、个人入口与仓库状态

用户要求在 hero 或图标下方增加语言、文档、贡献、反馈、个人入口或仓库徽章时，先把它们作为首屏辅助区治理，不把所有可找到的链接堆成装饰。内容资格由本方法负责，GitHub 构件由 `github-readme-canvas.md` 负责，hero 只为该区保留相邻位置。目标项目已经存在某一组语言、导航、品牌或作者入口合同时，该组使用项目真源；其它组仍可消费适用于目标 owner 的 `assets/readme-profile/profile.json`，不能因一个项目专属目标不同就判定整份 profile 不适用。个人 profile 不复制到目标仓库，也不覆盖当前用户要求或目标项目职责相同的正式配置。

辅助区按三个职责分行，缺少合格内容时整行省略：

1. **语言与项目导航**先放当前实际交付的 README 语言。个人默认以 `README.md` 为中文真源，依次提供中文、English 和日本語；当前页面语言使用非链接文本，其它语言链接到真实文件。完整优化时缺少的配置语言是待创建的完整页面，不是可省略偏好。语言组结束后用竖线依次追加文档、贡献和反馈：文档必须进入当前活动说明并由项目解析结果提供，贡献必须进入本次已存在或新建的真实 `CONTRIBUTING.md`，反馈必须进入当前仓库已启用的 Issue 或其它正式反馈入口。官网不自动加入；文档或反馈目标不存在、功能未启用或职责重复时只省略并报告对应入口，不能生成空页面、伪入口、移除其它辅助组，或让同一个 Issues 链接同时冒充贡献指南与反馈渠道。
2. **个人入口**只使用 profile 中已经确认、且适用于目标仓库所有者的 X、Telegram、博客和个人主页。它们说明作者或维护者去向，不冒充项目支持渠道、官方文档或社区规模。
3. **仓库状态**从目标公开 GitHub 仓库身份和当前文件事实生成 Stars、Forks 与许可证，不把数字、许可证名称或另一个仓库的 owner/repo 写死在 profile 或 README 中。动态徽章的点击目标分别进入对应仓库页面；许可证徽章只有当前许可证文件与公开范围成立时才出现。

个人 profile 是偏好真源，不是扩大每次任务范围的隐式授权。新写、整页重写或完整优化个人仓库 README 时，配置的三种语言和贡献指南默认进入同一交付结果，并从同一份公开事实、入口台账和章节材料单元生成；缺少时创建完整页面，不能用 `--allow-missing-languages` 把完整优化降级。修改现有首屏或只增加徽章时，只有已经存在或本次明确同时交付并验证的翻译文件才能成为语言入口；该局部任务可以省略缺失翻译并报告，但不能创建占位页、自动跳转页或只翻译标题的假版本。

Stars、Forks 和许可证之外的徽章不按流行程度自动添加。目标仓库确有活跃发布、正式 CI、Discussions、下载制品或其它会改变采用判断的入口时，可以给出建议；只有它拥有当前生产者、准确点击目标和可核对结果，并且用户接受后才进入辅助区。访问计数、代码行数、个人主页浏览量和其它不能帮助读者理解、信任、选择或行动的数字默认不加。

配置到成品必须经过同一生产链：`assets/readme-profile/profile.json` 提供语言顺序、导航职责和个人偏好，目标 Git 仓库、活动文档、反馈能力与许可证文件提供项目事实；项目专属文档通过 `--navigation-target docs=<活动 Markdown>` 传给 `scripts/readme_header.py`，生成器产生带管理标记的三行结构，README 保存结果，`scripts/audit_readme.py` 按同一 profile 和项目目标复核。项目没有活动文档时不传该目标，只省略文档入口。不能临时改写 profile、手写一份看起来相同的链接或徽章区，再用消费端假数据证明配置已经生效。

## 4. 建立材料预算

先形成页面级材料预算：

- **对象事实**：项目是什么，直接作用于什么对象，执行什么动作，边界在哪里。
- **核心价值**：目标读者使用后发生什么可观察变化。
- **采用层材料**：到访情境、用户输入、使用过程、可见结果、第一行动和采用边界。
- **操作层材料**：安装、命令、提示词、参数、兼容性和完成第一次成功所需的说明。
- **维护层材料**：内部机制、架构、目录、脚本、测试、协议和贡献方式。
- **证据池**：每项主要承诺由哪项已经通过上层来源与时效核定的代码、截图、输出、示例或测试支持。
- **必须出现**：不写就会影响理解、信任、选择、操作或真实下一步的内容，包括主页主身份和各项保留意图的可执行入口。
- **后移或省略**：只服务少数高级场景，或已有专项文档承载的细节。

再为首页和每个核心章节各建立一个章节材料单元：

```text
章节读者变化：读完本节后，读者新增哪项理解、形成哪项判断或知道怎样行动
对象身份：本节说的对象是什么，它与项目有什么关系
直接动作：谁执行什么动作
动作对象：动作具体作用于什么
可观察结果：读者能够看到、拿到、完成或确认什么
必要证据：哪项事实、产物、示例或测试直接支持结果
读者下一步：读完后可以继续查看、选择或执行什么
```

只有帮助读者完成当前变化或直接证明该变化的材料进入章节，证据池中的其余内容留在内部。采用层先独立回答普通访问者的问题；操作层让他完成第一次成功；维护层在读者需要深入时提供准确细节。README 的信息预算用于筛选，不用于把整个仓库压缩成一篇长文。每个章节只承担一个主要读者变化；同一事实再次出现时，必须增加新的关系、后果、选择依据或下一步行动。

## 5. 设计完整阅读路径

页面要让访问者依次完成五件事：

```text
认出自己的使用情境 → 理解项目带来的结果 → 相信主要承诺
→ 完成第一次成功 → 判断是否采用、深入或贡献
```

仓库没有更强的信息需求时，使用以下顺序：

1. **身份与可见价值**：项目名称、到访情境、一句具体定义，以及它会为读者改变什么。
2. **具体场景或直接证据**：项目价值抽象时，先用一个由仓库事实支持的使用过程让读者看见“我交给它什么、它做什么、我最后得到什么”；已有真实产物时优先展示产物。
3. **主要成功路径与其它入口**：主意图从必要前提连续到第一次可观察成功；其它独立主要意图提供紧凑入口或明确的下一位置。
4. **适用范围与信任边界**：说明什么时候值得用、哪些动作需要用户决定，以及结果如何确认。
5. **必要机制与技术深入**：只解释采用、正确操作、限制或风险所必需的机制；目录、脚本、内部协议、开发和贡献信息放在首次成功之后。

如果读者必须先理解某项机制才能安全操作或判断是否适用，可以把该机制提前；调整顺序时要说明它解决了哪个读者问题，而不是套固定章节模板。

### 章节内部的推进关系

章节顺序由材料之间的真实关系决定：

- 解释一个问题时，使用“读者问题 → 事实 → 原因或机制 → 实际影响”。
- 展示一次使用过程时，使用“输入 → 项目动作 → 检查点 → 可观察结果”。
- 说明一次改变或选择时，使用“触发 → 变化 → 取舍 → 选择 → 结果”。
- 比较方案时，让每个方案回答同一组判断标准。
- 并列入口或能力时，让每一项回答同一个读者问题，并分别给出入口或结果。

从材料中选择最短且完整的推进关系。章节模板只提供检查顺序，不代替材料本身的因果、时间、比较或并列关系。

### 第一屏测试

访问者不向下滚动时应能回答：

1. 这是什么。
2. 什么情况下我会需要它。
3. 我需要交给它什么或说出什么。
4. 它会替我完成什么，我最后能看到什么。
5. 接下来应查看哪项证据或采取什么动作。

hero 可以承担身份和价值，但不能独自承担全部证据。紧接首屏的内容应兑现首屏最重要的承诺。

首屏不需要平铺所有能力。读者进入快速开始或使用部分后，应能找到入口台账中保留的每项独立主要意图；突出主特色不以切断其它真实下一步为代价。

## 6. 让术语、关系和动作可理解

先判断术语是否应该出现在当前读者层。一个术语只帮助解释内部实现、测试方法、资源组织或维护流程时，把它和对应细节移到维护层，不在首屏通过增加括号解释来保留。对当前读者陌生但第一次真实操作确实需要的对象，在首次出现的同一段随当前用途说明：

1. 它是什么；
2. 它与主项目是什么关系；
3. 为什么此处需要提到它。

句子优先使用“谁对什么做什么，读者得到什么”的中文信息顺序。动词直接使用检查、生成、修改、验证、发布等能够指向实际行为的词；“支持、处理、赋能”等宽泛动词只有在没有更准确动作时才使用。需要改善表达时，重写整句或整段的主语、动作、对象和顺序，不做同义词替换式润色。技术术语确实帮助读者操作、判断边界或与代码对应时应保留，并在首次出现处建立关系。

### 把来源中的限制还原成行动

来源中的否定、限制和情态说明先还原为具体条件、动作、状态和结果。公开文字优先说明“在什么条件下，谁会执行什么，读者得到什么”；一项边界确实改变选择、操作或结果时，在对应决策位置准确写一次，然后回到主要行动路径。

### 普通读者回述测试

首屏与首个核心章节完成后，暂时移开仓库源码、内部合同和术语解释，只读用户可见内容。第一采用读者应当能够用自己的话说明：

1. 这个仓库实际是什么，自己、运行宿主和项目之间是什么关系；
2. 这个项目在什么情况下与自己有关；
3. 自己需要提供什么或说什么；
4. 项目会替自己完成什么；
5. 最后能够看到、拿到或使用什么；
6. 下一步怎样开始。

如果只能复述项目类别、功能名称、内部流程或形容词，返回主页主身份和材料预算重新组织。技术项目的读者可以使用完成第一次操作所需的专业词，但仍要说得出输入、动作、结果和下一步。

## 7. 让证据承担正确职责

主要承诺旁边只放已经通过上层材料资格判断、能够对应当前项目状态和公开职责的证据，再区分证据类型：

- 真实界面、输出和端到端示例可以证明读者最终能看到或得到什么。
- 可运行命令和经过验证的示例可以证明第一次成功路径。
- 源码和测试可以证明实现或行为，但不能自动证明易用性、性能或采用情况。
- 架构图和流程图只有在其中的对象与关系仍能由当前真源支持时才可以解释机制，不能冒充实际效果；过时或未验证的图不进入公开内容。
- 功能表只能陈述仓库已经实现并能核对的能力。

证据用于约束公开承诺，不要求把证据生产过程、内部字段或测试术语写进采用层。只有读者需要核对、复现或维护时，才展示相应准确细节。

不得编造痛点、比较优势、用户反馈、性能、兼容性、社区规模或采用情况。能力存在只能证明项目接受对应任务，不能自动证明某类用户正遭遇由项目名称联想到的问题。引用外部项目或替代方案时，只保留对选择有实际帮助且能够核对的差异。

## 8. 编辑与删改

### README 不是内部方法的镜像

公开 README 只解释项目身份、读者能够完成的结果、真实入口、第一次成功、适用边界、证据和后续导航。`SKILL.md`、reference、schema、测试和脚本中的内部判断新增或细化，不会自动成为 README 段落；只有它改变了第一采用读者的理解、选择、操作或下一步，才更新对应公开位置。

内部能力数量增加时，先检查现有稳定类别和入口是否仍准确。能够由同一个读者意图、输入、结果和停止位置概括的能力继续使用一个短入口，并链接活动真源；触发、例外、迁移和验证细节留在唯一方法所有者。不能为了让每项内部规则“有公开消费者”而在 README 逐条复述，也不能用折叠区或注释保存一份测试仍强制同步的第二套方法库。

Project Steward 自我进化时，README 默认不在影响文件中。只有项目公开身份、第一采用路径、主要用户入口、许可证与致谢、公开素材、语言与状态区或维护导航发生变化时，才把 README 纳入同一迁移。确定性测试验证内部规则的活动所有者和正式路由；README 测试只保护上述公开合同与可读性，不要求每条治理规则的原文出现。

- 采用层首段兑现首页读者变化，并交付项目身份、真实工作范围和直接入口。
- 每个章节兑现预先确定的读者变化；每句话提供项目身份、真实范围、直接动作、实际结果或必要证据中的至少一项。
- 每个段落新增事实、动作、因果关系、场景、判断依据或真实下一步中的至少一项。
- 项目身份、核心价值或可观察结果第二次出现时，增加新的关系、后果、判断依据或行动。
- 来源中的否定、限制和情态说明还原为具体条件、动作、状态和结果；有效差异写成“条件 → 动作 → 交付 → 停止位置”，权限在对应操作步骤出现一次。
- 首先修正事实、关系和行动路径，再润色句子。
- 一个机制只完整解释一次；其它位置通过结果、后果或链接承接。
- 为主页主意图保留一个完整成功示例；其它独立主要意图保留紧凑且可执行的入口，不堆放无法形成结果的命令和片段。
- 会影响采用决定、安全使用或结果解释的限制保持可见。
- 专项配置、完整 API 和维护细节已有稳定入口时，在 README 提供必要上下文和链接，不复制整份文档。
- 混合受众页面先完成采用层和第一次成功，再用后续章节或 `details` 承载较长维护资料；折叠不用于隐藏会影响普通使用者选择或操作的内容。
- 现有段落已经具体、准确、自然时保留，不为了制造“重新设计”的痕迹而改写。

对每个段落执行删除测试：删掉后如果不会降低读者对项目的理解、对承诺的信任、选择或操作能力，也不会切断一个真实下一步或某项仍受支持主要意图的唯一入口，就删除、合并或移到专项文档。移动或合并入口时先证明新位置仍能让原读者开始并得到同一结果。

## 9. 两轮回读

第一轮只检查事实和路径：

- 重要对象之间的关系是否明确；
- 首页和每个核心章节是否兑现预先确定的读者变化；
- 每项主要承诺是否有相邻证据；
- 主要成功路径是否由真实仓库内容支持并能连续执行；
- 入口台账中的每项保留意图是否抵达最终命令、提示词、步骤或链接；
- 新增或提高主特色后，是否只改变层级而没有原位替换其它不同结果；
- 每个章节是否承担独有职责；
- 限制、适用范围和下一步是否处在读者需要的位置。

第二轮只检查表达和信息价值：

- 第一采用读者能否通过普通读者回述测试；
- 项目本体是否被宿主名称、人格化比喻或项目名称联想替代；
- 正文和证据池是否只使用上层核定的当前事实与合格材料，没有恢复过时或未验证的内部产物；
- 前段每个请求和场景是否能回指活动入口、真实输入、交付和停止位置；
- 首次访问者是否需要猜测术语、主语、对象或因果关系；
- 句子是否具体说明谁做什么、得到什么；
- 采用层是否被内部机制、目录、脚本、测试和维护术语提前占据；
- 每个段落是否新增事实、动作、因果关系、场景、判断依据或真实下一步；
- 重复的项目身份、核心价值或结果是否增加了新的关系、后果、选择或行动；
- 段落是否通过删除测试；
- 修改是否保留项目原有声音，而不是变成统一、空泛的宣传语气。

两轮检查通过，正文已经具体、连贯并适合当前读者时停止。后续调整由新的事实、读者问题或可观察缺陷触发，不为统一腔调继续润色。

## 10. 按子类型返回结果

只读审计先给总体结论，再按读者路径指出证据充分的问题，并给出应保留、移动、合并、改写、补充或删除的准确建议。入口问题同时说明受影响的用户意图、当前入口和建议位置。建议必须说明它修复的是理解、信任、选择、操作还是下一步行动，然后返回只读审计并停止。

整页模式返回公开读者合同、读者与事实合同、主页主身份、独立使用入口台账、首页与核心章节的读者变化、页面级材料预算和章节材料单元，继续执行视觉资源与制作流程。完成页面后说明采用层、操作层和维护层怎样分开，每项入口如何处置，采用了哪些合格事实与真实证据、哪些过时或未验证材料没有进入，以及哪些内容被后移或省略，再提供本地预览。

## 11. 视觉与文字分工

视觉负责：

- 层级与身份；
- 关系、顺序和对比；
- 截图、产物和其它证据；
- 难以用短段落快速理解的结构。

Markdown 负责：

- 解释、命令、API 和配置；
- 链接、兼容性、限制和贡献方式；
- 需要搜索、复制、翻译或频繁更新的内容。

Hero 中的文字使用第一采用读者能够直接理解的项目定义和可见结果；内部机制图只有在首屏价值已经成立、且它确实帮助当前读者继续判断时才进入。命令、关键限制和必要说明不能只放在图片中。视觉必须服务已经确定的读者路径，不能用装饰或内部流程代替价值与证据。完成内容结构后返回已选择的 README 子类型。
